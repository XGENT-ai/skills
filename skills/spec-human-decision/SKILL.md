# spec-human-decision · 功能与决策确认

把已有 PRD、CRD 或开发计划中要开发的功能点，以及计划中的技术架构决策，整理成一份可交互确认的 HTML 表单。用户一次性逐项选择后提交，再按决定把文档改成一致的最终版本。界面语言与回复语言跟随用户。

## 适用与边界

- 用户要求逐项过功能或技术决策、确认做不做、调整需求或实现取舍时使用。普通撰写用 `prd` / `crd` / `dev-plan`，质量评审用 `review-prd` / `review-dev-plan`，按报告改稿用 `apply-doc-review`；这些技能无需成为本技能的安装依赖。
- 运行表单需要 Node 18 及以上和一个能打开本机地址的浏览器；表单只监听 `127.0.0.1`，不访问网络。
- 调用即包含按本次决定修订指定文档，无需每项再问是否允许改稿。用户限定仅讨论、不保存或另存时照办；背景引用与关联文档只读，未纳入的上游/下游只列同步需求。不实施代码、不更新 SPMS/Issue、不发送或发布文档。
- **PRD / CRD 保持产品边界**：讲清做什么、为什么、怎样算满足；实现方案只属于开发计划，测试脚本不写进 PRD。CRD 只写协作边界和对方的可观察交付，不代接收方设计内部实现。完整需求与分期分开，不把本期不做自动解释为终局删除。
- **计划保持事实与范围边界**：做法与决策来自本次读过的文档与必要代码事实；未知不编造，外部依赖不自动转成本方开发。保留适用的实施协议、稳定 ID、进度与历史证据；文档确认不能冒充开发或验收完成。
- **正文只保存最终结论**：需求/方案、必要理由与来源、约束及未决事项属于原文；确认/驳回经过、表单轮次和写作用了什么技能只进决定记录。计划排除项直接写最终范围及依据，不新增“本轮确认/驳回”“刚才”等依赖当前对话的措辞；必要来源写为“用户 YYYY-MM-DD 决定”。
- **决定与就绪分别判断**：用户确认是取舍的结论，不代替技术评审、事实核实或验收。关键范围、安全、数据、外部契约或 NFR 未决时保留阻塞；不凭确认数量把计划改成 `Ready`。

## 1. 读文档，列出待决条目

1. 从参数及已有上下文定位目标，读取适用仓库规则和完整文档，记下路径、当前版本与用户限定范围。续接时读取已有决定记录，比对内容与范围后沿用仍有效的答复。没有目标或多个候选无法消歧时才问；链接用当前可用方式读取，截断内容补读后再用。
2. 抽取范围内要开发的每项能力，以及会改变其行为、权限、关键 NFR 或验收的独立取舍。按用户能独立决定、能独立验收的能力拆分，不按章节、文件、函数或施工步骤逐项列出；能分别接受或拒绝的功能不能合并成一项。开发计划另抽技术架构决策：选定方案会约束多个功能、换方案会改变实现路径或代价时单列，文档里的备选方案和弃选原因一并带上；纯实现细节不单列。
3. 沿用需求 ID（FR、NFR、CRD 的 R-01 等）；没有 ID 时用临时 `D1…Dn` 对应原文位置，不冒充需求系统的真实编号。建立简短台账：条目/来源段落 → 当前内容 → 用户选择及说明 → 最终内容 → 关联影响。多文档用路径与 ID 联合定位，重复表述映射到同一条目。
4. 记下条目间的依赖与决策影响，它们决定表单里的后果标记。只确认某期时说清本次范围，其他期次不受这次取舍自动裁剪。本次已有明确且仍适用的答复直接沿用，不再放进表单；文档中的旧“已确认”标记不能代替本次未给出的答复。
5. 功能、价值或做法写得含糊时先查相关材料；仍缺依据就直接写“文档未说明”或“计划未说明”，让用户修改补充，不替用户发明理由。没有可确认的条目时如实结束，不造空表单。

## 2. 生成确认表单

按 [表单数据格式](references/form-data.md) 写 form.json。PRD 与 CRD 用 `requirements` 模板，侧重做什么、为什么、验收与分期；开发计划用 `dev-plan` 模板，先列技术架构决策（选定方案、理由、备选、代价、影响的功能），再列功能点（做什么、怎么做、里程碑、验证）。同时确认 PRD 和开发计划时分别生成两份表单，先确认 PRD。

- 每个字段通常一句话，用用户能理解的语言，保留会改变选择的关键限制、代价或依赖；不堆背景和术语，也不以简短为由隐藏取舍。字段内容是原文的转述，不是新写的方案：PRD 不补“怎么做”，计划缺做法就写待补，不能把临时设想写成原方案。
- 依赖写进 `dependsOn`，决策影响写进 `affects`，表单会在上游被驳回或修改时给下游打标。
- 不设默认选择，不把推荐写成预选，也不在表单里加第四种业务决定。

form.json 与 result.json 放在当前环境的临时目录，或项目约定的工作目录，不放进文档目录。运行：

```bash
node <skill-dir>/scripts/decision-form.mjs <form.json> <result.json>
```

脚本先校验数据，不合格时列出问题并以退出码 2 结束；按提示修正数据后重跑，不改模板绕过。通过后它打印 `FORM URL:` 并尝试打开浏览器，然后等待提交；用户提交成功时写入 result.json、打印 `RESULT:` 并以 0 退出。环境支持时后台运行并在进程退出后继续；不支持后台的环境用前台运行，并给足等待时间。把地址告诉用户，说明提交后会自动回到这里。

- 只有 result.json 记录的提交算用户答复。服务被中断、页面关闭、超时或用户口头说“差不多”都不算确认；未提交前不改文档、不宣布完成。用户明确放弃时停止服务进程并如实结束。
- 页面草稿只存在用户浏览器里，服务重启后地址会变；需要重新打开时用同一份 form.json 重跑脚本。

## 3. 读取结果，处理修改与连带影响

读取 result.json，核对 `form.title`、`round` 与本次表单一致后写入台账。各决定含义：

| 决定 | 处理 |
| --- | --- |
| 确认 | 接受表单展示的版本，纳入最终文档。附言只作澄清，不扩大范围。 |
| 驳回 | 不纳入本次确认范围；不自动改成延期，也不连带驳回其他条目。附言作为排除依据。 |
| 修改 | 附言是用户希望的改法；架构决策选了备选方案即改用该方案。修订稿须在下一轮再确认。 |
| 未决（`null`） | 保持待决，进入下一轮或在交付时列为剩余项。 |

然后准备下一轮表单，`round` 加一，只放以下条目：

1. 选了修改的条目：按附言起草修订稿，正文字段写修订后的完整版本，`revision` 写修订前后的变化与用户原话。附言含糊、可有多种读法时，按最贴近原话的读法起草，并在 `impact` 写明另一种读法，让用户确认或再改；不悄悄选一种解释定稿。
2. 受影响的条目：被驳回的前置、被修改的决策让其他条目不可行或含义改变时，写出具体影响和建议的最终版本，`revision.reason` 用 `dependency`，`cause` 写明起因。已确认的条目受影响也要放回来；不替用户连带删除或接受替代方案。与既有硬约束或上游承诺冲突时在 `impact` 列明冲突，不静默改写它们以使选择成立。
3. 上一轮未决的条目，原样放回。

下一轮的答复同样按上表处理。没有需要再确认的条目时结束表单流程；用户要求先停在当前轮时照办，剩余项如实保留。已决项不再追加整篇重复求批。

## 4. 按决定打磨文档

可按已决项逐步改稿，不必等所有轮次结束；未决部分保留待决标记及所缺说明。写入前重读受影响内容，保留用户和其他执行者的修改；发生冲突只暂停冲突部分。沿用原结构、语言、术语和稳定 ID，只改本次决定及必要关联位置。

- **确认**：保留实质内容，仅做不改变含义的澄清；不借润色新增能力、阈值、技术承诺或验收门槛。
- **驳回**：从本次有效范围、任务与验收中撤下，保留 ID 和简短排除依据，清理悬空引用。限定期次时只撤下该期承接，终局需求仍保留；未限定期次时，对所选 PRD 功能的驳回即从其终局范围排除。驳回架构决策时，原方案从计划中撤下，替代方案须由用户在修改或下一轮中给出，不自行补位。受影响的依赖与剩余能力须有用户决定，不能直接删整条链。
- **修改后确认**：将用户认可的最终版本写入正文，必要理由进入已有决策/约束位置；改用备选方案时同步更新弃选理由与受影响的实现路径。修订中的试案不当作定稿，尚未确认时不能标成已确认。

按类型同步受影响链路：

| 文档 | 同步位置 |
| --- | --- |
| PRD | 目标/非目标、角色与场景、FR/NFR、可观察结果与验收/UAT、分期及终验归属；正文保留确认后的完整能力。 |
| CRD | 范围与分工、对应 R 条目的请求、提出方立场、协作契约与验收；Q&A 与往返记录只按 CRD 自身规则追加，不改写历史。 |
| Dev-plan | 架构决策及备选、范围、需求映射、实现方案/契约、任务/里程碑、前置依赖、验证及风险；保留历史记录的原成果归属，新增工作不填成已完成。 |

默认保存决定记录，优先沿用项目既有位置；没有约定时，在目标旁写 `<文档名去扩展名>.decisions.md`，记录目标版本、覆盖范围、每轮提交时间、逐项原案/最终决定、用户原话、修订落点和剩余同步事项。原文只有聊天内容或远程不可写时，遵循用户指定或项目同类文档的目录约定另存，无法确定目的地才问。仅讨论时在聊天保留台账，不新建文件。

记录文件已存在时先读，本次决定放在可区分的独立节中续写，保留既有历史、阻塞记录及其 ID/结论，不将它们改成“功能已确认”。新决定推翻旧决定时保留旧案并标明取代关系；无实质变化的续接不重写记录。

## 5. 复核与交付

1. 回读文档与决定记录，对照范围内每项，确保都有最终决定或明确待决原因；全部驳回也是有效结果，不为填满文档补功能。
2. 检查正文、排除、映射、依赖、验收和分期有无残留矛盾或悬空引用。受影响且授权外的文档列出具体同步位置，不能为了表面一致顺手覆盖。
3. 计划范围或前置有变化时依真实条件核对原有 `Ready / Proposed / Blocked`，不把表单进度当计划状态；保留真实实施进展。只做文档所需检查，不能执行计划里的开发/业务验收来冒充复核。
4. 检查最终 diff 及实际保存结果，确认没有残留的表单服务进程。全部条目有最终决定且必要文档修订已核对，才交付“逐项确认已完成”；仍有未答、待确认或写入失败时，准确列出剩余项。

最终回复简短给出修订文档与决定记录链接、确认/驳回/修改后确认的数量及剩余待决项；修改后确认不重复计数，修订稿尚未确认仍算待决。用户确认不等于技术评审通过；需要独立评审时建议对应 `review-*`，不自动启动下一步。
