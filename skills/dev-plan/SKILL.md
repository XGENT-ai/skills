# dev-plan · 基于代码事实的开发计划撰写

## 你的角色与这份文档的命运

你同时是**资深产品经理**和**资深架构师**。写出的计划会交给另一个实现者(人或 Agent)在**单一上下文内从头做到验证收尾**——实现期不会回来问你问题,也不该重开设计讨论。所以:

- **产品经理视角**负责:需求吃透、范围收敛(敢砍、敢排期)、每条需求有落点或显式排除、实用性优先于炫技。
- **架构师视角**负责:方案建立在**读过的代码**上而非想象上、复用优先于新造、取舍写明代价、可行性经得起追问、验证与安全从计划期就定义好。

**一切失败模式的根源只有一个:计划里出现了没有事实来源的断言。** 每一句"复用 X""参照 Y""Z 已支持"都必须能回溯到:① 用户的原话,或 ② 本次调查中读到的代码/文档(带路径)。做不到就标为开放问题,不许编。

> **路径约定**:本 skill 可整目录拷到任何 repo 使用——面向所有用 SPMS(研发项目管理)App 管理研发的团队,不预设你在哪个代码库里。skill 自带的 `references/` 与 `scripts/` 永远可读;正文里凡属 SPMS 平台行为的陈述(工具名、错误码、幂等语义)是**平台契约**,不需要你读到平台源码来复核。文末「本仓库(xgent-ai-portal)默认值」一节**只在门户仓内工作时适用**——装到其他 repo 时忽略它,那些路径在你的 repo 里不存在,不要去找、不要去建。`evals/` 目录(若存在)是门户仓内部的回归夹具,skill 运行期从不读它,分发时不携带。

## 流程总览

```
0. 定位模板与范例   → 找到项目的计划模板和 2-3 份同类型高质量旧计划
1. 需求解析与定性   → 逐条编号需求;判定计划类型;识别必须先问的产品决策
2. 代码事实调查     → (重头戏) 并行调查,产出带路径的《事实清单》
3. 决策先行         → 先写 §0:决策表 + 关键取舍 + 明确不做
4. 撰写正文         → 照模板骨架,按类型裁剪
5. 自检与收尾       → 模板自检清单 + 路径真实性 + 需求映射全覆盖 + 交叉一致性
```

除非用户明确只要"简单聊聊思路",完整走全部六步。步骤 2 绝不可跳过——没有调查的计划就是命题作文。

## 第 0 步:定位模板与范例

1. **找模板**:依次尝试 ① 用户指定的路径;② 全仓库 glob `**/PLAN-TEMPLATE*.md`(计划模板的惯例命名;宿主 repo 有自己的模板约定就以它为准)。找到后**通读全文**——模板通常自带元原则、骨架、按类型裁剪指引和写作自检清单,那些就是本 skill 的具体化,以模板为准。
2. **找不到模板**:用本 skill 自带的通用骨架 `references/plan-skeleton.md`,并向用户说明"项目无计划模板,采用通用骨架"。
3. **找范例**:在模板同目录(或用户指定的计划目录)里挑 1-2 份**与本次计划同类型**的已完成计划(新独立模块型 / 既有模块增量型 / 纯前端型…),粗读其 §0 与里程碑节,校准"这个项目里的好计划长什么样"——尤其是决策表的颗粒度和验证的写法。模板若点名了样板文档,优先读那几份。

## 第 1 步:需求解析与定性

1. **逐条编号**用户的原始需求(R1、R2…)。这张清单贯穿始终:最终计划的"需求 → 设计映射"表必须逐条覆盖它,一条都不许吞。用户一句话里往往藏着多条需求,拆开;含糊的地方先记下,带着问题去调查。
   - **已有 PRD 时不要另起炉灶**:先找宿主 repo 里的 PRD 文档(`prd` skill 的产出,惯例 `docs/PRD-*.md`;代号按能力域取,**不与计划代号对齐**)或 SPMS 里的 `FR-N`/`NFR-N`(SPMS MCP 的 `requirement_list`/`requirement_get`)。有就**直接用真实 FR/NFR key 当 R1…Rn**——验收标准、非目标、开放问题都已经定过稿,映射表也能逐条指回 SPMS 实体。PRD 缺条目时补编 R#,并在汇报里点出"PRD 没覆盖到"。
   - **PRD 与计划是多对多,先划清本计划的需求集**:一份 PRD 可拆给多份计划(按技术依赖/里程碑分批),多份 PRD 的需求也常**合并**进同一份计划(同一块代码要动、同一次回归)。参考 PRD 的「建议分批」,但边界由你按技术依赖定;定完只把这组 key 当 R1…Rn,并在计划开头写明「本计划覆盖 FR-37/FR-38(出自 `docs/PRD-A.md`)+ NFR-9(出自 `docs/PRD-B.md`);PRD-A 其余条目由 <哪份计划/待立项> 承接」。
     两个方向都要防:**别把整份 PRD 一股脑塞进一个计划**;**合并时也别让被留下的条目无人认领**——凡本计划不吃的,逐条给去向。
     ⚠️ 合并只在**同一项目内**成立:`plan_create(requirementKeys)` 拒收别的项目的 key(报 `LIFECYCLE_MISMATCH`,平台契约)。跨项目就一个项目一份计划。
2. **定性计划类型**(新独立模块 / 既有模块增量 / 纯前端 / 平台横切面…),决定骨架怎么裁剪、去读哪份范例、调查往哪个方向使劲。
3. **识别"必须有人拍板"的产品决策**——真正影响范围与形态、无法从代码或惯例推出的那种(比如"面向管理员还是全员""要不要独立计费")。交互场景下现在就问用户;无法交互则选一个有依据的默认并把它连同理由写进计划的"开放问题"节,**不许默默替用户做重大产品决策而不留痕**。

## 第 2 步:代码事实调查(重头戏)

写计划前先把地基打在事实上。有子代理(Explore/general-purpose)就**并行**派活,每路带明确问题;仓库小或问题窄时自己搜也行。五路调查:

| 路 | 问题 | 产出 |
| --- | --- | --- |
| **现状盘点** | 与本需求相关的功能现在有什么?(路由、表、UI、服务、配置) | 现有能力清单 + 路径;避免重复造和漏改 |
| **复用范式** | 全仓库里与要做的东西**最同构的既有实现**是哪个?它的关键文件在哪? | "照抄 `<具体文件路径>` 范式"级别的锚点,而非"参照既有做法" |
| **上游契约核对** | 本计划要读写的每一个既有模块/服务的接口,现状够不够用? | 每个上游一条:**「已核实(`路径`):零改动」或精确增量清单**——没有第三种状态 |
| **端口/环境/命名现状** | 端口表、环境变量、命名空间的**当前真值**(读实际配置文件,不信旧文档) | 新增件不与现状冲突的依据 |
| **已知坑搬运** | memory 目录、CLAUDE.md、旧计划的 PROGRESS/DEFERRED 文档里,与本计划相关的坑 | 一行一坑 + 出处,直接搬进计划的"已知坑"节 |

产出一份**《事实清单》**(工作产物,不直接进计划),每条带标签与来源:

```
[现状]  issue 表已有 ai_assigned 字段但未使用 (apps/xx-server/src/db/schema.ts)
[契约·已核实] 文件服务 presign 面覆盖本需求,零改动 (apps/xx-files/src/routes/presign.ts)
[契约·增量]   通知服务缺服务态入口 → 需加 scope 一项 + notify.ts 服务态变体 (P0,漏则 M3 卡死)
[坑]    seed 后租户 UUID 重生成,跨库引用要重解析 (memory: reseed-recovery)
[开放]  未查到 X 的现有实现;是否自建待产品拍板
```

**红线:没读过的代码不许写"已核实"。** 调查中发现需求与代码现实冲突(比如用户以为存在的能力其实没有),这是重要发现——如实呈现并给出替代方案,不要顺着错误假设写下去。

**核实要核到行为,不止存在。** 「已核实」的对象是**计划所依赖的那个行为**——文件存在、函数同名、接口能调通,都不等于契约成立;实现期最贵的返工全部来自"行为想当然"。事实清单里凡属以下类别,必须把行为细节(数字、语义)抄进来:

- **分页/批量推进**:上游接口有没有 offset/cursor?"重复调用"会推进到下一批,还是永远命中同一批?你的方案若依赖"分批扇出",这一条不核实等于整个机制不成立。
- **限流/配额/上限**的具体数值与作用域(每租户?每调用方?每分钟?),超限行为是排队还是失败。
- **鉴权模板的 claims 形状**:要照抄的 gate 里到底有没有 `permissions`/`bypass`?抄了一个没有权限位的 gate,再叠"按权限下放"的设计就是空中楼阁。
- **密钥/加密的密钥域**:复用的加密函数绑的是哪个 env/密钥?轮换/灾备是否与你的数据绑死在别人的密钥上?
- **框架层行为**:如框架校验失败先于业务闸返 4xx——"业务错误一律 200"的承诺需要宽 schema/手动解析才能兑现,计划里要写明。
- **事务/失败语义**:被复用的"钩子/发射点"在事务内还是事务外?进程崩溃时丢不丢?你承诺的可靠性等级(at-least-once 等)必须与之相容。

## 第 3 步:决策先行

正文之前先把 §0 钉死——所有实现期会引发争论的点(形态/协议/凭证/权限/边界/复用策略)在这里一次拍完:

- **决策表**:每行 = 决策点 + 选择 + **含义**(对部署件/既有代码/边界的影响;能"零改动"的明说)。只写选择不写影响的决策等于没做。
- **职责边界**:一张"谁拥有什么"的表 + 一句话把职责切死,实现期所有"要不要顺手做"回来看这句。
- **关键取舍**:每条 = 选择 → **代价**(显式承认) → 缓解/兜底(实在缓解不了就写"风险显式承认")。重点覆盖:降级路径、幂等/重试、**并发与竞态**(两个层面都要:① 后台 worker/队列写清原子认领、基于截止时间的僵尸判定、计数器原子更新——读后写的熔断计数、按旧时间戳清扫 running 这类竞态在计划期就要堵死;② 普通请求路径上**任何跨请求的 check-then-write**——先查状态再写入的流程(如"检查问卷开放→插入答卷"对上"管理员并发关闭")必须写明事务内锁或条件写)、**数据生命周期**(每张新表对其引用的实体逐个走查"被删/被转移/被失效"场景:FK/NOT NULL/UNIQUE 约束必须与声明的回退语义相容——写着 NOT NULL 外键又承诺"删除后回退占位"是自相矛盾;快照列注明每条写路径的**服务端权威来源**,绝不信前端传值)、安全收口、显式截断、回归风险及其门。
- **明确不做**:所有容易蔓延的相邻功能逐条出表,**每条给去向**(二期 / 另立项 / 依赖某底座就绪)。产品经理的价值一半在这张表上——评审时会被问"那 X 呢"的都要提前出现在这。

## 第 4 步:撰写正文

照模板骨架 + 类型裁剪写。通用写作规矩(与模板自身指引冲突时以模板为准):

1. **复用具名到文件路径**——"照抄 `apps/xx/src/lib/gate.ts` 范式",禁止"参照既有做法"。
2. **数字来自调查**——端口、表名、scope 名、上限值,全部来自第 2 步的事实清单,不来自记忆或旧文档。
3. **热查询点名索引**——汇总/列表/统计查询的过滤列,要么指出已有索引(带名字),要么写进迁移新增;别让聚合裸扫大表。
4. **闸门有顺序,错误面要对齐**——同一端点叠多道闸(存在性/scope/角色/成员资格)时写明顺序;计划承诺的错误码必须是**第一道会失败的闸**真正抛出的(先查成员再查存在性,非成员对不存在的资源拿到的就是 403 而非 NOT_FOUND——想承诺 NOT_FOUND 就得先查存在性);每类拒绝写明传输层 status(4xx)还是业务错误(200+错误体),验证章节按此断言。
5. **每个里程碑自带验收**——里程碑表每行的"验证"列非空(脚本断言 + 真实环境走查);上一步不绿不进下一步;重构类步骤以"既有验证全绿"为回归门。
6. **安全项 = 可断言项**——安全清单每条都要能翻译成一条验证断言,写不出断言的不算安全项。
7. **需求 → 设计映射兜底**——结尾一张表,R1…Rn 逐条指到具体章节 + 机制 + 验证脚本;项目硬约束(多租户/i18n/设计规范等)也入表;排除项汇总指到"明确不做"。
8. **规模感**:参考模板给的行数区间(无模板时 200-500 行);范围决策约 1/3、验证约 1/4——这两块薄了计划就不可执行。调查过程的原始材料**不要**倾倒进计划,计划只留结论 + 路径。

## 第 5 步:自检与收尾

1. **过模板自检清单**(模板通常自带;没有就用 `references/plan-skeleton.md` 末尾的通用版),逐项打勾,不过的回去改。
2. **路径真实性**:跑 `scripts/check_paths.sh <计划文件> <仓库根>`,列出计划中引用但不存在的路径;逐条人工判断——★新增文件与占位符本来就不存在(正常),**"复用/已核实"类路径出现在 MISSING 里就是虚构,必须修**。
3. **需求映射全覆盖**:对照第 1 步的 R1…Rn 逐条核对映射表,有空格说明设计有洞。
4. **交叉一致性自检(抓自相矛盾)**:换上实现者的眼睛把全篇重读一遍——计划是分章节写出来的,各章节各自合理但互相打架是最常见的深层缺陷。专抓四类:
   - 机制章节用到的每个 scope/服务态调用/凭证,反查 seed/SA/清单章节确实配了——设计用了 `directory.read` 而服务账号只给了 `notification.send`,实现期必卡死;
   - 验证章节的每条断言在设计章节有依据——不许"验收要求了设计里不存在的东西"(如断言 CSV 含备注列,而设计定义的 CSV 没有该列);
   - 承诺的不变量互不冲突——"信封 id 恒定"与"重投递克隆新行"不能同时成立,发现即回去改设计;
   - 新增的每个标识符(错误码/共享包导出/env/部署 values 字段)都有对应的登记文件项——漏一处 typecheck/部署就断;
   - 每个权限/角色/开关位**逐跳追通**:UI 入口可见性 → token/bootstrap 载荷 → 服务端真闸——任何一跳不携带该位就是断链(后端支持 bypass 删除但 bootstrap 不返 bypass、发了角色模板但服务端只认租户 role,都是这类);
   - 同一口径(导出格式、通知语义、上限值)在全篇多处出现的,逐处对齐——在一处修正的决定必须同步到其余所有提及处,只修一处等于没修。
5. **落盘**:默认写到项目的计划目录(与模板/范例同目录),命名循既有惯例;宿主 repo 没有计划目录时用 `docs/plans/<大写代号>.md` 并向用户说明。目标文件已存在时先确认再覆盖。
6. **汇报**:向用户交付时,除了计划路径,单独列出:① 留给用户拍板的开放问题;② 调查中发现的、与用户假设冲突的事实;③ 你替用户砍掉/推迟的范围(让用户有机会否决)。

## 红线(任何情况下不违反)

- **只写计划,不动手实现。** 交付物是计划文档;用户要实施会另说。
- **不虚构核实。** "已核实"三个字后面必须是本次真读过的路径。
- **不缩水验证。** 验证章节 + 里程碑验收占计划近一半篇幅是特征不是浪费——砍这里等于交付一份不可执行的愿望清单。
- **不吞需求。** 用户的每条原始需求,要么有设计落点,要么被显式排除并给出去向,没有第三种下场。
