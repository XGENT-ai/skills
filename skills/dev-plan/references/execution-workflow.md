# 按计划实施：进度、记录与并行

实施或续做时读取本文件；写计划时仅在需要细化调度边界时读“并行执行”。不加载写作骨架或架构参考作为实施上下文。

## 先恢复最小上下文

先读仓库规则、计划的恢复快照/完成记录索引、当前任务对应的正文与依赖，再核对 `git status` / 相关 diff。记录与工作树不符时查明原因，不凭历史记录覆盖用户改动，不凭代码存在就推断验收已通过。

**独立记录按需读取**：只有继续某个未完任务、核实其前置验收、排查失败/偏差或审查交付时，才打开该里程碑记录的相关章节。无需例行复读最近完成的详细记录，更不要 `cat` 全部记录或把历史日志传给每个 subagent。只查结构一致性时运行校验脚本，看简短结果即可。

## 计划只存摘要，详情独立落盘

- 计划顶部保留七行恢复快照。当前状态列出在做的里程碑及最近实质进展，下一步给可执行动作；不写命令、断言列表、调试过程或完整改动清单。
- “完成记录”是一张里程碑索引：`Milestone / 状态 / 更新时间 / 简要记录 / 实现与验收记录`。每个已开始的里程碑最多一行，状态仅用 `进行中`、`阻塞`、`已完成`；摘要一到两句，写交付结果或“已做到哪里、还差什么”。进行中/阻塞不计入完成数。
- 默认每个里程碑一份 `<计划名>.records/M<n>.md`，在其中分开写“实现记录”和“验收记录”；链接相对计划文件解析，例如 `[M1 记录](FEATURE.records/M1.md)`。用户已有记录目录时沿用。详情只从完成记录链接，不在正文/快照重复嵌入。
- 记录首次有实施事实时再建；原始日志、截图、完整 diff 仅在有复核价值时单独保存并从记录链接。记录本身也要提炼证据，不复制终端流水、聊天或阅读清单。

### 独立记录的最小内容

按下面结构写真实内容，不预填通过；它不是另一份总进度表。

```markdown
# M1 · 实现与验收记录

- 对应计划：相对链接
- 最近更新：日期、时间与时区
- 状态：进行中 / 阻塞 / 已完成
- 代码基线：commit SHA；未提交写 dirty@起始SHA，非 Git 写可用版本标识

## 实现记录

- 已交付行为、关键改动路径、必要决策及计划偏差。
- 尚未完成项、阻塞事实及继续动作；完成后写无。
- 并行任务如有独立交付记录，在这里链接，不复制全部内容。

## 验收记录

| 退出条件 | 命令或走查步骤 | 环境/代码基线 | 结果与必要证据 |
| --- | --- | --- | --- |

逐条记录实际结果；未运行、失败、环境缺失明确区分。人工/UI 验证写环境、主路径与关键边界结论。必要的日志/截图用链接。
```

代码基线必须对应验证时的实现；dirty 时在实现记录列关键改动路径，不能用 HEAD 冒充已提交成果。主 agent 的集成修正若影响既有结果，应更新验收证据。subagent 完成自己的任务不等于里程碑通过验收。

## 每个里程碑及时回写

每次完成里程碑，或发生实质进展后准备暂停、受阻、切换任务、结束对话时，按顺序完成以下动作；并行任务逐个收敛，不等整个批次结束才补记：

1. **先保存独立记录**：及时记下实现与实际验收结果。全部功能/验收条件通过才标 `已完成`；未通过则保存已有成果和缺口，保持 `进行中` 或 `阻塞`。
2. **再刷新计划摘要**：同步七行快照和该里程碑的一行索引，链接到已存在的记录文件。由未完成转为已完成时，将该行移至已完成记录末尾，不增加重复行；已完成行按实际完成先后排列，“最近完成”取最后一条已完成记录，不按编号大小推算。并行时允许 M3 比 M2 先完成。
3. **有偏差就修正文**：范围、决策、接口、数据、风险或退出条件变化，修订对应章节，快照只点明变化及影响。不要把偏差藏在独立记录里。
4. **校验后再交接**：运行 `"$SKILL_DIR/scripts/check_progress.sh" <计划文件> [仓库根]`。先完成记录落盘与计划回写，再报告完成、提交代码或启动依赖该成果的任务；已经独立运行的任务可继续。

脚本检查数量、状态、里程碑 ID、最近完成和引用文件存在性，不默认读取所有记录内容，也不证明验收真实通过。主 agent 在记完成时核验该里程碑的证据；后续恢复只按需要复核。

旧计划首次按此流程续做时，将已有完成详情迁到独立记录，保留原时间、结果和基线；计划改成摘要索引。没有证据就保留缺口，不能补造通过记录。只迁移正在执行的这份计划，不批量改其他历史计划；旧规则中的串行限制若只是旧模板默认值，可按依赖核实后更新，项目确有顺序约束则保留。

## 并行执行

每次调度前检查依赖与当前工作树。**有两个以上可独立推进、不会互相干扰的任务且环境提供 subagent 能力时，启动多个 subagents 并发完成**；主 agent 同时处理不与它们冲突的任务或集成准备。不要只写“可以并行”却仍全部串行，也不要为了凑数量拆出无意义任务。

### 哪些任务可同时启动

- 前置成果已通过所需验收，输入/接口契约已稳定；同一里程碑内或不同里程碑之间都可并行，编号本身不是依赖。
- 写入的文件集合互不重叠，不会在另一个任务仍依赖的文件中改接口/导出/行为。共享类型、公共入口、锁文件、生成产物和迁移序号指定一个负责人，先确定契约或串行集成。
- 测试和运行资源互不影响：共享数据库、种子/迁移、端口、开发栈重启、同一浏览器会话或外部环境写入需隔离或串行。独立 worktree 只能隔离文件，不能自动隔离这些资源。
- 无法证明独立就先串行完成前置或重新划界。用户要求串行、工具不可用或资源受限时如实说明，按可用并发数调度，其余串行，不虚构已启动的 subagents。

### 委派、交付与集成

主 agent 给每个 subagent 一份精简任务说明：目标及计划章节/需求 ID、已稳定契约、允许写入与禁止修改的路径、可用运行资源、验收条件、独立记录路径、需回报的阻塞。不复制整段聊天或无关历史；工具支持时选择最小上下文，让 subagent 按需读取规则和相关文件。

**模型默认继承**：如无特别要求，subagent 使用与主 agent 相同的模型。启动工具支持继承时省略模型覆盖参数；必须显式指定时填写主 agent 的模型。只有用户或适用指令明确要求其他模型时才覆盖，不自行因任务难度、成本或速度降级/换模型。

每个文件同一时间只有一个写入者。**计划与里程碑汇总记录由主 agent 单写**；subagent 将详情写入各自的 `<计划名>.records/M<n>-<任务名>.md`，返回简要结果、改动路径、验证结论、缺口与记录链接。任务结束、阻塞或暂停时及时交付；不得替其他 agent 修改文件或回滚他人改动。边界变化先回报，主 agent 调整分工后再继续。

主 agent 逐项审查交付与当前 diff，按需读取相关任务记录，整合成果并完成里程碑所需的集成/回归验证；局部测试全绿不能替代集成验收。有任务失败就保留已交付成果，阻塞依赖它的任务，无关任务可继续。每个里程碑验收完成后立即独立回写，不能等所有 subagents 都结束。结束对话前收集或停止尚在运行的任务，记录可接续状态，不留下无人管理的写入任务。
