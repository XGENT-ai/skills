# 中国专利交底书编写

把用户提供的研发材料写成简体中文交底书，让专利代理人能复述方案、追问缺项，并据此开展后续工作。主动查新只为交底书提供参考。不做独立专利检索、申请办理、正式申请文件、专利布局、专利解读或审查答复。用户同时要求相邻任务时，说明本技能覆盖的部分；不要将它们自动作为下一步。

## 1. 确定主题与证据

- 以用户指定的主题和材料为准；只读明确提供或允许扫描的项目范围。优先读交底旧稿、设计文档、关键实现、实验记录与相关附图，并记下关键事实所在的章节、图号或文件位置。材料无法读取时，说明缺了什么，继续用其余可用材料。
- 未指定类型时按**发明（默认）**写；方法、系统、装置不是专利类型。明确指定实用新型或外观设计时直接使用对应写法。材料与当前类型明显不符时只询问一次，未经确认不自行切换。
- 从材料归纳本篇的核心机制或设计要点。若有几组无共同构思的方案，指出边界；先写用户指定或证据最充分的一组，不把它们硬合成一篇，也不自行分拆写多件。
- 分开已实现、拟实施、实测、机理推断与未确认事实。材料冲突时不静默择一；不补造部件、步骤、公式、数值、附图或测试结果。不确定是否真实的新构想不得写作已披露方案。只问会改变方案主线、关键实施细节或外观要点的问题；没有技术材料时先索取材料，已有可写内容时交付草稿并列出实质缺项。姓名、电话、邮箱等缺失不阻塞，模板要求时写「待填写」。
- 不把未公开材料、个人信息或项目文件名发送给外部工具或服务。面向交付方只保留必要信息；脱敏不能删掉实施所需的结构、条件或参数，未经确认不得用假值替代。

## 2. 主动查新，供本稿参考

新写交底书、实质改动技术方案或设计要点，或用户要求补查新时，先读 [公开查新与证据比对](references/prior-art.md)，在成文前用可公开的关键词主动查找文献。已有检索覆盖本稿要点且可核验时复用；仅润色、排版或修订无关字段时不重查。

用户要求保密、离线或不做查新时不联网；无法构造不泄露未公开方案的检索式时不发送。无安全词、检索工具不可用或没有可用对比文献，均不阻塞起草。用户提供的对比资料可直接核对和引用，不能把它们写成本次主动检索的结果。

## 3. 按类型成文

读取 [分类型交底书写法](references/drafting.md) 中的通用规则及本案类型一节。用户提供代理所或团队模板时，按该模板组织章节，保留本案类型的必要内容。

发明、实用新型都要写清**现有做法与局限 → 技术问题 → 方案 → 技术效果**，并区分必要特征和优选配置。软件或算法写明具体技术环境、数据或控制对象及实际技术作用，不把业务目标包装成技术效果。外观设计写可见设计要点及视图，不写成技术方案。

## 4. 核对与交付

- 逐项核对关键事实、问题与效果的因果关系、实施例或视图对正文的支撑，以及术语、图号、部件号、步骤和参数的一致性。修订已有稿时同步更新受影响章节和附图说明，不在用户未授权时覆盖原文件。
- 默认交付可编辑 Markdown；用户指定位置或文件名时按其要求。未指定且可落盘时，在当前工作区 `outputs/patent-disclosure/` 以 `案件名称_YYYYMMDDHHmmss.md` 另存，不覆盖既有稿；只要对话文本时不落盘。需要 Word 时，仅在用户明确要求且有可用本地生成能力时，从同一稿导出，不把导出当作成文前提。
- 关键技术事实或必需视图缺失时，把稿件标为「待补材料」，在对应处标「待确认」或「待补图」，不要称为定稿或可提交申请。交付回复给出稿件路径或正文，并简列需要发明人确认的事项；不把技能流程或自检清单写进交底书。
