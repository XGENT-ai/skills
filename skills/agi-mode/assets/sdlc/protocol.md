# 项目状态记录协议 · v3

本目录默认是仓根 `.xgent-ai/sdlc/`，随项目版本控制保存。`index.md` 只作导航；`status/<kind>/index.md` 列对象去向，`status/<kind>/<object_id>.md` 各保存一个对象的状态；`events/<kind>/<object_id>/` 保存该对象的独立事实记录，`event-template.md` 是写入模板。本协议可由任意 agent 或人工执行，无脚本、数据库或特定 skill 安装依赖。路径可按项目约定调整，以下文件名相对于本协议目录。

判断和回写前读取随仓保存的 [固定状态与证据校准](state-model.md)：使用固定状态码，区分原文自述与核查结论，并按其中的规则发现漏记的评审、处置和实施证据。台账、原文状态行都可能滞后，不直接照抄为当前事实。

## 分类与读取

- 本目录只保存状态及其索引、协议和事件。PRD、开发计划、评审报告、实施/验收记录、测试计划、原始日志/截图等继续按用户习惯与项目约定保存；不规定它们的目录或文件名，不搬迁、复制或创建在本目录。用 `artifact`、`sources` 及来源链接引用实际位置。
- `kind` 的默认目录名固定为 `prd`、`plan`、`review`。每个对象单独状态页；每轮评审也是独立对象，计划状态页链接各轮而不复制报告。类型索引只列 ID、标题、来源、状态页及活动/归档标记，不存所有对象的进度正文。
- 类型索引过大时按领域或年份分片，父索引列全分片与范围；归档另列索引，不删事件，不以文件年龄推断归档。顶层列直接文件、子目录入口和当前重点，不能悄悄截断活动工作。
- 显式枚举隐藏目录：`rg --files --hidden .xgent-ai/sdlc`。先看导航/分类索引，再按活动对象、用户选定范围及依赖读状态页和相关来源。比较该对象事件目录与其已纳入集合；没登记的对象/事件要提示，不默认全文加载所有历史。
- 旧 `docs/project-status/` 或其他登记台账沿原协议维护，不自动生成第二份。仅在台账迁移获授权时迁移状态资料，保留 ID、历史内容与来源版本，转换来源链接并记录旧路径映射；原文档保持原位；核验后登记新入口，旧入口只留指引。不要用本 v3 模板直接覆盖旧协议；协议升级与历史自由文本的兼容按 state-model.md 执行。

## 目录索引维护

本规则适用于 `.xgent-ai/` 下实际创建的每层状态目录，包括 `sdlc/`、`status/`、`status/<kind>/`、`events/`、`events/<kind>/`、`events/<kind>/<object_id>/`、非开发任务的 `tasks/` 与任务子目录，以及后续增加的归档或分片目录。每个目录都有 `index.md`，目录按需创建，不为索引预建空树。原文档目录不受本规则约束。

- **内容与边界**：写明目录用途、覆盖范围与本规则入口；列全直接文件和子目录，不自列 `index.md`。文件链接到自身，子目录链接到其 `index.md`，链接相对当前索引解析，不含机器绝对路径。类型目录一对象一行，保留 ID、标题/来源、状态页及活动/归档标记；事件叶目录一事件一行，保留事件 ID、facet/scope 和文件链接，不复制状态结论。普通导航只列名称、用途和入口，不在每层复制全树或进度。
- **职责与时机**：创建或改变目录内容的执行者，在同一批交付中维护受影响索引；先落状态文件/事件，再更新本层索引，最后更新入口有变化的祖先。首次创建目录同时创建索引；旧目录缺索引时在已授权维护范围内补齐。无关目录和内容不变的索引不重写，也不只为检查刷新时间。状态正文改变但身份、去向和目录成员不变时，无需改索引；当前重点实际改变时才更新重点。
- **新增与移动**：新对象、新事件、新子目录必须登记；已有对象的新事件只新增到对应事件清单，不逐级改总索引。获准移动状态文件时保持对象/事件 ID，更新旧、新父目录与受影响链接，保留历史路径映射；不改写不可变事件。原文链接变化须核实新位置，维护索引不授权移动原文。
- **归档与删除**：归档须有事实依据，更新活动/归档去向并保留可达入口和事件历史。索引过期条目只有确认目标已按授权删除或迁移后才删除或改指；本机目标缺失先标未同步/待核对，不能顺手删记录、删目录或裁掉历史。原文已删除也保留状态与事件，标明来源不可用。
- **增长与排序**：条目按相对路径或稳定 ID 排序，避免每次按状态、机器时间重排。索引过大时拆为 `index-<分片名>.md`，首页列全分片与明确范围；每项恰属一个分片。分片是导航文件，不产生对象或事件 ID；如另建物理目录，该目录也须有 `index.md`。活动项不能因分页或归档而从入口消失。
- **事件识别**：`index.md`、`index-*.md` 都是可修改导航，必须排除在事件读取、事件数量及已纳入事件集合之外。实际事件以 UUID 文件名和一致的 `event_id` 字段识别；疑似事件但格式损坏时报告待核对，不悄悄忽略。
- **多机合并**：写前重读本层索引。合并时按稳定 ID 与路径保留双方新增项，再对照合并后的实际文件和事实重建导航；不按时间或单边版本覆盖。相同 ID 指向不同内容、相同路径对应不同 ID 时保留冲突提示并核对。索引不是锁，不证明其他机器已同步；重建保留人工用途说明、当前重点及未解决问题。
- **检查与恢复**：回读受影响索引及祖先入口，枚举当前可见的直接内容与分片，检查漏项、重复条目、缺少子目录索引和断链；发现未登记目录时递归核对其索引覆盖，不需全文读历史事件。缺失目标明确可见性限制。保存事件成功而索引失败时保留事件并说明待修复，下次维护可补齐；查询模式仅报告索引缺失/陈旧，不自动写入。

## 事实与粒度

- PRD 正文定义需求；计划正文定义范围、门槛与恢复入口；实际实现、验证及处置记录支撑进度判断。原文自报状态不享有绝对优先级：与可核实交付不符时，台账保留自述并给有证据的规范状态及差异原因，不顺手修改原文或外部系统。
- PRD、计划、评审各有稳定 `object_id`。一份 PRD 可关联多计划，一份计划可关联多 PRD；依赖可细到需求、里程碑或检查，不强制串行。一轮评审可审多个对象，未关联计划的代码评审也可独立登记。
- 原文件名与状态对象 ID 分开：登记时沿用已有对象 ID，否则分配 UUID，不要求原报告用 UUID 命名。每次实际评审是独立对象，即使同日、同机器或同路径重跑也分配新的评审 ID；同轮整改沿原评审对象追加处置。复审用 `rechecks` 关联前轮，问题以 `评审 object_id + 报告内问题 ID` 定位。原报告被授权覆盖时，引用可取回的历史版本或用户约定位置的快照，不把快照放进本状态目录；仅有 hash 而内容不可取回时标证据缺失。
- 已有本协议 ID 时沿用；新对象/事件用独立生成的 UUID（例如 `python3 -c 'import uuid; print(uuid.uuid4())'`，也可用系统 UUID 工具），不依赖机器名、时钟或共享递增编号。文件移动保持对象 ID，并在新事件登记新路径和旧路径；复制出独立计划则新建 ID，关联 `derived-from`。
- 同一历史对象被两台机器首次导入为不同 ID 时，只有读到来源/版本/范围等证据确认相同，才新增带 `same-as` 关系的对账事件；保留原 ID 和所有历史。同名、同 hash 的两次真实评审不能因此合并。

## 事件字段

每次变化新建 `events/<kind>/<object_id>/<event_id>.md`，YAML frontmatter 加简短 Markdown 证据正文。用 `event-template.md`，去掉不适用的可选字段。记录一旦交付保存不覆盖；纠错/补证新建后续事件。写前重读相关记录，文件名已存在则核对，禁止覆盖不同内容。

| 字段 | 约定 |
| --- | --- |
| `schema_version` | 新事件固定为 3；旧事件不原地改写 |
| `event_id` | UUID，与文件名一致 |
| `object_id` / `kind` / `title` | 稳定对象 ID；`prd`、`plan`、`review`，必要时允许项目自定义类型；可读标题 |
| `artifact` | 对象的仓根相对路径；纯外部对象可写可访问的稳定 URL；不可访问则说明 |
| `facet` / `scope` | 本次更新的维度与范围；同一维度内用稳定 scope，如 `document`、`plan`、`M2`、`F-01`。不因措辞变化新造 scope |
| `state` | state-model.md 中对应 kind/facet 的固定状态码，无法确定用 unknown |
| `source_state` | 原文自述的原始状态文字；无状态文字用 null，不代替规范判断 |
| `evidence_status` | confirmed、provisional、stale、conflict、unknown，按状态模型判定 |
| `candidate_state`（可选） | 当前无法确认时的候选状态，必须属于同一枚举；不是已确认状态 |
| `review_type`（评审对象必填） | prd、dev-plan、code、other，由报告内容判断，不只看后缀 |
| `observed_at` | 带时区的 ISO 8601 观察时间；仅供展示，不决定新旧 |
| `predecessors` | 同对象、维度、范围上，本次明确接续/纠正的事件 ID 数组；初次为空；不是其他工作依赖 |
| `baseline` | 所观察 checkout 的 HEAD、branch、clean/dirty；非 Git 写可用版本或 unknown；它与报告所审版本分开 |
| `sources` | 路径 + 版本/hash + 稳定章节/问题定位；至少一个事实来源，未知版本明确写 unknown |
| `relations`（可选） | `type`、`target` 对象 ID、`scope`；如 `covers`（承接需求）、`reviews`、`rechecks`、`depends-on`、`derived-from`、`same-as`；关系在后续事件中可显式撤销并给依据，不默默遗失 |

正文记录事实摘要、证据、未完项/解除条件及建议动作。测试与报告的长内容留在来源文件，只链到必要段落。关系、状态变更及作废均须有依据。角色/责任人、实际活动日期、分期等按需补充，未知不填成默认事实。

维度与固定枚举分开保存；具体状态集合及证据门槛见 state-model.md。项目扩展先登记定义，不要求全部维度存在：

| 对象 / facet | 记录什么 |
| --- | --- |
| PRD / `document` | prd-drafted、prd-reviewed、prd-blocked、prd-ready、unknown；各轮意见另记 review 对象 |
| 计划 / `readiness` | dev-plan-drafted、dev-plan-reviewed、dev-plan-blocked、dev-plan-ready、unknown；原文 Ready/Proposed 等另存 source_state |
| 计划 / `implementation` | 按 `plan` 或里程碑 scope 记录尚未开始、进行中、阻塞、已完成及源进度链接 |
| 评审 / `review` | 评审种类、对象、范围、base/target 或文档版本、报告是否完整落盘、原结论和限制 |
| 评审 / `disposition` | 指定问题或整轮的修订/修复处置；待核实、已修改待验证、已验证、不采纳及依据等 |
| 计划等 / `acceptance`、`integration`、`release` | 独立验收线枚举 TBD；保留实际证据及已有项目枚举，不由开发完成自动推导 |

`Ready` 不计实施完成。报告写完不等于评审通过。整改已验证不改写原评审结论，不冒称独立复审。里程碑完成数取计划和可核验记录，不取事件数量；同一里程碑的多次更新不重复计数。局部验收不代表跨期需求终验，所有计划完成也不自动等于 PRD 全部交付。

## 回写流程

1. 正常先交付/更新原产物和证据，再登记本次变化。实质进展、阻塞、交接、评审完成、整改/复核完成时回写；普通任务切换和无变化查询不写流水。
2. 按对象、维度、scope 找已有事件和 ID。仅更新这次工作触及的维度，不为登记代码评审顺便改变计划的 Ready 或完成状态。不明确的关联保留待关联。
3. 新事件列出实际读过且接续的前序，记录当前来源版本与证据。根据 state-model.md 判断规范状态；来源、规范状态、证据质量/适用性、范围和关系均不变时不重复写，不因无关提交改变 HEAD 就新增事件；初始化只记当前可核实的状态，历史缺失不补造。漏记或滞后按模型的自愈规则补证、纠错，不直接覆盖旧事件。
4. 更新受影响的 `status/<kind>/<object_id>.md`，其中保留未关联、过期、冲突、缺证及关系。写本对象的观察时间、checkout 基线和精确的已纳入事件 ID 清单（排除索引文件）。按“目录索引维护”同步本对象事件清单、必要的分类索引与祖先入口，不每次重写所有状态页和索引。只看数量或最大时间不能发现遗漏。事实、来源适用性、可见范围和建议均无变化时无需重写视图，保留上次保存时间，在回复说明本次已核对即可。
5. 回读新事件与视图，核对链接、ID、前序、来源及目录索引覆盖。事件保存成功、视图/索引更新失败时保留事件并说明待刷新范围；原产物成功但登记失败时明确台账未同步，不回退产物。

其他技能只需读本协议与相关记录即可回写，不要求加载 agi-mode 的完整流程。用户要求仅聊天/只读/不保存时不登记。只安装部分技能、旧版技能或人工操作未回写的产物，由下一次盘点发现并提示，不能把“未登记”解释为“未发生”。

## 多机、分支与冲突

- 每次变化独立文件，降低并行追加的文本冲突；Git 只是传输方式，不提供自动同步或全局锁。协议、事件与状态页可纳入版本控制，不能放进本机缓存目录；原文和证据按项目原有方式同步，本目录只引用其位置与版本。记录未提交/未推送时说明尚未共享；不自动提交、推送、拉取或改分支。
- 只报告当前可见范围。分支名是线索，commit/内容和实际来源才是依据；已 fetch 的远程引用也不证明另机没有未提交工作。另一分支事件可列出，但不能当成本 checkout 已实现。
- 未提交代码的评审/验证保留 `dirty@HEAD`、所涉及的 tracked/untracked 路径及内容指纹或快照位置，不能只有 HEAD。指纹只能检测变化；缺少可同步的快照时明确“仅原工作树可复现”，另一台机器必须重新核对。hash 的文件集合和算法写清，不能把 index、工作树和未跟踪文件混为一谈。
- 文档评审记录所审文档 hash/可取回版本及依赖的代码基线；代码评审保留精确模式、base/target、文件限制和可选计划版本。对比相关内容确认当前适用性；后续无关提交不会自动使全部证据失效。
- 对同 `object_id + facet + scope`，沿 `predecessors` 找未被接续的末端。只有一个末端也仍需核对当前来源；多个末端是并发观测。两条一致且来源等价可合并展示但保留记录；矛盾或适用分支不同则并列标“待核对”，不得按机器时间或字典序取最后一条。前序缺失/成环也列待核对，不静默丢记录。
- 状态后退可以是真实回归；“已完成”不比“阻塞”优先。证据核实后新增对账事件，`predecessors` 引用全部被解决末端，并说明选择/合并的依据。跨 scope 的局部完成不覆盖计划整体状态；总进度仍核对计划本身。
- 合并时保留所有事件。对象状态页只是派生视图，冲突时从合并后的事件与来源重建；原 PRD/计划/报告发生冲突按原文件处理，不能只修对象状态页。相同 event ID 内容不同则先保留双方并标 ID 冲突，修复引用后再汇总。
- 记录找不到来源时区分未同步、已移动、已删除、历史版本不可访问与未知；不擅自删事件或把历史完成改成未开始。非 Git 场景可以同步本状态目录，原文和证据仍各按既有位置同步，再以 UUID 与来源核对，无法证明同步就写未知。

## 当前有效与下一步

对象状态页同时显示“固定状态码”“来源自述状态”“证据质量”与“当前核查限制”。历史评审通过后有相关改动，保留原结论并写当前待复核；源文档与记录冲突时展示双方出处，有充分证据可纠正台账并注明原文滞后，不能顺手覆盖原文。未评审、无需评审、评审结论不可判定、过期待核对不能混用。

建议只依赖已核实的前置，并尊重项目自己的门槛。发现独立计划可推进时列出；有共享文件、接口、环境或前置依赖时说明实际冲突。状态盘点不默认重跑测试、评审或开始开发；执行以用户已有授权和当前任务范围为准。
