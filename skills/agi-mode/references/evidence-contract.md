# 证据契约

用于多阶段、批量交付、反复变更使证据容易过期的任务。小任务直接检查产物即可。内置 [检查器](../scripts/check_evidence.py) 只读文件，不运行记录中的命令，也不提交或修改任务状态。要求 Python 3.9 或更新版本。

## 两份记录

沿用项目已有验收与记录；需要机器检查时，将其表达为下面两份 JSON。契约先于实现确定，收据在真实检查后产生。

契约包含目标与必要验收，每项指定必须通过的检查。例如：

```json
{
  "goal": "导出正确 CSV，并保持过滤行为",
  "requirements": [
    {"id": "csv-output", "checks": ["export-scenario"]},
    {"id": "filter-parity", "checks": ["filter-regression"]}
  ]
}
```

收据包含：

| 字段 | 含义 |
| --- | --- |
| `contract_sha256` | 此次验证所依据的契约文件 SHA-256 |
| `checks` | 检查记录列表；未执行时可为空 |
| 每条记录的 `id` | 与契约中的检查标识一致 |
| `status` | `passed` 仅用于确实通过的检查；其余状态不能通过一致性门槛 |
| `observation` | 实际入口、命令或操作、观察结果与限制的简短说明 |
| `inputs` | 验证前记录的输入文件指纹列表，包含实现、验证器及相关配置和依赖锁文件 |
| `artifacts` | 验证后保存的原始日志、输出、截图等证据文件指纹列表 |

每个文件指纹是 `{"path": "相对工作根目录的路径", "sha256": "实际的 64 位小写 SHA-256"}`。输入和证据必须分开，列表不能为空。未相关的探索失败可以留在记录中；检查器只要求契约引用的必要检查通过。

## 操作顺序

1. 把验收与用户目标核对，保存契约。目标、范围、验收或验证语义变化时显式修订契约，重新评估受影响证据，不能为过关删掉未满足项。
2. 验证前记录契约与输入指纹。验证结束后确认这些输入未变，再保存实际结果和证据指纹。不能在代码改变后重算指纹，继续沿用旧日志。
3. 跨阶段、恢复任务、批量交付前，在相关文件不再被并发写入的检查点运行检查器，修复缺失、未通过或过期的收据。
4. 最后仍需判断输入依赖是否完整、证据是否真的覆盖目标，以及外部状态是否仍成立。记录一致不代表任务成功。

以下命令从 skill 目录运行；工作根目录与记录位置替换为当前任务的真实路径：

```bash
python3 scripts/check_evidence.py fingerprint --root /path/to/work src/export.py tests/export_test.py contract.json
python3 scripts/check_evidence.py check --root /path/to/work --contract /path/to/work/contract.json --receipts /path/to/work/receipts.json
```

`fingerprint` 输出可放入 `inputs` 或 `artifacts` 的 JSON 列表；契约使用对应条目的 SHA-256。检查器退出码 `0` 表示记录一致，`1` 表示必要记录缺失、未通过或文件变化，`2` 表示输入或格式错误。输出字段故意叫 `records_consistent`，不叫 `task_complete`。

## 能检查和不能检查的内容

能检查必要检查覆盖、契约身份、输入与证据存在性、内容变化、重复标识及工作根目录外的路径。不相关文件变化不会自动使所有证据失效。

不能证明命令确实运行过、收据诚实、依赖列表完整、结论正确或授权成立。新增但未列入的依赖、工具版本、环境变量、进程状态和远端资源需额外核对。涉及这些因素时，将复现环境信息保存为输入记录，并在重新使用证据前核对实际环境；对旧环境快照做哈希不能证明远端现状。

验证器修订使原结果失效时，重新执行受影响检查并保存新收据。原始证据用于追溯，不就地篡改来匹配新结果。
