# 重构与迁移

重构改变结构并保持行为；迁移让调用方、数据或运行环境到达新的目标状态。先声明属于哪一种，避免把兼容性变化藏进“清理”。

## 执行

决策入口：划定兼容窗口读 [迁移闭合](../principles/complete-migrations.md)，结构取舍读 [复杂度](../principles/minimize-complexity.md)，安排批次读 [可验证单元](../principles/verifiable-units.md)。

1. 明确保持的行为、允许改变的接口、目标状态与迁移范围。建立调用方和资源清单，包含动态引用、配置、作业和外部消费者；无法穷尽的部分单独记录。
2. 在改变前建立行为基线或等价检查。依风险选择代表性输入、记录重放、集成检查或现有可靠测试。数据迁移另需核对数量、标识、关系与业务不变量。
3. 设计最小目标结构和迁移顺序。内部调用方都在控制范围且可原子更新时同批迁移；外部消费者、滚动部署或数据转换需要过渡期时，明确兼容窗口与旧路径退出条件。
4. 先迁移一个有代表性的单元验证方法，再扩展。重复操作适合脚本时，先验证样本、预览影响，并使重跑能够识别已完成项。
5. 数据与外部状态写入前确认授权、恢复方法及其实际可用性。转换不可逆时不能笼统声称“回滚代码即可恢复数据”。在允许的环境先演练。
6. 每批完成即验证行为、调用关系或数据不变量。失败时停止依赖该批结果的后续工作，保留已确认状态并按恢复方案处理。
7. 核对清单和实际使用情况。只有调用方已迁移且兼容窗口关闭后，才移除本次淘汰的旧路径；完成最终等价或集成检查。

重构中发现独立缺陷时记录并分离，不静默改变行为。若缺陷阻止目标完成，说明依赖并在授权范围内转入 [缺陷修复](bug-fix.md)。

## 验收与退出

- 重构的行为约束成立，目标结构确实减少了当前问题。
- 迁移范围内的调用方与资源有明确归宿，失败项和兼容期没有被遗漏。
- 临时兼容层仍是必要状态时，交付应标明阶段完成及其退出条件；用户要求全量迁移而仍有必要未迁项时不能宣称全部完成。

## 交付

改变的结构或迁移范围、行为与数据证据、当前版本和阶段、恢复限制、仍在使用的过渡路径及清除条件。
