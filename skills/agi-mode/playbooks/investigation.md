# 调查与诊断

用于解释“如何工作、为什么失败、瓶颈在哪里、方案是否成立”。交付答案或诊断。用户同时要求修复时，调查完成后继续进入对应实施流程。

需要从活进程或捕获文件提取 CPU、内存、线程和时间线证据时，使用 [运行时与离线取证](forensics.md) 的具体方法，再将结论带回当前问题。

## 执行

决策入口：缩小调查范围读 [信息价值](../principles/information-first.md)，决定自己查证还是向用户提问读 [自主决策](../principles/autonomous-decisions.md)。

1. 把问题收敛成需要判断的事实，确认对象、版本、时间范围和用户观察到的现象。先读相关入口和现有材料，不从全库漫游开始。
2. 沿真实路径追踪输入、状态变化、依赖与输出。解释“为什么这样设计”时寻找设计记录或变更历史；找不到则把动机标为推断。
3. 将最重要的解释与竞争解释并列，寻找能区分它们的证据。因果不清时读取 [实验与反证](../references/experiments.md)，优先运行现有无副作用的观察工具。
4. 根据材料选择观察路径：运行时问题检查现有进程、请求、资源及时间变化；捕获的 trace、profile、日志先确认采样窗口、负载和符号映射，再定位热点。采样占比不能直接证明因果。
5. 用另一条相关证据核实关键结论，例如调用路径与实际输出、热点栈与调用次数。对矛盾先查版本和观测口径，不挑选支持首选解释的材料。
6. 回答原问题，指出结论适用条件、未排除的解释，以及足以消除剩余未知的最小动作。

只读请求不修改产品、配置或线上状态。可以在临时位置解析材料；若必须加埋点或改变运行环境，说明为什么现有观察不足，核对授权后再做。诊断材料不可获取时，提出最小必要输入，不用猜测填满答案。

## 验收与退出

- 读者能从答案回到具体文件、记录或运行结果。
- 已观察事实、原因推断与待验证假设清楚区分。
- 回答足以支撑请求的判断后结束，不自动实现建议。
- 已授权修复且证据足够时，转入 [缺陷修复](bug-fix.md)，沿用复现和诊断。尚不能定位时，交付诊断边界，不声称找到根因。

## 交付

结论、最短关键路径、支持证据、影响与局限。若请求是方案判断，给出推荐及改变推荐的条件。
