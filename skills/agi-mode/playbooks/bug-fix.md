# 缺陷修复

用于有异常行为需要恢复正确性的任务。最重要的证据是原触发条件下的前后变化。

## 执行

决策入口：选择修复位置读 [根因](../principles/root-cause.md)，构造回归检查读 [行为测试](../principles/behavioral-tests.md)，重复失败读 [检验前提](../principles/challenge-premises.md)。

1. 确认预期与实际行为、触发输入、版本、环境和错误表征。在可达的原入口复现；暂时复现不了时缩小条件或检查现有运行记录，不宣布缺陷不存在。
2. 区分症状、机制和触发条件。沿输入到错误输出定位，使用能区分解释的观察；顽固问题读取 [实验与反证](../references/experiments.md)。只要诊断的请求转入 [调查与诊断](investigation.md)。
3. 建立能暴露缺陷的检查。存在便宜、稳定的自动化路径时先记录失败，再修复；只能在完整环境出现时记录可重放步骤和实际结果，不能制造一个不触及根因的测试来代替。
4. 实施证据支持的最小修复。优先纠正状态、生命周期、所有权或边界错误；症状缓解若只是临时措施，明确其作用与残余原因。
5. 在相同触发条件下复验，检查相关边界和邻近回归。确认检查使用新产物而非缓存或旧进程。
6. 移除本轮失去依据的补丁与临时埋点，保留有维护价值的回归检查。审阅差异，确保每项修改对应根因或必要集成。

同一前提下反复失败时，重新检验共同前提，不追加未经证明的保护层。无法访问原环境时，完成本地能够成立的修复与检查，并说明其证据限度。

## 验收与退出

- 原缺陷被复现并在修复后通过，或明确报告尚不能取得这项证据。
- 根因判断与证据一致，相关回归检查通过。
- 仅观察不到症状、测试偶尔通过或环境错误消失，都不足以直接宣布修复完成。
- 已授权创建 PR 或发布则继续对应流程。

## 交付

原问题、原因、修复、失败到通过的证据，以及受限的环境或仍需观察的条件。
