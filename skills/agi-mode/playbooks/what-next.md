# 项目状态与下一步（what-next）

回答三个问题：当前有哪些工作在推进，各自卡在哪里，现在最值得做什么。允许多 PRD、多计划、多轮评审和不同交付流程并存，不把整个项目压成一个线性阶段。`.xgent-ai/sdlc/` 只保存状态资料；原文档、报告、实施记录与证据始终按用户习惯和项目约定读取，不因初始化台账而创建副本、迁移或更改命名。

只问流程知识、产物区别或技能选择时使用 [SDLC 指引](sdlc.md)，无需先盘点项目。状态查询需要解释阶段条件、跨项目交接或测试/发布顺序时按需读该手册，复用本流程已核实的事实，不重复盘点；状态码仍以状态模型为准。

## 模式与边界

入口约定：`$agi-mode init-sdlc [PRD/计划/范围]` 明确授权初始化并保存状态；省略范围时盘点当前项目的可发现材料。`$agi-mode what-next` 默认只读，`what-next 更新` 保存核实后的变化；原有 `what-next 初始化` 等价于 `init-sdlc`。这些入口共用以下流程，不需要先运行另一条初始化命令。

- **查询（默认）**：只读盘点，聊天交付状态表和下一步。无跟进表也能工作，不能因缺表要求先初始化。用户指定计划或需求时聚焦该范围，同时读必要依赖。
- **初始化 / 更新跟进表**：用户要求建立、维护、刷新或保存状态时，核实来源，按仓内协议更新受影响对象的当前状态及必要索引。新台账日常不另建事件。首次读 [目录约定](../references/workspace-layout.md)，使用 [协议](../assets/sdlc/protocol.md)、[状态模型](../assets/sdlc/state-model.md)、[对象状态页](../assets/sdlc/object-status.md)、[分类索引](../assets/sdlc/type-index.md)、[导航](../assets/sdlc/index.md) 和 [通用目录索引](../assets/directory-index.md) 模板；符合独立留存条件时才读 [补充事件模板](../assets/sdlc/event.md)。已有等价台账沿用其结构和事实源，不另建竞争台账。
- **继续做**：本流程给出有证据的路由。用户同时明确授权继续某项工作时，完成状态核对后接续该任务；查询本身不授权开始实施、运行评审、提交、推送或部署。多个候选没有明确优先级时，推荐并说明理由，不擅自启动所有计划。

`init-sdlc` 可重复执行：已有台账按其协议补齐缺失结构、索引及本次核实的状态，不覆盖已有协议或重置历史；无实质变化不重写。沿用已登记的自定义台账，不因该入口另建默认目录或静默切换存储协议。新项目尚无可登记材料时，只创建 `.xgent-ai/index.md`、`sdlc/index.md` 及协议、状态模型，说明尚无工作项，不预建类型、事件树或事件模板。

不要求联网或外部项目管理工具，不把本机缓存、对话历史或远程跟踪分支当作全项目实时真相。用户已有的执行授权继续有效。

计划涉及 skill/AGENTS 进化时，沿原运行报告核对 [远端执行](../references/remote-evolution.md) 的实际完成范围：v2 主校准、基线诊断、逐项质量与辅助效度分别查证，再核对探索 keep、确认 passed、已授权 apply 与发布。TypeSafe usage 或辅助高分不能代替主分/独立确认；默认诊断不足停止搜索。显式获准的 bounded_exploration_v1 只在仅来源精度不足时最多一候选，其余质量门保持，不晋级/确认/采用，整体 inconclusive；不能把这一探索记为整期验收。用户明确要求精简仓库 AGENTS.md 时可路由到已安装的 `optimize-agents-md`，用 `use-prompt-dsl` 的 Odyssey RULE 精炼原则、去重补缺并保留项目事实与作用域；缺 DSL skill 时停止并建议完整安装，优化流程不写入目标文件。此流程不要求远端评测；状态查询与仅诊断仍保持只读，不以文件变短宣称行为收益。

## 1. 定位项目与记录

1. 读取当前仓与适用目录的规则。Git 项目用仓根定位，记录分支或 detached HEAD、HEAD、dirty 状态；非 Git 项目记录目录范围和可用版本标识。持久化路径使用仓根相对路径，不写机器绝对路径、用户名或带凭证的 remote URL。
2. 按 [目录约定](../references/workspace-layout.md) 定位台账：用户指定和仓库登记优先，已有 `docs/project-status/protocol.md` 可继续沿用；无旧台账的新默认是 `.xgent-ai/sdlc/`。多套台账没有明确切换记录时展示各自范围并核对，不武断选新目录为真。默认协议位于 `protocol.md`，导航和分类索引指向各对象当前状态页；有必要事件时才按类型和对象分目录。
3. 有台账时读协议、导航及分类索引，只展开活动或指定对象与依赖。有事件时，v4 按前序可达性核对已核对末端，旧协议核对其已纳入集合；未纳入事件说明存在待核对事实，旧事件不覆盖当前页后来直接回写的事实。历史正文按需读。发现状态时在存在的 `.xgent-ai/sdlc` 下显式用 `rg --files --hidden`；原文则沿用户指定、仓库约定、来源链接及仓内实际文档目录发现，不能只搜索状态目录。目录名只作候选；跳过依赖、构建产物和技能范例。核对各层 index.md 与实际目录及分片覆盖，查询时报告缺索引、漏项和断链，不自动修复。index.md 与 index-*.md 不当作事件。未展开的内容明确未核实，不能因只看首页就称全项目无待办。
4. 读取 PRD 范围/分期、每份相关计划的就绪状态、需求来源（PRD 与期次）和实施快照（含完成记录的提交 SHA）、报告基线/结论/处置节、决策记录的最新轮次，以及支撑下一步的验收记录。默认覆盖已发现的所有活动计划，归档项提供索引入口而不全文读取；没读到的范围明确标未核实。关联以原文需求 ID 和显式链接为准，不能因同名或相邻就关联。
5. 按 [状态模型的发现与自愈规则](../assets/sdlc/state-model.md#发现与自愈) 查漏：同名 `.review.md`、`.codereview.md`、`.code-review.md`、`.ui-review.md`（UI 验收评审，目标包为 `.ui-target.md`）、带轮次文件（如 `<计划名>.code-review.r2.md`，轮次最大者为最新一轮）及其他项目命名均作候选，打开报告确认目标/类型/范围后才补关联；在报告处置节、`.applied.md` 和实施记录查已处理证据，不要求固定处置文件。单文件损坏或来源未同步时保留问题并继续其他对象，不能把“未登记”或“未找到”直接解释为“未做”。

## 2. 校准当前状态

读取 [固定状态与证据校准](../assets/sdlc/state-model.md)，每个维度都给出一个固定状态码：按模型各节的判定顺序，取原文记录与可核验物支持的最强状态，再用 evidence_status 标依据质量与当前适用性；原文状态文字另存 source_state。只有完全没有可读依据时才写 unknown，不用 unknown 或候选代替判断。原文标为历史、废弃或已被取代的对象按模型的归档规则只列入口，不推就绪/实施状态，也不给下一步。

台账的状态模型低于技能自带版本时，查询按新版判定，并说明台账仍是旧口径；初始化或更新按模型「旧记录兼容」中的具体版本条件处理，项目改过的副本保留并列出差异。旧存储协议沿用仓内版本，用户明确要求精简或升级时才按协议切换为 v4，并保留项目原则、授权和审计要求。旧事件不改写，旧自由文本记录可在回答中映射。

- 分开列 **文档就绪、实施进度、评审结论、整改处置、验收/集成**。`Ready` 不是已完成，里程碑完成不是 PRD 全部交付，修复已验证不是重新通过独立评审。
- 对象状态页、事件与原文的状态行都可能滞后。计划定义范围与门槛，恢复快照、完成记录、登记的提交与实现/验证记录是实施依据；代码文件存在、复选框打勾、空 findings 或一次测试成功不能单独支撑完成。缺失、未核实、不适用、尚未做必须区分。
- 原文自述与记录不符时按记录取状态并注明原文滞后，例如计划仍写“未开始”但完成记录覆盖全部里程碑，判 dev-plan-completed。只有自述没有记录时状态照判，证据记 provisional 并给补证动作；记录之后相关文件又有改动时状态不降级，证据记 stale 并列出未覆盖的提交。真实回归或失败的验证照实修正状态，不为保持完成忽略失败，也不盲从状态行重新开发。
- 计划完成记录有「提交」列时，核对登记的 SHA 在当前分支可达，「待提交」表示成果仍在工作树。全部里程碑已完成但仍有「待提交」或缺 SHA，说明计划约定的最终提交未完成，不判 dev-plan-completed，列为缺口。
- `.review.md` 内容确认后说明做过文档评审，`.codereview.md` / `.code-review.md` 内容确认后说明做过代码评审，`.ui-review.md` 内容确认后说明做过 UI 验收评审，均不证明已 applied 或已通过。每轮分别判 review-recorded 与处置状态；完整且无需整改的评审用 review-not-required，不推荐无意义的 apply。报告结论首行的判定（文档评审「是否需要修改」、代码评审与 UI 验收的「验收判定」）是该轮原结论，记入来源与摘要，处置仍按证据核对；用户豁免通过的未修问题按延期处理，不算关闭。文档 ready 与实施 completed 分维度；独立验收线暂为 TBD，不自动推导验收通过。
- 每轮评审单独保留对象、范围、所审版本、报告及处置。报告之后代码/文档相关部分又有改动时，该轮状态保留，证据记 stale 并说明改动范围；只有需要对新改动下结论时才建议新一轮评审，不要求无关变更后重跑所有评审。
- 读取本地分支/工作树与可用提交历史，区分本分支状态、其他分支记录和未提交成果。本地找不到远端提交时写“本地不可核验”，不能判为没做；远程跟踪引用未经刷新不能证明已同步。不自动 fetch/pull/checkout/stash。
- 同对象同范围的矛盾记录按协议保留并列，不按日期、文件名或“完成优先”裁定。先核验能核验的来源；只对确实无法从仓内证据解决的决定提问，其余计划继续盘点。

## 3. 选择下一步

先服从用户当前目标和项目约定，再比较真实阻塞、已成立缺陷、依赖解除收益及可执行性。每条建议给出对象/路径、理由、前置条件、具体动作和完成判据；一般突出 1 个首选，另列可独立推进的工作。推荐专用技能时给可直接复制的命令（按当前客户端的技能调用写法），与该技能自身的收尾提示一致。不编造优先级、负责人或交期。

涉及 UI 循环时，先读取 `<前缀>.ui-review.json`、报告及安装回执以区分人工与 managed。managed 当前报告和未结束轮次从索引及匹配 engine 的只读状态返回定位，不按 mtime 或 Markdown 最大后缀覆盖它；`review status` 的退出 0 不等于 UI 通过。只读查询不执行 begin、import、安装、评审或修复。下表的 UI 修复建议先满足循环能力边界。

| 核实到的情况 | 可推荐的动作（遵循项目已定流程，不强制补全流水线） |
| --- | --- |
| PRD 尚有影响范围或验收的未决项 | 指出具体待决项；需要撰写/修订时用 `prd`，质量评审用 `review-prd` |
| 用户希望逐项确认已有 PRD/计划中的功能取舍 | `spec-human-decision <文档>`：每项讲清功能与价值，计划另述做法；固定确认/驳回/修改，修改须附说明并确认修订版，决定落实到文档；查询本身只推荐，不启动问答或改稿，逐项确认不等于技术评审或 Ready |
| 本项目是 CRD 接收方，需评估/答复、续接澄清或补回告实现结果 | 固定建议 `crd-respond <CRD>`；评估时基于最新工作树比较目标、原案与长期备选，在原文末答复，需改码时实际生成带来源 CR、承接范围和顶部完成回写约定的计划，未决契约按就绪门标 Blocked。已完成请求按证据追加实现结果及余项，不重开规划。仅原样追加/收录不重评或生成计划，仅评估/仅答复遵守边界，不发送或实施；查询本身不运行该技能 |
| 本项目是 CRD 提出方，需起草/修订、跟进或整合接收方返回稿 | 固定建议 `crd`，核对发出、返回与本地版本，整合实际答复、追加本方澄清/确认，维护需求与 Q&A；收到文件或答复反问不切换技能。角色不明先核实；对方已回复不等于已承诺或完成集成 |
| 文档评审有当前确认待处理意见 | 指定报告和原文交给 `apply-doc-review`；已 applied 或无需处理不重复执行，是否已处理不明时先补核查 |
| 需求已有边界但尚未有承接计划 | 以明确的需求集合、开发对象与排除交给 `dev-plan`，按 PRD 期次时用 `dev-plan <PRD> P<n>`；不默认一份 PRD 对应一份计划，依赖系统缺口保留提供方与前置，不自动转成本方开发 |
| 计划需要设计评审 | `review-dev-plan`，注明具体计划与版本 |
| 计划评审意见已 apply，状态仍为 `Blocked` | 以该计划交给 `resolve-blocked` 逐项解除：自行查证、交互补齐前置，收到答复后继续验证回写，外部缺口用 `crd` 创建/续写本地请求，不以找负责人代替行动；查询本身不运行或写入。查询回复也集中列全剩余阻塞、各方需提供什么、用户具体动作、解除条件与恢复入口，不能只说仍 Blocked 或让用户翻前文。已有 CRD 时按具体缺口建议交接、用 `crd` 修订/整合答复或补本方验证；条件满足后再运行 `resolve-blocked` 重判就绪，条件未变且无可执行动作时不空跑 apply、评审或解阻 |
| 验收条件已有口径但缺用例或执行证据 | 用例设计用 `test-plan`；已有用例则核对实际执行与覆盖缺口，不把用例草稿当通过，也不重复设计已覆盖项 |
| 计划可实施且前置已满足 | 直接读计划实施协议继续对应里程碑，用 goal 推进时为 `/goal 按 <计划> 开发`；不加载 `dev-plan` 重写计划 |
| 代码评审有当前仍成立的缺陷 | `apply-code-review <报告>`，计划可从报告头定位；修复后回到 `review-code <计划>` 复审。缺输入时先定位，不虚构关联 |
| 计划实施完成待验收、修复已完成或待审代码范围明确 | 有计划时推荐 `review-code <计划>`：按完成记录登记的提交与未提交改动定范围，已有本计划报告时按轮次复审；无计划时明确 base/target 或工作树范围与对应历史报告 |
| 来源 CR 的对应请求已有实现与约定检查证据，CR 仍只记未实现 | 核对来源 CR、承接范围与既有回告，建议按计划顶部合同或用 `crd-respond <CRD>` 补实现结果、计划/验证链接和剩余配合；一个计划完成不推导整份 CR、发布或对方验收完成，查询本身不写入，也不退回 dev-plan 重新规划 |
| 代码评审已通过验收，变更涉及界面，且没有覆盖当前版本的 UI 验收 | 可选推荐 `review-ui <计划>`，它不是必经步骤；用户跳过时按闭环推荐差异核查 |
| 已有 managed UI 索引，但 engine 缺失、不匹配、schema 未知或状态损坏 | 只读历史，可收集未登记素材；先说明如何恢复回执固定版本及匹配协议，恢复后续接原轮/revision。当前不推荐修产品、改目标/处置/计数/生成区，或换前缀、降人工重置历史 |
| 人工 Markdown UI 历史没有 managed 索引，CLI 不可用 | 可继续原人工合同，不要求补装才能读取或续接；接管须用户明确要求并显式 import，未知尝试/重构次数保持未知 |
| 匹配 managed 能力，索引当前轮仍草稿、缺证或等待确认评审 | 指向原轮次与缺项，建议用 `review-ui <原对象>` 续接补采/确认；不新开一轮绕过，不把旧轮通过或 CLI 退出 0 当本轮完成 |
| 最新一轮 UI 验收判定需要修改（含停滞预警或待裁定标记） | `apply-ui-review <报告>`，计划与目标包从报告头定位；修复后回到 `review-ui <计划>` 复审。带待裁定标记时，同时列出这些事项请用户决定 |
| 最新一轮 UI 验收判定需用户裁定 | 列出报告中停滞或待裁定的事项和可选项，等用户决定；用户给出方向前，不推荐继续 apply 或重跑评审 |
| UI 验收已通过，但其 UI 修复带来的代码改动尚未经代码评审 | `review-code <计划>` 复审这些改动，再按闭环推荐差异核查 |
| 实现已交付但验收缺证、未集成或未发布 | 给出具体补证/集成动作；不把评审通过当部署授权 |
| 计划完成而 PRD 覆盖还未核对 | 计划来自 PRD 时可推荐 `review-prd-dev-gaps <计划>`（从需求来源定位 PRD 与期次），按闭环通常在最新代码评审通过验收或用户豁免之后；需要时带上所有相关计划，不重复创建已有 gaps plan |
| 原计划状态滞后但实际交付已核实 | 显示规范状态与证据；写入模式修复 SDLC 跟进，原计划进度回写列为待同步项，在已有授权内处理，不重开已完成开发 |

推荐的技能不存在时给出等价动作与输入，不要求安装才能解释状态。不把所有“未评审”自动变成阻塞，也不把待用户决策的工作推荐为可直接开工。

开发验收默认由 Agent 执行；用户角色可按知识、资料与权限约束模拟，不因缺少真人测试者制造开发阻塞。确需真人的指标按原文来源与阶段列为公测/上线后验证；用户明确规定的开发真人门仍列实际前置，未验证项不算通过。缺设备、权限或真实集成证据时指出具体缺口，角色模拟不解除这些前置。

## 4. 保存（仅写入模式）

1. 首次建立默认台账时，将协议复制到 `.xgent-ai/sdlc/protocol.md`、状态模型复制到 `.xgent-ai/sdlc/state-model.md`，按导航/分类索引/对象状态模板创建实际需要的文件；每个实际创建的目录同步建立 index.md。没有必要事件不复制事件模板或创建事件目录。不建巨型 `STATUS.md`，不预建空对象。已有文件先核对；用户已要求精简/升级时按协议与模型的兼容规则切换，否则沿用。协议和模型随仓保存，使仅安装其他技能的机器也能回写。自定义位置沿用仓库已有登记方式；没有登记时在适用 `AGENTS.md` 中仅补一条台账路径，用户禁止改规则文件时说明自动发现限制。
2. 只登记本次核实的事实；旧材料导入记录的观察时间是现在，原活动时间能证实才写。不伪造中间阶段或历史轮次，关系不明的单列待关联。
3. 按仓内协议保存。v4 日常只更新对象页中本次触及的 `facet + scope` 分段，各段保留自己的核查时间、来源版本、基线和适用范围；页头只留共同身份。来源版本或证据变化也不自动新增事件。只有明确审计要求或无法由原产物及其可取回版本保留的并发/纠错事实才独立留存。补登记评审及处置沿用可确认对象 ID，新一轮评审仍独立建对象；同轮两个维度在同页分段。已有表格页沿原布局读取，布局转换须在已授权修订范围内；只修索引不造事件，不因“自愈”擅自改原文。
   **先复用来源再判断留存**：计划进度直接链接恢复快照/完成记录，实现、验收与阻塞链接已有里程碑记录，评审和整改链接原报告/处置章节及版本。里程碑推进、验证更新、最终提交、整份计划完成和状态校准均不单独产生事件。确需事件时先指出审计要求出处或无法由原记录及当前页保留的具体事实，其余内容只引用，不先造 event 再作为来源；旧协议强制事件时仍按其要求最小留存，不静默升级。
4. 写前重读受影响状态页，合并本次触及维度，保留唯一待决、授权依据、未解冲突与必要来源；不刷新未触及分段，不在页头、索引或其他维度重写摘要。计划不另抄完整里程碑明细，已解决过程和旧建议不留在当前正文。有事件只记已核对末端和历史入口，不抄全量 ID 或手工维护事件总数。索引只保存身份与入口，仅成员、去向或活动/归档标记改变时维护；工作项快捷链接仅随对象选择或入口变化维护。事实、来源适用性、可见范围和建议均无变化时不改文件或保存时间，仅回复已核对。回读来源、受影响页/索引及必要事件，检查范围、链接、冲突和遗漏；结构正确不代表验收通过。
5. 写入失败分别说明哪些记录/状态未完成；已保存事件保留，下次可恢复，不能仅从事件覆盖后来直接更新的事实。默认不提交、推送或改远端，明确未提交记录尚未随 Git 共享。

## 交付

聊天答复先用一句话说明总体情况和可见性边界，再给紧凑表格：`工作项（名称 / 原文文件） | 文档状态 | 实施进度 | 各轮评审/处置 | 证据 | 下一步`，遵循以下要求。写入台账时，索引只保留身份、原文和状态页入口；下列状态、证据及下一步保存到对象页对应分段，不将聊天汇总表复制进索引。

- **每项可定位**：工作项写业务主题或原文标题、文档类型及原文的仓根相对路径，路径文字直接可见并尽量可点击，如“登录一期（开发计划）· [goal/LOGIN-P1.md](goal/LOGIN-P1.md)”。不能只写“PRD”“开发计划”“来源 CR”，也不能只链接 UUID 状态页；状态页可作补充入口。同名文件用目录和期次区分。材料没有本地文件时写实际来源链接与范围，不编造文件名。
- **状态可理解**：用中文说明当前状态、进度和影响下一步的具体原因，同时保留固定状态码、轮次及证据码用于核对，如“实施受阻，3/7 完成：来源尚未提供完整对账接口（dev-plan-implementation-blocked）”。证据写“已核实（confirmed）”“待补证（provisional）”“已过期（stale）”“有冲突（conflict）”或“无可读依据（unknown）”，非 confirmed 时简述原因；不要只堆状态码或把部分交付写成整体完成。详细依据留在来源链接与台账。
- **下一步可执行**：说明对哪个文件/事项做什么、当前缺什么以及怎样算完成，再给带实际输入路径的可复制命令。引用期次、里程碑或问题 ID 时同时说明事项含义，如“M4（接入外部待办来源）”，不要只写“接续 Q&A”“补齐契约”“取得解锁证据”。等待外部材料时列出所需交付，将下游动作明确写为条件满足后执行；材料未说明的含义或解除条件标为待核实。

例如：

```text
| 登录一期（开发计划）· [goal/LOGIN-P1.md](goal/LOGIN-P1.md) | 已就绪（dev-plan-ready） | 已完成 4/4（dev-plan-completed） | 代码评审 R2 无需整改（review-not-required） | 已核实（confirmed） | $review-prd-dev-gaps goal/LOGIN-P1.md：核对登录一期需求覆盖，记录遗漏与差异 |
| 计费（开发计划）· [goal/BILLING.md](goal/BILLING.md) | 设计受阻：退款范围待定（dev-plan-blocked） | 尚未开始（dev-plan-not-started） | 计划评审 R1 意见已处理（review-applied） | 已过期（stale）：评审后 §5 退款范围有改动 | $resolve-blocked goal/BILLING.md：确认退款范围并回写 §5，重判就绪后才能开发 |
```

PRD 没有计划、代码评审没有计划关联也单列，不静默遗漏。原文状态滞后时明确说明；验收事实另列，不冒充已定义统一验收流程。

对象很多时按类型/范围分组并链接分类索引，首选动作突出但不静默遗漏其他活动项。各状态附源路径或事件链接，历史结论与当前判断分开。随后给首选动作和可并行候选，明确缺证/待决。写入模式附台账链接及同步情况；查询模式不声称已刷新文件。无活动工作或证据不足时如实说明，不强造下一项开发任务。

```text
使用 $agi-mode what-next 看看当前项目做到哪里、下一步做什么。
使用 $agi-mode init-sdlc，纳入仓内现有 PRD、计划和评审的状态。
使用 $agi-mode what-next 更新跟进表，重点核对 goal/LOGIN.md 与 design/billing-plan.md（使用项目实际路径）。
使用 $agi-mode what-next 我换了机器，核对本地可见进度和未同步的证据。
```
