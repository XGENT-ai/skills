# SDLC：从需求到运行维护的指引

用于解释软件开发生命周期（SDLC）、判断当前应做什么、选择技能，以及梳理阶段间交接。用户不必知道阶段名称；从其目标和手头材料切入。只问概念时直接解释，不先扫描仓库。询问实际项目状态时由 [what-next](what-next.md) 核实事实，本手册提供流程判断；不重复运行两套盘点。

本手册随 agi-mode 独立分发。下文的专用 skill 是按需使用的能力，不是全部安装的前置条件；运行前定位并读取实际可用版本，缺少时仍给出所需输入、动作和完成判据，不虚构调用。仓库专属工具、状态与审批要求以当前项目规则、工具合同及用户已有授权为准。

## 1. 先判断用户需要哪种帮助

| 请求 | 本次做什么 | 交付边界 |
| --- | --- | --- |
| “SDLC 是什么”“PRD 和计划有什么区别”“该用哪个 skill” | 解释与问题有关的阶段、产物、前后依赖，用一个具体例子说明 | 聊天答复，不创建文档、台账或任务 |
| “我们做到哪里”“现在该做什么”“可以上线了吗” | 按 what-next 读取相关范围与证据，再用本手册给建议 | 默认只读；缺材料说明判断条件，不猜项目阶段 |
| “帮我写 PRD / CRD / 计划”“按报告修复” | 进入对应专用技能或可用的等价工作流程 | 完成已请求产物，不停在推荐技能 |
| “按这份计划继续”“从想法推进到可验收交付” | 继承已有契约、进度与授权，进入 [自主任务总控](autonomous-run.md) 或当前实施流程 | 推进已授权范围，不因咨询插入而重新请求开工 |
| “初始化 / 更新 SDLC 状态” | 进入 what-next 的初始化 / 更新模式 | 保存状态，不据此启动实施或发布 |

先利用会话和项目已有资料明确目标、范围、当前产物、阻塞及授权。只有无法查明且会改变建议的输入才询问。依据不足时说“先核对 X，满足 Y 后做 Z”，不把一张流程图当作真实进度。

## 2. 生命周期地图：每一步解决什么问题

典型路径是「问题与价值 → 需求与验收条件 → 设计与交付安排 → 实施与验证 → 集成、验收与发布 → 运行反馈」。这是依赖地图，不是必须逐格盖章的瀑布流程。不同需求、计划和版本可以处于不同阶段；发现问题时返回真正需要改变的环节。

| 工作 | 要回答的问题与交接产物 | 何时具备下一步条件 | 对应能力 |
| --- | --- | --- | --- |
| 问题发现与范围 | 谁遇到什么问题、价值是什么、约束和非目标是什么；交接场景与待决项 | 关键目标与取舍可理解，未知风险有核实路径 | 本手册；需调查时用 [调查与诊断](investigation.md) |
| 产品需求 | 做什么、为什么、怎样算满足；PRD、功能/非功能需求、用户验收场景及分期 | 相关范围和验收可判断，关键产品决策有依据 | 撰写/修订用 `prd`；质量评审用 `review-prd` |
| 跨项目协作 | 谁需要另一方提供什么、双方怎样配合；完整 CRD、Q&A、逐轮答复 | 被当前工作依赖的契约与责任已明确，未承诺部分有追踪 | `crd`；详见第 4 节 |
| 方案与开发计划 | 怎么实现、依赖什么、如何验证与恢复；设计、需求映射、里程碑、实施入口 | 当前单元的关键设计与前置成立，项目要求的评审/处置已满足 | 写作或修订用 `dev-plan`，设计评审用 `review-dev-plan` |
| 文档评审处置 | 意见是否成立、怎样改才消除问题；修订原文与逐项处置依据 | 当前相关阻塞解除，其他待决项保留 | `apply-doc-review`；只审不改与落实修订分开 |
| 计划阻塞解除 | 处置后计划仍 `Blocked`：每个阻塞缺什么证据或决定、推荐怎么解；决策记录与回改后的计划 | 已解除项落进计划并重判就绪，剩余阻塞有解除条件与负责人 | `resolve-blocked`；能查证的先查证，需拍板的交互确认 |
| 测试设计 | 用什么数据、动作和观察验证验收条件；条件到用例的映射 | 当前范围可测，缺少判据的条目已明确回传 | `test-plan`；用例草稿不是执行结果 |
| 实施 | 本次单元实际改变了什么；代码、配置、迁移及实现/验证记录 | 该单元必要行为与回归检查有适用证据，依赖方能使用 | 直接读已有计划的实施入口；按需用 [功能交付](feature.md)、[缺陷修复](bug-fix.md) 或 [重构与迁移](migration-refactoring.md) |
| 代码评审与修复 | 改动是否引入具体缺陷或违反约定；报告、修复及复核记录 | 当前范围的必要问题已处理，检查覆盖本次版本 | `review-code`；有计划和评审报告时用 `apply-code-review` |
| 覆盖核查与验收 | 产品承诺实际上兑现多少、偏差是否合理；覆盖账本、差异、真实验收证据 | 约定范围满足或变更有明确依据，未决与未测不冒充通过 | 已完成开发与 PRD 对照用 `review-prd-dev-gaps`；验收执行按项目约定 |
| 集成与发布 | 哪个版本进入哪个环境、怎样确认及恢复；候选产物、发布和后置验证证据 | 集成、验收与项目发布门槛成立，目标动作已授权 | [PR 生命周期](pr-lifecycle.md)、[合并与发布](shipping.md) |
| 运行、反馈与退出 | 上线后是否达到目标、出现了什么问题、何时退出旧能力；运行证据、缺陷或新需求、迁移/退役安排 | 故障有处置与验证，反馈有去向；退役前依赖与数据处置已明确 | [调查与诊断](investigation.md)、[运行时取证](forensics.md)、缺陷修复或重构与迁移 |

### 几个容易混淆的交接

- **PRD / 开发计划 / 测试计划**：分别定义产品行为与验收条件、实现安排与技术验证、可执行测试方法。测试设计不能替产品决定未定义行为；实现方案也不能悄悄缩减验收。
- **评审 / 处置 / 复审**：评审发现问题，处置核实并修正，复审是一次有明确范围的新检查。无待处理意见无需空跑 apply；局部处置不代表整轮通过，作者复核不冒充独立复审。
- **就绪 / 实施完成 / 验收完成 / 发布完成**：分别需要开工条件、实施范围证据、目标行为证据、指定环境实际生效的证据。`Ready`、CI 绿灯或文件存在都不能替代后面的事实。
- **一期 / 整条需求 / 整份 PRD**：跨期需求保留完整目标、每期承接和终验范围；一期里程碑全完成不能自动关闭整条需求。一份 PRD 与多份计划可多对多，通过需求及验收项关联。

## 3. 按风险和真实依赖选择路线

- **新能力或重大变更**：先明确行为与验收，核实重要假设和外部依赖，再安排可独立验证的交付单元。安全、权限、数据、兼容、运维和恢复要求随相关需求进入设计与验证，不等上线前统一补课。
- **已有可执行计划**：先读实施须知、实施者定位、进度及本次所需记录，核对当前工作树和前置成果；继续目标里程碑，不调用 `dev-plan` 重写计划。确有影响范围或验收的变更时只打开相关设计决策。
- **小缺陷或低风险局部修改**：使用最短有效闭环，明确预期、必要时复现、修正、运行适当检查。不为补齐地图创建 PRD、完整计划或评审报告；仓库明定门槛仍须满足。
- **测试与开发并行**：验收口径稳定后可设计相应测试，相关实现及环境具备后才能执行。项目若有评审前置则遵循；无需一概等所有开发结束，也不让早期骨架验收尚未提供的端到端能力。
- **外部依赖未就绪**：定位被阻塞的具体契约、任务或验证，推进独立工作。模拟依赖能证明本地行为，不能证明真实联调已通过；不把一处阻塞扩成所有工作停摆。
- **开发完成后发现差异**：先区分明确遗漏、有依据的合理变更和需用户裁定的差异。已有 gaps plan 承接的事项不重复规划；仅报告时不生成计划；新 follow-up 只含已确定范围，创建计划不等于开始执行。
- **需求或契约变更**：沿「需求/CRD → 计划 → 用例 → 实现 → 验收/发布证据」核对受影响部分，保留变更来源与历史版本。旧证据仅在适用条件未改变时复用，不全盘作废，也不一概沿用。
- **线上故障**：先确认影响和当前运行事实，在授权内采取必要止损，保留证据并修复根因。紧急变更仍需相关验证、恢复路径和交付记录，不补造事前审批或把临时恢复写成根治。
- **退役或替换能力**：核对消费者、兼容承诺、迁移和数据保留/处置要求、退出条件及恢复安排；咨询只给步骤，实际删除或外部动作按授权和项目规则执行。

这些路线可迭代组合，不要求每个项目采用同一角色分配或固定数量的评审。阶段切换只核对实际前置；已授权且条件满足的工作继续推进。

## 4. 跨项目 CRD 如何接入 SDLC

CRD 承载一方向另一方提出的协作请求，QA 在这里是双方 **Q&A 澄清**。通常整份文档往返：发出 CRD → 对方在文末答复 → 返回完整 CRD → 提出方核对并续接。

1. 在需求、设计、实施或运行反馈中发现外部协作依赖时，明确提出方、接收方、可观察交付、配合事项与验收条件。CRD 可关联双方项目的 PRD/计划，不代替各自的内部工作安排。
2. 对方返回后核对发出基线、返回版本与本地当前稿，合并新增答复和本地补充，保留历史；直接修改的正文或冲突列为待确认，不按文件时间覆盖。不要求用户把文档内已有回复另行摘抄。
3. 回答问题、接受需求、承诺时间和实际交付分别判断。已确认的契约同步到受影响需求、计划与验收；提案不当作对方承诺。接收方完成仍需消费方适配及真实集成验证。
4. 优先处理真正阻塞当前单元的未答事项，其余问题保留跟进；记录下一步待哪一方提供什么。跨项目 ID 必须带项目/文档语境，不把对方的 R-01 误认为本项目的 R-01。

具体起草、答复或版本整合时使用可用的 `crd`。缺少该技能仍可按上述规则指导，不能声称已经发出文档或修改对方项目。

## 5. 给出能执行的下一步

建议由当前缺口决定，不背诵完整流水线。先说明“已核实什么、还缺什么、为什么现在做这一步”，再给 **对象/输入 → 动作或技能 → 预期产物 → 完成判据**；有实际路径时提供路径。通常突出一个首选，另列确实独立的工作。

例如：计划设计已就绪，但验收记录只覆盖主路径，当前没有发布授权。先建议补齐该版本的必要边界与集成验证；说明使用哪些记录、缺哪条判据。不能仅凭计划上的完成勾选推荐直接上线，也不必重写整个计划。

若已核实的材料没有待办，如实说明；如果用户只是了解后续流程，给条件化路线，不制造新目标。需要决策时说明选项与影响，只暂停其下游；事实可以自行核实的不甩给用户。

## 6. 状态、证据与工具边界

实际项目状态、并行计划与跨机恢复交给 [what-next](what-next.md)；持久化遵循 [目录约定](../references/workspace-layout.md)。`.xgent-ai/sdlc/` 只放状态与来源链接，原 PRD、CRD、计划、报告和验证记录继续留在项目约定位置。没有台账不妨碍咨询；只有初始化/更新或已有任务授权覆盖回写时才保存。

使用固定状态码时读取 [状态模型](../assets/sdlc/state-model.md)，已有项目遵循其登记版本。本手册的生命周期名称不是新增枚举。模型中的独立验收线仍为 TBD，不据此发明默认 `passed`、`accepted` 或 `released` 状态；事实、来源与尚未定义映射分开报告。

专用 skill、SPMS、CI、仓库或发布平台的可用能力在目标环境核实，不能从本手册或历史流程图推定已经安装、可写或具备某个接口。只装 agi-mode 时仍可完成流程指导；需要专用技能才说明具体缺口，不阻断不依赖它的工作。

使用 SPMS 时，`prd` 与 `test-plan` 的现有职责分别是需求与用例草稿；评审结论、执行测试和写入平台状态是不同动作。实际调用读取当时的技能及工具合同，遵循查重、真实 ID 和权限约束；没有平台工具时交付文档与未同步说明，不虚构实体或把平台终态要求泛化为所有项目的规则。

## 交付自检

- 建议能追到当前材料、明确条件或项目规则，未把历史快照当成现时能力。
- 产物职责、阶段条件和下一步清楚；已有成果不重做，未验证的结果不算完成。
- 咨询保持只读，执行遵循已有授权；缺工具、缺证和待决分别说明。
- 每次只加载当前需要的流程；最终回复用用户能理解的语言，不要求用户先学会全部缩写。

```text
使用 $agi-mode sdlc，讲讲 PRD、CRD、开发计划和测试计划怎样配合。
使用 $agi-mode，我们已有 PRD 和一份 Ready 计划，现在该做什么？先给建议。
使用 $agi-mode，对方返回了带回复的 CRD，这会影响开发和测试的哪些环节？
使用 $agi-mode，代码评审通过了，离上线还要核实什么？
```
