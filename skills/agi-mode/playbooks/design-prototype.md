# 设计与原型

用于技术或产品设计、可实施计划，以及需要观察才能决定的方案分叉。先确定交付的是设计、原型，还是设计后继续实现。

## 执行

决策入口：产品取舍读 [使用者结果](../principles/experience-first.md)，昂贵分叉读 [方案比较](../principles/explore-alternatives.md)，旧结构难以容纳需求时读 [重新设计](../principles/redesign-from-constraints.md)。

1. 从用户场景、现有接口与实际约束形成结果契约。检查已有方案和相关实现，记录会改变架构的未知，避免重开已决定的问题。
2. 写出调用方或用户怎样使用结果，再确定数据形状、状态归属、边界与失败行为。小改动在现有结构上设计即可。
3. 对代价大的分叉，比较真正不同的方向，如复用现有机制、局部重组、移除问题来源。用兼容性、迁移成本、运行约束和用户效果筛选，不固定要求候选数量。
4. 找出最可能推翻首选方案的假设。已有证据能决定时直接选择；需要实验时读取 [实验与反证](../references/experiments.md)，在独立临时位置实现只验证该假设的原型。
5. 使用相同场景比较候选。视觉设计查看实际呈现和交互，系统设计观察边界、负载或故障条件。原型的简化与生产缺口应明确记录。
6. 将选择收敛成可实施的设计：目标结构、关键接口、约束、依赖顺序、每阶段产物与验证方法。需要分期时明确中间状态如何可用、如何恢复、什么时候移除过渡层。

产品偏好无法由实验裁定时，给出具体候选与影响，等待必要决定，同时推进独立部分。用户选择仍在可行边界内时，不以技术偏好替换它。

## 跨阶段或多 PR 的实施计划

计划应当能由不了解本次对话的执行者接手。每个单元包含以下信息，简单单元可压成一段：

| 字段 | 可执行的内容 |
| --- | --- |
| 目标与依赖 | 一个可验收结果、必须先完成的单元与输入版本 |
| 修改边界 | 实际核对过的路径、接口与不可改区域 |
| 实施 | 具体变化、重要约束及中间状态 |
| 验证 | 场景、命令或操作、通过条件、证据存放位置 |
| 交付 | 停在本地、PR、可合并、已合并或部署中的哪一层 |
| 恢复 | 失败后如何恢复、不可逆部分、继续的入口 |

按需要覆盖单元、真实入口、性能与用户体验验证，不要求每个文案修改都运行全部类别。相关命令需从仓库核实；未能试跑的命令明确标记。用依赖图检查遗漏与环路，用目标逐项回查是否有单元承接。只有请求包含实施时才接续 [自主任务总控](autonomous-run.md) 或 [项目与队列编排](program.md)。

## 验收与退出

- 另一位实施者能知道做什么、按什么顺序、如何判断完成，无关键决定藏在“后续再看”中。
- 原型结论有真实观察，未验证的规模、可靠性或体验条件仍标为未知。
- 只要设计或原型时交付即止。已授权实现则转入 [功能交付](feature.md)、[界面交付](ui-delivery.md) 或 [重构与迁移](migration-refactoring.md)，不重复申请实施许可。

## 交付

推荐方案、关键取舍、原型或计划位置、验收路径和剩余决定。若有原型，明确其可复用部分及尚未满足的生产要求。
