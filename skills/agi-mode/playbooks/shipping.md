# 合并与发布

用于用户已请求的合并、部署或发布。只执行请求涉及的部分；合并、部署和对外发布是不同动作。

## 执行

决策入口：超时或重试读 [幂等效果](../principles/idempotent-effects.md)，候选版本变化读 [证据时效](../principles/evidence-lifetime.md)，宣称交付前读 [真实结果](../principles/prove-real-outcomes.md)。

1. 确认目标仓库、分支或环境，待交付版本，以及现有授权覆盖的动作。缺授权时先完成可独立进行的准备和验证，再提出针对具体动作的决定。
2. 核对实际候选产物与其验证证据。合并检查 head、base、必要状态和审查阻塞；部署检查产物标识、配置、目标环境与必要迁移。CI 绿灯不是完整交付证明。
3. 版本或环境在验证后变化时，重查受影响部分。不要把不同提交、镜像或配置的证明混用；无关且仍适用的检查无需全部重跑。
4. 在动作前明确后置验证和恢复方式。代码回退、数据恢复和外部通知不能混为一谈，恢复能力按实际检查结果描述。
5. 按依赖顺序执行已经授权的动作。堆叠变更从基础开始，每一步读回实际结果，再检查下一步是否仍符合预期。不要越过失败步骤继续发布依赖它的内容。
6. 请求超时或结果未知时，用操作标识与目标状态核对，按 [持续执行与恢复](../references/continuity.md) 处理。不可确认时保留未知状态，不盲目重复写入。
7. 完成后读取合并记录、已发布版本或运行环境，执行目标相关的健康与关键路径检查。发现失败时执行已授权的恢复；缺少恢复授权或结果未知时报告事实和下一步决定。

没有得到平台的允许不能自行绕过保护。用户授权的发布目标也不能被替换成“合并后应该会自动部署”的推测。

## 队列与验证时效

堆叠 PR 使用 [项目与队列编排](program.md) 的单一拓扑所有者与连续通过规则。每次只准备当前最低未合并项，成功后读取平台实际关系，再准备下一项。自动合并已启用仅证明请求被登记，不证明合并已发生。

多轮修订使用 [证据契约](../references/evidence-contract.md) 记录验证依赖。相同补丁在不同基线上可能表现不同；patch-id 相同不能替代集成检查。可确定未受影响的证据才复用，当前平台检查、目标分支状态和部署环境仍需及时读取。

独立验证是项目要求时必须取得对应证据。环境无法提供时标为缺口，不用作者自验替换既定要求，也不只为文档改动制造固定数量的审查者。

## 验收与退出

- 指定版本到达指定目标，实际状态与后置验证有证据。
- 只能确认合并时就报告合并完成，不称部署完成；发布发生但健康检查失败时分别报告两种状态。
- 剩余外部条件、失败恢复或未知结果留下具体操作标识和恢复入口。

## 交付

交付版本、目标、实际动作和结果、后置验证、恢复状态及必要链接。
