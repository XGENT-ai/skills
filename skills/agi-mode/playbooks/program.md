# 项目与队列编排

用于多个有独立生命周期的单元，而非给普通多步骤任务增加管理层。单人当前会话可完成的任务保留 [自主任务总控](autonomous-run.md)。

## 选择交付拓扑

决策入口：划分执行者读 [状态归属](../principles/state-ownership.md)，限制在途工作读 [关键路径](../principles/critical-path-throughput.md)，拆分与集成读 [可验证单元](../principles/verifiable-units.md)。

| 模式 | 依赖关系 | 交付边界 |
| --- | --- | --- |
| 独立队列 | 每项从目标基线开始，互不依赖 | 各自验证；只有已授权项才合并 |
| 线性堆叠 | 子项依赖父项，PR base 指向父分支 | 交付逐层可审查的链；用户保留落地主导权时不启用自动合并 |
| 长期项目 | 多条工作流与持续到来的完成事件 | 按依赖推进、持续集成并对总目标负责 |

同一项目可以有多个独立栈，不把独立工作强塞进一条链。明确哪些单元由用户保留决定，以及谁有权改变分支关系。

## 建立最小任务账目

复用已有项目记录，至少使每个单元能查到：目标、依赖、所有者、可写范围、工作位置、当前输入版本、产物、验证证据和下一动作。少量单元用一张表即可；规模需要时才分开任务、证据和事件记录。

采用有意义的状态转换：待执行 → 执行中 → 待验证 → 已验证 → 已交付。失败、阻塞和取消单独记录。新的相关输入或实现变化使“已验证”回到待验证；外部交付要读回成功才能记为已交付。

多轮交付使用 [证据契约](../references/evidence-contract.md) 检查过期和缺失记录。账目不代替真实产物。

## 执行与协调

1. **跑通样本。** 先让一个代表性单元经过实施、验证和本任务要求的交付边界，检查任务切分、环境与验收是否可用，再扩展同类工作。
2. **限定在途数。** 按实际执行和审阅能力保留有限在途工作，完成一个补一个。集成积压时优先消化已完成结果，避免最后只剩大量未验收分支。
3. **传递完整上下文。** 每项任务携带结果契约、读取位置、写入范围、输入版本、验收和返回格式。下游需要上游产物与结论，不能只知道“上游完成”。
4. **独立写入。** 允许多 agent 时，每个可写工作区只有一个所有者，栈拓扑也只有一个修改者。不能委派则用同样的单元边界串行执行。
5. **接收事件。** 完成通知先对应到账目和产物；结束当前关键操作后批量核对，不因通知打断正在进行的合并或状态更新。待审结果不能直接推进已交付数量。
6. **持续集成。** 验证过的单元按依赖进入集成，不等全队列完成才发现接口冲突。单项测试通过后还要检验组合行为。
7. **审查与落地。** 依据风险安排实际行为、回归和差异审查；环境允许的独立审查与作者自验分开记。执行 [合并与发布](shipping.md) 时按当前版本重新检查。

## 堆叠的具体约束

- 记录顺序、head、base 及最近一次拓扑变化。只有根 PR 面向目标主分支，子 PR 面向实际父分支。
- 构建可以并行，改 base、重排、变基和合并由拓扑所有者串行处理，并沿用用户授权。
- 只处理从根开始连续通过验收的部分；上层通过不能跨越下层缺口。
- 每次合并后读取新基线和平台实际父子关系，重算剩余队列。不要假定平台自动改对 base。
- patch-id 相同最多表明补丁文本等价，不能证明基线、依赖和环境未改变；重新检查受影响的验证与当前 CI。

## 失联、迟到与重启

通过可观察的进程、任务状态和产物判断存活，不能仅凭聊天安静或文件时间戳宣布死亡。慢任务先核对其预期阶段与资源，再缩小范围、恢复或替换。

替换任务前记录原所有者与当前产物，避免两个执行者同时写同一目标。迟到结果先对照当前输入版本和已集成内容，仅提取仍有效的独立贡献，不能直接合入旧分支。

重启后先恢复账目并核对外部状态，确认哪些任务仍存在再重派。用户暂停要传递到全部活动单元，并记录未能停止的外部动作。

## 验收与退出

每个开始的单元都有终态或明确接管者。最终数量来自账目与产物核对，不能从聊天印象统计。完成要求包括组合验收及指定交付边界；预算到达时优先验证和保存已有成果，列出未完成单元。

## 交付

目标完成数、单元及 PR 链接、当前依赖与版本、证据、失败或放弃原因、用户待决项和恢复位置。
