# 运行时与离线取证

用于 CPU 自旋、内存泄漏、交互卡顿、线程等待及给定 profile / trace / heap snapshot 的分析。交付诊断；已授权修复时再切入对应实施流程。

## 选择入口

决策入口：选择采集与查询读 [信息价值](../principles/information-first.md)，信号无法区分解释时读 [验证器反证](../principles/falsifiable-verification.md)。

- **已有捕获文件**：记录文件身份、格式、采样窗口、负载与版本。原件保持不变，派生数据写入独立位置；不先要求用户重录。
- **活进程**：确认目标进程与现象，用当前可用的采样、追踪或堆工具捕获信号。控制采集开销并记录采集对系统的影响。

## 从信号走到机制

1. 确认时间、大小、调用数的单位与统计含义。区分 wall time、CPU time、self time 与包含子调用的时间；不要重复累加嵌套耗时。
2. 用现有解析器形成可查询表示。文件太大或工具不足时按 [突破阻塞](unblock.md) 的能力构建路径制作最小解析器，不把完整数据倒入上下文。
3. CPU 问题沿热点栈及调用次数找重复工作；泄漏沿保留链追到根与所有者；线程问题核对等待对象和持有者；交互问题把输入、主线程任务和呈现时间关联起来。
4. 通过捕获自带的符号、source map 或对应构建映射回文件和函数。缺少符号就说明定位精度，不能猜出一个源码行号。
5. 有配对捕获时在相同负载和口径下比较。只有单份捕获时，给出数据最支持的解释及能证伪它的下一次观测，不能把相关性提升成已证实根因。
6. 需要干预才能确认机制时，在已授权的受控环境做最小实验；只读或生产诊断不自动允许注入、热补丁与重启。记录干预前后的可区分变化。

观察链路不能区分候选解释时，先修观测，不继续堆砌理论。实际故障面不可达时，说明已分析材料能证明到哪里。

## 验收与退出

- 结论可追溯到原始捕获中的事件、栈、对象或时间区间，并对应源码或明确的映射缺口。
- 确认机制与最强假设分开报告。
- 已授权修复则携带捕获与复现进入 [缺陷修复](bug-fix.md) 或 [性能优化](optimization.md)，修后用同口径验证。持续搜索请求交给 [Hillclimb](hillclimb.md)。
