# PR 生命周期

用于创建 PR、单次检查状态、处理审查意见或持续推进到可合并。打开 PR 不自动触发持续监控，达到可合并不自动授权合并。

## 选择模式

决策入口：选择动作范围读 [自主决策](../principles/autonomous-decisions.md)，复用检查或处理新 head 读 [证据时效](../principles/evidence-lifetime.md)。

| 用户请求 | 模式与边界 |
| --- | --- |
| “开一个草稿 PR” | 整理并创建指定类型的 PR，读回验证 |
| “看看 PR 状态”“还有什么没处理” | 单次只读检查和报告 |
| “处理这些评论” | 核实并处理评论涉及的问题，不自动接管全部发布流程 |
| “把 CI 修绿”“推进到可合并” | 持续处理范围内的检查、冲突与审查阻塞 |

用一句话说明所选模式。用户已经给出的授权无需再次询问。

## 执行

1. 确认仓库、目标 PR、head 与 base、草稿状态和分支归属。检查本地未提交改动，避免把用户无关工作包含进去。
2. 创建时先完成要求的本地验证，审阅准确差异，再按授权提交、推送和创建。标题与正文围绕问题、最终行为、验证与限制；创建后读回目标分支和内容。
3. 已有 PR 读取当前 head 对应的检查、审查、冲突和平台阻塞。单次检查模式在此汇总返回，不启动修复或监控。
4. 处理模式先归因。代码失败修具体缺陷；基础设施或偶发错误只有在有依据且重跑有信息价值时重试；审查意见使用 [评审与处置](review.md)。不因错误在未修改文件就断定一定是旧基线问题。
5. 冲突修复需读取两侧意图，保留双方必要变化并检查集成。共享分支的历史重写要核对专门授权；能够不重写历史解决时优先采用该路径。
6. 每轮修改后验证、审阅并按授权推送，重新查询新 head 的检查。旧 head 的绿灯不自动适用于新提交。向评论区发送回复只在请求已涵盖该动作时执行。
7. 持续模式等待新结果时使用现有查询或事件机制，遵循 [持续执行与恢复](../references/continuity.md)。依赖审批时推进其他独立事项，不重复触发无意义 CI。

堆叠 PR 按依赖定位阻塞：先解决阻挡后续验证的基础变更，独立上层工作可以并行。不要为了让状态好看而改 base、关闭检查或折叠用户要求保留的审查单元。

## 验收与退出

- 创建、状态检查、评论处理各到请求的边界即止。
- “可合并”需要平台当前状态、必要检查和阻塞意见共同支持；草稿、必要批准或队列规则仍阻塞时明确列出。
- 已要求合并则在条件满足后进入 [合并与发布](shipping.md)。只有推进到可合并的请求不执行合并或启用自动合并。

## 交付

PR 链接、当前模式和版本、修复或驳回的事项、检查结果及仍待满足的条件。
