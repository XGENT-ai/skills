# 从使用者的结果选择设计

**触发**：功能范围、默认行为、接口、交互和维护成本之间出现取舍。

## 决策

先写出使用者要完成的任务，再评价方案。使用者包括最终用户、调用 API 的开发者和接手维护的人。实现方便可以降低成本，但不能独自定义正确体验。

优先让核心路径完整、反馈明确、失败可恢复。每个选项和抽象都应解决实际选择或隐藏真实复杂度。用户明确要求的功能不能为了“精简”被静默删掉。

## 判据

让使用者从真实入口完成目标，检查理解成本、操作负担、等待和出错后的恢复。维护者能找到状态来源和改变规则。主观体验比较用同一场景的具体差异，不捏造满意度分数。

## 边界与反例

体验目标仍受正确性、可访问性、兼容和资源要求约束。额外动画、选项或隐藏错误不自动等于更好的体验。

例如：保存按钮立刻显示成功但后台仍可能失败，会误导用户；应展示真实的进行中与最终状态。
