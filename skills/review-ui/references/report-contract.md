# UI 验收报告合同

## 落盘与命名

- 默认保存完整 Markdown 报告、本轮截图、采集清单和评审原始结论，不询问是否保存。它们是下一轮评审的输入，不能只放在聊天里。
- 首轮报告的路径按以下顺序确定：
  1. 用户指定的路径；
  2. 附带本地计划时，计划同目录的 `<计划名去扩展名>.ui-review.md`；
  3. 仓库已有的报告目录；
  4. `docs/reviews/<主题>.ui-review.md`。主题取页面或路由名，路径中的特殊字符换成 `-`。
- 首轮报告路径去掉 `.ui-review.md` 后缀（不是这个后缀时去掉 `.md`），就是本循环的**前缀**。其他文件都按前缀命名：

| 文件 | 路径 |
| --- | --- |
| 目标包 | `<前缀>.ui-target.md`；导出的目标图放 `<前缀>.ui-target/` |
| 第 n 轮报告 | 首轮 `<前缀>.ui-review.md`，之后 `<前缀>.ui-review.r<n>.md`，n 取已有最大轮次加 1 |
| 第 n 轮截图 | `<前缀>.ui-captures/r<n>/` |
| 第 n 轮采集清单 | 同目录的 `capture.md` |
| 第 n 轮评审原始结论 | 同目录的 `judge.md` |
| 修复记录（没有计划时） | `<前缀>.ui-review.applied.md` |

- 每轮另存，不覆盖历史轮次。用户给某轮指定的路径已被占用时，另存为未占用的名称并说明。不把报告写进计划、目标包或代码文件。
- 报告由主 agent 单独写入，写完回读核对。写入失败时说明未落盘及目标路径，并在聊天中给出完整内容。

## 采集清单与评审原始结论

**`capture.md`** 在采集完成后写入：被测版本、目标指纹、采集条件；每张截图对应的单元、状态、视口和主题，以及它的出处（实际访问的地址、拍摄时间、所用工具，拦截了哪些请求）；没采到的格子及原因。它会交给评审当作看图的清单。下一轮比较目标指纹时，读的也是它，不必打开报告。

**`judge.md`** 是本轮评审结论的合并，只包含三部分：

- 各单元的四个维度分、单元总分和每个维度的理由；做了确认评审或重评时，每个单元保留分数较低的那份；
- 评审来源的全部未关闭差距：本轮复核后仍未关闭的旧差距（沿用编号，附最新状态），以及本轮新增的差距（已换成正式编号）；
- 建议。

`judge.md` 不写门槛、判定、机器检查、主 agent 核实的差距、核对说明和任何修复信息。下一轮评审只通过它了解上一轮的结论。

## 报告结构

1. **评审对象**（紧跟标题），一行表格：

| 轮次 | 开发计划 | 目标包 | 被测版本 | 截图 | 上轮报告 |
| --- | --- | --- | --- | --- | --- |
| R<n>；重建基线或限定范围时注明 | [<计划标题>](<相对路径>)，没有写「无」 | [<目标包>](<相对路径>) · 目标指纹前 12 位 | HEAD 短 SHA，含未提交改动时加指纹；访问地址 | [r<n>](<相对路径>) | [<上轮报告>](<相对路径>)，首轮写「无」 |

2. **验收判定**：首行写判定（见下文），再写本轮分数与门槛、停滞预警或待裁定标记，以及 1–3 句理由。
3. **评分**：每个单元的四个维度分和单元总分；本轮分数；历史最佳；门槛。做了确认评审或重评时，列出各位评审的单元分和最终取的较低分。
4. **轮次轨迹**：复制上一轮的表格，再追加本轮一行。

| 轮次 | 本轮分数（最低单元） | 历史最佳 | 未关闭 P0/P1 | 重构轮 | 备注 |
| --- | --- | --- | --- | --- | --- |
| R1 | 5.5（U2） | 5.5 | 3 | — | 首轮 |
| R2 | 7.0（U1） | 7.0 | 1 | — |  |

5. **上轮差距复核**（复审才有），表头为：编号 | 上轮严重度与摘要 | 上轮处置（取自修复记录） | 本轮结果 | 依据。
   - 评审来源的差距由本轮评审复核；机器检查和主 agent 核实的差距由主 agent 重新检查。
   - 本轮结果只用这几种：已解决、部分解决、仍存在、回归、待核实、不再适用、本轮未复核。
6. **差距清单**：所有未关闭的差距，即除已解决、不再适用以外的全部旧差距，再加本轮新增的。按 P0 → P3 排序，同一严重度内按可挽回分从高到低。属于待裁定事项的，在标题上标出。
7. **待裁定事项**：每项写清原因、相关差距、已有的尝试和可选项。
8. **建议（不扣分）**。
9. **机器检查**：检查项、工具与版本、结果、对应的差距编号；没检查的写明原因。
10. **采集与覆盖**：
    - 环境与被测版本，采集工具与条件，目标文件的 hash 清单；
    - 已采和未采的格子，未采的原因，以及补采记录；
    - 环境噪声；
    - 评审方式：派了几位 subagent、怎么分组、有没有确认评审或重评、是否单上下文评审；
    - 主 agent 对评审结论的核对说明（见下文）。

## 差距格式

```markdown
### UI-03 · [P1] 窄屏筛选栏挤压表格（U1 · 布局 · 可挽回 1.0）

- 位置：[U1-default-390-light.png](<相对路径>) 顶部筛选栏
- 现状 → 期望：筛选控件横排，表格只剩约四成宽，还出现了横向滚动 → [orders-m.png](<相对路径>) 中筛选收成一个「筛选」按钮，表格占满宽度
- 修法：窄屏下把筛选项收进抽屉，复用现有 Drawer；去掉表格容器的固定最小宽度
- 来源：评审 R2（机器检查或主 agent 核实时注明）
```

- 每条差距都必须指向本轮实拍的截图或页面实测结果。读代码产生的怀疑不进清单，可以写进「采集与覆盖」，作为下一轮补拍或实测的线索。
- 编号用 `UI-<两位序号>`，同一问题跨轮沿用原编号。
- 评审给新差距时先用临时编号。主 agent 合并时按顺序换成从未用过的正式编号，不重排，也不复用已关闭的编号。
- 重建基线后，仍适用的旧差距沿用编号，不适用的标「不再适用」。
- 主 agent 认为评审看错时，只在差距下附「核对说明」，写清截图里实际看到的事实。核对说明不改分、不删差距，也不改变门槛项；由修复方核实后决定是否不采纳，下一轮由评审复核。

## 计分与门槛

- **单元分**：评审给的四个维度分之和；做了确认评审或重评时，取其中较低的。
- **全量轮**：用户没有限定范围、应当采集目标包全部单元的轮次。全量轮全部单元都评到分时，才有**本轮分数**，即各单元分中的最低值。**历史最佳**是自上次重建基线以来本轮分数的最高值。
- **门槛**：默认 8/10。用户指定其他门槛时从其规定，记在报告里，后续轮次沿用。门槛不写入目标包，也不告诉评审。
- **门槛项**：未关闭的 P0/P1 差距，不论来自评审、机器检查还是主 agent 核实。
- **单元达标**：单元分 ≥ 门槛，且该单元没有门槛项。
- **待裁定事项**：单靠修改解决不了、需要用户决定的事。包括：
  - 停滞的差距（见下文）；
  - 修复方标为不采纳，但下一次评审仍判存在（仍存在、部分解决或回归）的差距；
  - 修复方标为待决定或阻塞、仍未解除的差距；
  - 目标图与规范之间的冲突。

  一旦成为待裁定事项，就一直保持，直到用户就它给出方向，或评审判它已解决、不再适用。修复方跳过它时记「待决定」，不记「未处理」。
- **可修复的差距**：未关闭、且不属于待裁定事项的差距。

## 停滞

逐个范围判断。范围有两种：**全局**；或**某条差距**，它的重构针对差距所在的单元。是否做过重构轮，以修复记录为准。自上次重建基线以来，每个范围最多重构一次。

**预警条件**，满足任一即成立：

- **全局平台期**：本轮分数低于门槛；自上次重建基线以来已有至少 3 个有本轮分数的轮次；本轮的历史最佳，比两个这样的轮次之前的历史最佳提高不到 1.0。
- **顽固差距**：某条 P0–P2 差距，自评审上一次判它以来，修复记录中有一轮把它标为已修改待评审，而本轮评审仍判它仍存在或回归；或者它已连续两次被判部分解决，且两次之前都被修改过。

**判定**：

- 预警条件成立，且该范围还没重构过：发**停滞预警**，要求下一轮修复对该范围做重构轮。
- 上一轮已发预警，但修复方没做重构轮：再次发预警，不判停滞。
- 预警条件成立，且该范围已经重构过：该范围**停滞**。差距停滞后成为待裁定事项；全局停滞时，判需用户裁定。

## 验收判定

按以下顺序，取第一个成立的判定，写在「验收判定」首行；最终回复也先给它。

1. **需补证**：属于以下任一情况。写明缺什么、怎么补；报告照常列出已评单元的分数和差距，修复方可以先修这些。
   - 全量轮中有单元或必需的格子没采集到，包括截图不符合真实性要求的；
   - 有 P0/P1 差距补采后仍判待核实（截图看不出）；
   - 应用起不来；
   - 两次派发评审都没拿到有效结论；
   - 目标包缺少某个单元的期望。
2. **通过验收**：全量轮；本轮分数 ≥ 门槛；没有门槛项；需要确认评审时，确认后仍达标。剩下的 P2/P3 差距（包括待裁定的）不阻止通过，列为可选的打磨项。
3. **需用户裁定**：属于以下任一情况。列出待裁定事项、已经试过的做法、截图对照和可选项。
   - 全局停滞；
   - 尚未通过，且已没有可修复的差距；
   - 剩下的门槛项都是待裁定事项，而分数已达门槛（限定范围的轮次看范围内各单元分）。此时继续修 P2/P3 也无法通过。
4. **需要修改**：其余情况。按需带上标记，例如：
   - 「需要修改 · 停滞预警（全局）」
   - 「需要修改 · 停滞预警（UI-07 所在 U3）」
   - 「需要修改 · 待裁定（UI-04、UI-09）」
5. **用户豁免通过**：用户明确接受当前的整体界面。在本轮报告的验收判定后追加记录：日期、用户原话、豁免的差距编号及剩余影响。原分数和差距不改写，豁免不算已解决。

**限定范围的轮次**按同样规则判定，只有两点不同：

- 没有本轮分数，不判全局平台期；
- 范围内单元都达标时判需补证，并说明要一轮全量评审才能判通过。

验收判定只表示界面在所测版本和条件下的验收结论，不是合并、发布或产品终验的授权。
