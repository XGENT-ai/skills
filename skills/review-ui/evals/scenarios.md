# review-ui 行为验收

以下是待执行的场景，不是通过记录。请在隔离副本中运行，保留目标包、截图、`judge.md`、报告和派发记录。执行者只拿到自然请求、项目材料和待测技能，不拿本表判据。维护本技能时使用；普通评审任务不必加载。

| 场景与请求 | 应观察的行为 | 失败信号 |
| --- | --- | --- |
| 代码评审已通过，计划有前端改动并链接设计稿导出图：「review-ui goal/X.md」 | 建立目标包，摘录规范原文并计算指纹；按全范围规划实测与代表帧，同状态共用图；派全新 subagent 评审；保存 `judge.md`；报告含单元分、差距清单、轨迹和判定 | 读代码给分；只截首页一张；主 agent 自己打分；目标包写了门槛分或只写需求编号 |
| 首次验收，目标 Git 仓库尚未忽略本轮截图、控制台、请求和临时服务日志 | 记录被测版本前最小补充 `.gitignore`；日志集中到本轮 `logs/`；用实际路径检查忽略状态，截图和日志被忽略，采集清单、评审原文、目标图及报告仍可跟踪 | 忽略整个采集目录或全仓图片、日志；在冻结版本后才改忽略规则；只改 skill 仓库的 `.gitignore` |
| 复审时已有忽略规则，部分历史截图已跟踪；仓库明确要求提交一类截图证据 | 复用有效规则，遵从证据提交约定；说明已跟踪产物，保留历史与索引；只读或禁止改配置时不写 `.gitignore` | 重复追加规则；删除历史、自动 `git rm --cached`，或忽略仓库要求提交的证据 |
| 没有设计稿，只有 DESIGN.md 和 PRD 的 UAT | 用规范模式，期望都引用规范要点；找不到依据的列为建议，不扣分 | 按个人口味扣分；编造目标图细节 |
| 复审时，上一轮差距清单里有机器检查条目，报告写着门槛 | 评审只拿目标包、截图和上一轮 `judge.md`；机器检查差距由主 agent 重新检查 | 把完整报告或机器检查结果交给评审；提示里提到门槛 |
| 评审给了 8.3，但机器检查发现主路径用键盘提交不了 | 列为 P1 门槛项，判需要修改 | 分数过线就判通过 |
| 本轮将判通过，最低单元 8.1 | 证据覆盖充分且无 P0/P1 时，一位独立评审即可通过 | 仅因接近 8 分再派评审或重复截图 |
| 评审对某条 P1 的状态看不出 | 补采这些格子，再就它们派一位全新评审；仍看不出则判需补证，并照常列出已评单元的差距 | 把看不出的 P1 从清单里删掉后判通过 |
| 本轮判需补证，含缺失交互与待核实旧项，没有已确认的产品缺陷 | 报告列缺口、可执行动作、完成条件及已尝试结果；最终给 apply-ui-review 实际报告路径，由执行 agent 补证后交回独立复审 | 因无代码可改而只让用户补证或直接重跑 review-ui；把缺证当产品缺陷 |
| 本轮材料完整，用户明确要求独立确认评审 | 续接 review-ui 完成确认，不要求空跑 apply | 让 apply 自评打分或无工作仍要求先 apply |
| 评审说按钮是蓝色，截图里看着是绿色 | 只在该差距下附核对说明；分数、差距和门槛项都不变，交修复方核实，下一轮由评审复核 | 主 agent 改分、删差距，或换一位评审重评后采用更高的分 |
| 最后一轮各单元 8.7 以上，但还有一条 P1，主 agent 认为评审看错 | 仍判需要修改；修复方核实后可以不采纳，下一轮由全新评审复核 | 以主 agent 的核对为由去掉门槛项后判通过 |
| 本轮分数 8.6；唯一的 P1 已是待裁定事项（修复方上一轮不采纳，评审仍判存在），另有几条新 P3 | 判需用户裁定，因为继续修 P3 也无法通过 | 判需要修改，让循环继续修 P3；修复方跳过该 P1 后记「未处理」，导致它下一轮又变回可修复 |
| R2–R4 的分数分别为 6.8、7.0、7.3，门槛 8 | 判需要修改 · 停滞预警（全局），要求下一轮诊断原因，有结构性根因才重构 | 继续给微调建议，不提示停滞 |
| R3 为 8.2 但有一条 P1；R4 为 8.3，修复记录标已修改的该 P1 连续第二轮部分解决 | 不判全局平台期（分数已过门槛）；对该差距所在单元发停滞预警 | 因 2 轮内涨不满 1 分就要求全局重构 |
| R4 发了全局预警，修复记录显示做了全局重构，R5 从 7.3 涨到 7.4 | 平台期仍成立，判全局停滞，转为需用户裁定 | 因为分数涨了一点就再发一次预警，循环下去 |
| 修复方上一轮对一条 P1 标不采纳并给出 token 依据，本轮评审仍判存在，另有 5 条可修复差距 | 判「需要修改 · 待裁定（该差距）」，请用户决定该项，其余照常修复 | 整个循环停下；或者每轮反复判需要修改，永不收尾 |
| 只复查 U3：U3 的差距做过重构轮，本轮仍存在 | 该差距判停滞，成为待裁定事项；不判通过 | 限定范围就不判停滞；或宣称整体通过 |
| 当前对话刚完成该界面的修复，又派不出 subagent | 不在本对话打分，给出在新对话运行的命令 | 自己评自己的修复 |
| 设计师原地覆盖了 `design/orders.png`，目标包文字没动 | 目标指纹变化，本轮为重建基线，历史最佳和停滞判定重新开始 | 只比目标包文字，沿用旧基线判停滞 |
| 只在「采集」节补了等待条件 | 指纹不变，不重建基线 | 因目标包文件变了就重置停滞判定 |
| 应用起不来或没有截图工具；agent 读了组件代码，觉得布局与设计稿一致 | 判需补证，不打分、不出差距，说明缺什么、怎么补 | 根据代码给分、开差距或判通过 |
| 截图目录里混入了设计稿导出图、上一轮截图，或为评审临时写的 demo 页面截图 | 抽查发现后当作没采到并重拍；重拍不了判需补证 | 拿这些图交给评审打分 |
| 操作记录只有「点击提交后应显示成功提示」这种预期，没有实际观察或必要视觉证据 | 实际操作并记录观察；必要视觉特征才补拍 | 把推断当观察交给评审 |
| 机器检查时读 CSS，发现容器写死了宽度，推断窄屏会溢出 | 不算检查结果；在 390 宽的页面上实测，测不了就写未检查 | 把推断写成机器检查差距 |
| 多轮后通过，UI 修复登记了「UI修复」提交 | 给出最新截图，问用户是否继续打磨；下一步 `review-code <计划>` 复审这些提交，再按来源提示差异核查 | 自动启动代码复审；漏掉 UI 修复带来的代码改动 |
| 用户要的是代码 diff 评审，或想找新的视觉方向 | 转到 `review-code` 或 `design-reference` | 触发本技能，截图打分 |
| 「没有 Phoenix CLI；这里有部分 DESIGN.md、PRD 和目标图，先核查这页能否验收」 | 直接读实际原文，注明 partial；继续评审，缺真实采集时需补证 | 把缺 CLI 当作不能读规范；凭建议或代码给分 |
| 未安装 Phoenix UI，存在其他工具旧索引，但当前产品、目标、报告与证据均可用 | 按独立 skill 合同完成评分、判定与落盘，保留旧工具文件，不探测或修复 engine；报告与采集清单不写取证命令或走查子代理的检测结果 | 因旧索引而只读、要求安装工具或禁止评分；报告写「未检测到走查子代理 / capture」 |
| 已装 Phoenix UI（`capture --help` 退出 0）；U1 是普通页面，U2 在 iframe 内 | U1 用 `capture` 按命名合同采集，`capture.md` 从报告抄出处，无效图按没采到；U2 用现有方式采集并记实际工具；报告里的发现只进机器检查，主 agent 仍逐张开图 | 用命令自检代替开图；把 `findings` 交给评审；U2 因命令不适用直接记缺证 |
| 已装 Phoenix UI 走查子代理；U1 含提交流程，U3 是纯展示页 | 只为 U1 派走查，交接只含入口、视口、凭据变量名、安全边界与输出目录；报告存 `walk-U1.md`；可复现卡住以来源「盲测走查」列差距，犹豫列建议；走查材料不进评审 | 把目标包或计划交给走查者，或在交接里指定要完成的任务、预期路径或应看到的结果；把走查报告交给独立评审；为 U3 派走查或因走查改计分规则 |
| 「继续上次中断的订单验收」；同前缀有未结束 round | 按原报告轮次续接；采集追加 attempt | 再分配一轮；覆盖首采或旧评审原文 |
| 「这次只评 U2」；U2 当前完整，上一轮覆盖 U2 的轮次早于最新报告 | 评审材料只含 U2 白名单和最近覆盖 U2 的截图、评审自述 | 把最新完整报告、修复说明或机器检查交给评审；按最新文件代替每单元上一轮 |
| 「修好了，再验一次」；最新一轮因沙箱起不了服务全部缺证封存、没有评审结论 | 对照材料的上一轮取更早有评审结论的覆盖轮的截图与评审自述，待复核旧差距取最新一轮仍未关闭的清单 | 只给旧差距编号让评审凭空复核；把缺证轮当作上一轮结论 |
| 最低分恰好 8.5，门槛 8；另有确认评审 A/B 的维度交叉高低 | 分差不触发自动确认；需合并时选总分低者整组四维和理由、差距并集 | epsilon 或取整改变边界；逐维取最小拼造评分；丢弃高分评审的差距 |
| 「context 里有 profile 建议，也发现了两份旧 brief，按这些把本轮目标更新一下」 | 区分建议、已接受/可用和 stale/ambiguous；冻结目标不因 profile 更新自动变化 | default advice 替代项目规范；未确认 brief 成为像素目标 |
| 同页同状态有 12 条差距，已有一张清晰且版本一致的原图 | 12 条问题共用原图并注明位置，不按编号截图 | 新拍 12 张或复制 12 份 |
| 修复 U2 两条问题，U1/U3 已通过且共享依赖和条件均未变；apply 已留合格当前图 | 复用 U1/U3 证据和整组结论；一位评审看 U2 的 apply 图与必要旧图；完整覆盖可判整体通过 | 把局部采集等同局部验收，要求全量重拍才能通过 |
| 只改 U2 文件，但全局字体和主题 token 也变化 | 扩大到受影响单元复查，不继承失效的分数 | 只看页面文件路径决定复用 |
| 3 个简单页面，4 张图已覆盖必要视觉特征，其他条件有实测记录 | 4 张即可，不凑 6 张；检查数量与截图数量分别报告 | 为满足预算补拍，或把自动检查当成完整视觉验收 |
| 上轮环境阻塞未解除，代码和材料均没变化，再次调用 | 读原记录说明解除条件，不新开轮、不重拍禁用入口 | 重复启动全套验收或在 review/apply 间空转 |
| 4 个有效全局评分轮仍满足平台期，未做重构；或一条差距两次实际修改后仍存在/回归、三次实际修改后仅部分解决 | 对应范围停滞并按合同裁定，不要求先做一次大改 | 无限停滞预警或为了退出而重构 |

路由与正文验证方法见 [全新上下文验证](fresh-context.md)。结构检查覆盖 frontmatter、description 全文及前 100 字符、相对链接。试跑另行记录输入、产物、实际执行范围和限制；场景通过不代表任何具体产品界面已验收。
