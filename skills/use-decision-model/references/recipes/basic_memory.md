# 按客户记住会影响后续工单的事实

同一句“仪表盘很慢”，对云版客户应交云平台组，对 Windows 自托管客户则应交 Windows 组。给原有 `ask(state, questions)` 加一个同参同返回值的包装器：先带着该客户的记忆回答，再判断**本次工单**是否值得保存。应用维护 `客户 ID → 记忆列表`，不用模型自己记住会话。

**两个串行判定。** 输入 `state` 含可信的 `customer.id` 和工单的编号、日期、主题、消息。第一题是 `Choice`：“哪个团队适合处理这张工单？”限定为云平台、自托管 Linux、自托管 Windows、计费、企业客户事务、通用产品问题、`none_suitable`。给各选项写明分工，例如企业客户的技术问题仍归技术组，不因合同类型转企业事务。无合适团队时允许返回 `none_suitable`，由代码转待分派。

第二题读取**原始工单 + 刚才的回答**，问：“客户或客服在本次工单中明说了哪怕换一个问题也会影响处理方式的长期事实吗？”版本类型、操作系统、套餐、合同或长期偏好可算；今天在机场用手机、临时休假不算。路由答案仅供理解上下文，不能当成客户陈述，更不能拿上次的记忆充当本次新事实。

```text
id = state.customer.id
history = memories.get(id, [])
context = 带有 earlier_tickets_from_this_customer=history 的 state 副本（无历史则用原 state）
response = ask(context, questions)
pair = {request: 原始 state, jev_answered: 问题到可读答案的映射(response)}
p = 本次工单含长期事实的概率(pair)
if p >= 0.5: memories.setdefault(id, []).append(pair)
return response
```

保存的是**原请求和答案对**，不是带历史的 `context`，否则旧记忆会层层嵌套。可读答案用所选团队的职责描述；数值问题则保留数值。是否写入由代码决定，不改变第一次的返回值。缺少可信 ID 时不用共享桶顶替；记忆评估缺失不作写入，派单也不能绕过宿主权限。

**离线验算。** 给 A 的工单“我们在 Windows Server 上自托管”填保存概率 0.97，给 B 的“我们按月付云版 Team 套餐”填 0.98，两条分别入各自列表。A 下一条“我在机场用手机查上月账单”填 0.02，应答复但不写入。检查下次组装的输入：A 看不到 B 的套餐；“仪表盘很慢”本身没有新增长期事实，即使派到了 Windows 组，也不重复保存。源例两位客户各发三条相同消息，不带记忆命中预期团队 3/6，带记忆是 6/6，仅是小样本演示。

**边界。** 0.5 是示范写入线。用业务工单标注“值得保存／不值得保存”，另留样本验线；误记代价高就提高门槛。这个字典随进程退出消失，没有筛选、过期或替换机制，每次都附上该客户的全部历史；错误路由即使不能独自触发保存，也可能随真实工单被保存并继续误导。持久化、挑选相关记忆、替换过时事实都是后续设计，不是这段包装器已有的能力。
