# 从技能目录中建议至多一个技能

“最像哪一个”和“有没有合适的”是两个问题；只问前者，即使目录里没有用户需要的服务也总有第一名。输入是当前请求和本地目录，每项有 `name`、短描述 `description`、完整描述 `description_full`、正文 `body`。输出是一个目录内的名字或空结果，不是加载、更改文件或操作账户的授权。

**第一轮：泛读全目录。** 用所有名字和短描述做一次 `Choice`，按概率从高到低排序。同轮独立问四道是非题，取得各自 `P(是)`：

- `act`：需要实际操作用户的文件、设备、账户或服务吗？
- `procedure`：需要查阅特定操作规程，而非只用一般知识吗？
- `prose`：仅凭文字解释，不用工具、文档或文件就够了吗？
- `named`：是否点名了工具、格式、模板或方法？

**第二轮：精读前三项。** 对入围者用“完整描述 + 正文开头 700 字符”重新做一次 `Choice`，选出最合适的 `winner`。同时用每项的完整描述分别问 `fits[name]`：“它确实能完成请求中的那个具体操作吗？”这是绝对适配度，可以三项都低。

```text
action = (act + procedure + (1 - prose)) / 3
if action < 0.30 and named < 0.50: return ()
shortlist = 前三名(第一轮排名)
winner, fits = 读取第二轮判定(shortlist)
if max(fits.values()) < 0.30: return ()
return (winner,)
```

`named` 单独过门槛，避免把“按指定模板制作”的请求当成纯解释。第二轮比较的是**最高适配度能否过线**，不是取适配度最高者当赢家。离线可录入原例：请求修改已有演示稿时，建稿技能和办公技能的 `fits` 分别为 0.77 和 0.76，复选的 `winner` 却是办公技能，应建议后者。反例：用户想发往目录不支持的平台，虽然 `action=0.86`，第二轮最高 `fits=0.28`，所以返回空。上述阈值、候选数和截取长度均是示例设置。

保留原目录，在其后追加本轮提示：“可优先查看某技能；若与实际请求不符，请忽略。”空结果则明说“目录中未发现适用技能”。评估缺失时也不猜名字；建议本身不触发工具，加载和执行仍由宿主代码按已有权限控制。

**怎样验证。** 分开统计两种首轮错误：有标准技能时，首次加载错误或未加载；无适配技能时，却加载了任何技能。原例对同一批 452 条请求比较无提示、给建议、给标准答案三种条件。280 条有标准技能的请求中，建议纠正了 29 条，也带偏了 7 条；这些请求是按技能材料编写的，不代表真实流量。换目录时尤其要保留“相近但做不到”的反例。
