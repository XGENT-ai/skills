# 结构化排期：先出低成本候选，逐条核验再升级

**输入**是一段会议需求，含工作时段、忙碌区间、时长和偏好。**输出**是一个候选会议记录及采用哪级答案的理由，不写入日历。两个生成步骤可以用本地模型，也可先用固定的两份回复演练路由。

1. 给较小模型原任务和输出约束：“只给一个 JSON 对象，含 `day`（工作日枚举）、`start_time`、`end_time`（24 小时 `HH:MM`），不加其他字段。”代码解析**整段**回复，检查必填项、允许值与时间格式；失败直接升级，不从坏回复里截取看似合法的片段。
2. 合法的 JSON 也可能约错时间。把**原任务和候选**一起交给本地核验器，不提供参考答案。一次问六个二元问题，统一取 `P(违规)`：是否与任一人的忙时重叠？是否超出允许日期或工时？是否违背明说的偏好？若要求最早，是否还有更早的可行时段？时长是否不符？是否没给出唯一时段？未要求最早时第四题应为否。
3. 示例规则为 `升级 = 格式失败 或 任一违规概率 > 0.70`（严格大于）。记录所有触发项，不取六项平均。未触发就保留低成本答案；触发才让较强模型用同一原任务和约束重新作答，再解析同一 schema。升级答案格式仍不合格就返回失败，不拿坏记录补位。

**演算**：要求周一 09:00–17:00 内约一小时，参会者 11:00–11:30 已忙，14:00–15:00 均有空。第一份回复 `{"day":"Monday","start_time":"10:30","end_time":"11:30"}` 格式全对，但冲突题得 `0.97`，已足以升级。若第二份回复给 `14:00–15:00`，再核对日程可见它满足条件。不要把“采用较强模型”当作正确性证明。

**选阈值**：在已有离线记录上逐个阈值回放，比较可行解比例、升级率和成本（小模型 + 实际核验 + 仅升级时的大模型）。有多种合法时段就都算对；参考日程用来评分，不参加路由。核验器若比升级本身还重，级联未必划算。
