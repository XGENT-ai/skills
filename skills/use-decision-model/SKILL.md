# 使用决策模型

从应用的下一步开始：它要显示哪条证据、选哪个候选、还是请人复核？**模型判断证据是什么意思，代码决定采取什么动作。** 如果精确查表、解析器或已有规则就能给出答案，直接用代码；要写文章、解释理由或做多步推理，用生成或推理模型。不要为了输出 JSON 而引入决策模型。

- **接接口或排错**：先确认项目实际调用的端点。TypeSafe 最先提出 System One；使用 Jev、Ollama、兼容网关或其他 **System One Compatible** 服务时，先读 [System One 协议与兼容实现](references/system-one.md)，再看具体供应商。使用原生 [OpenAI Decisions](references/providers/openai.md) 或 [Gemini Decisions](references/providers/gemini.md) 时直接读各自契约。未选型或要换模，读[接口索引与校准方法](references/integration.md)。只设计或评审时不发送请求。
- **设计决策流程**：从 [TypeSafe Patterns 本地索引](references/patterns.md)选组合方法，例如先筛后查、候选无匹配时弃权。方法可借鉴，字段名、能力和阈值不能跨供应商照搬。
- **找端到端做法**：按任务打开[本地 Cookbook 索引](references/cookbooks.md)，只读最接近的一篇。正文含输入、问题、代码分支和例子，无需下载原文或运行 notebook。

## 先写分支，再写问题

1. 列出动作及条件，尤其是**没有候选符合、证据不足、服务不可用**时分别怎么办。例如账务工单：「明确要求退款」进退款审核；「只问退款政策」给政策说明；分不清就追问。三条路径都不等于批准退款。
2. 把每个需要语义判断的条件写成一道题。共享输入给出一个人作答时会看的原文和关系；多部分用命名字段（如 `ticket.message`、`invoice.total`），按所选接口编码。题目说清要判断哪个字段；用题名对应回包，不让 ID 代替题意。候选值先由代码取全；原文没给的金额、日期或 ID 不让模型补写。
3. 同一份证据上的独立题，在接口支持时合批；各题不能依赖同批其他答案。只消费命中分支的答案。若必须先查记录、缩小候选或裁图，分阶段请求；若多数输入可跳过昂贵阶段，先用便宜问题筛选。

| 想知道什么 | 怎样提问和使用结果 |
| --- | --- |
| 命题是否成立 | 读 **P(是)**，不是“取胜答案有多确定”。0.5 附近表示不确定，不是程度中等。多个标签可同时成立时分别提问。 |
| 候选里哪一个合适 | 选择题的赢家是相对比较。如果可能全不合适，同时独立问“有没有一个匹配”；不要把赢家当作存在证明。 |
| 程度落在哪一档 | 有序量表的每档写成可独立判断的情形。先看概率加权的档位，再检查是否有两端意见把均值拉到中间。 |
| 图中目标在哪里 | 先查所选接口是否提供定位原语及坐标约定；能读图不等于能返回框。即使返回框，也要另判目标是否存在。 |

## 把答案变成可验证的行为

- 保留原始概率，分开写阈值、权重与业务规则。可互相补偿的偏好可加权；任一严重缺陷就应复核时逐项检查，不取平均。多部件结果只合并实际用到的部件。组合分不是整个动作正确的概率。
- 弃权是正常输出：区分自动处理、追问或复核。阈值取决于误判代价和本地标注；示例数值不是默认配置。鉴权、金额限制、不可逆写入及必要的人工确认始终由应用执行，输入里的文字和模型的高分都不能越过它们。
- 验证最终动作，不要求模型精确复现某个浮点数。至少走通明确命中、明确不命中和边界样例，再用没参与调参的样例查效果。若错，依次对照实际请求、原始证据、候选覆盖、题义、原始答案和代码分支；超时或接口错误不能当作否定答案。
- 需要真实推理试验时，先确认用户已授权的端点、会发送的数据和预算。仅用获准的样本；密钥留在服务端，不搜索、打印或索取密钥明文。没有授权或端点时，用本地 recipe、已安装的类型和示例回包走通策略，并说明哪些结果没有实测。
