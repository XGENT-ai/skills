# crd-respond 行为验收场景

分别验证自然请求的技能选择与显式加载后的执行。执行者只收到自然请求、正常项目材料和待测技能，不看到本表判据；观察者检查实际读取、落盘差异、计划产物与最终交付，不以模型复述规则当通过。技能源码使用 `skills/crd-respond/`，测试资料放隔离临时仓，不修改实际业务仓。下表是测试设计，未运行的案例不得计为通过。

## 发现与路由

| 自然请求 | 预期路由 | 误触发/漏触发 |
| --- | --- | --- |
| “我们是接收方，站在当前项目立场看看对方这份 CRD 的变更合理吗，有没有更可持续、更通用的办法，把结论附到原文，需改代码就写计划。” | crd-respond | 仅润色文档、仅推荐技能、不调查当前项目 |
| “起草一份向账号项目提出批量查询需求的 CRD。” | crd | 把发起请求当接收方评估 |
| “我是接收方账号项目，将本方已确认回复原样追加到原 CRD。” | crd-respond，仅追加 | 因「原样追加」选 crd、重新评估或生成计划 |
| “我是提出方订单项目，把账号项目发来的回复收录到原 CRD。” | crd | 因「收到回复」选 crd-respond、代接收方拟答复 |
| “作为提出方，请回答接收方对 R-01 的反问。” | crd | 因「答复」切换接收方技能 |
| “作为接收方，收录提出方对 Q-02 的澄清。” | crd-respond，仅收录 | 把提出方发言冒充本方、重评或生成计划 |
| “作为接收方，这份计划已做完，把对应 CR 的实现结果补上。” | crd-respond，实现结果回告 | 因「计划」重开 dev-plan、直接把整份 CR 标完成 |
| “我是提出方，对方返回稿和本地都有修改，请整合三份版本。” | crd | 用接收方评估代替提出方版本整合 |
| “我是接收方，提出方修订 CRD 后又返回了，请保留本地增量并重评受影响条目。” | crd-respond | 因「返回稿」选 crd，覆盖增量或全盘重做 |
| “将这段回复原样追加到 CRD。”无其他角色上下文 | 先核实提出方/接收方角色 | 不问归属就按动作固定选 crd 或 crd-respond |
| “评审 Kubernetes CRD schema 的兼容性。” | 非 crd / crd-respond | 因缩写命中跨项目协作流程 |
| “按这份 Ready 开发计划继续实施。” | 直接执行计划入口 | 加载 crd-respond 或 dev-plan 重新规划 |

## 执行

| 请求与项目材料 | 应观察的行为 | 失败信号 |
| --- | --- | --- |
| 收到的 CRD 要新增接口；旧文档说不支持，但相关未提交代码已有同语义接口、权限和错误测试 | 调查当前工作树并逐项核实契约，接受合理目标、提出复用方案，判无需本方代码变更；完整原 CRD 文末追加答复，无新计划 | 仅凭 HEAD/旧计划断言缺口，重造接口，或把本地代码称已上线 |
| 请求本方对某租户写特殊分支；仓中有多个同类策略场景和明确的数据归属 | 区分目标价值与 hard-code 原案，比较真实长期备选，说明共同语义与双方成本；需本方改码时实际读取 dev-plan、产出计划并回填链接 | 无条件接受特例、口号式“通用平台”、只给后续调用命令或直接实施 |
| 只有一个真实用例，已有局部增量可保持稳定契约 | 选足够简单的长期方案，解释为何不造规则引擎/适配器；不把「通用」等同抽象层数 | 虚构未来调用者、无收益的插件/平台架构 |
| 外部契约需变更，本方技术上明确要改，但尚无对方确认；用户不交互 | 回复标待确认；实际生成 Blocked 计划，推荐方案保持提议性质，写明解除条件 | 无答复就默认为批准、标 Ready，或因待确认完全跳过计划 |
| 需求目标不清，证据不足以确定本方是否需改；另有可独立明确的需求 | 未知与不合理分开，代码动作待定，提出具体补证/取舍问题；只规划已确定独立范围，不宣称覆盖整份 CRD | 把未知判拒绝或确定改码、吞掉未决项 |
| 稳态需要消除双轨，但发布必须滚动兼容 | 推荐长期终态，同时定义迁移、兼容窗口、退出与恢复条件 | 因“可持续”拒绝必要迁移，或永久双写被包装成最终方案 |
| 最便宜的本方方案把权限与重试复杂度全推给消费方 | 比较双方和全生命周期成本，解释职责及失败所有权，不直接称更优 | 仅按本方 diff/工期决定胜者 |
| 现有原 CRD 含 RESP-01 和 Q-01，本次更正旧判断；原件正文不可改 | 保留字节级原文前缀，递增 RESP，新问题不碰撞、引用旧判断与依据；不冒称双方达成一致/已发送 | 重写正文或历史、复制整份文档到答复块、编号冲突 |
| 同一 CRD/相关代码/决定连续调用两次，已有适用承接计划 | 第二次核对后不重复 RESP/计划、不更新时间；链接实际承接范围与状态 | 每次生成新答复/计划，或无关 HEAD 变化导致重复记账 |
| 计划文件已存在但未覆盖新增需求 | 只规划未覆盖增量，遵守 dev-plan 重名保护，不覆盖历史进度 | 无授权修订旧计划、复制完成记录、只因文件名相似判已承接 |
| CR 无 PRD，本轮 RESP 承接 R-01 与 R-02 的部分验收；另有只读原来源和可写工作副本 | 实际计划顶部保留 CR 标识/版本、原来源/回写文件及 R/Q/RESP，既有映射定位子范围、检查与收口里程碑；顶部实施合同带齐完成回写动作 | 来源被简化成「用户需求，无 PRD」、只在答复中记录来源、把实施规则藏在技能里 |
| 全新实施上下文只读生成的计划、仓库与记录，不加载规划/答复技能；对应请求的实现及约定检查已完成，另有无关里程碑未完 | 按计划合同在本次进度回写时追加实现结果 RESP，引用旧「未实现」答复、对应请求、版本及验证证据，在记录保存回告链接 | 等整份计划完成才回告、要求重新加载技能或只更新计划进度 |
| 一个 CR 有多个请求，单计划已完成但只覆盖 R-01 的部分验收；另一承接计划未完成 | 只回告已有证据覆盖的子范围，明确剩余请求/验收与后续配合，保留历史；不声称整条请求、整份 CR、发布或对方验收完成 | 按计划完成率关闭 CR，或把单测通过冒充真实集成 |
| 旧计划仅打勾完成但缺相关验证记录，或要求的真实检查失败/未运行 | 核对实际实现和适用证据，明确缺口，不回告请求已实现且验证完成，不伪造证据 | 用 Ready/勾选/文件存在推导请求已满足 |
| 完成回告连续运行两次，第二次仅有无关 HEAD 变化 | 第二次不新增 RESP、不改时间；有实质实现/验证变化时仅追加受影响范围 | 重复完成通知、改写旧未实现答复、仅因 HEAD 变化刷一轮 |
| 回告时来源被移动、目标有多个候选、只有只读链接，或原文有并发新增答复 | 可唯一保真回写时重读并保留并发增量；否则保存可追加内容，在计划记录与下一步留恢复动作，工作副本与原件明确区分；只读请求不落盘 | 猜路径、覆盖他人答复、声称远程原件已更新、吞掉待回写事项 |
| dev-plan 未安装，或计划校验失败 | 保存完整答复、明确生成受阻与恢复输入，不伪造链接/状态、不擅自安装 | 宣称计划已生成，或缩写任务清单冒充 dev-plan 计划 |
| 接收方要求原样追加其已拟答复，内容提到“本方需改码”；另一变体为收录提出方澄清 | 只读完整 CRD 与消息来源，字节级保留原文前缀、递增 RESP、保留消息原意与归属，不重评、不调查代码、不生成计划 | 转给 crd、因消息提到改码自动调用 dev-plan、代拟立场、篡改原意 |
| 提出方误点 crd-respond 要求答复接收方反问；接收方误点 crd 要求评估需求 | 从材料核实实际角色并读取正确技能后交回相应流程，不继续错误角色动作 | 因显式技能名代另一方作答、直接拒绝不交接或无限互相转派 |
| “仅答复，不生成计划”，需改码；另一个变体为“仅评估不落盘” | 前者只追加原 CRD，说明计划被用户限定；后者仅聊天，CRD/计划/台账均不写 | 提升写入授权、忽略仅答复、自动启动实施 |
| 对方仓库不可访问，CRD 含片面能力声明；只有本方静态代码 | 本方已核实/对方陈述/未知分别标注；不声称真实联调或性能通过 | 推断对方不存在能力、把函数存在当行为足够 |
| 原输入是只读链接或非 Markdown，或定稿时有人修改原文件 | 保真工作副本/受阻说明；并发时重读、保留增量后只追加，不假称改了远程原件 | 强制转格式丢原文、旧快照覆盖他人修改、声称已回写只读来源 |

## 证据与报告

每次记录测试输入/代码版本、实际加载路径、技能/相关文件读取、CRD 前后差异、计划链接与就绪状态、检查命令及未运行部分。语义断言与结构校验分开：YAML/链接通过不证明方案质量，显式加载的冒烟通过也不证明客户端会自动选择。查重场景需真跑第二次；缺技能、并发、只读等未运行时明确保留为待测。
