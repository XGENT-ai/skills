# 文档评审处置合同

## 写入位置与历史

- 默认就地修订用户指定原文，在源评审报告追加或更新「修订处置与复核」节。调用本技能已经授权这些写入，不再询问是否保存；明确只核实、仅聊天或另存时以用户要求为准。
- 原报告的问题、证据、评审基线和原结论保持不变；当前处置与修后判断独立成节，标明日期和修后版本。原文只保留修订后的产品/设计结论及必要决策理由，不混入 F-ID、采纳经过和评审流水。
- 源报告只读或用户要求保留文件不变时，另存同目录 `<报告文件名去扩展名>.applied.md`，在处置文档中链接源报告和修订目标；远程来源没有本地目录时遵循仓库惯例，无惯例则用 `docs/reviews/<主题>.applied.md`。重名且未获更新授权时加日期及序号，不覆盖无关文件。
- 多份报告对应同一原文时合并修订，但每份报告均能追踪其问题处置；同一 F-ID 不能跨报告混用。多份原文的版本与结论分别记录。
- 重复运行先读已有处置，以报告原始版本/问题 ID 匹配更新，不重复应用修改。新报告改变主张时标明新来源；本技能追加的处置内容改变报告 hash 不应把旧 finding 变成新问题。

## 逐条状态

| 状态 | 使用条件 |
| --- | --- |
| 已修订并复核 | 当前问题成立，最小修订已落盘，文档层面的复核条件通过；不代表未来实现验收通过 |
| 已修订待核实 | 已改文档，但事实、关联一致性或必要检查仍缺证；说明缺什么及下一步 |
| 已解决无需修改 | 当前原文已解决，有具体段落与证据，不冒领成此次修订 |
| 不采纳 | 误报、不适用、纯偏好或与明确要求冲突，有反证与理由；缺陷仍成立时不能仅因建议不合理就关闭 |
| 待核实 / 待决策 | 缺事实或用户选择，说明受影响范围、所需证据/问题及可继续部分 |
| 待修订 / 阻塞 | 意见成立但尚未落实，说明依赖、已做部分和解除条件 |
| 未处理（用户限定范围） | 用户明确排除的条目，不计入本次关闭数量 |

产品增强提案未获采纳授权时说明「提案未纳入」，不当成缺陷修复完成。用户主动延期或拒绝解决仍成立的问题时保留问题事实、决定来源和剩余影响，不伪装成误报。

## 处置节最小结构

```markdown
## 修订处置与复核

- 来源：<报告原始版本/hash；原问题 ID 保持不变>
- 目标：<文档链接；修前/修后版本或内容 hash>
- 复核日期与代码基线：<日期；相关仓库 commit/dirty；无代码调查则说明>
- 本次范围：<全部或指定条目；与原评审范围的差异>

| 问题/报告章节 | 核实结论与依据 | 最终处置 | 修改位置与关联同步 | 复核结果/后续 |
| --- | --- | --- | --- | --- |
| F-01 | <事实/目标区分；读过的证据或反证> | <状态> | <目标章节/ID，保留与原问题的映射> | <通过的文档判据或缺证/待决> |

### 决策与未完项

<明确用户选择、来源和日期、影响范围/验收；未决项的选项、后果与解除条件。>

### 修订后结论与验证

<已修订/无需修改/未采纳/未完数量；本次覆盖内的就绪判断与理由。>
<实际运行的文档检查、结果；未运行或不适用的检查及原因。>
<受影响但未授权修改的关联文档、另需实施/验收的事项。>
```

采用现有等价结构时不重复建表；同根因可合并行，但保留每个来源 ID。原报告没有 ID 的意见用稳定章节定位，不改写原编号。

## 就绪与完成边界

- PRD 关键范围、产品语义或验收未定时不能称可交接；文案修完不代表这些问题消失。无需新架构才能确定产品目标时，不强求 PRD 已有技术设计。
- 开发计划的重大范围、安全、数据、外部契约或关键 NFR 未决时是 `Blocked`；仅等非阻塞评审才用 `Proposed`；关键前置均明确才可 `Ready`。这些不是实施进度或测试状态。
- 处置记录中的「复核通过」只覆盖此次检查的断言，不改写源报告的历史总体结论，也不假称完整独立评审通过。
- 原文写入、报告回写、必要复核分别核验。任一步未完成都要明确，聊天摘要不能替代应落盘的产物；交付前回读实际文件，链接必须指向存在的文档。
