# elintp · 把事情讲清楚，而不是把读者讲低

输入：$ARGUMENTS

目标：读者看完能用自己的话把这件事讲给别人听。

## 两种输入

**输入是主题**（一个系统、一个概念、一次故障）：自己组织内容，按下面的准则写。

**输入是文档**（文件路径、链接、或直接粘进来的正文——PRD、开发计划、技术方案、评审纪要、RFC）：先完整读一遍原文，判断它是什么类型、在讲什么、定下重心，再按同一套准则重写成 HTML。产出形态、红线、写作准则全都一样，只多两层约束——**先判型再定重心**，以及**你在转述，不在创作**。

分不清用户给的是主题还是文档，就问一句，不要猜。

## 语言选择

用户没指定语言就用简体中文；用户用哪种语言提问就用哪种，文档模式下也可以从原文判断。代码、文件名、标识符保持英文。

## 红线：文档里不出现关于读者的话

只写主题本身，不写读者是谁、懂不懂、需不需要懂。下面这类句子**一句都不能出现**——正文、开场白、副标题、图注、脚注，一律算：

- 「这份说明写给不写代码的人。」
- 「面向非技术人员 / 业务同事 / 小白 / 外行 / 门外汉」
- 「你不需要懂技术也能看明白」
- 「用大白话讲 / 通俗版 / 简化版 / 人话版」
- 「简单来说，你只要记住一句话就够了」

**为什么**：这类句子对理解主题零贡献，却把整篇的定位从「解释一件事」降成「照顾一群人」，读的人会觉得被冒犯。读者的背景决定的是**你怎么写**，不是**你写什么**——它应该体现在措辞里，而不是被声明出来。

**替代做法**：开篇第一句直接给主题本身的事实或结论。

- ✗ 「这份文档写给不写代码的同事，介绍我们的消息队列。」
- ✓ 「订单提交后不会立刻扣库存，中间隔着一个排队环节，平均等待 200 毫秒。」

## 写作准则

- **先给结论，再给机制。** 每一节的第一句就是这一节的答案，后面才是它为什么成立。开篇不要铺垫，第一行就是答案。
- **一句话一个意思**；写操作步骤时，一句话一个动作。
- **主动语态，写清是谁做了什么。** 「校验拦下了这次发布」，不写「这次发布被拦下了」。
- **句子要短。** 读到一半得换口气的句子，本来就是两句。
- **一个词一个意思，一个意思一个词。** 同一个东西不要换着叫——读者会以为你在指不同的东西。
- **用现在时**，除非时间本身就是要讲的事实。
- **宁可用列表，也不要密不透风的段落**——但列表不等于可以丢掉条目之间的关系，该写清先后、因果、依赖就写清。
- **术语该用就用，但首次出现时用一句话给出含义**，紧跟在术语后面，不要道歉、不要加引号强调「这个词很专业」。实在没有通俗说法的术语，就写读者会看到什么、要做什么，术语本身在括号里出现一次。
- **代码、命令、配置项是精确字符串。** 用户要敲、要跑的东西一个字都不改，解释写在它周围。
- **类比服务于精确，不服务于亲切。** 一个类比只有在它能让读者对下一段做出正确推断时才留下；不要为了显得亲切而把事情说成儿童故事。
- **不省略读者会用到的量级。** 多快、多少、多贵、失败率多高——数字比形容词管用。
- **不确定的地方直说不确定**，不要用模糊表述糊过去。
- **篇幅目标是原文的一半以内**，除非「转述硬规则 1」或用户点名的条数不允许。

- **同一事实只说一次**，图或表已经表达的不在正文重复。
- **列表列全，不以「等」收尾**；列不全就写完整清单在哪。
- **不描述自己怎么做的**，只给结果与依据。

## 文档模式第一步：判型，定重心

拿到文档，动笔前先做两件事：

1. **判型。** 这是 PRD、开发计划、技术方案、评审纪要，还是故障复盘？
2. **定重心。** 读者读完要能回答哪几个问题？重心决定什么放前面、展开写，什么退到后面、一句带过。

**重写不是把原文逐段换个说法再过一遍。** 原文的目录是按写作者的思路排的（背景、目标、方案、排期、风险……），新文档按读者的问题排。两者的顺序本来就不该一样。

### PRD

读者要能回答：

- **会多出什么？** 用用户能看到的行为写，不写模块名。
- **做完之后系统变成什么样？** 和现在的差别在哪。
- **建议怎么实施？** 分几步、先后顺序、每一步做完能看到什么。

### 开发计划

先看计划里的记录，判断它做完了没有——勾选框、状态字段、进度回写小节、修订记录都是信号。

- **还没做完**：重心是**要开发什么**，以及**技术路线是什么**——选了哪条路，为什么是它，代价是什么。
- **已经做完**：重心是**做出了什么**、**读者怎么自己验证**（具体到点哪里、跑什么命令、看哪个数），以及**还有什么遗漏和要接着跟的**。
- **做了一半**：两段都写。先讲已完成的和怎么验证，再讲剩下的和技术路线。哪部分算完，以原文的记录为准。

计划里写着「已完成」而这次会话没有实际验证过，就写「计划记录为已完成」，不写「已经完成」——转述硬规则 3。

#### 已完成计划：补齐引用的过程记录

完成记录里引用的实施日志、里程碑记录、测试报告、验收记录等也是输入，不能只读计划里的汇总。以引用所在文档为基准解析相对路径，读完这些过程文档；如果过程文档继续引用支撑完成结论的记录，也跟进读取，同一来源只处理一次。无关链接不用展开，无法读取的引用注明缺失，不猜内容。

- **每份过程记录都生成摘要**：做了什么、关键决策或变更、验证方法与记录中的结果、问题与处理、剩余缺口。按里程碑或主题合并到最终 HTML 的过程摘要中，保留来源对应关系，不只列原文链接。过程记录同样遵守转述硬规则；来源之间的状态或结果有冲突时，注明出处和差异，不自行裁定。
- **有截图就附上**：检查过程文档中嵌入或链接的截图，查看可读取的图片，在对应摘要旁嵌入并注明它展示的步骤、结果和来源。截图只证明画面里可见的内容，不据此宣称测试通过或功能全部完成；缺失或无法查看的截图如实标注。
- **可交给 subagent**：环境支持时，把独立的过程文档分派给 subagent。提供文档路径或内容、摘要重心和转述硬规则，要求返回摘要、精确来源、截图路径及说明、无法读取的引用和未解决问题。subagent 负责分配到的材料，主 Agent 负责核对来源、合并重复内容和处理冲突，最后统一措辞、图片嵌入与 HTML 排版；没有 subagent 能力时由主 Agent 完成。

### CRD

读者要能回答：谁向谁要什么、为什么要；对方的立场与答复；已经谈定的约定；还没谈定的问题，以及下一步由谁做。

### 其他类型

技术方案、评审纪要、故障复盘等其余文档用通用模板。同样先问一句「读者读完要能回答什么问题」，再定重心。判不准类型，或者判不准计划做完没有，就问用户，不要猜。

### 重心不是丢东西的借口

重心决定的是**顺序和详略**，不决定去留。转述硬规则 1 照旧：原文的每条警告、风险、数字、前提，重心之外的也要在文档里出现——可以放到后面、压成一行，但不能没有。

## 转述硬规则（输入是文档时）

1. **只做减法，不做粉饰。** 原文里的每一条警告、风险、数字、前提条件，重写后都还在。丢掉 ⚠ 那行的「摘要」是一种谎。涉及安全、数据丢失、以及任何难以撤销的操作，展开写全，不缩写。
2. **数字原样。** 金额、数量、日期不四舍五入。指明某个动作的工单号、PR 号照抄。
3. **和原文一样真，不比原文更真。** 原文的说法仍然是说法：写「计划里说测试会全部通过」，不写「测试会全部通过」——除非这次会话里你自己验证过。
4. **不清楚的地方保持不清楚。** 原文含糊的地方就写「原文没有说」，不要靠猜把它补圆。

## 选模板，写内容稿

| 判型结果 | 模板 |
| --- | --- |
| PRD | `prd` |
| CRD 及其往返答复 | `crd` |
| 开发计划 | `plan`，按原文记录填 `progress: todo / partial / done` |
| 主题与其余文档 | `general` |

写之前读 [内容稿格式参考](references/draft-format.md)。内容稿放临时目录或项目约定的工作目录，不放文档目录；正文只写内容和数据，不写样式、版式或图形坐标。小节按模板的 slot 顺序组织；重心外但不能丢的警告、数字与前提放进 `more`。

## 产出形态：一个本地 HTML 文件

用当前读取的本 skill 目录运行（Node 18+，不依赖第三方包）：

```sh
node <skill 目录>/scripts/render.mjs <内容稿.md> <输出.html>
```

成功退出码为 0，stdout 的 `PAGE:` 给出页面绝对路径。退出码 2 表示内容稿格式有误：按 stderr 每行的行号与改法修改内容稿，再运行；不改脚本或模板绕过。出现 `WARN` 时核对缺失图片并如实交代。相对图片与图文件路径从命令的当前目录解析。

**默认写到本地，不发布。** 单文件、样式与脚本内联、不依赖外网资源，双击就能打开、也能直接当附件发出去。路径听用户的；用户没指定就放当前目录（仓库里已有 `docs/` 就放 `docs/`），文件名用主题命名，文档模式下跟着原文档的名字走。写完把路径告诉用户。

只有用户明确说了「发布 / 给个链接 / 用 Artifact」时，才改用 Artifact 工具发布（那时先载入 `artifact-design` skill）。

这份文档要靠看，不靠读；外观由固定模板提供，内容稿负责选用组件：

- **大图示**：核心流程/结构用一张占满宽度的图讲完，图能独立看懂（自带标注，不依赖正文）；用 `:::figure` 引用图。
- **关键数字做成指标块**：用 `:::metrics` 写数值、名称、含义，模板用大字号呈现数值（`200ms` 下面写「用户几乎察觉不到」）。
- **图表必须带图例和轴标签**，颜色不是唯一区分手段。
- **表格的表头带释义**：可能不自明的列名写成 `列名 :: 释义`，模板在表格下提供可用键盘展开的释义。
- 第一段结论写在小节前；补充结论和提醒用 `:::conclusion`、`:::reminder`，表格状态用 `[ok]`、`[no]`、`[warn]` 加文字，操作步骤用从 1 开始连续递增的有序列表。
- 移动端可读；宽内容自己横向滚动，页面本身不横向滚动。模板提供亮暗切换，三个及以上小节提供大纲。
- 文档模式下，正文**末尾**注明原文出处（路径或链接）和你读到的版本，方便读者回去核对。开头不写，开头留给主题本身。内容稿用 `source:` 填写，每个来源一行。

### 脚本不可用时

`node` 不存在、版本低于 18，或脚本以 0、2 之外的退出码结束时，手写单文件 HTML；不为此安装 Node。保留上面的视觉要求：大图示、指标块、图例与轴标签、表头释义、结论与提醒、符号加文字的状态、步骤、移动端阅读；样式和脚本内联、使用系统字体栈、没有外部资源。交付说明写明未使用模板及实际原因，不把格式错误当作脚本不可用。

**合并后仍是一个离线 HTML**：用 `:::figure` 的 `reader:` 引用 phoenix-diagram 交付的自包含 HTML，由脚本嵌入带标题的 `iframe srcdoc`；不使用指向另一个文件的 `iframe src`。自绘 SVG 经白名单校验后内联，写法见格式参考。截图用 `![说明](本地路径)`，脚本以 data URI 嵌入；只用已存在的本地图片，不生成图片，缺失如实标注。手写降级时也遵循相同的离线嵌入要求。嵌入区域要有足够高度和移动端宽内容滚动，不能裁掉图、标签或图例。合并后检查最终 HTML 的图和截图是否完整显示；phoenix-diagram 原图的校验结果不能代替最终页面检查。

## 交付前自检

自检对象是生成后的页面，不是内容稿；发现问题改内容稿并重新生成，再检查修改后的页面。手写降级时修正手写页面。

1. 通读全文，搜一遍有没有描述读者身份/水平的句子——有就删掉，不要改写成委婉版本，直接删。
2. 第一句话是不是主题本身的事实？如果它在介绍这份文档，重写。
3. 每张图、每个数字：去掉它，读者会不会漏掉一个结论？不会就说明它是装饰，删。
4. 找一个具体问题（「出故障时会怎样？」「这东西一天处理多少？」），看文档能不能答上来。答不上来就补。
5. 文档模式：重心里的那几个问题，文档能逐个答上来吗？答不上来的补。
6. 文档模式：把新文档的小标题和原文目录并排看——如果一节对一节、顺序基本一致，说明你只是在逐段换说法，按重心重组。
7. 文档模式再加一遍对照：原文的每条警告、风险、数字、前提，在新文档里都能找到吗？找不到的补回去。
8. 已完成的开发计划：完成记录引用的每份相关过程文档都有摘要和来源吗？可读取的截图都附在对应摘要旁了吗？缺失材料和来源冲突是否注明？
9. 属于上表的图：是否由 Agent 检查 phoenix-diagram 并在可用时调用？最终 HTML 离线打开后，嵌入的图和截图是否完整、可读？只报告实际做过的校验与检查。

交付说明固定包含：页面路径；所用模板，或未使用模板及原因；实际做过的自检项；没做或做不了的自检项；仍未解决的问题；图由 phoenix-diagram 交付还是自绘及原因；脚本输出的 `WARN`（没有就写无）。不把生成成功当作自检通过。

## 常见坑

- **用户说「没看懂」是反馈，不是质疑。** 重讲一遍就好，不要辩解、不要用同样的高度再讲一次、也不要在重讲里夹带「我当时是这么想的」。
- **重讲不是偷偷改错。** 如果重讲时发现原来写的是错的，那是一处更正，明说；不要在「更简单的版本」里悄悄换掉。
- **任务做到一半被问「等等，这是什么意思？」**：先重讲那一处，再回到原来的任务，别把线索丢了。
- **原文本来就已经写得很清楚**：说一句「原文已经够清楚了」，然后停手。为了显得有用而造一个不同的版本，是灌水。
