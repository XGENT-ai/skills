# 用量统计服务接入指引

面向**需要上报用量的 App 开发者**——你的独立后端产生了可计量的消耗（LLM token、存储字节、解析页数、AI 动作次数……），想让这些数字进入门户的租户用量页（`/admin/usage`）、平台用量页（`/console/usage`）与未来的计费体系。本文讲清：你的 App 如何按统一契约把「某租户某天用了多少 X」**推**给门户，而不必自己建聚合表、自己做管理报表。

> **用量统计是门户内置的平台级计量（metering）底座**（`apps/api/src/modules/usage/`），不是独立后端 App。它只存**日聚合**（`usage_daily` 表，长期保留、永不清理），请求级明细留在你自己的库里——对账/下钻走你的明细，计费审计走门户聚合，两边职责不重叠。设计文档见 [`goal/USAGE.md`](../goal/USAGE.md)。
>
> **本期是「计量」，不是「计费」**：门户回答「用了多少」，不回答「该收多少钱」。你上报的 `estimatedCost` 等成本类指标是参考口径，不是应收金额。计费引擎下一期在聚合数据之上加价格与账期，**不会回头改本文的采集契约**——现在照此接入，将来直接进账单。
>
> 阅读前置：[`SSO与App开发指引.md`](SSO与App开发指引.md)（TDT、scope、服务账号概念）。所有 HTTP 约定遵循 [`CLAUDE.md`](../CLAUDE.md)：业务状态不走 HTTP 状态码，一律 `200 + { ok, data | error }`。

## 1. 一图看懂接入面

```
你的独立后端 (source App)                      门户 portal-api (:3000)
┌─────────────────────────────┐
│ 你的明细表（call_logs / files…）│
│        │ 定时 worker 重聚合    │
│        ▼                     │
│ ① 自签服务态 TDT              │──► POST /api/tokens/service
│    (client_credentials,      │      Basic <SA clientId:secret>
│     scope=usage.report)      │      { grant_type, tenant_id, scope }
│        │                     │◄──   { access_token }   # 带 azp=<你的 listingKey>
│        ▼                     │
│ ② 整桶上报（绝对值，可重推）    │──► POST /api/v1/usage/report
│    { records:[{tenantId,     │      Bearer <服务态 TDT>
│      metricKey, day, dims,   │◄──   { upserted, rejected[] }
│      value}] }               │            │ upsert 覆写
└─────────────────────────────┘            ▼
                                    usage_daily（日聚合，长保留）
                                           │
                              /admin/usage · /console/usage · Dashboard widget
                                           │
                                    （下一期）计费引擎只读此表
```

接入 = **实现一个上报 worker**（①+②），零门户改动（指标目录登记除外，见 [§3](#3-指标目录与命名空间)/[§10](#10-新指标接入-checklist)）。门户不会来拉你的库——采集方向是**源 App 主动推**（push）。

已接入的两个参考实现：

| 源 App | 指标 | 模式 | 代码 |
| --- | --- | --- | --- |
| `llm-gateway` | requests / tokens.input / tokens.output / tokens.total / cost.estimated | counter + 水位线，每小时 | `apps/llm-gateway-server/src/lib/usage-report.ts` |
| `files` | storage.bytes / storage.objects | gauge + 快照，每天 2 次 | `apps/files-server/src/lib/worker.ts` |
| `sms`（学校管理） | teacher-seats.allocated / .available / student-seats.allocated / .available | gauge + 快照，每天 2 次 | `apps/sms-server/src/lib/usage-report.ts` |
| `portal`（门户自身） | seats.total / app-seats.available / app-seats.allocated | 进程内直写 | `apps/api/src/modules/usage/worker.ts` |

> **App 自管席位(seatRoles)一例 —— `sms`**：学校管理的「教师账号数 / 学生账号数」按套餐配额限制，但席位单元(教师/学生)不都是门户成员(学生走 sms 自签会话),故不用门户 `seatBased`/`mintForApp` 收口,而是 **sms-server 自身在建号时收口** + 把占用当 gauge 上报本表。配额由门户按 `(套餐 × 角色)` 发布(`app_seat_quotas.role`),sms-server 用服务态令牌(scope `seats.read`)读 `POST /api/v1/seats/quota`。这是 seatRoles 模式的参考实现,和 spms 的成员席位(`seatBased`,门户签发门收口)正交。

## 2. 核心概念：指标 / 日桶 / 幂等覆写

### 2.1 两类指标（kind）

| kind | 语义 | 计费期聚合 | 例子 |
| --- | --- | --- | --- |
| **counter** | **流量**：桶内累计发生量 | 账期内**求和** | token 数、调用次数、解析页数 |
| **gauge** | **水位**：桶内快照值 | 账期内取**峰值 / 期末** | 存储字节、对象数、席位数 |

选错 kind 会导致查询层聚合口径错误（counter 被取 MAX、gauge 被求和都是灾难），登记指标时想清楚。

### 2.2 日桶（UTC 日切）

- 粒度固定**一天一桶**，按 **UTC 日切**（`day = 'YYYY-MM-DD'`）。全平台统一，展示层可换算文案但数值桶不换时区。小时级留在你自己的明细表。
- 唯一键 = `(tenantId, metricKey, day, dimsKey)`。`dims` 是受白名单控制的维度对象（如 `{ model: "gpt-4o" }`），`dimsKey` 是门户派生的规范化串（排序后 `k=v&k2=v2`，空维度 `''`）——你不用传，门户自己算。

### 2.3 幂等覆写（最重要的心智模型）

上报体是「**桶内绝对值**」，不是增量。门户按唯一键 **upsert 覆写**：

- 同一个桶重报多少次都安全——重试、重启、补报、回放天然幂等，**无需对账游标、无需去重日志**。
- 反过来要求：你的 worker 在补报窗口内必须能**从明细整桶重算**。上报 `+N` 增量语义是错的（重试必双计）。
- 上报失败不用告警重试队列：下一轮整桶重推即自愈。

## 3. 指标目录与命名空间

### 3.1 内置目录（本期：代码登记）

指标必须先在共享目录里登记才能上报（未知指标整批拒收）。目录在 [`packages/shared/src/usage.ts`](../packages/shared/src/usage.ts) 的 `USAGE_METRICS`：

```ts
interface UsageMetricDef {
  key: string;            // 'llm-gateway.tokens.total' —— 前缀必须 = 你的 listingKey（§3.2）
  appKey: string;         // 来源 App：'llm-gateway' | 'files' | 'portal' | <你的 listingKey>
  kind: "counter" | "gauge";
  unit: "tokens" | "bytes" | "count" | "microUSD";
  dims: string[];         // 允许的维度键白名单，如 ['model']；上报越界键整批拒
  label: { zh; en; tw };  // 三语展示名（用量页 / 排行 / CSV 都用它）
}
```

> 目前 4 个源（llm-gateway / files / sms / portal），目录走代码常量（改目录 = 改门户代码 + 重启 api，见 [§10](#10-新指标接入-checklist)）。App manifest 声明式注册已在设计上预留，后续接入连门户代码都不用改。

#### `portal.*` 门户内置指标（进程内直写，非 HTTP 上报）

门户自身的水位由 `apps/api/src/modules/usage/worker.ts` 的 6h 快照进程内直写（无需服务账号 / 上报契约）：

| key | kind | unit | dims | 说明 |
| --- | --- | --- | --- | --- |
| `portal.seats.total` | gauge | count | —— | 租户 active 成员数（人头水位） |
| `portal.app-seats.available` | gauge | count | `app`（= 席位制 App 的 listingKey） | 可用席位 = 套餐配额 + 加购；**`unlimited` 套餐不上报此指标**（gauge 表达不了 ∞，缺行即「无上限」） |
| `portal.app-seats.allocated` | gauge | count | `app` | 已分配席位（join active membership，幽灵不计；装了没分配显式报 0） |

> 席位指标（USAGE-2）随席位制 App 自动出现在 `/admin/usage`、`/console/usage` 与 CSV，读侧零改动。**展示要点**：usage summary 对目录内指标总会返回一项，`unlimited` 租户的 `available` 长成 `last:null`——前端须结合租户 `plan`（MeDTO 已带）把 null 渲染成「∞ / 无上限」，**严禁**显示成 0 或空态；capped 套餐的 null 才是真「暂无数据」。计费口径：账单可直接取 `available`（购买口径）或 `allocated`（使用口径）的月度 gauge 聚合。

### 3.2 命名空间强制 = 上报者身份（防伪造）

`metricKey` 前缀（第一个 `.` 之前）**必须等于你令牌的 `azp`**（= 服务账号绑定的 App listingKey）：

- `llm-gateway.*` 只能由 llm-gateway 的 SA 上报；files 的 SA 报 `llm-gateway.tokens.total` → 整批拒收。
- `portal.*` 由门户进程内直写，不走 HTTP，外部永远报不了。
- 这是计费数据，完整性优先——**没有任何 header / 参数可以绕过**。

### 3.3 成本即指标，不是特殊列

想带成本就再报一条独立的成本指标（如 `llm-gateway.cost.estimated`，unit=`microUSD`（百万分之一美元）、kind=counter），表结构永远「一行一个数」。**不要**把成本塞进别的指标的 dims。

### 3.4 dims 白名单：防高基数

`dims` 键必须在指标声明的白名单内，值为 1–120 字符的字符串。白名单存在的意义是防高基数维度打爆聚合表——**不要**把 userId、requestId、时间戳这类无界值当维度（成员级用量留在你自己的 App 页面做；门户日桶只到租户 × 少量业务维度）。

## 4. 前置准备：服务账号三件套

上报身份复用你已有的 M2M 服务账号（就是你调门户自省用的那个），需要**三个增量**：

| 项 | 值 | 作用 |
| --- | --- | --- |
| capabilities | += `client_credentials` | 允许自签服务态 TDT |
| scopes | += `usage.report` | 上报端点的 scope 门 |
| ownerAppKey | = 你的 **listingKey** | 服务态令牌带 `azp`（上报者身份，[§3.2](#32-命名空间强制--上报者身份防伪造) 的命名空间校验依据） |

配置方式（三选一）：

1. **平台内置 App**：在 [`apps/api/src/db/provisioning.ts`](../apps/api/src/db/provisioning.ts) 的 `SA_DEFS` 给你的条目加 `usageReporter: { ownerAppKey: "<listingKey>" }`。`ensureServiceAccount` 对**已存在的 SA 幂等补齐**这三件套——`bootstrap:prod` / `provision:global` / 按需部署重跑即自动升级，不动密钥。
2. **dev 种子**：destructive 主种子（`seed.ts`）或你的非破坏性增量种子里，插入/升级 SA 时带上三件套（参考 `seed-llm-gateway.ts` 的 upgrade-in-place 写法）。
3. **手工**：平台控制台 `/console/service-accounts` 编辑该 SA——能力勾 `client_credentials`、scope 加 `usage.report`、「归属应用」填 listingKey。

> **铸币时的安装校验**：`ownerAppKey` 非空的 SA 为某租户签服务态令牌时，门户会校验该 App 在**那个租户**已安装且 `active`，否则拒签（`APP_NOT_INSTALLED` / `APP_DISABLED`）。所以你只能为「装了你的 App 的租户」上报——这是特性不是限制（没装你的 App 的租户不该有你的用量）。

## 5. 上报契约：POST /api/v1/usage/report

### 5.1 第一步：换服务态令牌（按租户）

```
POST {PORTAL_API}/api/tokens/service
  Authorization: Basic base64(<SA clientId>:<SA secret>)
  Content-Type: application/json
  { "grant_type": "client_credentials", "tenant_id": "<租户UUID>", "scope": "usage.report" }
→ 200 { ok:true, data: { access_token, token_type:"Bearer", expires_in, scope } }
```

- 令牌是**租户维度**的——你的 worker 服务全租户时，按租户分批：每租户铸一把、报一批（参考实现都这么做）。
- **务必检查返回的 `data.scope` 含 `usage.report`**：SA 还没授权时铸币不会报错，只会返回空 scope 的令牌（交集语义）。此时应视为**可重试失败**（管理员补授权后自动恢复），而不是永久跳过——两个参考实现的 `mintUsageToken` 都是这个语义，照抄。
- `APP_NOT_INSTALLED` / `APP_DISABLED` / `TENANT_NOT_ALLOWED` 才是**该租户的永久跳过**（响亮 log 后继续别的租户，别让一个租户卡死全体）。

### 5.2 第二步：整批上报

```
POST {PORTAL_API}/api/v1/usage/report
  Authorization: Bearer <服务态 TDT>
  Content-Type: application/json
{
  "records": [
    { "tenantId": "<租户UUID>", "metricKey": "llm-gateway.tokens.total",
      "day": "2026-07-03", "dims": { "model": "gpt-4o" }, "value": 183204 },
    { "tenantId": "<租户UUID>", "metricKey": "llm-gateway.requests",
      "day": "2026-07-03", "dims": { "model": "gpt-4o" }, "value": 42 }
  ]
}
→ 200 { ok:true, data: { "upserted": 2, "rejected": [] } }
```

规则（全部硬性）：

| 规则 | 说明 |
| --- | --- |
| **仅服务态令牌** | 用户态 TDT 一律 `403 FORBIDDEN`；令牌必须带 `azp`（SA 没绑 `ownerAppKey` 也是 403） |
| **单批 ≤ 500 条** | `USAGE_REPORT_MAX_RECORDS`；超了拆批 |
| **all-or-nothing** | 任何一条不合法 → **整批拒收**（`upserted:0`，`rejected` 逐条列 `{index, reason}`）。校验拒收是确定性的——同样的数据重试不会变好，修数据再整桶重推 |
| `metricKey` | 必须在目录内，且前缀 = 你的 `azp` |
| `day` | `YYYY-MM-DD`（UTC），**不能是未来** |
| `value` | 非负安全整数（`Number.isSafeInteger`）。字节/微美元都用整数 |
| `dims` | 键 ⊆ 指标白名单；值为 1–120 字符的非空字符串；可省略（= 空维度） |
| `tenantId` | 必须存在；**平台租户不参与计量**（会被拒） |
| 限流 | 与其它 Open API 共用 `(aud, tenant)` 每分钟桶，额度按租户套餐（标准 120 / 专业 300 / 旗舰 600，`PLAN_RATE_LIMITS`）。批量上报每租户每轮只有零星几个请求，完全够用 |

**成功判定**：`body.ok === true && body.data.upserted === records.length`。收到 `rejected` 非空说明你的数据或配置有 bug——**响亮 log 全文**，别静默吞。

## 6. Reporter 实现模式一：counter + 水位线（参考 llm-gateway）

适用：流量类指标，明细落在你自己的事件/日志表，且**迟到写入**可能落在日切附近。权威实现 [`apps/llm-gateway-server/src/lib/usage-report.ts`](../apps/llm-gateway-server/src/lib/usage-report.ts)（每小时跑）。

```
① 读持久化水位线 watermark（最后一个「已确认整批上报成功」的 UTC 日；
   首启初始化为昨天。llm-gateway 存自己库的 gateway_worker_state KV 表）
② 对明细表按 UTC 日切整桶重聚合 [watermark, 今天]：
   SELECT tenant_id, to_char((created_at AT TIME ZONE 'UTC')::date,'YYYY-MM-DD') AS day,
          <维度>, count(*) …, coalesce(sum(<量>),0) …
   GROUP BY tenant_id, day, <维度>
③ 按租户铸令牌 → ≤500/批整桶上报
④ 本轮全部成功（无可重试失败）→ 水位线推进到【昨天】；
   今天的桶保持开放，下一轮继续覆写（捕捉当天后续流量）
```

要点（每条都是踩过的坑）：

- **水位线只在全绿后推进**。任何可重试失败（门户不可达、5xx、SA 缺授权）都保持水位线不动——宕机三天，恢复后第一轮自动补报缺口内全部日桶。「窗口滑过即永久丢失」在计费底座上不可接受。
- **watermark 当天也重推**（区间含端点）：捕捉日切附近的迟到写入。正常稳态就是每轮「昨天 + 今天」两桶。
- **补报深度受明细保留期约束**：缺口超出保留期时，按现存数据上报并 **log 缺失天数**（不静默）。
- **聚合 SQL 用 `to_char(... ,'YYYY-MM-DD')` 出字符串**，别用裸 `::date`——postgres-js 会把 date 解析成 JS `Date`，序列化后过不了 `day` 校验，整批被拒。
- **每桶报齐一组指标**：llm-gateway 每个 `(tenant, day, model)` 桶产出 5 条记录（requests / tokens.input / tokens.output / tokens.total / cost.estimated）；成本为 null 的明细行计 0 照常求和。
- **回放/一次性补报**：手动把水位线调低到目标日期，跑一次触发脚本即可（幂等覆写保证安全）。llm-gateway 的钩子：`apps/llm-gateway-server/scripts/report-usage-once.ts`。
- worker 从 `index.ts` 启（不是 `createApp`），verify 脚本驱动 `app.handle()` 时不拉起定时器——沿用你后端既有惯例。

## 7. Reporter 实现模式二：gauge + 快照（参考 files）

适用：水位类指标，任意时刻可以从库里直接算出「现在的总量」。权威实现 [`apps/files-server/src/lib/worker.ts`](../apps/files-server/src/lib/worker.ts)（每天跑 2 次——快照幂等，跑两次防单次失败，无需水位线）。

```
① 按租户聚合当前水位：
   SELECT tenant_id, coalesce(sum(size),0), count(*) FROM files
    WHERE status='active' GROUP BY tenant_id     -- dims {kind:'files'}
   （renditions 同理 → dims {kind:'renditions'}）
② 按租户铸令牌 → 上报【今天】的桶（gauge 语义 = 当日最后快照值）
```

要点：

- **声明了的维度要报齐**：`files.storage.*` 声明了 `kind` 维度，即使某租户没有 renditions 也要**显式报 0**——否则对象数与 CSV 导出口径残缺。
- **清空也要报零**：租户删光最后一个对象后聚合查询不再出这行，但你必须仍为它推零值桶，否则门户会把昨天的水位当成「当前」。files 的做法：快照租户集合 = 聚合行 ∪ **所有配过存储的租户**（`storage_configs`）。你的等价物是「所有启用过你的 App 的租户」。
- **峰值口径由查询层保证**，你只管报快照：门户对 gauge 先把同日多维度行求和成「当日总量」，再取期末 + 峰值。你不需要（也不应该）自己算峰值。
- 手动触发钩子：`apps/files-server/scripts/snapshot-usage-once.ts`。

## 9. 查询与展示（你不用做,但要知道数字去了哪）

你的数字上报后自动出现在：

| 面 | 路径 | 内容 |
| --- | --- | --- |
| 租户管理员 | `/admin/usage`（导航「管理 → 用量统计」） | 时间范围 + 概览卡 + LLM/存储/全部指标 Tab + 按维度日曲线 + CSV 导出 |
| 平台管理员 | `/console/usage`（导航「平台 → 平台用量」） | 全平台概览 + 指标切换的租户排行（分页）+ 单租户下钻 + 跨租户 CSV |
| 工作台 | Dashboard widget「用量统计」 | 本月 token + 存储水位，仅租户管理员可见，点击跳 `/admin/usage` |

读侧 API（`assertAdmin` / `assertPlatformSession` 会话态，你的 App 一般不用调）：

```
GET /api/admin/usage/summary?from&to          # 期内汇总：counter 求和；gauge 期末+峰值（先按日合维度）
GET /api/admin/usage/series?metricKey&from&to&dim=<维度>   # 按日序列，top-8 维度 + __other__ 归并（归并数注明）
GET /api/admin/usage/export?from&to           # CSV（text/csv 直出，非信封）
GET /api/console/usage/overview?from&to
GET /api/console/usage/tenants?metricKey&from&to&page&pageSize   # Page<T> 契约
GET /api/console/usage/tenants/:tenantId/summary|series
GET /api/console/usage/export?from&to
```

聚合口径（写进 verify 的防回归断言，理解它有助于自查数字）：**counter → SUM(value)**；**gauge → 先把同日多维度行求和成「当日总量」，再取期末值（最后一日总量）+ 峰值（日总量的 MAX）**。直接对行取 MAX 会拿到最大的单一维度分量而非总水位——门户不会犯这个错，你自查 SQL 时也别犯。

页面明示「统计截至 <最后上报时间> · UTC 日切」——小时级滞后是**预期行为**（你的 reporter 周期决定），不用做成实时。

## 11. 拒收与错误目录

认证/传输错误与上报入口业务失败：

业务失败统一是 `HTTP 200 + { ok:false, error:{ code } }`；只有真正的认证/传输错误使用非 200。客户端必须同时检查 `body.ok` 和 `error.code`，不要只按 HTTP status 分支。

| code | HTTP | 场景 |
| --- | --- | --- |
| `UNAUTHENTICATED` | 401 | 缺 Bearer 令牌 |
| `TOKEN_EXPIRED` / `INVALID_TOKEN` / `TOKEN_REVOKED` | 401 | 令牌过期 / 无效 / SA 被禁用或轮换（`saVersion` bump） |
| `INSUFFICIENT_SCOPE` | 403 | 令牌没有 `usage.report`（多半是 SA 没授权→铸出空 scope 令牌，[§5.1](#51-第一步换服务态令牌按租户)） |
| `FORBIDDEN` | 403 | 用户态令牌调上报；或服务态令牌缺 `azp`（SA 没绑 `ownerAppKey`） |
| `VALIDATION_FAILED` | 200 | 缺 `records` / 超 500 条 |
| `RATE_LIMITED` | 200 | 触发 `(aud, tenant)` 限流；响应为 `ok:false` 业务错误信封 |

铸币层（`POST /api/tokens/service`，业务失败 `200 + error`）：

| code | 场景 | 你该 |
| --- | --- | --- |
| `CAPABILITY_NOT_GRANTED` | SA 没有 `client_credentials` 能力 | 补配置（[§4](#4-前置准备服务账号三件套)），可重试 |
| `TENANT_NOT_ALLOWED` | SA 被钉在租户白名单外 | 该租户永久跳过 |
| `APP_NOT_INSTALLED` / `APP_DISABLED` | 你的 App 未装/停用于该租户 | 该租户永久跳过（响亮 log） |

上报层逐条拒收 reason（`200 + { upserted:0, rejected:[{index, reason}] }`，**整批生效**）：

| reason（要点） | 原因 |
| --- | --- |
| `未知指标 <key>` | 没在 `USAGE_METRICS` 登记（或 api 没重启） |
| `指标 <key> 不属于上报者 <azp> 的命名空间` | metricKey 前缀 ≠ 你的 listingKey（[§3.2](#32-命名空间强制--上报者身份防伪造)） |
| `day 必须是 UTC 日期 YYYY-MM-DD` / `day <d> 在未来（UTC）` | 日期格式/未来日（注意 [§6](#6-reporter-实现模式一counter--水位线参考-llm-gateway) 的 `to_char` 坑） |
| `value 必须是非负整数` | 负数 / 小数 / 溢出 |
| `维度 <k> 不在指标 <key> 的白名单 [...]` | dims 越界键 |
| `维度 <k> 的值必须是 1–120 字符的字符串` | dims 值类型/长度 |
| `未知租户 <id>` | tenantId 不存在（脏数据防线：**整批**拒，不静默丢） |
| `平台租户不参与用量计量` | 报了平台租户 |

## 12. 本地开发与联调

### 12.1 环境变量（你的后端侧）

上报只依赖你后端**已有**的 SA 凭证与门户地址，无新增专属变量：

```bash
API_BASE_URL=http://localhost:3000                    # 门户 Open API 基址（铸币 + 上报都用它）
<你的前缀>_SA_CLIENT_ID=your-app-server               # 已有：自省同一个 SA
<你的前缀>_SA_CLIENT_SECRET=…                         # 优先；dev 缺省回退 <前缀>_RESOURCE_KEY
<你的前缀>_USAGE_REPORT_INTERVAL_MS=3600000           # 可选：worker 间隔（如需要）
```

### 12.2 把本地 SA 授权补上

本地库是老数据时（SA 还没有 `usage.report`），三选一：重跑 `bun run db:seed` 链（destructive）；重跑你的非破坏性增量种子；或最快——一行脚本调 `ensureServiceAccount`：

```bash
cd apps/api && bun --env-file=../../.env --env-file=../../.env.local -e "
import { ensureServiceAccount } from './src/db/provisioning';
await ensureServiceAccount('<你在 SA_DEFS 里的 key>'); process.exit(0);"
```

### 12.3 联调闭环（5 分钟）

```bash
bun run dev:all                                        # 起全栈（别单独叠跑某个 dev:<app>，见 CLAUDE.md）
# ① 在你的明细表造几行今天的数据（或真实操作你的 App 产生消耗）
# ② 手动触发你的 reporter（示例是 llm-gateway 的）：
cd apps/llm-gateway-server && bun --env-file=../../.env run scripts/report-usage-once.ts
# ③ 看门户：以租户管理员登录 → /admin/usage → 你的指标应出现在「全部指标」Tab
# ④ 再触发一次 → 数字不变（幂等覆写）
```

回归套件：`cd apps/api && bun run verify:usage`（契约层 + llm-gateway 对账 + files 快照 + 零值桶，40+ 断言）；全量冒烟 `bun run verify:all`（reseed 后必跑）。

### 12.4 常见症状速查

| 症状 | 多半是 |
| --- | --- |
| 铸币成功但 `scope` 为空 → 上报 403 `INSUFFICIENT_SCOPE` | SA 没授 `usage.report`（[§12.2](#122-把本地-sa-授权补上)）。reporter 应视为可重试，别推进水位线 |
| 上报 403 `FORBIDDEN`（服务账号未绑定所属应用） | SA 缺 `ownerAppKey` |
| 铸币 `APP_NOT_INSTALLED` | 该租户没装你的 App（本地常见于新建的测试租户——先去应用市场装） |
| `rejected: day 必须是 UTC 日期` | SQL 里 `::date` 被驱动解析成 JS Date（用 `to_char`） |
| 数字比预期大/小一天 | 你的聚合没按 UTC 切日（`created_at AT TIME ZONE 'UTC'`） |
| `/admin/usage` 数字滞后 | 预期行为——reporter 周期决定，页面有「统计截至」标注 |
| 门户数字 ≠ 你明细求和 | 先对齐口径：UTC 日切？成功+失败都计？null 成本计 0？再手动触发 reporter 覆写 |

## 附录 A：类型参考（DTO）

权威定义见 [`packages/shared/src/usage.ts`](../packages/shared/src/usage.ts)（前后端同一份）：

```ts
const USAGE_REPORT_MAX_RECORDS = 500;

interface UsageReportRecord {              // 上报体的一条 = 一个桶的绝对值
  tenantId: string;                        // 租户 UUID（逐行带，源 App 服务全租户）
  metricKey: string;                       // 前缀 = 你的 listingKey
  day: string;                             // 'YYYY-MM-DD'，UTC
  dims?: Record<string, string>;           // ⊆ 指标白名单；省略 = 空维度
  value: number;                           // 非负安全整数，桶内绝对值
}
interface UsageReportResult { upserted: number; rejected: Array<{ index: number; reason: string }>; }

// 读侧（你一般用不到，供对账自查）
interface UsageSummaryMetric {
  metricKey: string; appKey: string; kind: "counter" | "gauge";
  unit: "tokens" | "bytes" | "count" | "microUSD";
  label: { zh: string; en: string; tw: string };
  total: number | null;                    // counter：期内求和
  last: number | null; peak: number | null;// gauge：期末 / 日总量峰值
}
interface UsageSummaryDTO { from: string; to: string; metrics: UsageSummaryMetric[]; updatedAt: string | null; }
interface UsageSeriesDTO {
  metricKey: string; kind: string; unit: string;
  days: string[];                          // [from..to] 逐日，零填充
  series: Array<{ name: string; data: number[] }>;  // name 哨兵：__other__（top-8 外归并）/ __unlabeled__（空维度值）
  mergedDims: number;                      // 归并进「其他」的维度数（不静默截断）
}

function usageDimsKey(dims): string;        // 规范化 dimsKey（排序 k=v&…），门户与测试共用
```
