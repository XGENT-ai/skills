# 因子表与档位刻度

> 这份文件是本 skill 的**判定标准**。所有规则只有一个设计目标:**三个人拿同一个输入包,数出同一个因子向量。**
>
> 因此每条规则都写成「命中当且仅当输入包里逐字出现 X」的形式。凡是需要"感觉一下体量"的措辞,都是缺陷,发现即修。
>
> **这套刻度是绝对的,不靠任何项目的历史点数支撑,也不绑定任何代码库、语言或框架。** 因子命中的是可核对的事实(技术影响说明的某个字段是否为「无」、验收标准里有没有某个词),命中数到档位的映射写死在 §3。一个刚立项、一条历史需求都没有的项目,照样能用这张表估出与老项目可比的点数。历史点数怎么用见 §7,一句话:**只用于事后观测因子表本身准不准,永远不参与单条判定。**
>
> 目录:§1 输入包 · §2 因子表(四轴十六因子) · §3 命中数 → 点数 · §4 `unknown` · §5 输出结构与比对口径 · §6 非代码交付物 · §7 档位含义与历史点数 · §8 判定溢出 · §9 样例(通用业务场景) · §10 可选:文件清单 → 影响说明的路径映射

## 1. 输入包(判定的全部依据)

| 输入 | 必需 | 来源 |
| --- | --- | --- |
| 标题 + 正文 + **验收标准**(逐条编号 AC1..ACn) | ✅ | `requirement_get`;工单经关联需求取,或由调用者显式给出 |
| **技术影响说明**(§1.1 的九个字段) | ✅ | 已批准的开发计划(改动面 / 数据模型与迁移 / 集成与契约 / 前端 各节),或调用者按模板显式给出 |
| 代码基线(commit 或版本号) | ✅ | 判定依据要能回溯到同一份代码 |

**判定只看这些,而且只看字面(§2.0)。** 需求正文(`description`)**整段都不是判定依据**——"这个改动挺大的""要重构一遍"这类形容词固然不算,连正文里写着"幂等""并发"也不算。文本侧被用到的只有**标题**和**验收标准里逐字出现的关键词**。

缺技术影响说明 → **不估点**,报「输入不足」。(非代码交付物走 §6,不需要影响说明。)

⛔ **「这个项目没有历史点数」不是输入不足。** 输入包里没有「历史点数」「团队吞吐」「同类需求以前打了几分」这一项,**它们也不允许被当作判据**。

### 1.1 技术影响说明(固定九字段)

这九个字段是复现性的装置:**每个字段直接对应一条因子**,填「无」就是不命中,填了内容就是命中,没填就是 `unknown`。它与代码库形态无关——单体、多仓、微服务、无服务器都能填。

| 字段 | 填什么 | 对应因子 |
| --- | --- | --- |
| **发布单元** | 本次要改动的、可独立发布的单元列表(如「订单服务」「商家后台前端」「小程序」;同一个部署包内的前后端算一个) | C1 |
| **服务端** | 无 / 新增或修改的接口与业务规则(逐条) | T1 |
| **数据模式** | 无 / 新表、新列、新索引、改类型——凡需要 DDL 或迁移脚本的 | T2 |
| **前端** | 无 / 修改既有页面(写明哪个)/ **新增**页面或**新增**可复用组件(写明哪个) | T3 |
| **外部集成** | 无 / 新接入或改协议的外部系统(支付通道、短信、邮件、身份提供方、对象存储、第三方 API、消息队列…) | T4 |
| **运行环境** | 无 / 新定时任务、新队列消费者、新服务进程、新配置项或环境变量、部署拓扑变化 | T5 |
| **不变量** | 无 / 事务、行锁、幂等键、唯一约束、并发控制、鉴权闸——写明哪个 | C2 |
| **存量数据** | 无 / 需要一次性回填、迁移或清洗的存量数据——写明什么 | C3 |
| **契约变更** | 无 / 被其他模块或系统消费的接口、事件、数据格式的变化——写明消费方 | C4 |

三个填写规则:

- **「无」要明写。** 字段留空、没提、写「待定」都按**未说明**处理 → 对应因子进 `unknown`(§4),不能替调用者补一个「无」。
- **调用者给的是文件清单而不是这张表时**,先按 §10 的路径映射把清单**转写**成九字段(逐字段引用清单原文),再判定;映射覆盖不到的字段(不变量 / 存量数据 / 契约变更 / 外部集成 / 运行环境)只认清单里的**说明文字**,没有就是未说明。
- **修改既有 ≠ 新增。** 「前端」字段只有写明**新增**页面或**新增**组件才命中 T3;改十个既有页面也不命中——它量的是"用户可见面是否变多",不是改动量。

## 2. 因子(命中即 +1)

### 2.0 判定的字面性原则(先读这条,它管着下面十六条)

**只看字面,不做推断。** 一条因子命中,必须能指着输入包里的**一处原文**说"就是它":

- **清单侧** = 技术影响说明的某个字段的**原文**;
- **文本侧** = 需求**标题**,或**验收标准**的某一条(AC 编号)。

三条硬规则:

1. **正文(`description`)不是判定依据。** 正文是背景叙述,里面出现的词(哪怕写着"幂等""退款")**一律不计命中**——判据只认标题与验收标准。
2. **语义等同不算命中。** 「不重复发送」≠「幂等」,「同时点两下」≠「并发」,「拿回钱」≠「退款」。要么逐字命中关键词表,要么不命中。
3. **推断不算命中。** 「这种改动大概要开事务」「登录肯定得存令牌」——**不计**;输入不足以判定时走 §4 的 `unknown`。

这三条是复现性的地基:同一份输入,三个人**指着同一处原文**才会数出同一个向量。

### 2.1 领域轴(D):这个功能点属于哪类业务 —— 证据来自**标题 + 验收标准**

领域轴量的是**业务本身的固有风险**:同样"加一个接口",碰钱、碰权限、碰状态机、碰统计口径的,出错代价与验证成本天然更高。

| 因子 | 命中当且仅当(标题或任一 AC 里**逐字**出现) | 明确**不**命中的情形 |
| --- | --- | --- |
| **D1** 资金 · 计费 · 配额 | 金额 / 价格 / 费用 / 计费 / 扣费 / 付款 / 支付 / 退款 / 结算 / 对账 / 发票 / 余额 / 积分 / 配额 / 额度 / 优惠券 / 折扣 | 只在正文里出现;「成本」「预算」这类管理词汇(不是交易语义) |
| **D2** 身份 · 权限 · 安全 | 登录 / 登出 / 注册 / 鉴权 / 认证 / 单点登录 / SSO / 验证码 / 角色 / 权限 / 越权 / 令牌 / token / 密码 / 加密 / 脱敏 / 审计 / 403 | 「管理员可以…」这类只是主语带了角色名而不涉及权限判定的——**D2 看的是权限本身是否为验收对象**;角色名的多寡归 V3 |
| **D3** 状态流转 · 审批 · 生命周期 | 审批 / 审核 / 驳回 / 撤回 / 撤销 / 作废 / 归档 / 生效 / 失效 / 过期 / 流转;或「状态」与 变为 / 改为 / 置为 / 回退 / 从…到 连用 | 「加载状态」「空状态」「禁用状态」这类 UI 状态;只有一个开关字段的启停 |
| **D4** 统计 · 报表 · 聚合 | 统计 / 汇总 / 报表 / 图表 / 趋势 / 排名 / 排行 / 聚合 / 合计 / 导出 / 占比 / 环比 / 同比 | 列表的简单计数(「显示共 N 条」);排序与筛选 |

### 2.2 技术栈轴(T):碰了哪些技术层 —— 证据来自**技术影响说明**

| 因子 | 命中当且仅当 | 明确**不**命中的情形 |
| --- | --- | --- |
| **T1** 服务端逻辑 | 「服务端」字段非「无」 | 只改数据模式而无逻辑;只改前端;只改脚本或配置 |
| **T2** 数据模式变更 | 「数据模式」字段非「无」(需 DDL / 迁移脚本) | 往既有 JSON 类列里加键;只改 ORM 模型注释;只加种子数据 |
| **T3** 新页面或新可复用组件 | 「前端」字段写明**新增**页面或**新增**组件 | 修改既有页面 / 组件(不论改多少);新增的是工具函数、状态仓库、类型文件 |
| **T4** 外部系统集成 | 「外部集成」字段非「无」(新接入,或改既有集成的协议 / 版本 / 凭据方式) | 调用一个**已经封装好**的既有集成(只是多调一次) |
| **T5** 运行环境变更 | 「运行环境」字段非「无」 | 只改既有配置项的**值**;只改日志文案 |

### 2.3 复杂程度轴(C):改动的结构性难度 —— 证据来自**技术影响说明**

| 因子 | 命中当且仅当 | 明确**不**命中的情形 |
| --- | --- | --- |
| **C1** 跨 ≥2 个可独立发布单元 | 「发布单元」字段列出 ≥2 个 | 前后端在**同一个**部署包内(算一个);只有一个服务 |
| **C2** 并发 · 幂等 · 事务 · 安全不变量 | 「不变量」字段非「无」 | 只在验收标准里出现「并发」字样而影响说明写「无」——**验收侧的并发要求归 V2**,C2 只认实现侧是否真引入了不变量 |
| **C3** 存量数据一次性处理 | 「存量数据」字段非「无」 | 运行期的对账 / 修复逻辑(每次请求都跑的,不是一次性);只加有默认值的新列 |
| **C4** 公共契约变更 | 「契约变更」字段非「无」(写明了消费方) | 新增一个**只有本次前端消费**的接口;向后兼容地**新增**可选字段而无消费方需跟改 |

### 2.4 验收复杂度轴(V):验证它要花多大力气 —— 证据来自**验收标准**

| 因子 | 命中当且仅当 | 明确**不**命中的情形 |
| --- | --- | --- |
| **V1** 验收标准 ≥ 6 条 | 按逐条编号计,AC 条数 ≥ 6 | 一条里用顿号并列了六件事(那是写得不合格,不是六条;可在汇报里提示改写) |
| **V2** 含非功能断言 | 任一 AC 里出现**带单位的量化指标**(秒 / 毫秒 / ms / QPS / TPS / 万条 / 万行 / MB / 并发数 …),或逐字出现 响应时间 / 吞吐 / 兼容 / 降级 / 可用性 / 离线 / 弱网 | 「不卡顿」「体验流畅」(无法断言,也不命中——可在汇报里提示改写) |
| **V3** 多角色 · 多端 · 外部环境 | 任一满足:① 验收标准里逐字出现 **≥2 个不同的角色名**(泛称「用户」不计;如 申请人 / 审批人、教师 / 学生、买家 / 卖家);② 出现 ≥2 种终端或触达渠道(PC / 移动端 / 小程序 / App / 邮件 / 短信 / 推送);③ 出现 沙箱 / 真实第三方 / 联调 / 生产环境 / 线上环境 | 一个角色贯穿始终;只提一种终端 |

## 3. 命中数 → 点数

```
0 → 1    1 → 2    2 → 3    3–5 → 5    6–9 → 8    ≥10 → 13
```

档位是斐波那契,**没有 4 分、没有 6 分**,也不允许"5 到 8 之间取个 6.5"。

**这个映射是全局常量**,不按项目 / 团队 / 技术栈调参。**13 分档位自带一条提示**:十个以上的面同时被触到,通常已经超出一个迭代条目应有的粒度——汇报里附「建议拆分后再排期」,但**不替人拆**。

## 4. `unknown` 处理(强制)

某条因子按 §2 **无法判定**时(影响说明的对应字段未说明、工单没有验收标准、文件清单映射不到某字段):

1. **不计命中**(不许用"大概会改"补);
2. 把该因子号写进输出的 `unknown[]`;
3. **`unknown` 非空时,点数标注为「下限」**,并在汇报里写清楚**缺哪个字段的哪句话**才能定——通常调用者补一句「不变量:无」就够了。

`unknown` 里的因子**不出现在 `evidence`**——没有证据才叫 unknown。

**工单(Issue)没有验收标准时**:文本侧证据整体缺失——V1–V3 进 `unknown`;D1–D4 只按**标题**判,标题不命中的也进 `unknown`(少了一整个证据面,没资格下"不命中"的结论)。清单侧九个字段照常判。

## 5. 输出结构(逐字段比对用)

```json
{
  "points": 8,
  "matchedFactors": ["C1", "C2", "D2", "T1", "T2", "T4"],
  "unknown": [],
  "evidence": {
    "C1": ["影响说明.发布单元: 「身份服务、管理后台前端」"],
    "C2": ["影响说明.不变量: 「外部账号与本地账号绑定表加唯一约束(provider, external_id)」"],
    "D2": ["标题: 「企业微信扫码登录」", "AC1: 「…登录后…」"],
    "T1": ["影响说明.服务端: 「新增 OAuth 回调接口 + 账号绑定逻辑」"],
    "T2": ["影响说明.数据模式: 「新表 external_identities」"],
    "T4": ["影响说明.外部集成: 「企业微信 OAuth2」"]
  }
}
```

- `matchedFactors` 与 `unknown` **按字母序再按数字升序**排列(C → D → T → V;否则"集合相同"要靠人眼比对);
- `evidence` 每条写成 `「来源」: 「原文摘录」`,来源只有三种形态:`标题`、`AC<n>`、`影响说明.<字段名>`。**列出该因子命中的全部来源**(关键词在标题和三条 AC 里都出现,就写四条),不是只写第一处——来源集合是比对对象,漏一处就是不一致。摘录是给人核对用的,**比对时只看来源**。

**输出里没有「参照的历史需求」这一项,也没有「同类需求以前打几分」**——点数完全由因子向量经 §3 的常量映射得出。要判断"这个数合不合理",看 §7 的档位含义,那是跨项目通用的。

汇报时可以另附一行**四轴分布**(如「领域 1 · 技术栈 3 · 复杂度 2 · 验收 0」)帮人一眼看出难在哪——它由 `matchedFactors` 直接算出,**不参与比对**。

### 逐字段比对口径(三会话复现性用)

四个字段**全部**参与比对,缺一不可:

| 字段 | 比对方式 |
| --- | --- |
| `points` | 数值相等 |
| `matchedFactors` | **集合**相等 |
| `unknown` | 集合相等 |
| `evidence` | **逐因子比对来源集合**——剥掉「原文摘录」,只比 `标题` / `AC<n>` / `影响说明.<字段>` 这些来源标签;顺序不计 |

只比 `points` 不算过——**三次靠不同因子凑出同一档,是复现性假象**。

## 6. 非代码交付物(文档、流程规范、配置模板、操作手册)

没有技术影响说明,不走 §2,走三因子——**每条都在估点当时可判定**(不含"几轮实测才稳定"这类只有做完才知道的未来信息):

| 因子 | 命中当且仅当 |
| --- | --- |
| **N1** | 需要**新定义**一套可复现的判定标准或操作规范(而非复述既有约定) |
| **N2** | 需要经工具**写回并复核闭环**(不只是产出文本) |
| **N3** | 验收含「多次 / 多人 / 多会话运行结果一致」这类**须实测复现**的断言 |

```
0 → 1    1 → 2    2 → 3    3 → 5
```

## 7. 档位的绝对含义(跨项目通用,不需要历史点数)

命中数到点数的映射(§3)是常量;这一节说的是**每个档位客观上意味着什么**。两者合起来就是刻度的完整定义——**它不由任何团队的历史点数决定,所以换项目、换技术栈、开新项目都直接可用**。

「面」= §2 的十六个因子。档位含义就是**这次改动碰到了几个面、碰到了哪一类面**:

| 点数 | 命中数 | 该档位的客观含义 | 典型形态(与技术栈无关) |
| --- | --- | --- | --- |
| **1** | 0 | **零面改动**:全落在既有代码内部,不碰高风险领域,验收一两条就完 | 改一段文案;调一处默认排序;改一个既有分支条件 |
| **2** | 1 | **单面改动**:只触到一个面 | 只加一个服务端只读接口;只加一个页面而服务端零改动;只有一次纯加列的迁移 |
| **3** | 2 | **双面改动**:两个面,但还没碰高风险领域、不变量或跨模块契约 | 一个新接口 + 前后端两个发布单元;一个新页面 + 一批验收条目 |
| **5** | 3–5 | **跨面改动**:典型是前后端联动之上,再叠一个领域风险、一个不变量或一批非功能验收 | 新接口 + 新页面 + 跨两单元 + 审批语义;一次带回填的加列 + 服务端逻辑 |
| **8** | 6–9 | **契约级改动**:通常已同时包含高风险领域、数据模式或外部集成、不变量——**改动开始波及别的模块或系统** | 接入第三方登录并落绑定表;新增一类实体贯穿迁移 → 服务端 → 前端 → 多角色验收 |
| **13** | ≥10 | **全面改动**:十个以上的面,含资金 / 状态机等高风险领域与外部集成或存量数据处理——**建议拆分** | 一次交付完整的退款流程:状态机 + 支付通道 + 新表 + 幂等 + 多角色多端验收 |

这一列「客观含义」就是 §8 自检时用的第二把尺:**它对照的是改动形态,不是团队产能**。所以一条 8 分的需求在任何项目里都指同一件事——契约级改动;不同团队的差别体现在**一个迭代能装下几分**(那是 `capacity` 的事),不体现在**同一改动值几分**。

⚠️ 「客观含义」是对命中数的**同义复述**,不是额外的门槛。**当它与因子向量看起来打架时,以因子向量为准**(比如 2 条命中却"感觉很难" → 仍是 3 分)。它的用途只有一个:§8 的 ≥2 档分歧自检。

### 历史点数怎么用(可选;且**不改变**任何单条判定)

项目**有**人工确认过的历史点数时,可以做一次**事后偏置观测**——目的是检查**因子表本身**准不准,不是给本次估算找标尺:

1. 取 3–5 条已交付、点数经人工确认的需求,回填输入包(找到各自的技术影响说明),按 §2 复算因子向量;
2. 比对因子档位与人工点数;
3. **只有出现系统性偏差**(多数条目同向偏高或偏低)才动手,而且改的是**这份因子表 / 档位定义**(改规则),不是某一条的结果;改完记进本文件;
4. 个别条目差 1 档 = 斐波那契刻度上的正常噪声,**不改任何东西**。

⛔ **三条禁止**:① 不得因为"以前同类需求打了 5 分"就把本次判定改成 5 分;② 不得因为项目没有历史点数就拒估或标「暂无标尺」;③ 不得跨项目搬历史点数来"找感觉"。

**迭代吞吐同样与估点无关**:同一项目相邻迭代的 committed 能漂出 2–4 倍,不同项目之间更没有可比性——吞吐既不参与点数判定,也不用于推断容量。**容量口径永远以该 Sprint 自己的 `capacity` 为准**(`capacity` 为 `null` 时容量闸不成立,见 SKILL.md 第 4 步)。

## 8. 判定溢出规则

因子表用精度换复现性(设计时显式承认的取舍):一条"算法很绕但只碰一个字段"的需求会被低估,这是**已承认的代价**。

**缓解**:把本次改动按 §7 的**档位含义**独立归一次档(那是一次表查询,不是"感觉"),若与因子档位差 **≥2 档**,**必须报出分歧**,写清「因子命中 N 条 → X 分;按 §7 的档位含义归档为 Y 分,理由是……」,让人裁决。

⛔ **不允许**自己偷偷调档。调了档,复现性当场归零。分歧只上报,不改 `points`。

## 9. 样例(通用业务场景,可直接复跑)

每条给出**输入包 → 因子向量 → 点数**。场景、系统名、字段名全部是**虚构的通用业务**,不对应任何真实代码库——它们是为了让判定规则的边界可核对,不是为了让你去找这些文件。

⚠️ **本节是校准样例,不是输入源。** 两条硬约束:

1. **估点时不得从这里抄技术影响说明。** 影响说明只能来自本次调用者给的,或本次真去读的开发计划。哪怕本次要估的需求"看起来和某个样例一模一样",也照样要重新取输入包。
2. **做「三会话复现性」复测时,输入必须选一条不在本节里的需求**——本节每条都自带答案,拿它去测就是让被测者读答案。

### 样例 8 · 正文与语义等同都不算的边界(3 点)

- 标题:每日 08:00 向逾期任务的负责人发送提醒邮件
- 正文(节选):「…**并发**触发时要保证**幂等**,同一天同一任务不重复发…」

```

  C2 ✗ 不变量字段明写「无」;正文里的「并发」「幂等」按 §2.0-1 不算;AC3「只发一封」按 §2.0-2 是语义等同,不算
```

## 10. 可选:文件清单 → 技术影响说明的路径映射

有些团队的开发计划只给**文件清单**而不写九字段。此时需要为该代码库**一次性**写下「路径形态 → 字段」的映射,记进本文件末尾,之后所有估算都用同一份——映射写死了,转写才可复现。**映射尚未写死前,对应字段按未说明处理(→ `unknown`),不许临场猜。**

映射只能覆盖四个字段(其余五个必须靠清单里的说明文字):

| 字段 | 从清单里怎么判 | 示意(**虚构布局**,按你的仓库改) |
| --- | --- | --- |
| 发布单元 | 清单涉及几个独立部署的顶层目录 / 仓库 | `services/<名>/` 各算一个;`web/` 算一个;`mobile/` 算一个 |
| 服务端 | 清单含服务端业务代码路径 | `services/*/src/(api\|handlers\|domain)/**` |
| 数据模式 | 清单含新迁移文件 | `services/*/migrations/*.sql` 新文件(只改 ORM 模型文件不算) |
| 前端 | 清单含**新增**页面 / 组件文件(改既有不算) | `web/src/pages/**` 新文件;`web/src/components/**` 新文件 |

写映射时把清单视作**完整**的:清单里没有迁移文件 = 数据模式「无」;没有新页面文件 = 前端不命中 T3。这四个字段因此不会进 `unknown`——但**不变量 / 存量数据 / 契约变更 / 外部集成 / 运行环境**五个字段从路径上读不出来,清单里没有说明文字就是未说明。
