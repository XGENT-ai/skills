# 处置结果与实现记录合同

## 记录归属

1. **输入计划自身约定优先**：沿现有记录链接更新对应实现/验收文档，不用本 skill 的默认路径覆盖已有组织形式。只读与当前问题、前置和退出条件有关的内容。
2. 采用 `dev-plan` 记录协议时，更新计划旁的 `<计划文件名去扩展名>.records/M<n>.md`；例如 `goal/LOGIN.md` 的 M2 对应 `goal/LOGIN.records/M2.md`。不存在时只为实际有处置结果的里程碑新建，不预建空记录。
3. 自定义/历史计划没有独立记录但有明确里程碑时，可按上述位置创建对应记录并补入现有进度索引，不重排计划模板；没有里程碑编号时沿用任务标识与仓库约定。找不到稳定任务归属且无法据计划确定时询问映射，已明确属于本次范围的修复可继续，但不得伪造 M 编号或宣称记录回写已完成。
4. 一个问题跨多个里程碑时，选直接承载修复的里程碑为主记录；其他实际受影响记录只同步相关验证/状态并链接主记录，避免复制整份处置表。集成终验归其原定收口里程碑，不新造“评审整改”里程碑改变总数。
5. 记录已有内容须保留仍有效的交付事实、证据与未完项，只更新受影响部分。保留源 `xxx.code-review.md` 的问题与原结论；用户明确要求更新它时，追加可区分版本的处置摘要及记录链接，不把历史评审结论改成“当时就正确”。

## 逐条处置

以 **报告路径 + 报告版本/hash + 问题 ID/章节** 标识来源，避免不同报告都含 F-01 时串项。复跑同一报告、同一问题时更新已有条目并重新核对当前代码，不重复建表/记录，不重复施加补丁；新版本改变主张时注明新来源。状态可沿用仓库等价用语，但至少分清：

| 最终处置 | 所需依据与后续动作 |
| --- | --- |
| 已修复并验证 | 修前目标确有缺陷；合理修复已实现；证明修复及相关回归的检查通过，注明具体覆盖 |
| 已修改待验证 | 代码已改，但必要检查未运行、失败或环境缺失；写清缺口和下一步，不视为关闭 |
| 已解决无需修改 | 当前代码已无该问题，有现有实现/后续变更及适当验证证据；不冒领为本次修复 |
| 不采纳 | 误报、当前不适用、与明确要求冲突或纯偏好；给反证/契约位置与原因。缺陷成立但建议修法不对时不能仅以“不采纳建议”关闭缺陷 |
| 待核实/待决策 | 缺事实、验收条件或关键选择；给影响、需要的证据/决定及可继续范围 |
| 待修复/阻塞 | 已确认合理且需修，但尚未实施或依赖未满足；给阻塞、已完成部分和继续动作，不用“不采纳”掩盖未做 |

用户排除的条目标“未处理（用户限定范围）”，说明来源范围即可，不展开额外调查。仅核实或全部不采纳时也记录相关结论，但不得据此增加完成数量或声称有代码修复。

## 记录最小内容

沿用原文档结构；缺相应位置时补一个精简的“评审修复”节和必要的验收行，不另造每个 finding 的文档或完整整改报告。

```markdown
# M2 · <里程碑名>

- 计划：[LOGIN](../LOGIN.md)
- 更新：<YYYY-MM-DD HH:mm + 时区>
- 状态：<进行中 / 阻塞 / 已完成，按实际退出条件>
- 验证基线：<commit SHA；未提交时 dirty@起始SHA + 关键改动路径>
- 环境：<共同测试环境；与单项不同的在相应证据标注>

## 交付与必要偏差

<当前实际行为、关键路径、已授权且影响续做的偏差；保留有效的原交付内容。>

## 评审修复

来源：<报告相对链接 + 版本/hash；报告所审基线与当前修复目标的必要差异>

| 问题 | 关联任务/检查 | 核实结论与证据 | 处置与修改落点 | 验证/后续 |
| --- | --- | --- | --- | --- |
| F-01 | M2 / V-3 | <当前触发条件、实际后果或反证，代码/契约定位> | <最终处置；必要改动路径/行为或不改原因> | <下表检查 ID 或明确缺口> |

## 验收

| 检查 ID/覆盖范围 | 命令或步骤 | 结果/必要证据 |
| --- | --- | --- |
| V-3 / F-01 <触发及保留行为> | <实际命令/步骤> | <通过/失败/未运行/环境缺失；必要输出或证据链接> |

## 未完项与继续动作

<尚未关闭的问题、待决策、待验收、下一步与解除条件；没有则写无。>
```

- 只写复核结论、修改结果、验证及续做所需事实，不保存讨论流水、完整成功日志、skill 使用过程或源码中的评审标签。
- 对需要行为测试的修复保留必要的修前失败/修后通过证据；若无法先复现则如实说明依据与限制。新回归用例可沿用现有检查 ID 的覆盖范围，不改造整份验收编号体系。
- 同一检查组可支持多条问题，表内引用同一证据，不重复粘贴结果。头部基线表示本次目标；引用旧证据时保留旧版本和复用依据，不能把更新头部当成旧测试已在新版本重跑。
- 因修改失效的旧通过证据标明不再支持当前结论及待重跑范围，保留其历史版本事实；不要用仍然存在的旧成功记录掩盖当前失败。

## 计划同步与完成门

- **顺序**：先更新记录并确认落盘，再更新计划恢复快照的变化字段及对应完成记录行。摘要只留 1–2 句当前成果/缺口，命令和逐条处置只在记录中。相关正文确有已授权偏差时就地改结论，不在计划里追加评审讨论历史。
- **一里程碑一行**：沿用原记录链接，只更新受影响行；不为同一里程碑追加“修复一次”“再复核一次”的流水。按 `dev-plan` 协议，已记进展的里程碑状态只用「进行中 / 阻塞 / 已完成」，带时区；完成时移动到已完成行末，最近完成取最后一条已完成记录。
- **完成不等于修复数**：只有该里程碑所有退出检查通过或有仍有效的复用证据，才记已完成；修完 F-01 不能自动完成 M2，更不能完成整期。未改动的无关里程碑不重复验收或变更状态。
- **必要时重新打开**：已完成里程碑的缺陷推翻退出条件，或修复使关键证据失效且尚未补齐时，改为进行中/阻塞，同步 n/N、最近完成、下一步及阻塞。若本次已补齐相关检查且其他证据仍有效，可保留完成状态，说明依据。仅低影响非阻塞建议不自动推翻已完成状态。
- **受影响的下游**：检查直接依赖该行为的前置验收与集成终验。只重开被反证或失效证据覆盖的部分；不能假定上游修复即恢复所有下游结论，也不机械将所有下游标失败。
- **分清计划状态**：`Ready / Proposed / Blocked` 是方案/实施前置状态，不是测试结果。普通 bug 或待验证不自动修改它；只有发现影响范围、安全、数据、外部契约或关键 NFR 的未决前提时，按计划约定同步相应决策与状态，不以降低验收标准解除阻塞。
- **自查**：核对 n 只计已完成行、N 与既有里程碑数一致、最近完成准确、相对链接确实存在、记录与快照不矛盾。有计划指定的进度校验命令时先核查命令内容再运行；缺失/不适用则人工核对，不安装额外技能或迁移整份计划来凑校验。

结束对话、受阻或交接时，同样保存实质成果与缺口。记录/计划写入失败须报告哪些已落盘、哪些未同步，不因代码已修复就声称任务全部完成。
