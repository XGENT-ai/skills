# 四个 PRD 审查视角

Reviewer 读自己的节；跨视角复核再读关联节。按本次产品范围裁剪检查深度，不能用一张通用清单制造功能或阻塞。

## A. facts：核实代码现状与前置

先把关键主张分成现状、未来能力、约束、假设、验收目标。事实核实优先覆盖会改变范围、产品形态、权限、兼容、质量或依赖的陈述。

### 从文件存在追到实际行为

1. 用 `rg --files` / `rg` 定位声明和真实调用者，读取相关入口、授权、业务实现、返回/状态展示及必要配置。文件名、路由、类型或函数存在，只能证明那个入口存在，不能证明已经满足用户场景。
2. 按 PRD 依赖的行为追踪：谁能发现/执行、输入边界、状态迁移、结果是否可消费、错误/降级、重复与冲突、分页与规模、跨租户/用户边界。发现对应测试时读其断言和替身，区分真实行为与 mock 假设；未执行测试不写「测试通过」。
3. 核实可复用依赖的契约、权限、配置和目标环境：可检索不等于可安装，HTTP 入口不等于支持 Agent 原生消费，模型网关存在不等于当前应用/主体可调用，前端隐藏按钮不等于后端拒绝越权。
4. 声称「不存在」时说明检查过的目录/入口/配置和搜索范围，必要时跟踪动态注册或外部服务。仅未搜到关键词只能写「在已查范围未定位」，不能断言整个系统没有能力。
5. 声称已验证兼容、性能、UI 或生产可用时核对实际环境、版本与记录。当前源码存在、历史计划完成、SPMS 状态与生产部署不是同一事实。没有部署证据不推断线上版本；没有有效测量不声称达到门槛。
6. 数字、业务规则和平台约束给来源；区分代码现状与规范要求。两者冲突就同时定位，不因代码不同自动废除约束。旧文档/README/记忆仅是线索，不代替本次行为核实。
7. 涉及当前生态支持、版本能力或外部限制时先读依赖/配置，再查官方文档或一手来源，保留版本、日期与链接。不能访问就标具体待核实项，不以记忆冒充最新结论。

### 现状核实矩阵

| PRD 主张/定位 | 类型 | 代码现状及证据等级 | 与目标的关系 | 产品影响/所需补证 |
| --- | --- | --- | --- | --- |
| <已有能力/可复用/未支持等陈述> | <现状/目标/约束/假设> | <路径:行号/符号;源码核实/测试记录/实测/未核实> | <已有满足/部分满足/真实增量/行为冲突/未核实> | <改正背景、明确增量、补前置/决策/证据> |

「真实增量」仅表示本次已查实现不具备目标能力，不表示 PRD 有缺陷。「已有满足」也不自动撤回需求，可能仍需要新的可用性、质量或治理边界。用户已明确不考虑存量时尊重该选择，不强加迁移兼容；其他产品前置仍须核实。

已有代码缺陷只有被本 PRD 依赖、放大或直接阻断目标时进入评审；无关代码问题不扩展成本次代码审计。源码不可访问时交付明确的核实清单与证据缺口，继续其他维度；不能冒充已核实或直接判依赖不存在。

## B. product：创新、先进性、AI 与范围

从用户问题推导价值，检查采用的选择是否在约束内把任务设计充分。先进性以用户收益、质量和合理成本判断，技术新旧、术语数量或功能多少不自动加分。

- 是否仅转录功能清单，遗漏完成关键任务必须的发现、理解、决策、使用与维护环节？是否有比照搬现状/参考项目更有价值的产品形态？指出具体场景、收益与取舍，不能只写「不够创新」。
- 参考产品、官方生态能力是否适配目标用户、租户、身份和使用环境？区分声明、已核实能力和拟新增能力，避免承诺未经验证的兼容组合。
- AI 能改善发现、理解、创作、决策或重复劳动时是否有合理方案？未采用但有充分理由则可接受；没有 AI 不自动算缺陷，用户排除或价值不足时不强加。
- 已采用 AI 是否有明确任务、触发、授权输入、可用输出、依据/不确定性、用户采纳/修改/拒绝/撤销、质量口径、成本与不可用状态？辅助 AI 不可用时基本任务能否继续；AI 是核心时是否如实进入等待/失败，而非虚假成功？
- 原始诉求、目标、范围、非目标及决策是否一致？终局是在本 PRD 范围内充分设计，不是整个产品无限扩张。PoC 说明要证明的假设及成立判据，不能自动扩成完整系列，也不能仅罗列技术组件。
- 是否把怎么实现混进产品决策？内部架构、表/端点设计、算法/模型选型移交开发计划；已给定约束和外部可消费契约保留必要产品语义。

交回：`产品选择 | 用户价值/目标 | 依据与约束 | 取舍/不足 | 必要修订或非阻塞机会`。遗漏机会只有在直接影响已确认目标、且收益和适配有依据时才作为缺陷；其他合理改进单列提案，不能未经确认写成承诺。

## C. experience：可用、便捷与美观 UI

逐角色走主旅程：`找到入口 → 理解信息/条件 → 完成任务 → 确认结果 → 再次使用或失败恢复`。无 UI 产品仍走调用方/Agent/运维的相应消费旅程，可用性不能随 UI 一起跳过。

- 主路径是否能完成端到端任务，而不是只有数据、API 或几个按钮？用户是否被迫理解内部术语、反复输入信息、切换入口或自行补步骤？首次与高频路径是否合适？
- 相关的等待、空数据、无权、错误、部分成功、重复/冲突、取消及恢复是否状态清楚、结果真实、下一步可行动？角色与权限改变不能只靠前端隐藏。
- 默认信息、主操作和信息层级是否支持任务；细节是否渐进展示；风险和必要前置是否始终足够可见？
- 美观是否落实为信息主次、排版、密度、留白、视觉语言与宿主一致性；是否只写「现代 UI」或仅有可访问性指标？适用的窗口、主题、语言、键盘/焦点、对比度等是否有产品要求与验收？
- 区分产品交互与实现：一次引用跳转、状态反馈、可撤销操作属于 PRD；组件库、CSS/DOM 与焦点代码的实现不应被强制补进 PRD。

| 实际材料 | 支持的结论 | 必须说明的限制 |
| --- | --- | --- |
| PRD/流程/源码 | 任务闭环、规则与交互要求的合理性 | 文档/静态代码推演，不能证明美观或真实交互通过 |
| 设计稿/截图 | 可见布局、信息层级与视觉一致性 | 静态评审，不能证明操作和权限行为 |
| 已授权的原型/浏览器实测 | 本次实际观察的旅程、状态与视觉 | 记录环境/版本/场景/结果；没有走过的路径仍未验证 |

没有实现页面不自动阻塞 PRD；关键在产品状态与验收是否已定清。现有页面可安全只读走查时按目标仓浏览器工作流采集证据，不为评审改动真实业务数据。UX findings 写清哪个角色在什么任务中被怎样阻碍，不能把个人审美偏好当缺陷。

## D. acceptance：SMAR、UAT 与分期终验

SMAR 检查目标与需求：

| 原则 | 核对要点 |
| --- | --- |
| Specific | 角色、对象、场景、作用域、权限与能力边界明确，领域词和状态语义一致 |
| Measurable | 预期状态可判断；数值有作用域/负载/样本/分母/窗口，明确枚举、是/否、相等/不变也合格 |
| Actionable | 用户或授权主体能执行具体业务动作，得到可用结果；不只写愿景或技术名词 |
| Reasonable | 价值、质量、成本、依赖及支持范围与用户约束相容，未知前置没有被写成无条件承诺 |

区分验收门槛、上线观察指标与 PoC 比较基线；建议数值不能冒充已实测结果。不用 Time-bound 编造工期，已有外部日期、性能时延、超时、有效期及观察窗口仍有效。

双向追踪：`原始诉求/目标 → 场景 → FR/NFR → 验收 → UAT 预期状态 → 分期/终验`。

- 每个目标有需求承接，每个重要用户场景有预期状态与通过条件，每条完整能力有可判断的验收。UAT 应描述结果是否可用、反馈、下一步及数据变化，不只是一条提示文案。
- 成功与本产品相关的空、拒绝、冲突、取消、失败/恢复和 AI 不确定/降级场景有清晰结果。不能到测试计划阶段才决定产品状态，也不能把造数、脚本、探针、故障注入当 UAT 内容。
- 没有 TC、没有 SPMS key、章节不同本身不算缺陷。真实 key 不可伪造；缺少验收语义才是问题。代码/设计内部断言若无法表达外部结果，要求改为业务边界，不要求 PRD 拟写测试过程。
- 每期有独立用户价值、范围与出口判据，不按前后端技术栈切期。终局需求不因交付节奏被删小，非目标不充当延期列表；已明确的其他 PRD 分工可作为范围去向。
- 每期开发计划尽量 5–8 个 Milestone；连续性例外 9–10 个说明理由，最多 10 个；小范围可以更少，不凑数。这里只检查规模预算，详细任务和准确拆解由 dev-plan 核实，超出则反馈拆期。
- 逐条核对分期验收分配和最终完成期；跨期条目正文、分期矩阵及已录入系统的终验声明口径一致。部分交付不能被标成整条完成，前置条件不归本 PRD 的不得被默默视为已就绪。

交回断链 ID/章节、相互矛盾的两处、受影响用户场景与最小产品修订。不能因没有开发计划的技术里程碑而判 PRD 不可行动。
