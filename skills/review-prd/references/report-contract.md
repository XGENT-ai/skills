# 问题判定与 PRD 评审报告合同

ODC 声明约束评审和报告编写，不复制进报告；下方 Markdown 模板、表格与报告顺序是交付接口。

## 落盘与交付

```formal
RULE @prd_report_storage:
  UNLESS: explicit_chat_only_or_no_file_request
  MUST: ["默认保存完整 Markdown 报告，由主 agent 单写并回读实际文件；空 findings、缺源码或需补证仍须保存",
         "核对 findings、待核实、代码矩阵、覆盖、映射/分期、结论及修订顺序，检查定位与文件链接；已保存后聊天给实际链接、结论和关键摘要"]
  MUST_NOT: [treat_chat_preview_or_path_notice_as_saved_report, ask_whether_to_save_as_delivery_confirmation]

RULE @prd_report_path:
  WHEN: file_report_required
  MUST: ["路径按用户指定 → 本地 PRD 同目录 <PRD 文件名去掉扩展名>.review.md；仅聊天输入/远程原文按仓库报告目录惯例，无则当前工作区 docs/reviews/<主题短名>.review.md；按需建目录，不因未给路径停下",
         "写前查同名，已授权更新/覆盖该报告则执行；否则保留旧报告，依次尝试同目录 <主题>.review.<YYYY-MM-DD>.md、<主题>.review.<YYYY-MM-DD>-2.md 等空闲名；用户指定路径冲突也另存并说明实际路径"]
  MUST_NOT: overwrite_source_prd_or_code

RULE @prd_storage_fallback:
  MUST: [=>[explicit_chat_only_or_no_file_request, "在聊天交付完整报告"],
         =>[report_write_tool_unavailable_or_write_failed, "明确报告未落盘、原因和目标路径，聊天保留完整结果，保存标未完成，不链接不存在文件"]]
```

## 原文档引用（报告头）

报告标题后、findings 前必须写「评审对象」，供 `apply-doc-review` 仅凭报告定位原文；即使没有 findings 也保留。每个实际评审目标一行，背景资料和关联计划不混作修订目标。

```markdown
## 评审对象

| 类型 | 原文档 | 所审版本 | 评审范围 |
| --- | --- | --- | --- |
| PRD | [<原文档标题>](<相对报告所在目录的原文路径或稳定 URL>) | <内容 hash / 可取回版本；不可得则 unknown> | <全文或指定章节/需求 ID> |
```

```formal
RULE @prd_source_reference:
  MUST: ["本地引用相对实际报告目录计算，不按 cwd/仓根/默认报告位置；空格路径用合法 Markdown，原文位置/文件名不变，不写机器绝对路径，另存或加日期后重新核对",
         "远程原文用稳定 URL 与可用版本；无持久原文的聊天输入写‘聊天输入，无原文路径’，不造链接，并说明 apply 需要可定位目标",
         "回读时沿链接打开原文，核对类型/身份/版本/范围；原文变化说明基线及适用性，处置保留历史所审版本，修后版本写处置节"]
```

## 复审记录

复审报告在标题及评审对象之后注明：上轮报告的相对链接与版本、所审对象的前后版本、本轮范围、已有处置记录链接，以及“修复效果复审”或“完整重审”。历史报告与原结论保持不变；默认按本合同另存新报告。

在原报告结构中增加“上轮问题复审”表，与本轮新增问题分开：

| 来源报告 / F-ID或稳定章节 | 上轮问题与结论 | 已有处置 / 修后版本 | 本轮结果 | 当前证据 / 验证 | 剩余动作 |
| --- | --- | --- | --- | --- | --- |

```formal
RULE @prd_recheck_evidence:
  WHEN: re_review_with_prior_report
  MUST: ["结果仅用已解决、仍存在、部分解决、回归、待核实、不再适用、本轮未复核；已解决满足原关闭判据，回归有先前解决及当前再失败证据，不再适用有范围/契约变化依据且不等于实际修复，缺证不关闭，未选旧项标本轮未复核",
         "来源身份为报告路径/原始版本 + F-ID，有台账再保留评审对象 ID；同链路沿用旧号，多报告同号不混合，新问题用未占用号并注明本轮，同根因合并保留来源映射，不重编号抹历史",
         "默认覆盖上轮全部问题及待核实，限定范围时逐项列未复核或完整 ID 清单；读处置后独立核实实际结果和旧证据适用性，只查修复影响的必要回归，不自动重跑无关全量验证",
         "分别总结旧问题解决情况、修复引入的新问题、未覆盖/缺证范围；无新增 findings 不等于旧项关闭，局部通过不等于整体通过；SDLC 按仓内固定状态与范围登记，不造 state 枚举"]
```

## 什么进入 findings

```formal
RULE @prd_finding_admission:
  MUST: ["确认问题同时有 PRD 定位、已核实依据、具体用户场景/触发、对已确认目标的实际后果及可执行最小产品修订；一条一独立根因，重复症状合并并保留关键定位",
         "断言缺少 X 前先查正文/引用/附录/确认约束，并证明 X 为目标必要条件；前置误判、虚假现状或缺少产品增量有证据才报问题",
         "证据不足列待核实，写所需证据与结论影响，关键缺口仍可阻塞通过；约束内有依据的高价值非必要机会单列提案"]
  MUST_NOT: ["将纯格式、偏好、无关旧代码或不同章节标题报缺陷", "将新功能未实现报 PRD 错误",
             "凭源码未定位或依赖未联调断言能力不存在", "将所有合理备选报缺陷或自行增加产品承诺"]
```

## 严重度与置信度

| 等级 | PRD 评审中的含义 |
| --- | --- |
| P0 | 已确认的产品规则直接要求重大安全、数据或业务灾难，需立即纠正；极少使用 |
| P1 | 核心任务、权限/数据边界、关键依赖或终验口径存在高影响错误/缺口，进入下游计划前须修订 |
| P2 | 局部产品行为、体验、验收或分期存在可证实缺口，相关范围交接前修正 |
| P3 | 有明确依据和收益的小改进，不阻塞交接；个人偏好不算问题 |

严重度表示后果，置信度用高/中及依据表达证据强弱。仅猜测的风险不能靠降为 P3 混进 findings，不设问题数或评分指标。

## 单条问题格式

```markdown
1. [P1] F-01 · <可行动的标题>
   - 定位：<PRD 文件:行号/稳定章节；冲突时两处；需求/场景/验收 ID>
   - 场景与问题：<什么角色在什么条件下要完成什么，按当前 PRD 会产生什么后果>
   - 证据：<读过的代码文件:精确行号/符号、用户约束/规则定位、运行证据或官方文档 URL/版本/日期>
   - 修订：<最小需要补定/改正的产品行为、状态、边界、前置或验收；不展开内部实现>
   - 复核：<改稿后应一致的产品断言/依据；未来效果验证与本次文档复核分开>
   - 置信度：<高/中 + 依据>；阻塞：<目标/需求/交接范围或否>
```

```formal
RULE @prd_finding_citations:
  MUST: "本地用可点击文件链接与短行定位，必要时补稳定标题/符号；定位到原 PRD 应承载要求处，不指向 reviewer 新报告；只引已读原文，截断先补读，不把外部例子数字当产品承诺"
```

## 完整报告顺序

1. **确认问题**：P0 → P3，F-01 等稳定编号；无确认问题如实写「未发现可确认的问题」。复审沿用编号，区分已解决、仍存在、新增。
2. **待核实/待决策**：缺什么证据或产品决定、影响哪项需求、谁能提供及应在何交接节点前明确；负责人未知写待指定，不虚构日期或用户承诺。
3. **代码现状核实矩阵**：`PRD 主张/定位 | 类型 | 实际行为与证据等级 | 已有满足/部分满足/真实增量/行为冲突/未核实 | 产品影响`。代码读不到仍列关键主张、调查限制和所需材料，不留空表假装核实完毕。
4. **覆盖与基线**：PRD 版本/路径、代码仓/commit/dirty、日期、实际 reviewer 分工或串行方式、四维覆盖。六个产品维度分别给结论/不适用理由；记录实际代码、测试、设计稿及浏览器证据等级与缺口，只列结论相关来源，不倾倒读文件日志。
5. **需求追踪与分期终验**：列目标/场景/需求/验收/UAT 断链或已核对范围；检查每期独立价值、5–8 个 Milestone 预算/最多 10 个的连续性例外、关键前置、跨期终验及相互冲突的口径。建议产品交付顺序，不生成技术任务、并行波次或测试脚本。
6. **产品增强机会**：有依据的非必要提案，写价值、场景、约束/代价及采用后需调整的需求；无则写「无」，不为创新凑数。
7. **总体结论与修订顺序**：首行写「是否需要修改：需要 / 无需」（判定条件见主技能第 5 节），再写建议结论、阻塞范围与解除条件。先修事实/约束，再定产品语义/体验/AI，随后同步验收、UAT 和分期终验。未解决的重大未知不能藏进「通过」。

短 PRD 可以用紧凑段落/表格承载这些内容；完整报告不是固定字数，也不是 reviewer 原始回报的拼接。结构借鉴 `review-dev-plan`，判断对象是产品需求，不沿用其实施就绪状态或技术编排要求。

## 结论口径

- **通过**：所审范围产品目标、行为、状态、验收与分期清楚，关键现状和前置有证据，剩余建议不影响交接；说明覆盖限制。
- **需修订**：有已确认且阻塞交接的产品问题，列具体范围和修订条件。无关独立能力可单列已满足条件，不能将整份含阻塞的 PRD 宣称通过。
- **需补证**：暂无已确认的交接阻塞，但关键现状、依赖或产品决定仍不能成立/未确认，列所需证据与节点。已有阻塞缺陷同时存在时用「需修订」并继续列补证项。

状态按影响与证据判断，不能靠总分平均。纯产品方向已经足够明确、技术实现选择留给开发计划时，不因尚无架构方案阻塞 PRD；核心依赖能力是否存在/授权/适配仍须核实。

评审通过不表示功能已实现、线上部署、性能达标、UI 已通过浏览器验收，也不自动批准需求或变更 SPMS 状态。

```formal
REVIEW:
  CHECK: [@prd_report_storage, @prd_report_path, @prd_storage_fallback, @prd_source_reference,
          @prd_recheck_evidence, @prd_finding_admission, @prd_finding_citations]
  ALSO: ["评审对象、问题模板、复审表、严重度及完整报告顺序均遵守本合同",
         "是否需要修改、通过/需修订/需补证与证据及阻塞范围一致，下一步符合主技能第 5 节"]

```
