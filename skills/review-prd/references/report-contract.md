# 问题判定与 PRD 评审报告合同

## 落盘与交付

- **默认保存完整 Markdown 报告**；只有用户明确要求仅聊天或不写文件时跳过。聊天正文、拟写入内容和路径预告都不算已落盘，不把「是否保存」留作交付前的确认问题。
- 路径优先级：用户指定 → 本地 PRD 同目录的 `<PRD 文件名去掉扩展名>.review.md`。输入只有聊天文本/远程文档时遵循仓库报告目录惯例，无惯例则写当前工作区的 `docs/reviews/<主题短名>.review.md`。按需建目录，不因未给路径停下。
- 写入前检查同名。已授权更新/覆盖该报告则执行；否则保留旧报告，依次尝试同目录 `<主题>.review.<YYYY-MM-DD>.md`、`<主题>.review.<YYYY-MM-DD>-2.md` 等未占用名称。用户指定路径冲突也保留旧文件并说明实际路径，不覆盖原 PRD 或代码。
- 主 agent 单写完整报告并回读实际文件，核对 findings、待核实项、代码矩阵、覆盖、映射/分期、结论和修订顺序齐全；检查引用定位与文件链接。空 findings、缺源码或「需补证」不免除落盘。
- 最终聊天给实际报告链接、结论与关键摘要；仅聊天模式在聊天交付完整报告。写入工具不可用或失败时明确「报告未落盘」、原因与目标路径，在聊天保留完整结果，将保存标为未完成；不能链接不存在的文件。

## 什么进入 findings

确认的问题同时具备：PRD 可定位的主张/缺口、已核实依据、具体用户场景/触发、对已确认目标的实际后果、可执行的最小产品修订。每条一个独立根因，重复症状合并但保留关键定位。纯格式、偏好或无关旧代码问题不进入 findings。

「没有写 X」先查正文、引用、附录及已确认约束，证明 X 是本产品目标的必要条件；章节标题不同不算缺失。新功能未实现不算 PRD 错误；可确认的前置误判、虚假现状或缺少产品增量才是问题。源码未定位、依赖未联调不是「能力不存在」的证据。

证据不足的主张放待核实项，写需什么证据及对结论的影响；关键证据缺口仍可阻塞通过。高价值且在约束内的增强机会有依据则单列提案，不能把每个合理备选都报成缺陷，更不能借评审自行增加产品承诺。

## 严重度与置信度

| 等级 | PRD 评审中的含义 |
| --- | --- |
| P0 | 已确认的产品规则直接要求重大安全、数据或业务灾难，需立即纠正；极少使用 |
| P1 | 核心任务、权限/数据边界、关键依赖或终验口径存在高影响错误/缺口，进入下游计划前须修订 |
| P2 | 局部产品行为、体验、验收或分期存在可证实缺口，相关范围交接前修正 |
| P3 | 有明确依据和收益的小改进，不阻塞交接；个人偏好不算问题 |

严重度表示后果，置信度用高/中及依据表达证据强弱。仅猜测的风险不能靠降为 P3 混进 findings，不设问题数或评分指标。

## 单条问题格式

```markdown
1. [P1] F-01 · <可行动的标题>
   - 定位：<PRD 文件:行号/稳定章节；冲突时两处；需求/场景/验收 ID>
   - 场景与问题：<什么角色在什么条件下要完成什么，按当前 PRD 会产生什么后果>
   - 证据：<读过的代码文件:精确行号/符号、用户约束/规则定位、运行证据或官方文档 URL/版本/日期>
   - 修订：<最小需要补定/改正的产品行为、状态、边界、前置或验收；不展开内部实现>
   - 复核：<改稿后应一致的产品断言/依据；未来效果验证与本次文档复核分开>
   - 置信度：<高/中 + 依据>；阻塞：<目标/需求/交接范围或否>
```

本地引用使用可点击文件链接与短行定位，必要时补稳定标题/符号；定位指向原 PRD 应承载要求的位置，不指向 reviewer 自己的新报告。只引用读过的原文，截断内容先补读；不能把外部例子数字当成本产品承诺。

## 完整报告顺序

1. **确认问题**：P0 → P3，F-01 等稳定编号；无确认问题如实写「未发现可确认的问题」。复审沿用编号，区分已解决、仍存在、新增。
2. **待核实/待决策**：缺什么证据或产品决定、影响哪项需求、谁能提供及应在何交接节点前明确；负责人未知写待指定，不虚构日期或用户承诺。
3. **代码现状核实矩阵**：`PRD 主张/定位 | 类型 | 实际行为与证据等级 | 已有满足/部分满足/真实增量/行为冲突/未核实 | 产品影响`。代码读不到仍列关键主张、调查限制和所需材料，不留空表假装核实完毕。
4. **覆盖与基线**：PRD 版本/路径、代码仓/commit/dirty、日期、实际 reviewer 分工或串行方式、四维覆盖。六个产品维度分别给结论/不适用理由；记录实际代码、测试、设计稿及浏览器证据等级与缺口，只列结论相关来源，不倾倒读文件日志。
5. **需求追踪与分期终验**：列目标/场景/需求/验收/UAT 断链或已核对范围；检查每期独立价值、5–8 个 Milestone 预算/最多 10 个的连续性例外、关键前置、跨期终验及相互冲突的口径。建议产品交付顺序，不生成技术任务、并行波次或测试脚本。
6. **产品增强机会**：有依据的非必要提案，写价值、场景、约束/代价及采用后需调整的需求；无则写「无」，不为创新凑数。
7. **总体结论与修订顺序**：建议结论、阻塞范围与解除条件。先修事实/约束，再定产品语义/体验/AI，随后同步验收、UAT 和分期终验。未解决的重大未知不能藏进「通过」。

短 PRD 可以用紧凑段落/表格承载这些内容；完整报告不是固定字数，也不是 reviewer 原始回报的拼接。结构借鉴 `review-dev-plan`，判断对象是产品需求，不沿用其实施就绪状态或技术编排要求。

## 结论口径

- **通过**：所审范围产品目标、行为、状态、验收与分期清楚，关键现状和前置有证据，剩余建议不影响交接；说明覆盖限制。
- **需修订**：有已确认且阻塞交接的产品问题，列具体范围和修订条件。无关独立能力可单列已满足条件，不能将整份含阻塞的 PRD 宣称通过。
- **需补证**：暂无已确认的交接阻塞，但关键现状、依赖或产品决定仍不能成立/未确认，列所需证据与节点。已有阻塞缺陷同时存在时用「需修订」并继续列补证项。

状态按影响与证据判断，不能靠总分平均。纯产品方向已经足够明确、技术实现选择留给开发计划时，不因尚无架构方案阻塞 PRD；核心依赖能力是否存在/授权/适配仍须核实。

评审通过不表示功能已实现、线上部署、性能达标、UI 已通过浏览器验收，也不自动批准需求或变更 SPMS 状态。
