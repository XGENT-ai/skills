# 生成结果验收

在生成或实质修改 `verify-*` 后使用。目的是发现错误选择、隐含前置和假绿灯；不为局部文案修改强制重跑全套。判据来自用户范围和已核实契约，不由生成结果反推。

## 1. 结构与选择

先检查 YAML、名称与目录、description 全文及前 100 字符、链接和实际命令。没有配方拆分就不要求索引，没有 helper 就不要求脚本目录。

再用普通用户措辞检验选择边界；不要在每条请求中显式点名目标 skill，否则测不到发现能力：

- 验证目标应用中已覆盖的场景：应选中本 skill，定位正确 ID/配方。
- 只解释实现或只写测试计划：不启动验证流程。
- 验证同仓另一个应用、或尚未覆盖的场景：不误报支持、不退回全量执行；指出缺口或使用其他现有能力。

可用独立 agent 仅查看候选技能的名称/描述和自然请求，返回选择与下一步；再以单独的显式加载试跑检查执行。前者只验证模型在给定目录中的选择，不证明宿主已自动发现/加载。没有独立条件时人工检查并标为自验，不冒称运行轨迹。

## 2. 作者实跑与故障辨别

按成品指令选择一个范围，记录实际入口与动作、输入、输出、退出码、证据和清理；对照范围检查是否夹带无关场景。单场景产物执行该场景；已有多场景产物应选其中一个，确认其他场景没有执行。未知范围不得静默替换为全量。

判据辨别分两层记录：

| 层级 | 运行方式 | 能证明什么 |
| --- | --- | --- |
| 断言校准 | 同一个判定器接收已知好/坏观察样本 | 判定器能拒绝该错误样本 |
| 入口到结果的故障检测 | 正常隔离副本通过；在另一个隔离副本制造与契约矛盾的行为，用同一配方、判据和命令执行 | 整条路径能发现该产品故障 |

选择便宜且有判别力的故障，例如应用仍返回成功但数据未保存。保持测试、判据与验证命令不变；失败须来自目标行为，不是语法错误、缺依赖或固定拒绝未知哈希。未知构建被 Doctor 拒绝只说明身份检查有效。模拟观察只能支持第一层；无法安全注入产品故障时说明第二层未执行，不降标准或修改共享环境来凑结果。

故障与正常轮次分别留证，失败后同样检查清理；产品正常验证和故障检测通过是两个结论，故障副本本身仍应报告失败。

## 3. 冷启动交接

复杂生成、新增关键 helper 或修改交接流程时，条件允许且委派已获授权则让独立 agent 试用成品。它只获得：自然验证请求、目标项目副本与成品 skill。不给生成会话、生成器全文、作者命令历史、旧运行目录、隐含变量、预期答案或判定标准。

使用不同临时路径的干净项目副本，排除作者启动的实例、临时数据和历史证据；保留仓库本来就要求的配置来源与工具。允许正常读取项目以执行文档写明的步骤，但不能靠猜未记录的前置来掩盖缺项。

检查独立执行者能否仅凭这些材料完成范围选择、启动/Doctor、操作、取证与清理。记录猜测、追问、临时修补及其原因；作者补充口头提示后跑通，不能算原产物冷启动通过。

发现缺项后先修生成产物；若缺项来自生成规则，同时修生成器，再用新的干净副本重验受影响部分。不能复用已经知道隐含答案的执行者来宣称全新的独立验证。无独立执行条件时保留作者实跑结论，冷启动标未执行，不因此虚构能力或强制安装工具。

## 4. 交付与维护

在生成交付记录中简短说明每层实际做到哪里、结果与证据位置：结构、选择、作者实跑、断言校准/产品故障检测、冷启动。缺项标未执行或受阻，无需建立新的统一评分系统。这些检查属于生成/维护过程，不复制成 `verify-*` 每次验证业务的固定步骤或报告要求。

增量维护重点检查原有 ID、人工说明和未受影响的配方是否保留；新增场景可独立选择，共享启动/清理没有被复制。记录只反映本轮已测范围，不从一次交接成功推导跨平台或全产品可用。
