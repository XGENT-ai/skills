# 工作流与 Agent + Skill 的选型

在决定是否接入 workflow-service、拆分 Agentic 任务或设计混合流程时读取。以下是结合本服务边界的工程建议，不表示某个 Agent 执行器已在目标环境部署。

## 区分控制流程、求解过程与知识

工作流把可预先约定的步骤与转换规则交给程序执行；Agent 根据执行反馈决定接下来采取什么行动。固定规则可以包含分支、并行、循环和模型调用，所以“有 AI”或“结果不固定”不等于需要自主 Agent。[概念依据：Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)。

Skill 是 Agent 按需读取的知识、步骤、脚本与资源包。它能让做法复用，也能指导 Agent 执行固定步骤；调度、执行记录和恢复能力仍来自运行它的系统。[概念依据：Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)。

本服务拥有流程定义、版本、实例、等待与审批状态；实际执行交给登记的动作执行面。它能编排 Agent 执行任务，但不因加载了一个 SKILL.md 就自动获得对应执行器。

## 如何选择

先判断普通代码、单次模型调用、脚本或已有 job 系统是否足够，再考虑增加编排层。不要把业务的每一步都交给模型，也不要把探索时的每次工具调用都固化成流程节点。

| 关键问题 | 优先工作流 | 优先 Agent + Skill |
| --- | --- | --- |
| 下一步如何决定？ | 阶段、分支条件、循环边界可提前写清 | 需要查看新证据、修正假设，再选工具或方法 |
| 谁需要理解和接手进度？ | 多个成员／系统围绕业务实例协作，离开当前会话仍要看清责任与状态 | 主要由当前 Agent 求解，交付产物、证据和必要执行记录 |
| 等待什么？ | 人工审批、业务事件、截止时间、其他系统的结果 | 查询／实验／测试的反馈，用来决定下一次探索 |
| 复用的是什么？ | 稳定的业务生命周期、交接规则和版本 | 专业知识、操作方法、工具用法和验收方式 |
| 失败后恢复什么？ | 从明确业务阶段恢复，原审批、事件和已产生效果不能丢失 | 恢复上下文、证据和尝试记录，由 runtime 继续有界求解 |

这张表不是计分器。任务既有稳定的业务生命周期又需要局部探索时，选混合。耗时、步骤数量和是否调用多个 Agent 都不单独决定方案；已有 Agent runtime 具备可靠持久化时，也不必为了“能断点恢复”再套一层工作流。

### 典型场景与容易误判的情况

| 场景 | 建议 | 决定因素 |
| --- | --- | --- |
| 报销、退款、上线审批与发布 | 工作流，具体执行用代码或已有服务 | 角色交接、审批依据、业务状态与审计稳定 |
| 排查未知故障、实现一项需求、做开放式研究 | Agent + 相应 Skill | 路径依赖现场证据，不能事先列完有效动作 |
| 固定的“生成 → 校验 → 评分 → 有界补足 → 人工审核” | 工作流 + 模型／业务动作 | 使用 LLM 和质量反馈，也可以遵循已定义规则，不必增加自主 Agent |
| 调查异常 → 提出修复 → 审批 → 执行 → 对账 | 混合 | 调查要自主求解，后续授权与业务写入有固定边界 |
| 已有持久化 Agent 任务，只需加载专业指引 | Agent + Skill，复用现有任务记录 | 知识复用不要求再建一份流程实例 |
| 简单的格式转换／固定 API 调用／单次分类 | 代码、脚本或单次模型调用 | 没有必要增加流程引擎或自主循环 |
| Agent 临时需要触发一条已发布的审批／发版流程 | Agent 经 MCP 调用既有工作流 | Agent 仍负责当前目标；被调用业务流程有独立实例和授权规则 |

若同一业务既可由代码也可由 Agent 完成，应先验证 Agent 带来的效果是否值得增加成本与不确定性。高影响写入本身不强制使用本服务，但其权限、审批、输入校验与效果核验必须由实际系统落实，不能只写在 Skill 提示里。

## 混合时把边界放在哪里

工作流拥有外部业务阶段，Agent runtime 拥有某个阶段内部的求解过程；业务 App 拥有权威对象和实际效果。适合画成流程节点的是可交接、可等待、可独立核验的业务里程碑，Agent 的每次读文件、搜索或调整假设通常留在其会话内部。

接入前明确以下约定；这些是执行方设计项，不是新增的 workflow API 字段：

- **输入与能力范围**：目标、对象引用、必要上下文、允许的工具与操作。Skill 告诉 Agent 怎么做，实际工具权限决定它能做什么。
- **输出与验收**：事先约定输出 schema、产物／证据引用、成功与失败条件。模型声称“已完成”不等于业务成功，执行方须核验可观察结果；需要人判断的事项用已设计的分支或审批表达。
- **预算与退出**：执行方限定时间、费用和探索轮次；工作流 timeout 覆盖该执行预算与必要通信时间。预算耗尽、需要补资料、结果未知不能伪装成 completed，也不能发明引擎未识别的 state。
- **恢复与去重**：记录 Agent 任务／会话与动作提交的关联；同 submissionKey 重传回同一执行记录，同 businessKey 防重复业务效果。原结果不明时先回查，不让工作流节点重试和 Agent 内部重试同时重做同一外部效果。
- **审批与版本**：Agent 可以提出计划和产出草稿，执行权限仍由服务端校验；必需的人类审批不能被模型自行通过或跳过。固定外部流程版本与执行器／Skill 版本的对应关系，运行中不因修改提示词就悄悄改变已批准的业务阶段。

可按“发起 → Agent 调查／产出建议 → 校验 → 必要审批 → 执行 → 对账”分工。这里描述业务阶段；校验与执行要映射到已有动作或业务服务，不假定引擎有同名通用节点。若不需要独立业务阶段或多方交接，不必为了装下 Agent 再建一个空壳流程。

## 在当前服务中落地

先通过能力／动作目录确认目标租户已有可用执行器，再按 [动作执行面](action-provider.md) 接入；长任务异步受理、可回查、如实处理取消与未知结果。没有已登记的 Agent 执行面时，说明还缺哪段接线，不虚构 `uses: agent/skill` 之类动作，也不把任意 Skill 文件路径塞进 YAML 期待服务端执行。

[MCP](mcp.md) 是外部 Agent 调用 workflow 的方向，不自动提供 workflow 启动 Agent 的能力。Agent 可以按用户授权建草稿或调用既有流程；发布后的结构仍由已发布版本和引擎规则执行。单个 `ai.structured` 动作也不自动成为有工具循环和会话恢复的 Agent runtime。

给出选型建议时，说清选择、下一步的控制方、业务状态的事实源，以及现有能力与尚需接入的部分。建议用 Agent + Skill 时，不继续要求用户登记／发布 workflow；建议混合时，明确哪些阶段固定、哪段允许自主求解，并分别验证业务推进与 Agent 的真实产物。
