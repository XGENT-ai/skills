# 问题与报告合同

## 落盘与交付

- 默认保存完整 Markdown 报告；只有用户明确要求仅聊天/不写文件时跳过，不询问是否保存。
- 路径优先级：用户指定路径 → 附带的本地计划同目录 `<计划名去扩展名>.code-review.md` → 仓库既有报告目录 → 当前工作区 `docs/reviews/<主题>.code-review.md`。无本地计划时，主题可用 `uncommitted`、`commit-<短SHA>`、`range-<短A>-<短B>` 或 `against-<基准分支短名>`；将分支中的 `/` 等路径字符转换为 `-`，不把 ref 直接作为目录。
- 写前检查文件已存在与否。仅在用户明确授权更新/覆盖该报告时覆盖；否则另存 `<主题>.code-review.<YYYY-MM-DD>.md`、`<主题>.code-review.<YYYY-MM-DD>-2.md` 等未占用名称。指定路径冲突也遵守此规则，最终说明实际路径。不得把报告写到代码或原计划文件，即使名字碰巧一致。
- 由当前主 agent 单独写入完整报告，回读实际文件核对内容与定位。空 findings、`inconclusive` 和部分覆盖不免除落盘。不要只写摘要或拼接未经裁定的 reviewer 回报。
- 最终聊天给实际文件链接、总体结论和重要问题/限制摘要。写入失败时明确“报告未落盘”、原因和目标路径，聊天提供完整报告以保留结果，落盘仍标未完成；不链接不存在的文件。

## 问题格式

每条一个独立根因，优先级置于简短行动标题前（标题不超过 80 字符）；问题正文用一段说明触发条件、实际行为、影响和关键依据。不要在正文堆阅读日志。

```markdown
### F-01 · [P1] <简短、可执行的修复标题>

- 定位：<目标路径:短行范围，target/index/base 侧及版本；须与 diff 重叠>
- 问题：<在具体输入或状态下，改动如何导致故障，影响哪个调用方/契约，为什么是本次引入。单段。>
- 证据：<上下游代码、需求/计划/仓库规则的精确定位，或复现命令与实际结果>
- 修复与验证：<最小修复方向；验证该行为的断言/回归场景，不自动实施>
- 置信度：<高/中及依据；可用 0–1 数值，但不把主观分值伪装成统计测量>
```

主定位取最小有意义的 diff 行范围，通常 1–5 行，避免超过 10 行。删除缺陷定位到基线侧删除行并标 SHA；缺失行为定位到应负责它的改动入口/调用点，不凭空造一个不存在文件的行号。完整需求遗漏确实没有 diff 锚点时，放计划符合性缺口，说明影响，可影响结论，但不伪装成行内 finding。

本地当前文件用可点击路径；历史版本另标 `SHA:path:line`，需要可点击证据时链接实际存在的版本快照文件。支持证据可在 diff 外。基于仓库规则的结论须引用实际读过且适用的规则最小行范围；不能只写“违反最佳实践”。

不强制给代码片段。确有助益时最多三行；`suggestion` 块仅含可直接替换的最小代码，保留原缩进，不在块内解释。自然语言足以说明修复时不生成 patch。

## 严重度与置信度

| 等级 | 含义 |
| --- | --- |
| P0 | 必须立即停止其他工作处理的普遍性严重故障，阻断发布/运行/主要使用，无须额外输入假设；极少使用 |
| P1 | 紧急，应在下一修复周期处理的高影响缺陷；写明受影响条件与范围 |
| P2 | 应修复的一般缺陷，有明确局部功能、兼容性、性能或维护后果 |
| P3 | 有证据、值得修复但优先级低的小问题；纯风格和个人偏好不报 |

严重度描述后果，置信度描述证据。只有猜测的风险属于待核实项，不以 P3 收纳。不要把所有安全字样都升为 P0，也不把未运行测试自动降格成已证实失败。

## 完整报告顺序

1. **确认问题**：按 P0 → P3 排序，F-01 等稳定编号。没有时写“未发现可确认的问题”，不凑数；复审沿用编号并区分已解决、仍存在、新增。
2. **待核实/待决策项**：缺少什么证据、影响哪个结论、如何补证；无法访问的文件/环境、需求歧义、尚未运行的关键验证放这里。
3. **覆盖与验证**：一句话意图；仓库根与日期；原输入、解析 SHA、比较方式、工作树/index 指纹或快照、文件限制、纳入/排除项；已审行为链与未覆盖部分；实际命令、目标版本、结果、失败原因。区分静态、测试、浏览器与外部资料证据；注明实际 reviewer 分工（若有）。
4. **计划符合性（有计划才写）**：计划路径和版本、本次任务/里程碑；仅列相关需求的映射和缺口，包含未核实及后续范围。不要复制整份计划或更新其进度。
5. **总体结论与修复顺序**：结论、1–3 句理由与覆盖限制；优先解除契约/数据/安全根因，再修局部行为，最后验证相关回归。明确解除阻塞的可观察条件，不把评审结论当作 merge/deploy 授权。

### 正确性结论

- `patch is incorrect`：有已证实影响正确性或形成实质阻塞的缺陷/本期需求缺口，引用对应编号或计划缺口。其余覆盖不足仍须说明。
- `patch is correct`：在明确审查范围内未发现上述缺陷，证据足以支撑判断；非阻塞的小问题不自动否定正确性。表述为评审判断，不保证不存在未知 bug。
- `inconclusive`：尚无足够证据裁定，或没有实际可审变更，例如基线不明确、关键调用方无法读取、冲突未解或关键验收无法核实。说明缺口，不把它写成代码已证实有错。

空 findings 不自动等于正确；未运行全量测试也不自动等于不可裁定，依据关键行为的实际证据判断。报告落盘成功与代码是否正确是两个不同结论。
