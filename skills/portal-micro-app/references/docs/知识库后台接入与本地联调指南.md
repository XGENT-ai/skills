# 知识库后台接入与本地联调指南

> **读者**：开发知识库后台的第三方团队（下称「知识库团队」）+ XGENT 平台团队。
> **读完即可**：(1) 知道知识库后台按什么契约接入；(2) 交付什么；(3) 在**自己本地**把整条链路跑通、自测，不必每次依赖平台团队配合。
> **前置必读**：[`SSO与App开发指引.md`](./SSO与App开发指引.md) 的 **§5（嵌入式微应用）、§7（独立后端应用）、§11（跨应用调用/令牌交换）**。本文是该指引在「知识库」这一具体应用上的落地补充，不重复其原理。

## 0. 一页速览：谁做什么

知识库后台属于**集成方式三：独立后端应用**（有自己的进程、自己的数据库，消费门户签发的 TDT）。和平台已有的 `files` / `spms` / `qbank` 同构。

整条链路的工作分两边。**指引能让知识库团队完成的，只有「运行时契约」这一半**；另一半「门户侧注册与部署接线」的代码全在平台 monorepo 里，知识库团队改不了，必须平台团队做。

| 工作 | 由谁做 | 说明 |
| --- | --- | --- |
| 资源服务器验 TDT（introspect + 四道闸） | **知识库团队** | 抄 `apps/spms-server/src/lib/gate.ts`，见 §2.1 |
| 租户隔离、限流、审计、`/health` | **知识库团队** | §2 |
| 临时前端（micro-app，用 portal-sdk 握手） | **知识库团队** | §2.6（此前端是临时测试用，后续会被新前端替换） |
| 后端 docker 镜像 + 契约清单交付 | **知识库团队** | §4 |
| 落地 ACL Manifest | **平台团队** | 知识库团队提供 JSON，平台写进**市场清单 `aclManifest` 字段**（APP-INTEGRATION，无需改 `manifests.ts`；代码注册表仍作回退） |
| 落地 scope `knowledge.read`/`knowledge.write` | **平台团队** | 随**清单 `scopes`+`scopeLabels`** 配置入库（APP-INTEGRATION，App 命名空间 scope 无需改 `scopes.ts`） |
| 把占位 listing 补成真清单（`embedUrl`/`scopes`/`navItems`/`dependencies:[files]`/`aclManifest`/`serviceBaseUrl`/`exchangeTargets`） | **平台团队** | 现在 `knowledge` 仅作为「依赖 files」的占位清单存在 |
| 服务发现 + `/svc/knowledge/` 路由 | **平台团队** | 运行时按清单 `serviceBaseUrl` 解析（已删 `SERVICE_REGISTRY`）+ Caddy 一条通用 `/svc/*` 规则（命名约定 `knowledge-server:8080` + 已注册 key 白名单 map） |
| 反代 CSP（同源托管） | **平台团队** | 同源托管下 `frame-src 'self'` 维持不变；额外 `connect-src` 由清单 `embedCsp` 声明。iframe 调后端走宿主代理同源，**不再需要 per-App CORS**（APP-INTEGRATION） |
| 创建服务账号（`token.introspect`，必要时 `client_credentials`） | **平台团队** | 把 clientId/secret 发给知识库团队 |
| token-exchange grant：`knowledge → files` | **平台团队** | 若知识库要读文件 |
| compose profile `app-knowledge`（指向**对方镜像**）/ K8s Deployment | **平台团队** | 现有 App 都长在单一 monorepo 镜像里；知识库是**外部独立镜像**，作为额外服务接入 |
| 提供「本地联调套件」给知识库团队 | **平台团队** | §5.1 |

> **关键架构点**：现有 6 个独立后端全部 `image: ${XGENT_IMAGE}` + `command: bun --filter @xgent/<key>-server`，即同一个 monorepo 镜像靠 compose profile 区分。知识库只交一个**外部镜像**，刻意**不进** monorepo 镜像，而是作为独立镜像的额外 compose service / K8s Deployment 接入。`DeploymentDriver` 抽象照样能管任意镜像，只要平台侧注册好 service 映射。

## 1. 集成模型

- **listingKey / appKey / TDT 的 `aud`** 三者同名，固定为 **`knowledge`**。
- **依赖** `files`（文件管理）。安装知识库会按拓扑序先补装 files（[指引 §4.5](./SSO与App开发指引.md)）。
- 身份模型回顾（[指引 §1/§9](./SSO与App开发指引.md)）：知识库后端**不持有门户 HS256 密钥、不自己验 JWT 签名、不自己实现登录**。它只做一件事——把收到的 `Authorization: Bearer <TDT>` 发给门户自省端点，换回已解析的声明，再据此鉴权。

## 2. 知识库团队要实现的（运行时契约）

> 强烈建议**直接对照 `apps/spms-server/`** 实现，它是最贴近的参考：自己的库、自己的 gate、token-exchange 调 files 的同构案例。下列每条都能在 spms-server 找到对应代码。

### 2.1 验 TDT：自省 + 四道闸

照 `apps/spms-server/src/lib/gate.ts`：

1. 取 `Authorization: Bearer <TDT>`，缺失 → `401 UNAUTHENTICATED`。
2. `POST {PORTAL_INTROSPECT_URL}`，带服务账号 Basic（`Authorization: Basic base64(clientId:secret)`），body `{ token }`。
   - 自省一个**无效/已撤销** TDT 也是**成功**返回，只是 `active:false`——不要当传输错误。
   - 结果**缓存到 `exp` 前**（上限 60s），降低往返。
3. 四道闸（缺一不可）：
   - **身份**：`(claims.listingKey ?? claims.aud) === "knowledge"`，否则 `401 INVALID_TOKEN`（不是发给你的令牌）。自省补了稳定身份 `listingKey`（= `contentOwner`）；独立后端禁 appKey 漂移，故二者相等，但按 `listingKey` 鉴权对「安装态 appKey」透明、更稳（APP-INTEGRATION §4.0）。
   - **scope**：所需 scope ∈ `claims.scopes`，否则 `403 INSUFFICIENT_SCOPE`。
   - **管理操作**：结构性管理看 `claims.role === "admin"`（`requireAdmin`）。
   - **细粒度操作**：看 ACL —— `claims.bypass || claims.permissions 命中目标 PID`（`requirePerm`，[指引 §12](./SSO与App开发指引.md)）。
4. **服务态 TDT**（`kind:"service"`）无用户、`permissions` 为空、`bypass=false`——按 **scope** 授权，不走 PID。

### 2.2 租户隔离

每条业务查询都按 `claims.tenant_id` 收口。同一应用在不同租户下是相互独立的数据。**永远不要**信任请求体里自带的 tenantId，只认 TDT 里的。

### 2.3 scope

知识库专用：`knowledge.read`（读）/ `knowledge.write`（写）。这两个 App 命名空间 scope 由**平台团队**随**市场清单 `scopes`+`scopeLabels`** 配置入库（APP-INTEGRATION，无需改 `packages/shared/src/scopes.ts`）；知识库团队只需在实现里按上面四道闸校验它们。读文件另见 §2.4。

### 2.4 读文件：令牌交换到 files（[指引 §11](./SSO与App开发指引.md)）

知识库后端要读门户文件服务里的文件时，**不要**直接拿用户的知识库 TDT 去调 files——`aud` 不匹配会被 files 拒。走 OAuth Token Exchange 换一个 `aud=files` 的 TDT：

```
POST {PORTAL}/oauth/token
  grant_type    = urn:ietf:params:oauth:grant-type:token-exchange
  subject_token = <知识库当前 TDT>
  audience      = files
  client_id     = knowledge          # 必须等于 subject_token.aud
  client_secret = <知识库 App Secret>
→ { access_token: <aud=files 的 TDT>, scope, expires_in }
```

前提（平台团队配置）：建立 `knowledge→files` 授权关系、files 开启交换并把 knowledge 加入白名单、用户事先在交换授权页同意。参考 spms-server 调 files 的实现。

### 2.5 限流 / 审计 / 健康检查

- **限流**：自己做一层，按 `(aud, tenant)` 每分钟固定窗口（spms 默认 600/min）。
- **审计**：关键操作（建/改/删）用**当次用户 TDT** 调 `POST {API_BASE_URL}/api/v1/audit`（scope `audit.write`）写入平台统一审计，不要自建审计表（[指引 §13.8](./SSO与App开发指引.md)）。
- **健康检查**：暴露 `GET /health`，返回统一信封 `{ service, db, redis, time }`（deploy-controller 用它判 `ready`）。照 `apps/spms-server/src/app.ts`。

### 2.6 临时前端（micro-app）

> 当前这个前端是**临时测试用**，后续会被正式知识库前端替换。所以不必在它上面过度投入。

- 用 `@xgent/portal-sdk` 握手：`createPortalClient()` → `sdk.ready()`（[指引 §5.2](./SSO与App开发指引.md)）。
- 调自己后端**优先走宿主代理，零跨域**：`sdk.callService("knowledge", "/api/...", { method, body })`。宿主会代铸/复用 `aud=knowledge` 的 TDT 带上去——iframe 完全不碰 CORS。
- ACL UX 门：`sdk.acl.can("knowledge:action:...")` 隐藏无权入口（仅 UX，真安全门在后端 §2.1）。

## 3. 环境变量契约

镜像里**不含任何 `.env`**（与平台约定一致），所有配置在运行时注入。下表照 spms-server 的 `env.ts` 同构，前缀换成 `KNOWLEDGE_`：

| 变量 | 必填 | 默认 / 示例 | 说明 |
| --- | --- | --- | --- |
| `KNOWLEDGE_DATABASE_URL` | ✅ | `postgres://…/xgent-knowledge` | **自己的库**，不要落进门户库 |
| `KNOWLEDGE_SERVER_PORT` | | `8080`（容器内统一） | 监听端口。**容器/生产统一 8080**——反代一条通用规则按 `/svc/<key>` → `<key>-server:8080` 路由（APP-INTEGRATION）；本地裸跑可另取（如 4700），但容器镜像务必听 8080（或读 `PORT`） |
| `REDIS_CONN_STRING` | | 空 | 可选；不配则降级到进程内缓存（限流/自省缓存） |
| `PORTAL_INTROSPECT_URL` | ✅ | `http://localhost:3000/api/tokens/introspect` | 门户自省端点 |
| `KNOWLEDGE_SA_CLIENT_ID` | ✅ | `knowledge-server` | 服务账号 Basic（平台团队发给你） |
| `KNOWLEDGE_SA_CLIENT_SECRET` | ✅ | —（明文只发一次，妥存） | 同上 |
| `API_BASE_URL` | ✅ | `http://localhost:3000` | 门户 Open API 基址（审计/通讯录回调） |
| `PORTAL_BASE_URL` | ✅ | `http://localhost:5300` | 门户 web 源——**宿主代理从这个源发来**，CORS 必须放它 |
| `KNOWLEDGE_APP_URL` | | `http://localhost:5309` | 你的临时前端源（独立调试/健康检查用） |
| `KNOWLEDGE_AUDIENCE` | | `knowledge` | 接受的 TDT `aud`（= listingKey） |

> **dev 自省捷径（可选）**：门户在 `DEV_MOCK_OAUTH=true` 时支持 `x-resource-key` 免服务账号自省，**但门户只比对 `FILES_RESOURCE_KEY` 一把 key**（不识别各 App 自己的 key）。若想用这条捷径，把你发出的 `x-resource-key` 设成门户那把 `FILES_RESOURCE_KEY` 的值即可；否则一律走 Basic（推荐）。生产 `DEV_MOCK_OAUTH=false` 一律拒绝该 header。

## 4. 交付物（不止一个镜像）

只交后端镜像**不够**。完整交付：

1. **后端 docker 镜像** —— 资源服务器，监听 `KNOWLEDGE_SERVER_PORT`（容器内 **8080**），暴露 `/health`，按 §3 读环境变量。
2. **临时前端** —— 静态产物（`dist/`，由平台服务在 `/apps/knowledge/`）；交付方式见 §6。
3. **契约清单**（一页 markdown / json）：
   - `listingKey: "knowledge"`、`version`
   - 需要的 scopes：`knowledge.read` / `knowledge.write`（+ 经交换访问 `files.*`）
   - `dependencies: ["files"]`
   - **ACL Manifest（JSON）** —— 平台据此渲染权限矩阵、算有效权限，见附录模板
   - `navItems`（贡献到左侧导航的入口）、`embedUrl`、`allowedOrigins`
   - **完整环境变量契约**（§3 那张表的最终取值口径）
4. **运维命令清单**：
   - DB 迁移命令（镜像内可执行，如 `bun run src/db/migrate.ts`）
   - 每租户 bootstrap 命令（首次某租户安装时跑：建默认数据/接线）
   - `/health` 路径与判活口径

## 5. 本地联调：知识库团队如何在本地测试

难点：完整链路（市场安装 → iframe 握手 → mint `aud=knowledge` 的 TDT → 自省）需要一个**已把 knowledge 注册好**的门户，而注册代码在平台 monorepo 里，知识库团队改不了。因此分两层测试。

### 5.1 联调套件（平台团队已产出 → [`deploy/knowledge-devkit/`](../deploy/knowledge-devkit/)）

平台团队交给知识库团队：

- **已预注册 knowledge** 的门户镜像两个（`xgent-ai-portal` + `xgent-ai-portal-proxy`，已预置 listing/manifest/scopes 清单配置 + Caddy 一条通用 `/svc/*` + `/apps/*` 规则（`knowledge` 已在 `/svc` 白名单 map），**不再烘焙 `SERVICE_REGISTRY` / per-app 路由**），以 `docker save` tar 包交付（§6）。
- `deploy/` 目录，其中 `deploy/knowledge-devkit/` 含：
  - `docker-compose.knowledge-dev.yml` —— 一个**叠加在 `deploy/docker-compose.yml` 之上**的 override，只加两样东西：① 指向你们镜像的 `knowledge-server`（profile `app-knowledge`）；② 把你们前端 `dist` 卷挂进反代的 `/apps/knowledge/`（同源，绕开 `frame-src 'self'` 限制）。
  - `compose.env.knowledge.example` —— 追加到 `deploy/compose.env` 的增量（`DEV_MOCK_OAUTH=true`、SA 密钥、`KNOWLEDGE_IMAGE`、`KNOWLEDGE_FRONTEND_DIST`、各连接串）。
  - `README.md` —— 完整的起栈步骤（本节是摘要，**以它为准**）。

> 知识库团队**只需装 Docker**，无需平台源码。

### 5.2 起栈（知识库团队，摘要——详见 devkit `README.md`）

```bash
# 1) 载入门户镜像 + 你们的后端镜像（无需 docker hub，见 §6）
docker load < xgent-ai-portal.tar.gz && docker load < xgent-ai-portal-proxy.tar.gz
docker load < knowledge-server.tar.gz

# 2) 配 env：基础模板 + knowledge 增量；填 KNOWLEDGE_IMAGE / KNOWLEDGE_FRONTEND_DIST(绝对路径)
cp deploy/compose.env.example deploy/compose.env
cat deploy/knowledge-devkit/compose.env.knowledge.example >> deploy/compose.env

# 3) 基础设施(自动建 xgent-knowledge 库) + 门户库迁移/种子
docker compose --env-file deploy/compose.env -f deploy/docker-compose.yml --profile local-infra up -d postgres redis minio
docker compose --env-file deploy/compose.env -f deploy/docker-compose.yml run --rm portal-api bun run db:migrate
docker compose --env-file deploy/compose.env -f deploy/docker-compose.yml run --rm portal-api bun run db:seed

# 4) 起门户 + 反代 + 你们的 knowledge-server（注意两个 -f + app-knowledge profile）
docker compose --env-file deploy/compose.env \
  -f deploy/docker-compose.yml -f deploy/knowledge-devkit/docker-compose.knowledge-dev.yml \
  --profile local-infra --profile app-knowledge up -d reverse-proxy portal-api knowledge-server

# 5) 你们自己的库迁移（命令以你们镜像为准）
docker compose --env-file deploy/compose.env \
  -f deploy/docker-compose.yml -f deploy/knowledge-devkit/docker-compose.knowledge-dev.yml \
  --profile app-knowledge exec knowledge-server <你们的迁移命令>
```

后端改代码的内循环：重建你们的 `knowledge-server` 镜像（或让本地 `bun --watch` 实例以服务名 `knowledge-server`、端口 `8080` 接入 compose 网络），门户那一坨不用动。反代现按命名约定固定路由到 `knowledge-server:8080`——**已无 `KNOWLEDGE_UPSTREAM` 覆盖环境变量**。

### 5.3 冒烟步骤（走通主路径）

打开 `http://localhost/` →

1. **dev 登录** → 选 `rockie`（晨光教育集团 admin + 平台管理员）。
2. **应用市场 → 安装「知识库」** → 应连带补装 `files`，状态变 `ready`。
3. **应用中心打开知识库** → iframe 加载你的临时前端，`sdk.ready()` 握手成功。
4. **前端调后端**：`sdk.callService("knowledge", "/api/...")` 通 → 证明宿主代理 + 你的四道闸 + 自省全链路 OK。
5. **读文件**（若实现）：触发一次读文件 → 证明 `knowledge→files` 令牌交换生效（首次会弹交换授权页）。
6. **租户隔离**：顶栏切到另一个租户 → 看不到上一租户的知识库数据。

### 5.4 纯后端自测（不依赖完整 UI 链路）

只想验 §2.1 的四道闸时，不必走 iframe。在 dev 门户里：

1. 用 admin 会话**自助注册**一个 `knowledge` 应用（`POST /api/admin/apps`，[指引 §3.2](./SSO与App开发指引.md)），声明 scopes，建一把 App Secret。
   > 注意：自助注册的「裸应用」**没有 ACL Manifest/navItems**，足够测 aud/scope/租户隔离，但 `requirePerm` 的 PID 细粒度要等平台团队把 manifest 注册后才完整。
2. 走 [指引 §6](./SSO与App开发指引.md) 拿一个 `aud=knowledge` 的 TDT（`/api/tokens/authorize` → `/oauth/token`）。
3. `curl` 你的后端：

```bash
# 经反代同源到达（容器内统一 8080，devkit 仅 expose 不发布到宿主；knowledge 已在 /svc 白名单）：
curl http://localhost/svc/knowledge/api/whatever -H "Authorization: Bearer <TDT>"
# 预期：scope/aud 不符 → 403/401；正确 → 200 信封
```

### 5.5 常见问题

- **iframe 打不开 / `/svc/knowledge` 502**：你的 `knowledge-server` 没起或刚 crash；`docker compose logs knowledge-server`。
- **自省被拒（401）**：服务账号 Basic 不对，或想用 `x-resource-key` 捷径但值不等于门户的 `FILES_RESOURCE_KEY`（§3 注）。
- **`db:seed` 后浏览器要重登**：seed 重新生成 UUID，会话失效，重新 dev 登录即可。
- **跨源 iframe 调试不透明**：临时前端尽量同源（`/apps/knowledge/`）或用宿主代理 `callService`，少用跨源直连。

## 6. 不发 docker hub 的镜像交付

两条镜像（知识库后端 → 平台；平台 devkit → 知识库团队）都不上公网 registry：

- **首次 / 偶发**：`docker save` + `docker load`，传 tar 包。零 registry，最简单。
  ```bash
  # 交付方
  docker save knowledge-server:1.0 | gzip > knowledge-server-1.0.tar.gz
  # 接收方
  docker load < knowledge-server-1.0.tar.gz
  ```
- **迭代频繁**：用**私有 registry**（平台已在 KubeSphere 节点上跑 `registry:2`，或自建 Harbor / 用 TCR 私有实例）。
  ```bash
  docker tag knowledge-server:1.0 <私有registry>/knowledge-server:1.0
  docker push <私有registry>/knowledge-server:1.0
  ```
- **不建议**从源码构建交付——违背「只交镜像」，且要把对方依赖 vendor 进构建。

## 附录 A：ACL Manifest 模板（知识库团队填，平台团队落码）

照 [指引 §4.4](./SSO与App开发指引.md) 的类型（`packages/shared/src/acl.ts`）。PID 语法 `knowledge:<page|action>:<key>`，数据范围 `own < team < all`。

```ts
const KNOWLEDGE_MANIFEST = {
  version: "1.0.0",
  landingPageKey: "docs",
  groups: [{ key: "kb", label: { "zh-CN": "知识库", en: "Knowledge" }, sort: 0 }],
  pages: [
    { key: "docs", path: "/docs", label: { "zh-CN": "文档", en: "Docs" }, navItemId: "nav-docs",
      parentKey: "kb", supportedScopes: ["own", "team", "all"], defaultForMember: true },
    { key: "admin", path: "/admin", label: { "zh-CN": "知识库管理" }, supportedScopes: ["all"] },
```
