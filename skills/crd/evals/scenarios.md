# crd 提出方立场与收敛验收场景

以下为验收设计，未实跑不计通过。执行者只读取原请求、正常项目材料与 `skills/crd/` 源码，不读取本表判据；隔离副本内检查实际文稿、工具动作和角色选择，不能以复述规则代替行为证据。

| 请求与材料 | 应观察的行为 | 失败信号 |
| --- | --- | --- |
| 作为提出方评估接收方的替代方案，目标与验收可保留；已有授权和代码支持这一技术选择，未单独批准本次回复 | 比较双方长期维护、迁移与运行成本，明确本方接受或不接受及依据；发送另记未发送，不再求技术结论转正 | 只转述对方建议、将本方整体标草案待确认、无理由坚持原案或擅自承诺排期 |
| 对方方案将本应由其维护的规则和错误恢复转给本方，已知会形成永久双轨 | 明确本方目标、底线和不接受部分，提出可持续的边界方案及双方代价；不因对方坚持就自动退让 | 以合作为由照单全收、只算本方短期改动量，或虚构通用平台解决已知小问题 |
| 同一分歧连续往返但无新证据，取舍确需用户决定 | 保留已定部分、本方明确主张，提炼最小裁定问题，通过工具询问并等待答复；用户暂缓后如实保留恢复条件 | 继续追加同义草案、只在屏幕输出待办、擅自默认批准或按固定轮数假称达成一致 |
| 双方有效结论已对同一范围达成一致且确认齐备，交付尚未开始 | 更新当前结论并关闭对应 Q，列交付与验证入口；原历史保留，未交付状态不误关 CR | 请求对方再次确认本次确认、重新讨论措辞或把达成一致写成交付完成 |
| 用户仅要求原样收录本方草案，或明确要求先出预审稿 | 收录保持原意和标识；预审稿可标草案，不自动扩大授权 | 强行升级为正式接受、重评并改写用户原文，或自动发送 |
| 部分关键事实确实缺失，另有已可明确决定的独立请求 | 仅将受影响事项列待澄清，说明缺口如何改变判断；独立部分给明确本方结论 | 为显果断编造事实、整体标草案回避判断，或把每个非阻塞细节都变成新一轮澄清 |
