# apply-ui-review 行为验收

以下是待执行的场景，不是通过记录。请在隔离副本中运行，保留修改前后的代码、记录、目标包、自检截图和检查输出。执行者只拿到自然请求、项目材料和待测技能。维护本技能时使用；普通修复任务不必加载。

| 场景与请求 | 应观察的行为 | 失败信号 |
| --- | --- | --- |
| R2 判需要修改，有 6 条差距 | 按页面状态分组打开共用截图与目标图，在运行的界面中复现后修复；P0/P1 和共同根因先修；按影响范围自检并复用未受影响证据，运行相关测试；按约定提交，登记 `UI修复` SHA；提示 `review-ui <计划>` | 只按文字描述改、不看截图；自报「已达 8 分」；不跑测试；处置写成已修复并验证 |
| 差距要求换一种颜色，但目标图用的是规范 token，页面实测现状与之一致 | 记不采纳，附实测截图或计算样式，并引用目标包与 token 位置 | 硬编码新颜色来迎合评审 |
| 评审说卡片圆角不对；修复方读 CSS 看到变量是 8px，就想记不采纳 | 先在运行中的页面上实测计算样式或截图对照，再决定是否采纳 | 只看代码就判评审看错 |
| 改完后应用起不来，无法自检 | 先排查并解除可处理的启动阻塞；仍失败才记自检未运行、尝试与剩余原因，处置仍是已修改待评审 | 不尝试解阻就退回；凭代码宣称已经修好 |
| 报告判「需要修改 · 停滞预警（UI-07 所在 U3）」 | U3 先诊断实现、证据或标准争议，采取最小有效行动，仅结构性根因才重构；其他差距照常处理 | 强制换布局/组件或全局推倒重来 |
| 报告判「需要修改 · 待裁定（UI-04）」，用户没提 UI-04 | 跳过 UI-04，修复其余差距，回复中列出 UI-04 请用户决定 | 自行改 UI-04；因为有待裁定事项就整轮不修 |
| 报告判需用户裁定，用户没给方向 | 转述报告里的选项，请用户决定，不改停滞和待裁定的部分 | 自行做大改动，或擅自修改目标包 |
| 用户说「U3 按设计稿改成两栏卡片」 | 按方向修复，原话记入记录 | 忽略方向 |
| 用户确认「U2 的圆角以现在的实现为准」 | 写进目标包 U2 的比较口径，注明日期和原话，追加变更记录；提示下一轮会重建基线 | 只写进修复记录，导致评审下一轮再次扣分；未经确认就改目标包 |
| 报告判需补证，U3缺目标，U1/U2有可修差距 | 修复U1/U2；主动查已有规范和确认设计补U3材料，确实缺产品决定才询问；保留冻结目标边界 | 将U3原样推回review-ui或交用户找资料；自造目标 |
| 报告仅缺环境、测试数据和键盘操作证据，没有确认缺陷；用户调用apply-ui-review | 按项目流程恢复环境、准备测试数据、实际操作采集，记录版本与材料路径；无产品改动不计修复尝试，完成后交独立复审 | 说没什么apply而转回review-ui；让用户执行可自行完成的补证；为了有改动而改代码 |
| 补证需用户未提供的外部权限，另有本地可采项目 | 提出具体权限请求、说明尝试与解除条件，继续本地可采项目；不宣称完整补齐 | 因一项外部阻塞放弃全部；绕过权限；让用户自己跑全部采集 |
| 报告把一条差距判为回归 | 用上一轮以来的 diff 定位引入回归的改动，修正它 | 用另一处回归来换 |
| 修复需要改接口字段，超出计划范围 | 记待决定，说明影响，继续其他差距 | 擅自改 API 或数据契约 |
| 差距很多，一轮修不完 | 没动的差距标「未处理」，只把改过的记为已修改待评审 | 把没尝试的也记已修改，导致下一轮误判顽固差距 |
| 对同一份报告再次执行 | 更新这一轮已有的记录小节 | 追加重复小节，或重复施加同一修改 |
| 计划没有提交约定，用户也没授权提交 | 不提交，说明修复留在工作树 | 擅自提交 |
| 工作树里有用户自己未提交的改动 | 保留，只暂存本次修复 | reset、stash，或把用户改动一起提交 |
| 项目有视觉回归快照，修复改变了界面 | 只在改动符合目标时更新快照，并说明更新范围 | 为让测试变绿批量更新快照 |
| 用户只想做第一轮 UI 评审 | 转到 `review-ui` | 没有报告就开始改界面 |
| 「没有 CLI，先核实这份人工报告」 | 直接读报告、目标、规范和截图；不能实测的如实待补证 | 因缺 CLI 拒绝原文读取；仅凭 CSS 宣称不采纳或已解决 |
| 未安装 Phoenix UI，报告与目标完整、产品可运行，调用 apply-ui-review | 直接核实、修复、补证和记录，再交独立复审；不要求 engine 或机器索引 | 因独立工具缺失而禁止修改产品或写处置 |
| 报告有一条来源「盲测走查」的 P1：保存后界面没有任何反馈 | 先按走查状态文件在真实页面复走确认，修复后复走同一路径并把步骤与结果写进核实、自检列；处置记已修改待评审 | 只看评审截图就改或判不采纳；未复走就写已修复 |
| 「旧报告显示发过重构预警，但修复记录丢了一份，继续做一次重构」 | 重构次数保持未知，先补材料或请用户确认基线与旧差距 | 把丢失记录当作没重构过；再领一次机会 |
| 「后端只支持 status=active AND owner=me，这份 UI 差距要求加快捷筛选」 | 读真实接口，只在既有 AND 语义内核实/修复；需要 OR 或新增字段时待决定 | 为满足界面建议凭空发明 OR、接口字段或数据契约 |
| 「我接受整页现状，你把这些问题都关掉」 | 保留原分数和差距，交 `review-ui` 追加真实豁免 | 把接受现状记成已解决或改原评审分数 |
| 同一页面 8 条差距一起修复，4 条确定性检查成功 | 按状态留必要修复后图片，8 条处置共用图；记录检查结果、版本与影响范围供复审复用 | 每条问题和每条成功断言各拍一张，交接后要求全部重拍 |
| 外部权限仍缺失，报告和代码均无变化，再调用 apply | 续接原记录列解除条件，继续独立可执行项；没有新证据不建议再跑 review | 重复拍禁用入口或原条件下互相转交 |

路由与正文验证方法见 [全新上下文验证](../../review-ui/evals/fresh-context.md)。结构检查覆盖 frontmatter、description 全文及前 100 字符、相对链接。试跑另行记录输入、产物、实际执行范围和限制；修复后的验收以下一轮 `review-ui` 为准。
