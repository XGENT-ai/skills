# UI 验收修复记录合同

## 记录位置

整个验收循环只用一个记录位置，`review-ui` 每轮都去那里读取。

1. 输入计划有自己的记录约定时，沿用它。
2. 采用 `dev-plan` 记录协议时，第一次处置选定一份里程碑记录 `<计划名去扩展名>.records/M<n>.md`，在其中建「UI 验收修复」节，之后各轮都写在这一节：
   - 优先选差距所在界面所属的里程碑；
   - 跨里程碑或无法区分时，选负责 UI 走查或阶段收口的里程碑。

   不新建「UI 整改」之类的里程碑。
3. 没有计划时，写在 `<前缀>.ui-review.applied.md`，前缀见 `review-ui` 的报告合同。
4. 每轮一个小节，不改写前几轮。对同一份报告再次执行时，更新这一轮已有的小节，不重复追加。`review-ui` 靠这些小节判断哪些差距被尝试过、哪个范围做过重构轮。

## 每轮内容

```markdown

### R2 → 修复 · 2026-10-08 14:30 +11:00

- 来源：[R2 报告](../LOGIN.ui-review.r2.md)（判定：需要修改 · 停滞预警（UI-07 所在 U3））；目标包 [LOGIN.ui-target.md](../LOGIN.ui-target.md) · 目标指纹 <前 12 位>
- 修复版本：UI修复 `abc1234`（未提交时写 dirty@<起始短 SHA> 和关键改动路径）

- 用户方向：<本次调用中用户给出的方向或决定，附原话；没有写「无」>

| 差距 | 核实 | 处置 | 改动落点 | 自检 |
| --- | --- | --- | --- | --- |
```

处置只用以下五种：

| 处置 | 含义 |
| --- | --- |
| 已修改待评审 | 本轮实际改过 |
| 不采纳 | 附反证或目标包、规范的位置 |
| 待决定 | 写明需要谁决定什么；按报告跳过的待裁定事项也记这一项 |
| 阻塞 | 写明依赖和解除条件 |
| 未处理 | 本轮没尝试，或在用户限定的范围之外 |

没有「已修复并验证」：是否解决由下一轮独立评审判定。

核实和自检列的依据，必须来自运行中的界面：本轮截图、页面实测值或实际操作结果。应用起不来时写「未运行」及原因，不用代码阅读代替。

只写核实结论、改动、检查结果和续做需要的事实，不写讨论过程、完整日志或技能使用经过。

## 计划同步

- **顺序**：先写记录并确认落盘，再在完成记录对应里程碑行的「提交」列追加 `UI修复` 加短 SHA，保留原有 SHA，例如 `a1b2c3d；修复 e4f5a6b；UI修复 c7d8e9f`。然后按计划约定单独提交这次登记，这次提交不回填自己的 SHA。计划没有「提交」列时，把修复版本写在记录的来源行。
- **里程碑状态一般不变**：UI 修复不会自动完成或重开里程碑。只有当修复推翻了某个里程碑已记录的退出检查时，才按计划协议把它改回进行中，并说明原因。
- **恢复快照**：只在「下一步」或阻塞确实变化时更新，摘要写 1–2 句；命令和逐条处置只放在记录里。
- **校验**：有计划指定的进度校验命令就运行。结构校验通过不代表界面验收通过。
