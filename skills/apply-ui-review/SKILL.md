# apply-ui-review · 落实 UI 验收评审

把独立评审给出的差距清单变成真实的界面改进，优先关闭验收阻断项和共同根因。评审看过目标和截图，所以可修复的差距默认全部处理；但每条仍要对照截图、目标包和规范核实一遍，评审看错的、与目标包矛盾的，不照着改。用户调用本技能，即授权在报告与项目范围内核实、修复、补证、解除可自行处理的阻塞、运行必要的检查、按计划约定提交并回写记录。没有代码可改，不等于没有工作；报告中的缺证清单也是执行输入。

**核实和自检都以运行中的真实界面为准。** 无论是判断评审看错、判断差距已不存在，还是确认修复生效，依据必须是当前有效的实拍截图、页面实测值和实际操作结果。同页面、状态、视口、主题、语言、数据与版本的多个问题共用一图，注明位置；不得按问题编号分别截图。已有证据经版本、条件、目标和影响范围核验仍有效时直接引用；历史证据不冒充新采集。不能读了代码就下结论。

**本技能不给自己打分。** 修复是否到位，由下一轮 `review-ui` 的独立评审判定，所以记录里的处置最多写到「已修改待评审」。不改评审报告、评审截图和 `judge.md`；只有用户明确确认后，才把用户的决定写进目标包。推送、部署等按已有授权处理。

`references/` 相对本文件解析。启动方式、组件库、设计规范和检查命令从目标仓发现。语言跟随用户。

本技能是独立的 SDLC 执行流程。
依据报告、目标包和修复记录续接，不绑定工具版本、规则版本或 skill 文档指纹；独立工具缺失或不兼容不阻止核实、修复与补证。

## 1. 锚定输入

1. 定位用户给的 UI 验收报告，从报告头的「评审对象」找到计划、目标包、截图目录和上轮报告，并核实它们确实对应。用户没给报告时，从上下文或计划同目录取轮次最大的 `.ui-review` 报告，不按文件修改时间或猜轮次。有多份无法判断时询问。
2. 按报告的验收判定处理：
   - **需要修改**：处理可修复的差距。带「停滞预警」时，按下文诊断原因，不强制重构。带「待裁定」时，那些事项先不改，记「待决定」，除非用户本次已就它给出方向。
   - **需补证**：本技能执行报告中的补证工作，并处理已评单元的可修复差距；不因缺证或没有确认缺陷而直接退回 `review-ui`，也不默认让用户准备环境或采集证据。按下节补齐可执行项后交独立复审。
   - **需用户裁定**：用户本次没给方向时，转述报告里的选项，请用户决定，不动停滞和待裁定的部分；给了方向就照做，并把用户原话记下来。
   - **通过验收 / 用户豁免通过**：只有用户要继续打磨时，才处理剩余差距。
3. 用户接受某处偏差或修改期望时，经用户明确确认后，写进目标包对应单元的比较口径或规范要点，注明日期和用户原话，并追加变更记录；下一轮评审会据此重建基线。用户接受整体界面时，提示由 `review-ui` 记为豁免通过，本技能不改报告。
4. 读目标包、报告中的差距清单、待裁定事项和上轮复核表，以及以往各轮的修复记录（见记录合同）。记下当前 HEAD 和未提交改动，分清哪些是用户已有的修改、哪些是本次修复。用户限定了差距编号或单元时，只处理这些。

## 补证与解阻

- 读取报告、采集清单及缺失状态的原始记录，逐项确定缺什么、执行动作和完成条件。能在当前权限和项目范围内完成的立即做，不把清单原样交给用户。
- 依项目既有流程启动或恢复测试环境，准备测试账号与种子数据，复用已有 mock/拦截方法到达目标状态，执行缺失交互并实测，必要视觉转折才截图；明确模拟范围，不把替身结果冒充真实集成。只用测试数据，不修改真实业务数据、不绕过权限或扩大产品范围。缺目标时先找已有规范及已确认设计；找不到或互相冲突才请求决定，不自造期望。
- 补证时发现真实产品缺陷，核实后在授权范围内修复并自检。仅缺截图或执行记录时完成采集即可，不为体现“apply”而改代码。待裁定项可先补事实，但不替用户决定期望或修复方向。
- 补采文件放 `<前缀>.ui-captures/r<n>-apply/`，记录被测版本、目标指纹、单元/状态/视口/主题、操作、实际结果和文件路径；保留每次必要采集，不按问题复制同状态图片，不覆盖评审截图、报告或 `judge.md`。临时服务用完清理，截图与日志遵循项目忽略约定。
- 在原修复记录位置的本轮补证小节记录补证动作、结果与剩余阻塞；纯补证不伪造差距编号。没有产品修改的采集不记「已修改待评审」，不增加修复尝试或重构计数。
- 只有缺少无法自行取得的权限、资料或需要产品决定时，才向用户提出具体请求，写清已尝试动作、所需输入与解除条件，并继续不受阻的事项。保留原报告、材料和修复历史，不重置记录。
- 补证材料是交接输入，不是独立验收结论。`review-ui` 核对目标、版本、条件与出处后直接引用有效的 apply 材料，仅失效或看不清时补采，并完成独立评分；不把 apply 截图冒充下一轮新采集。只有剩余工作确实是独立评审/确认评审，或可执行项已完成时，才交回复审；仍有外部阻塞时说明解除条件，不建议原条件下空跑。

## 2. 核实与排序

- **核实**：按页面状态分组打开报告截图和目标图，一次复现核实该状态的全部相关问题；同一原图只需打开一次，看不清先放大，不逐条重复截图。再对照目标包的规范要点、比较口径和 DESIGN.md。
- **成立的**：进入修复。
- **不采纳**：以下情况记「不采纳」并写明依据，不改代码：评审看错（运行中的界面与评审描述不符，附截图或实测值）；与目标包或规范矛盾；属于比较口径排除的差异。报告附了核对说明的差距，同样自己核实，确实不成立就记不采纳。
- **待决定或阻塞**：需要素材、文案、数据、接口或产品决定才能修的，记「待决定」或「阻塞」，然后继续处理其他条目。
- **待核实**：先在运行中的界面上确认现状；已经没问题就附截图如实记录，不为它改代码。
- **建议**：不扣分。与规范一致且代价小时可以顺手做，但不能因此降低对目标的还原度。
- **顺序**：P0/P1 先修；同一严重度内按可挽回分从高到低。能一次消掉多条差距的共同根因优先，例如字体没加载、token 用错、布局原语选错、容器约束。

## 3. 修复

- 在正确的层级修根因，层级从高到低依次是：主题与 token、共享组件、页面布局、单处样式。用 DESIGN.md 的 token 和现有组件，不为贴合截图写魔法数字，也不为单个页面复制一份共享组件。目标确实要求偏离规范时，记下依据。
- 只改界面范围内必要的代码、样式、素材和测试。修复需要改接口、数据契约或计划范围时，记「待决定」，不擅自扩大。
- 保留用户已有的修改，不 reset、stash 或回退。
- **回归**：报告判为回归的差距，先用上一轮以来的 diff 找出是哪个改动引入的，修正它；不要用另一处回归来换。
- **停滞诊断**：报告带停滞预警时，只诊断预警范围（全局，或某条差距所在单元）：
  1. 写清以往的尝试为什么没奏效。
  2. 先区分实现缺陷、证据不足和标准争议；有实现依据时再检查根因：布局模型或组件选错；素材质量不够；token 或主题不符；字体或图片没正确加载；容器与断点约束；数据形态；采集环境与目标不一致。
  3. 选证据最强的一条，采取最小有效修复或补证；只有结构性根因才重构，不为提分强制换组件或布局。标准争议记待决定。
  4. 把范围、诊断、实际改动与证据写进记录。实际重构每个范围每基线最多一次；没有重构也照实记录，重复实际修改仍无效时由复审转为停滞，不无限微调。
- **只记真正改过的**：一轮做不完的差距，如实标「未处理」，不算尝试过。只有真正改过的才记「已修改待评审」，下一轮的顽固差距判定以此为准。

## 4. 自检

1. 启动当前代码，先复用现有自动检查验证受影响条件，再按页面状态统一采集必要代表帧，与目标对照；共享组件、主题、字体、素材、依赖或布局变化时扩大复查范围。未受影响的有效结果复用，不机械重跑全部页面。一张修复后的状态图可核实多条差距。可供复审的截图直接存到 `<前缀>.ui-captures/r<n>-apply/`，不覆盖评审截图。
2. 运行计划和仓库要求的相关检查：组件测试、单元测试、类型检查、lint、构建。项目有视觉回归测试时，只在改动符合目标的情况下更新快照，并说明更新了哪些。检查失败时，分清是新引入的回归、原本就有的失败，还是环境问题；新引入的回归要继续修。
3. 应用起不来或无法截图时，先按补证与解阻流程处理；仍不能完成时，自检记「未运行」并写明已尝试动作及剩余原因，不能凭代码判断已经修好；处置仍是已修改待评审，由下一轮评审在真实界面上判定。
4. 自检不算验收：不估分，不宣称已经达标。

## 5. 提交、记录与交付

1. 按 [记录合同](references/record-contract.md) 保存本轮处置。更新这一轮已有的小节，不重复追加；保留用户文字、其他轮次和历史评审。
2. 计划有提交约定，或用户授权提交时：
   - 只暂存本次修复和记录，遵守仓库的提交规范，不跳过提交钩子；
   - 提交后，在完成记录对应里程碑行的「提交」列追加 `UI修复` 加短 SHA，再单独提交这次登记。

   两者都没有时不提交，修复留在工作树，下一轮评审以工作树为被测版本。提交失败就如实记录，不伪造 SHA。
3. 回读记录和计划的改动；查看最终 diff，确认没有无关修改，评审报告、截图和 `judge.md` 都没被改动，目标包只多了经用户确认的决定，用户的修改没被覆盖。
4. 回复内容：
   - 各类处置的数量和关键改动；
   - 重构假设（如有）；
   - 补证与解阻的动作、结果、材料路径及剩余缺口；
   - 自检和检查结果；
   - 提交 SHA，或未提交的原因；
   - 记录链接；
   - 待用户决定的事项。

   交接附影响范围、共用截图到问题的映射、可复用材料及仍缺的条件。没有新改动、新证据或阻塞解除时续接原记录，说明解除条件，不建议原条件下再次 review/apply。

   有新的可评证据、可执行的修复与补证完成后，结尾给下一步：用 `review-ui <计划路径或原范围>` 复审，按当前客户端写法给出（如 Codex `$review-ui`、Claude Code `/review-ui`）。不自行启动评审。

调用示例：

```text
使用 $apply-ui-review goal/LOGIN.ui-review.r2.md
使用 $apply-ui-review goal/LOGIN.ui-review.r3.md，只处理 UI-04 和 UI-07。
使用 $apply-ui-review goal/LOGIN.ui-review.r5.md，U3 按设计稿改成两栏卡片。
```

## 项目状态回写

若仓库已登记状态台账，或存在仓根 `.xgent-ai/sdlc/protocol.md`（兼容已有 `docs/project-status/protocol.md`；两套并存且未登记切换时先核对，不能双写），交付原产物后读取台账的回写规则（默认目录读上述协议），按仓内协议更新受影响对象的当前状态与来源链接，必要时维护索引；v4 日常直接更新当前页，事件留存条件或旧版事件要求以仓内协议为准；未启用时不自动建表，不依赖另装技能。只读/仅聊天/不保存约束优先，登记失败须说明，不影响如实交付已完成的原产物。

接着原评审对象登记处置：差距编号、处置、修复版本、自检结果和未完项，并链接实现记录。「已修改待评审」不登记为已解决，修复也不能登记成独立复审通过。
