# 审查重点

两位 reviewer 各读自己的节，跨重点追问时再读关联节；主 agent 读 C 节。实施者能在仓库同构代码中自行正确决定的细节不报，检查深度与计划改动面相称，不为填清单创造需求或阻塞。

## A. facts：计划与代码事实是否吻合

把关键陈述整理成“计划主张 → 类型 → 来源 → 核实结果”。优先核实会改变技术选择、依赖或交付结果的事实：

- 声称存在或可复用的路径、符号、路由、表、包导出、命令、配置是否真实存在；新增项明确标注即可，不能要求它已存在。
- 追到调用者与实现的行为：参数/返回、错误、分页、排序、事务、幂等、权限传播、缓存失效和删除语义。函数同名、类型匹配不等于行为满足。
- 安装/初始化、存量升级、部署配置和生产执行链是否与开发态假设一致。计划声明“无需改动”的邻接面是否真的支持目标。
- 数字与结论是否有用户要求、代码、配置、运行证据或明确决策来源；没有来源的性能承诺、规模、工期不能成为架构依据。
- 对照全文的范围/非目标、契约字段、事实归属、鉴权、数据生命周期、失败语义、迁移回滚和验收断言，找互斥陈述。矛盾同时定位两处，并说明在什么操作上无法同时成立。
- 旧文档与当前代码不一致时标明时间和基线；规则约束与运行事实分开，不能因为文档旧就自行废除规则。已有缺陷只有被本计划依赖或放大、导致目标无法交付时才进入本次 findings，并说明关联。

交回关键核实表：`主张/计划定位 | 事实/设计/假设/目标 | 证据定位 | 已核实足够/已核实缺口/未核实 | 影响`。无关事实不用穷举。

## B. architecture：架构与技术路线是否先进、可持续、不凑合

“先进性”评价的是在真实约束下能否改善交付、性能、安全、可靠性或维护成本。**新技术不自动加分，旧技术也不自动合格**。

1. 从本期 R/NFR/C 推导要解决的问题，找出决定形态、数据模型、契约、模块边界和迁移策略的关键选择。比较沿用现有范式与有实际收益的现代方案：能力差距、生态支持、复杂度、可维护性、迁移与运行成本。仅因版本旧而建议升级不算问题；已有方案无法满足受支持版本、必要能力或明确约束时指出。
2. 涉及版本能力、弃用、支持周期、安全公告或外部服务限制等时效性事实，先读目标项目依赖/锁文件，再查官方文档、发布说明或原始论文，标记版本、查询日期和 URL。不能联网则列具体待核实项，不用记忆冒充最新结论。
3. **持续性**：已有来源的后续需求（PRD 后续期次、已知 CR、仓库正在推进的迁移方向）能否在此设计上增量推进，而不是下期推倒；事实是否单一归属，接口是否有深度、变化是否局部；新旧版本共存、迁移/回填、切换、不可逆步骤与回滚是否成立。没有来源的“将来可能”不构成持续性要求。
4. **补丁式开发**：根因在共享模块、数据模型或契约，计划却在调用方或边缘叠特判、标志位、兼容分支、重复逻辑或适配层绕过；复制既有实现而不扩展它；同一状态散落多处靠手工同步；把临时方案写成终态而没有替换条件。这些都要定位根因所在层，给出在该层的修法。
5. **回避正确但难的做法**：正确做法在本期范围内可行，计划却因工作量绕开，例如用前端过滤代替服务端权限、用默认值兜底代替数据迁移、用冗余字段代替正确关系、用轮询代替已有事件机制、以“先这样后续再优化”跳过契约修改。指出时写明正确做法、额外成本和它避免的长期代价；只有长期成本显著更低时才报。用户已确认的取舍（分期、先能用）不推翻，可指出代价并建议计划记录重审触发条件。
6. **反过度设计**：按主技能 `@plan_proportionality` 双向核对。本期真实会发生的并发写、重复投递、跨资源部分完成、超时与不可信输入，是否有足够且最简的保证（条件写、唯一约束、事务、幂等键等）；没有真实触发、后果可接受或已由框架/约束/平台保证的事务、重试、租约、降级、补偿、自愈、沙箱/隔离、额外校验，以及只减少转发层的新抽象或基础设施，按其增加的实现与维护成本报为过度设计。未明确要求的 NFR 按 `@fr_before_nfr` 只看是否选了开销相近却明显更差的做法。
7. 开发对象与允许改动须能追溯到用户任务及项目职责；外部缺口应有提供方、契约及解除条件，不替依赖方设计内部实现。
8. 技术路线是否具体到实现者可直接编码：关键改动落点、可照着改的同构实现，新增或改变的签名、数据结构、错误语义有定义处。读代码、读依赖源码或小实验就能查清的未知被写成「实施时确定」「到某里程碑再冻结」，作为问题指出；需要 spike 的未知写验证问题、成功判据、影响的决策和最晚完成点，不在评审中自动实现。

交回关键决策评估：`选择 | 驱动需求 | 证据与版本 | 收益/代价 | 先进性与持续性 | 必要修订或保留理由`。只是另一种同样可行的做法放非阻塞建议，不能当缺陷。

## C. 主 agent 硬检查

需求映射、依赖编排、批次节奏、测试规模、进度格式与 UI 细节不再逐项审查。主 agent 只查下列会让交付出大错的问题，确认后按报告合同进入 findings：

- **范围越界**：范围外系统的工作写进本方里程碑或交付物，或范围外依赖没有提供方、所需行为与解除条件；同仓、自有、源码可访问不构成扩范围依据。
- **发布与评审**：生产发布、上线、放量及其生产验证列为里程碑时，未经评审的代码会随实施上线，应定位该里程碑并建议移出：它们在代码评审通过后进入发布流程，发布顺序、放量与回滚门留在 §8。仅用户明确要求在计划内发布（通常为线上联调）时可单列，须写明用户依据与目的。代码评审被写成里程碑、退出条件、阻塞项、恢复快照下一步或计划成功条件，同样指出：评审由用户独立发起，不属于计划。
- **需求落点**：本期需求或验收行完全没有设计或检查落点，或延期项没有去向。
- **交付断点**：按计划做完后，用户主路径仍缺必要环节（入口、权限/种子、迁移、配置、安装或升级路径）而无法使用。
