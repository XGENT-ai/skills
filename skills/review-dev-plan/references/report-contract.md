# 问题判定与报告合同

## 落盘与交付合同

- **默认保存完整 Markdown 报告**，只有用户明确要求仅聊天或不写文件时才跳过。聊天中的报告正文、拟写入内容或路径预告都不算已落盘。
- 路径优先级：用户指定路径 → 本地计划同目录的 `<计划文件名去掉扩展名>.review.md`；例如 `docs/plan/cache.md` 对应 `docs/plan/cache.review.md`。输入只有聊天文本或远程文档、没有本地计划文件时，遵循仓库报告目录约定；无约定则写当前工作区的 `docs/reviews/<主题短名>.review.md`。按需创建目录，不因用户未指定路径而停下询问。
- 写入前检查目标是否已存在。用户已明确要求更新或覆盖该报告时按授权执行；否则保留旧报告，在同目录依次尝试 `<主题>.review.<YYYY-MM-DD>.md`、`<主题>.review.<YYYY-MM-DD>-2.md` 等未占用名称。用户指定路径发生同名冲突时也另存，并在最终回复说明实际路径；不得覆盖原计划或代码。
- 主 agent 单独写入下文「完整报告顺序」的全部内容，然后回读实际文件，核对问题、待核实项、覆盖与基线、实施编排和总体结论均已保留，检查引用定位与报告路径有效。空 findings、部分证据缺失或 `Blocked` 不免除保存义务，按实际覆盖情况写明限制。
- 最终聊天回复只给实际报告链接、建议状态和关键问题/待核实项摘要，避免重复整份报告；明确仅聊天时才在聊天中交付完整报告。
- 无可用文件写入工具或写入失败时，明确说明“报告未落盘”、原因与目标路径，在聊天中提供完整报告以保留结果，并将落盘标为未完成；不能声称已保存或给出不存在的产物链接。

## 什么进入 findings

确认的问题须同时具备：计划中的可定位主张或缺口、已核实的依据、具体触发/受影响场景、对本期目标的实际后果、可执行的最小修订。建议作者换个人偏好的技术、堆更多章节、覆盖无关老问题，都不算。

“没有写 X”须先确认全文/引用中确实没有，并证明 X 是本期交付必要条件。证据不足的风险放待核实项，写所需证据及影响；关键待核实项仍可阻塞就绪判断，不能伪装成已证实缺陷。

每条只解释一个独立根因。合并重复症状时保留涉及的需求、里程碑和规则来源。无实质影响的拼写、偏好、格式不报；违反适用合同而会造成实施偏差的格式问题说明其后果。

## 严重度与置信度

| 等级 | 在计划评审中的含义 |
| --- | --- |
| P0 | 已证实、无须额外假设就会造成重大安全/数据/运行灾难的计划指令，必须立即纠正；极少使用 |
| P1 | 核心目标不可达，或范围、安全、数据、外部契约、关键 NFR 存在高影响错误；受影响任务开工前必须修订 |
| P2 | 局部功能、验收或编排有可证实缺口；在对应里程碑前修正 |
| P3 | 有明确收益和依据的小改进，不阻塞实施；纯偏好不进入 findings |

置信度用高/中/低及依据。严重度表示后果，置信度表示证据强弱，不互相替代。仅猜测的问题不靠降为 P3 混入 findings。

## 单条问题格式

```markdown
1. [P1] F-01 · <简短、可执行的标题>
   - 定位：<计划路径:行号或稳定章节；冲突时给两处；关联 R/M ID>
   - 问题：<在什么条件下，按计划会发生什么，为什么影响本期目标。简短一段。>
   - 证据：<代码路径:精确行号/符号、适用规则定位、实测结果或官方文档 URL/版本/日期>
   - 修订：<最小需要补充、改正的决策/契约/任务；避免整份重写>
   - 复核：<改稿后检查的断言或实现后的验收；区分二者>
   - 置信度：<高/中 + 原因>；阻塞：<受影响任务/里程碑或否>
```

本地文件优先使用可点击路径和短行定位；行号变动大时同时给稳定标题/符号。定位指向原计划有责任承载该要求的位置，不能指向 reviewer 自己新写的报告。代码行号不必位于 git diff 内，计划评审可能没有 diff。

## 完整报告顺序

1. **确认问题**：P0 → P3 排序，稳定编号 F-01 等；空结果写“未发现可确认的问题”，不凑数。复审沿用原编号，区分已解决、仍存在、新增。
2. **待核实/待决策**：每项写缺什么证据、影响哪个决定/任务、谁可提供以及最晚确认点；责任人未知就写待指定，不虚构用户承诺。
3. **覆盖摘要**：记录计划与代码基线、实际 agent 分工、四维覆盖/跳过理由、脚本及浏览器实际执行情况。只列结论相关来源，不倾倒阅读日志。无 UI 可写不适用；交付可用性不能随 UI 一起跳过。
4. **映射与实施编排**：列断链 ID 或确认映射完整的核对范围；给依赖边、并行波次、共享文件/资源负责人角色和汇合验收。现有编排成立时简要确认并引用原计划，只展开有必要调整的部分，不重抄完整映射或为形式新增里程碑/过程文档。只报文件不冲突、不报依赖条件的“可并行”不合格。小计划可合成一张短表。
5. **总体结论与修订顺序**：建议状态、理由、与原状态的差异，先纠正前提/契约，再修设计、映射与编排；写清解除阻塞的可观察条件。

### 就绪判断（沿用 dev-plan 的含义）

- `Blocked`：仍有会改变范围、安全、数据、外部契约或关键 NFR 的未决项，或核心交付无法成立；说明具体阻塞范围。无关且独立的前期工作可以单列，不把整个计划宣称 Ready。
- `Proposed`：方案与实施前置完整，只等待非阻塞评审；不能用它收纳重大未知或实质开工阻塞。
- `Ready`：所审范围的实施前置均已解决，关键证据无缺口，剩余非阻塞建议不影响承诺交付。说明评审覆盖限制，不把 Ready 当作实现完成或产品上线许可。

严重度和状态不是机械一一对应：同一个 P2 在某计划中可能阻塞关键外部契约，另一个 P2 只是非关键局部改进。依据影响判断，不使用总分平均掉阻塞项。
