# 问题判定与报告合同

ODC 声明约束评审和报告编写，不复制进报告；下方 Markdown 模板、表格与报告顺序是交付接口。

## 落盘与交付合同

```formal
RULE @plan_report_storage:
  UNLESS: explicit_chat_only_or_no_file_request
  MUST: ["默认由主 agent 单写完整 Markdown 报告并回读实际文件；空 findings、部分缺证或 Blocked 仍须保存，按覆盖说明限制",
         "核对问题、待核实、覆盖/基线、实施编排、总体结论、引用和路径齐全有效；已保存后聊天只给实际链接、建议状态和关键问题/待核实摘要"]
  MUST_NOT: treat_chat_preview_or_path_notice_as_saved_report

RULE @plan_report_path:
  WHEN: file_report_required
  MUST: ["路径按用户指定 → 本地计划同目录 <计划文件名去掉扩展名>.review.md，如 docs/plan/cache.md → docs/plan/cache.review.md；仅聊天输入/远程原文按仓库报告目录惯例，无则当前工作区 docs/reviews/<主题短名>.review.md；按需建目录，不因未给路径停下",
         "写前查同名，已授权更新/覆盖该报告则执行；否则保留旧报告，依次尝试同目录 <主题>.review.<YYYY-MM-DD>.md、<主题>.review.<YYYY-MM-DD>-2.md 等空闲名；用户指定路径冲突也另存并说明实际路径"]
  MUST_NOT: overwrite_source_plan_or_code

RULE @plan_storage_fallback:
  MUST: [=>[explicit_chat_only_or_no_file_request, "在聊天交付完整报告"],
         =>[report_write_tool_unavailable_or_write_failed, "明确报告未落盘、原因和目标路径，聊天保留完整报告，保存标未完成，不声称已保存或链接不存在产物"]]
```

## 原文档引用（报告头）

报告标题后、findings 前必须写「评审对象」，供 `apply-doc-review` 仅凭报告定位原文；即使没有 findings 也保留。每个实际评审目标一行，背景资料和关联 PRD 不混作修订目标。

```markdown
## 评审对象

| 类型 | 原文档 | 所审版本 | 评审范围 |
| --- | --- | --- | --- |
| 开发计划 | [<原文档标题>](<相对报告所在目录的原文路径或稳定 URL>) | <内容 hash / 可取回版本；不可得则 unknown> | <全文或指定章节/里程碑 ID> |
```

```formal
RULE @plan_source_reference:
  MUST: ["本地引用相对实际报告目录计算，不按 cwd/仓根/默认报告位置；空格路径用合法 Markdown，原文位置/文件名不变，不写机器绝对路径，另存或加日期后重新核对",
         "远程原文用稳定 URL 与可用版本；无持久原文的聊天输入写‘聊天输入，无原文路径’，不造链接，并说明 apply 需要可定位目标",
         "回读时沿链接打开原文，核对类型/身份/版本/范围；原文变化说明基线及适用性，处置保留历史所审版本，修后版本写处置节"]
```

## 复审记录

复审报告在标题及评审对象之后注明：上轮报告的相对链接与版本、所审对象的前后版本、本轮范围、已有处置记录链接，以及“修复效果复审”或“完整重审”。历史报告与原结论保持不变；默认按本合同另存新报告。

在原报告结构中增加“上轮问题复审”表，与本轮新增问题分开：

| 来源报告 / F-ID或稳定章节 | 上轮问题与结论 | 已有处置 / 修后版本 | 本轮结果 | 当前证据 / 验证 | 剩余动作 |
| --- | --- | --- | --- | --- | --- |

```formal
RULE @plan_recheck_evidence:
  WHEN: re_review_with_prior_report
  MUST: ["结果仅用已解决、仍存在、部分解决、回归、待核实、不再适用、本轮未复核；已解决满足原关闭判据，回归有先前解决及当前再失败证据，不再适用有范围/契约变化依据且不等于实际修复，缺证不关闭，未选旧项标本轮未复核",
         "来源身份为报告路径/原始版本 + F-ID，有台账再保留评审对象 ID；同链路沿用旧号，多报告同号不混合，新问题用未占用号并注明本轮，同根因合并保留来源映射，不重编号抹历史",
         "默认覆盖上轮全部问题及待核实，限定范围时逐项列未复核或完整 ID 清单；读处置后独立核实实际结果和旧证据适用性，只查修复影响的必要回归，不自动重跑无关全量验证",
         "分别总结旧问题解决情况、修复引入的新问题、未覆盖/缺证范围；无新增 findings 不等于旧项关闭，局部通过不等于整体通过；SDLC 按仓内固定状态与范围登记，不造 state 枚举"]
```

## 什么进入 findings

```formal
RULE @plan_finding_admission:
  MUST: ["确认问题同时有计划定位、已核实依据、具体触发/受影响场景、对本期目标的实际后果及可执行最小修订",
         "断言缺少 X 前查全文/引用确实无 X，并证明为本期交付必要条件；缺证列待核实、所需证据及影响，关键缺口仍可阻塞就绪，不伪装成确认缺陷",
         "一条一独立根因，合并症状保留需求、里程碑及规则来源；适用合同的格式问题须说明实施偏差后果"]
  MUST_NOT: "将个人技术偏好、堆章节、无关旧问题或无实质影响的拼写/格式报缺陷"
```

## 严重度与置信度

| 等级 | 在计划评审中的含义 |
| --- | --- |
| P0 | 已证实、无须额外假设就会造成重大安全/数据/运行灾难的计划指令，必须立即纠正；极少使用 |
| P1 | 核心目标不可达，或范围、安全、数据、外部契约、关键 NFR 存在高影响错误；受影响任务开工前必须修订 |
| P2 | 局部功能、验收或编排有可证实缺口；在对应里程碑前修正 |
| P3 | 有明确收益和依据的小改进，不阻塞实施；纯偏好不进入 findings |

置信度用高/中/低及依据。严重度表示后果，置信度表示证据强弱，不互相替代。仅猜测的问题不靠降为 P3 混入 findings。

## 单条问题格式

```markdown
1. [P1] F-01 · <简短、可执行的标题>
   - 定位：<计划路径:行号或稳定章节；冲突时给两处；关联 R/M ID>
   - 问题：<在什么条件下，按计划会发生什么，为什么影响本期目标。简短一段。>
   - 证据：<代码路径:精确行号/符号、适用规则定位、实测结果或官方文档 URL/版本/日期>
   - 修订：<最小需要补充、改正的决策/契约/任务；避免整份重写>
   - 复核：<改稿后检查的断言或实现后的验收；区分二者>
   - 置信度：<高/中 + 原因>；阻塞：<受影响任务/里程碑或否>
```

```formal
RULE @plan_finding_citations:
  MUST: "本地优先可点击路径及短行定位，行号变动大补稳定标题/符号；定位到原计划有责任承载要求处，不指向 reviewer 新报告；代码证据不限 git diff，计划评审可能无 diff"
```

## 完整报告顺序

1. **确认问题**：P0 → P3 排序，稳定编号 F-01 等；空结果写“未发现可确认的问题”，不凑数。复审沿用原编号，区分已解决、仍存在、新增。
2. **待核实/待决策**：每项写缺什么证据、影响哪个决定/任务、谁可提供以及最晚确认点；责任人未知就写待指定，不虚构用户承诺。
3. **覆盖摘要**：记录计划与代码基线、实际 agent 分工、四维覆盖/跳过理由、脚本及浏览器实际执行情况。只列结论相关来源，不倾倒阅读日志。无 UI 可写不适用；交付可用性不能随 UI 一起跳过。
4. **映射与实施编排**：列断链 ID 或确认映射完整的核对范围；给依赖边、并行波次、共享文件/资源负责人角色和汇合验收。现有编排成立时简要确认并引用原计划，只展开有必要调整的部分，不重抄完整映射或为形式新增里程碑/过程文档。只报文件不冲突、不报依赖条件的“可并行”不合格。小计划可合成一张短表。
5. **总体结论与修订顺序**：首行写「是否需要修改：需要 / 无需」（见下文），再写建议状态、理由、与原状态的差异，先纠正前提/契约，再修设计、映射与编排；写清解除阻塞的可观察条件。

### 就绪判断（沿用 dev-plan 的含义）

- `Blocked`：仍有会改变范围、安全、数据、外部契约或关键 NFR 的未决项，或核心交付无法成立；说明具体阻塞范围。无关且独立的前期工作可以单列，不把整个计划宣称 Ready。
- `Proposed`：方案与实施前置完整，只等待非阻塞评审；不能用它收纳重大未知或实质开工阻塞。
- `Ready`：所审范围的实施前置均已解决，关键证据无缺口，剩余非阻塞建议不影响承诺交付。说明评审覆盖限制，不把 Ready 当作实现完成或产品上线许可。

严重度和状态不是机械一一对应：同一个 P2 在某计划中可能阻塞关键外部契约，另一个 P2 只是非关键局部改进。依据影响判断，不使用总分平均掉阻塞项。

### 是否需要修改

以计划文本是否需要改动判定，与建议状态分开写：

- **需要**：有 P0–P2 确认问题；或待核实/待决策项须写进计划（如补登记阻塞、修正前提）；或建议状态与计划自报状态不一致。
- **无需**：只剩 P3 或无问题，且计划自报状态与建议状态一致。此时仍为 `Blocked` 表示计划已如实登记阻塞，下一步是逐项解除阻塞，不是改稿。

```formal
REVIEW:
  CHECK: [@plan_report_storage, @plan_report_path, @plan_storage_fallback, @plan_source_reference,
          @plan_recheck_evidence, @plan_finding_admission, @plan_finding_citations]
  ALSO: ["评审对象、问题模板、复审表、严重度及完整报告顺序均遵守本合同",
         "是否需要修改独立于 Ready/Proposed/Blocked，按影响与证据判定，不以总分或严重度机械替代状态；下一步符合主技能第 5 节"]
  EXPOSE: on_issue
```
