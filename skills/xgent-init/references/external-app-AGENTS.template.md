# AGENTS.md

行为准则，用来减少常见的 LLM 编码错误。与项目自身的规范合并使用。

**取舍**：这些准则偏向审慎而非速度。琐碎任务自行判断。

## 1. Think Before Coding

**不要假设。不要藏起困惑。把取舍摆出来。**

动手之前：
- 明确说出你的假设。不确定就问。
- 有多种解释时全部列出来——不要默默选一个。
- 有更简单的做法就说出来。该反驳时反驳。
- 有不清楚的地方就停下。指出困惑在哪。问。

## 2. Simplicity First

**用最少的代码解决问题。不做预留。**

- 不做没被要求的功能。
- 不为一次性代码造抽象。
- 不加没被要求的「灵活性」「可配置性」。
- 不为不可能发生的场景写错误处理。
- 写了 200 行而它可以是 50 行，就重写。

自问：「资深工程师会不会觉得这写复杂了？」会，就简化。

## 3. Surgical Changes

**只碰必须碰的。只清理自己造成的混乱。**

改既有代码时：
- 不「顺手改进」相邻代码、注释、格式。
- 不重构没坏的东西。
- 匹配既有风格，哪怕你会用别的写法。
- 发现无关的死代码就说出来——不要删。

自己的改动造成孤儿时：
- 删掉**因你的改动**而不再被使用的 import / 变量 / 函数。
- 不删既有的死代码，除非被要求。

检验标准：每一行改动都能直接追溯到用户的诉求。

## 4. Goal-Driven Execution

**定义成功标准。循环到可验证为止。**

把任务转成可验证的目标：
- 「加校验」→「为非法输入写测试，然后让它们通过」
- 「修 bug」→「写一个能复现它的测试，然后让它通过」
- 「重构 X」→「保证重构前后测试都过」

多步任务先说一句计划：
```
1. [步骤] → 验证：[检查点]
2. [步骤] → 验证：[检查点]
```

## 5. Evidence & Quotation

**凡引用必见原文。没读到的不写。**

- 引用任何文件的措辞、编号、数值、状态、命令或日期前，先亲眼读到那段原文；不凭上下文推断补写，不把「大概如此」写成事实。
- 工具回显被截断（长文件只给首尾）时，中段是**未知**：要引用就先按行范围或搜索结果回读定位，再引。
- 正式产物（CR、计划、运维手册、commit message、给用户的事实陈述）里每一处「据 X 说 Y」，X（文件与段落）与 Y（内容）都要能当场指出。
- 发现引用与原文不符：全仓搜出同一错误的所有副本一并修正，并向负责人说明，不留两处互相矛盾的版本。

## Project Conventions

本文件适用于支持项目指令的 coding agent。开工先读本仓 README、包管理与工具链配置、相关开发计划；已有 PRODUCT.md / DESIGN.md 时一并读取。命令、端口、服务名、数据库名和 App 身份以本仓配置为准，不套用其他项目的值。

### 本地开发

- 用本仓已有的启动、检查、测试与构建入口，遵循现有包管理器、锁文件和工具链配置；有统一启动入口时优先使用它。
- **缺服务、缺容器就停下来问，不要擅自装。** 未获授权时不下载镜像、不另起基础设施容器；先确认已有环境和依赖，再说明缺什么、请用户协助。
- 共享数据库上的测试只使用明确的测试库。会 TRUNCATE / reset 的测试先核对目标库；共享状态的用例按项目约定串行执行，不清理其他项目或用户的数据。
- `@xgent/*` 依赖从平台私有 registry 安装，配置以本仓 registry 与 CI 为准。401/404 先查凭证有效性与版本是否已发布；不通过复制源码或 file/link 依赖绕过。
- 未经用户明确要求，不升级依赖 Major。

### Portal App 接入

本节与下方 onebox、Portal 前端及发布约定只适用于 XGENT.ai Portal App。清单事实源是本仓的 `app.manifest.json`；`listingKey`、App 名称和 `type` 从清单读取，不在本文件维护另一份副本。

- `listingKey` 同时决定令牌 audience、安装态 appKey、服务路由和 scope 命名空间，改 key 等于换 App，不作为普通重命名处理。
- 修改清单要同步更新 `version`。安装期字段是租户快照，改清单不等于已安装租户已经更新；验证时同时检查新安装与已有安装的行为。
- 身份来自门户真实自省，解开响应信封后再读 claims；后端校验 audience、tenant、scope、角色和 ACL，自省失败必须拒绝放行。查询按 claims 的租户收口，不信前端自报的身份或租户。
- 接入、清单与 API 契约查 `portal-external-app`；SDK、iframe、导航和版头查 `portal-micro-app`；跨应用授权查 `portal-app-exchange`。这些 skill 是平台口径的事实源；缺少相关 skill 时说明缺失，不猜平台步骤或引用目标仓访问不到的门户源码路径。

### 本地联调：一盒（onebox / one-box）

**本地起前端不等于门户联调通过。** iframe 握手、TDT、consent 和服务反代要接真实 onebox。初始化、注册、启动、体检和排错先读 `portal-dev-setup`，按该 skill 的脚本与当前配置执行，不 clone 门户、不改门户代码、不自行重建门户镜像。

- **一台机器复用一盒**：先检查已有栈，其他 App 接到同一套联调底座；已有 onebox 时不再初始化第二套。镜像仓库、凭证、端口和目录从现有配置读取，缺凭证请用户找开发团队，不猜值。
- **一盒仅供开发**：mock OAuth、开发服务账号和明文开发密钥不用于生产，不提交凭证到 git。
- **先核对镜像版本与架构**：文档和运行行为不符时先查当前镜像；门户 onebox 镜像与自己的 App 镜像可能属于不同 registry 项目，不混用。App 镜像架构与运行平台必须匹配。
- **核对 App 数据库与迁移**：onebox 不会自动创建每个出仓 App 的库。按本仓配置核对所需库；创建或迁移前确认目标。onebox 没有部署控制器，换成带新迁移的 App 镜像后，须按本仓迁移入口显式执行，健康检查绿不代表 schema 已更新。
- **注册先于反代启动**：注册后先确认演示租户市场里出现 App 卡片，再检查安装、授权、宿主入口和服务路由。404/502 先跑 onebox doctor 与 skill 排查表，核对注册、反代与后端状态。
- **dev 注册不等于已装租户同步**：导航、helpEntry 等安装期快照变更后，要通过租户管理员的市场更新入口同步，再验收宿主上的显示与行为。
- **把首次同意屏算进走查**：「授权并打开」是正常步骤。onebox 的部署任务可能停在 `deploying`，因为没有部署控制器；是否可用以实际宿主链路为准。
- 有本仓 onebox 冒烟入口时运行它，随后从宿主进入验证实际功能。

### 前端 UI 开发与验收（有前端时）

涉及页面、组件、布局、交互或视觉的改动，走完设计与浏览器验收两步：

- **设计阶段用 impeccable**：先读已有产品与设计上下文，覆盖视觉层级、信息架构、间距对齐、配色、动效、可访问性以及空状态和错误状态。当前环境没有该 skill 时说明缺失并提示安装，不声称已经使用。
- **验收使用当前 Agent 可用的真实浏览器通道**：Chrome extension、`kimi-webbridge` 或 Playwright 均可，按实际可用能力选择，不绑定某一种 Agent。
- **Portal App 必须从宿主进入**：从已有宿主入口打开 App，走通主路径与关键边界；首次接入时还要覆盖市场卡片、安装与授权。确认浏览器显示的是最新产物；standalone 页面或直接打开 dev server 只能作为补充。
- 检查本次改动涉及的导航、面包屑、关键操作与保存结果、空 / 错状态、权限边界；涉及响应式、主题或语言时检查相应状态。查看 console 与失败请求，保留实际步骤、结果及必要截图作为验收证据。
- **类型检查、lint、单测和 build 不能替代浏览器验收**；只看 diff 不算完成。环境跑不起来时先按现有配置排查；仍受阻则明确写「未在浏览器中验证」、说明原因与需要的协助，不声称 UI 已验收通过。

### Portal 前端约定（micro App）

- 版头的应用图标、应用名与 tagline 归门户；App 内只显示运行期上下文，不重复绘制应用身份。脱离门户的 standalone 壳按需保留。
- 页面层级由视图驱动的 effect 调用 `sdk.setBreadcrumbs` 全量上报，首页传空数组，label 用当前语言解析。内部路由调用 `sdk.routeSync`，同时订阅 `sdk.onRoute` 处理宿主切页。
- 自己的后端通过 `sdk.callService` 调用，App key 来自清单。令牌交给 `sdk.getToken()` 管理，不自行存入 localStorage，不随意裁剪 scopes。
- `sdk.acl.can(pid)` 用于按钮显示，后端仍须校验权限；不能用管理员走查代替普通成员的权限验收。
- 跨源沙箱 iframe 不使用 `window.alert` / `confirm` / `prompt`，改用 DOM 模态框。
- 下拉框复用项目 Select 原语；使用原生 `<select>` 时关闭原生箭头（`appearance-none`）并自绘 chevron，验证文字、箭头与主题的实际显示。
- App 图标要契合用途，并确认门户注册表支持该名称；不依赖静默回退来掩盖配置错误。

### API: HTTP status code 只反映传输/路由层，不反映业务状态

- 404 = endpoint 不存在（路由层）；「数据不存在」用 200 + 业务字段（如 `data: null`）。
- 业务成功统一 200，含新建/更新/删除/覆写，不用 201/204。
- 业务失败（校验不过 / 状态非法 / 资源冲突）也走 200 + 响应体错误结构。4xx/5xx 只留给参数不正确、未登录、未授权、真传输/服务层故障。

### 性能：热路径上不许 N+1，读多写少的事实必须缓存

「表小 / 量不大 / 上限只有 1 000」都不是不优化的理由——tsc、lint、verify 对 N+1 全绿，只有压测和生产 p95 看得出来。请求路径与 worker 热路径一律适用，算法上能提高的就要提高，不能偷懒：

- **循环里逐条 `await` 查询 = N+1，禁止**。同一批 id 一条 SQL `inArray` 取回，再在内存里映射；Redis 同理用 `mget`。反例（已修）：typed 通知入口逐个 `isActiveMember` 校验 1 000 个 userIds = 1 000 次串行往返；Router 每收件人每 push 渠道各查一次端点 = 200 人 400 条查询。
- **一批写入用多行 INSERT + `RETURNING`**，按业务键（不是数组下标）把返回行映射回输入；`onConflictDoNothing` 只返回真插入的行，冲突那部分要再查一次。超过 1 000 行分块（PG 单语句 65 535 个参数）。范本：`modules/notifications/router.ts` 的 `writeRecipientBatch`。
- **读多写少的配置/字典必须有进程内短 TTL 缓存**。管理员改完要即时生效的（事件定义、策略、模板、lane 开关、渠道连接）加显式 `invalidateXxxCache()` 在写侧调用；纯展示快照（App 名/图标/颜色）30 s TTL 就是契约，不要求写侧失效——写点散在十几处且 worker 是别的进程，失效调用本来就到不了。同一次请求 / 同一批处理里同一事实只查一次（先整批取到手再进循环）。
- **不许缓存的**：发送/扣费/授权前的「当下资格」重查（成员是否 active、App 是否仍安装、端点归属）——它们存在的意义就是新鲜；一条带索引的点查即可。
- **热路径上的聚合（`count(*)` / `min()`）不许每次现算**：`/health` 与背压这类每秒会被打的入口共用一份短 TTL 缓存（`modules/notifications/ops.ts` 的 `laneStatsCached()`）。
- **事务里不做外部调用，持连接只覆盖写入**；渲染、解密、供应商调用都在事务外。
- **改了热路径要给前后数字**：`apps/api` 有 `notification:loadtest` 这类参数化压测，改完跑一遍把 recipients/s 或 p95 写进提交说明；没有压测的路径至少 `EXPLAIN` 一次。

### 完成标准与发布

- 执行与改动相关的本仓检查、测试和构建入口，报告实际执行结果与未验证项。
- Portal 后端改动验证无 token 的 401、缺 scope 的 403、租户隔离和经宿主服务路由访问的健康检查；权限改动覆盖普通成员，不只用管理员账号。
- 有前端改动时完成上述真实浏览器验收，报告入口、主路径、关键边界和结果；阻塞项明确列出。
- 发布时使用 `xgent-app-release`，镜像交付使用 `xgent-image-push`。发布前验证 release-cli 身份；换镜像带 `--wait`，以新版本实际运行作为成功依据。
- 发布清单不携带密钥值，镜像 tag 不可变；迁移打进镜像、持锁、失败非零退出，并兼容仍在运行的旧版本。onebox 手动迁移与生产控制器迁移分别验证。
