# 产品推演、SMAR 与 UAT 状态验收

写新 PRD、整体优化或评审时使用;局部修改只检查受影响部分。推演发生在共同理解确认之前,成文时只综合已确认的产品选择。

## 1. 在约束内把产品推演充分

先明确用户任务、现状阻碍、用户给定约束、宿主能力和本 PRD 的能力边界。沿「发现 → 理解 → 决策 → 完成任务 → 再次使用 / 异常恢复」走一遍主旅程,省掉无关环节,从以下六个维度寻找有价值的改进。

| 维度 | 应推演的产品问题 | 成文落点 |
| --- | --- | --- |
| 创新性 | 除了照搬现状或参考产品,能否改变用户完成任务的方式,减少过去必须承担的判断或工作? | 与常规方案有实质差异的产品选择、价值与取舍 |
| 先进性 | 当前生态或 AI 能力是否让新的使用方式成立?哪些只是声明,哪些已有行为证据? | 能力边界、准入条件与依赖;外部能力核到当前官方资料,不能将参考项目说明当成已支持 |
| 可用性 | 关键角色能否完成完整任务?空数据、无权、依赖缺席、失败时仍能理解状态和下一步吗? | 完整 FR、相关 NFR、状态与恢复判据 |
| 便捷体验 | 能否减少重复输入、记忆术语、切换入口和无价值确认?首次与高频使用是否都有合适路径? | 默认信息、最短业务路径、渐进展示、便捷性判据 |
| 美观 UI | 信息主次、排版、密度、留白和视觉语言是否支持任务?各状态与不同窗口下是否保持清晰一致? | 信息层级、视觉原则与可核对要求;沿用宿主设计约束,不只写「现代、美观」 |
| AI 赋能 | AI 能在哪个环节改善发现、理解、创作、决策或重复劳动?如何判断比基本路径更有价值? | 输入/输出、触发与用户控制、质量/成本边界、降级状态及验收 |

六维是思考方向,不要求增加六组功能。对影响主旅程的选择比较有实质差异的候选,写清为什么选、牺牲什么、怎样算成立。将采用的方向落到目标、FR/NFR 和验收中;无 UI 或 AI 无适用价值时说明理由,不为填表添加界面或模型。

终局始终在用户给定范围内。技术 PoC 要把重要假设及成立/不成立的判据推演透;完整产品要把用户任务推演透。不因技术 PoC 默认只需几个技术组件,也不把一个 PoC 扩成整个产品系列。

## 2. 产品设计与实现设计的边界

| PRD 要决定什么 | 下游计划再决定什么 |
| --- | --- |
| 用户按任务发现内容,理解匹配依据;增强不可用时仍可基本搜索 | 向量索引、检索算法、模型供应商、调用编排 |
| 同一内容面向人和 Agent 提供不同的消费结果,证据不足时明确为空 | 内部编译阶段、数据模型、存储结构、服务接口拆分 |
| 用户从出处一次跳转到原文被引段落,能辨认当前位置 | 前端组件、路由状态、焦点管理代码 |
| 关键状态在首屏可见,主操作突出,详情按需展开,视觉遵守宿主规范 | CSS 数值、组件库选型、DOM 结构 |
| 受控条件下响应达到门槛,失败后已有内容不丢失 | 压测工具、测试数据生成、故障注入脚本 |

用户动作描述不等于测试步骤:「发布者确认发布后,版本可消费」是在定义产品行为;「登录测试账号、依次点击三个按钮、运行查询核对记录」是在设计怎么测。前者留 PRD,后者交 test-plan。

已有外部契约或用户指定技术约束可以引用,注明来源和产品影响;不借这些约束自行决定内部实现。评测或诊断工具本身是交付能力时,写它应展示的结果、指标定义和证据,把验收它的测试方法留给下游。

## 3. AI 赋能必须形成产品闭环

在有价值的环节主动设计 AI 能力,不能满足于一个泛化聊天入口。每项采用的 AI 能力应回答:

- **价值与触发**:谁为完成哪项任务,主动触发或在何种已授权条件下触发?替用户省掉什么工作,需要哪些有权使用的输入,得到什么输出?
- **用户控制**:结果是建议、草稿、解释还是自动业务动作?用户如何理解依据、修改、采纳、拒绝或撤销?重要写入的授权与确认边界是什么?
- **质量与不确定性**:怎样判断结果可用?无依据、低置信度、矛盾或未验证时显示什么?定义质量指标的口径,不把模型生成或读取成功当成业务成功。
- **依赖与成本**:权限、预算、可用性不足时进入什么状态?辅助型 AI 保持基本任务可完成;AI 是核心能力时,明确等待、失败和可恢复条件,不假装仍能完成核心任务。

这些是产品决策,不要求预先选择模型、提示词、RAG 管线或 Agent 框架。AI 不适用或被用户排除时,保留理由;不将「AI 开发」等同于「所有功能都需要运行时 AI」。

## 4. 用 SMAR 检查目标与需求

| 原则 | 必须能回答 | 不合格信号 |
| --- | --- | --- |
| Specific | 谁、在哪个场景、对象是什么、能力和权限到哪? | 通篇「用户」或「智能管理」,同一个状态有多种含义 |
| Measurable | 到达什么可观察状态、按什么口径判断通过? | 「体验好」「准确」「安全」,只有数字没有作用域/分母 |
| Actionable | 用户或授权主体能执行什么动作、获得什么可用结果? | 只有愿景/技术名词,没有可完成的任务 |
| Reasonable | 价值、质量、成本、依赖是否与用户约束相容? | 承诺未知生态组合全部兼容、依赖不明仍无条件承诺、为了先进堆功能 |

Measurable 不等于每行硬塞数字。明确的枚举、结果集合、是/否、相等/不变也可验收。性能和质量数值要附必要的负载、语料、样本或分母;指标有观察窗口时说明窗口和未知数据的处理,不在 PRD 展开采样脚本与执行步骤。

区分三类口径:产品验收门槛、上线后观察指标、PoC 比较基线。数值来自用户/既有约束则给来源;新提出的门槛标为产品提案并确认,不声称已实测,不把基线当效果承诺。

不用 Time-bound 为 AI 开发编造工期或发布日期。以独立用户价值切期,每期开发计划建议 5–8 个 Milestone;连续性例外可为 9–10 个并说明理由,最多 10 个。PRD 表达规模预算,dev-plan 核实并拆解;小任务可更少,超出则反馈拆期,不能删掉完整验收。已有外部日期约束仍须尊重,性能时延、超时、有效期和观察窗口也不能被删除。

## 5. UAT 写预期状态,不写测试程序

每个重要用户场景写清「角色与前置状态 → 业务意图/动作 → 预期状态 → 清晰的通过条件」,关联真实需求 key 与验收行。只覆盖相关状态:成功、空数据、拒绝、重复/冲突、取消、失败/恢复、AI 不确定/降级。状态包括结果是否可用、显示的解释、允许的下一步和数据是否改变;不能只写一句提示文案。

以下为写法示例,不预设具体项目承诺:

| 角色与前置 | 业务动作 | 预期状态与通过条件 |
| --- | --- | --- |
| 普通成员,没有可用证据 | 提问 | 明确无可靠内容,出处集合为空,无伪造回答;页面给出获取证据的下一步 |
| 发布者,内容已通过本产品要求的检查 | 确认发布 | 该确切版本可消费;发布成功与兼容验证分别表达,不因发布而显示已验证 |
| 维护者,AI 给出资料建议 | 拒绝建议 | 正式资料和原始内容保持不变;建议不进入正式分发 |
| 成员,已有本地内容 | 取消升级 | 原内容与选定版本不变;不显示升级成功 |
| 成员,AI 增强不可用 | 搜索 | 可用基本结果且模式明确,用户仍可继续任务;不显示增强成功 |

定稿检查三件事:每条需求有可判断的验收;每个关键用户场景有预期状态与通过条件;目标/场景/需求/验收/UAT 相互可追踪。此时无需已存在 TC。测试计划随后决定账号、数据、执行步骤、工具、故障模拟和完整覆盖,不能在写测试计划时才首次决定产品应到达什么状态。

## 6. 交付前按挑剔评审者的视角自审

先读完成稿,逐项找反例并改正文,不把自审过程倾倒进 PRD:

- 哪个关键任务仍要求用户自己补步骤或猜状态?是否只罗列功能,没有形成完整体验?
- 创新/先进/AI 选择有什么具体收益和合理边界?是否只是换术语、跟风或加入口?
- UI 是否只写可访问性门槛,却遗漏信息主次、视觉一致性和主路径便捷性?
- 任意一条验收能否无歧义地判定通过/不通过?是否用测试动作替代了预期状态?
- 是否把用户给定范围之外的能力硬塞进终局,或用分期删掉终局要求?
- 每期是否有独立用户价值、计划规模预算和清晰终验期?是否将阶段完成冒充整条完成?

仍有会改变产品语义的缺口则回到对应决策;已确认且符合约束的选择直接成文,不重复泛化访谈。
