# PRD 骨架 · `docs/PRD-<代号>.md`

`<尖括号>` 为占位;引用块是写作指引,**写完删掉指引**。示例里的 `docs/PRD-A.md` / `docs/PRD-B.md` 这类具体文件名也是占位——它们在本 repo 里没有对应文件,写作时替换成宿主 repo 的真实 PRD 名。全篇聚焦产品行为、体验与预期状态,不展开技术方案(表/端点/库/技术里程碑)或测试方法。用户只要文档时不要求落库;未录入的新需求用明确工作号,不能伪造 FR/NFR key。
规模参考:**160–380 行**。范围(§1 目标/非目标)约占 1/4,需求条目(§3)约占 1/2;领域语言、场景与决策只留能改变理解的内容,不为凑篇幅扩写。

**架构约定(全篇按此写)**:§0–§6 是**终局蓝图**——目标写终局结果,需求条目写完整能力,一条都不因「这期做不完」提前砍掉或写小。**交付节奏只出现在 §7**,等全局盘完之后一次给出,并逐条标出「终验期」= 整条需求算完成的那一期。跨期需求的终验期要在三处齐:§7.3、该需求 SPMS `description` 开头的终验块、`acceptanceCriteria` 逐行 `[P#]` 前缀。

## 1. 背景与目标

### 1.1 问题陈述与现状

> 先从用户视角说清「谁正被什么阻碍、造成什么影响」,再写现状与为什么是现在。不要把待做功能换个语序当成问题。有数据放数据（多少人/多少次/多少时间）。
> 调查中读到的现状带路径或出处，与用户假设冲突的地方在这里说清楚。

### 1.2 目标（**终局**、符合 SMAR 的结果，3–5 条封顶）

> 写这块能力**做完之后**要达成的结果，不是「首期做到哪」。检查 Specific / Measurable / Actionable / Reasonable;不用 T 编造开发日期。区分验收门槛、观察指标和 PoC 基线,数值注明来源或「待确认的产品提案」,补必要口径。分期在 §7。

| # | 不做什么 | 为什么 / 去向 |
| --- | --- | --- |
| N1 | <最容易被认为「顺手也该做」的相邻功能> | <另立项 / 属于别的产品域 / 明确永远不做及理由 / 依赖的底座本身另立项> |

> 这张表是评审的挡箭牌。凡会被问「那 X 呢」的，都要提前出现在这里。

## 3. 需求条目

> 每条一小节。SPMS key 在创建后回填;**已录入的需求标题和实体引用必须使用真实 FR/NFR key**。未录入的新需求明确标工作号。`R#` 不是需求编号,只在「承接」和 §6.1 作原始诉求来源标识。
> FR 与 NFR 分开成组（对应 SPMS 的「功能性 / 非功能性」分组）。
> **每条按完整能力写**——验收标准覆盖本 PRD 范围内这条能力**做完**该有的全部断言,不写「本期版本」。「分期」行是 §7 定稿后回填的,不是写作时先定的。

### FR-<N> <标题（动宾短语，一眼看出用户能做什么）>

- **优先级**：`urgent|high|medium|low|none`（紧急度）　**重要度**：`critical|high|medium|low|none`（与紧急度正交，两个都给）
- **承接**：原始诉求 R<#> · 目标 G<#> · 场景 S<#…>
- **分期**：<P#｜跨期写「P1 / P2，**终验期 P2**」>（§7 定稿后回填，与 §7.2 逐字一致）
- **背景**：<为什么需要这条，一两句>
- **行为**：<谁在什么场景下能做什么。用户可感知的能力，不写实现。**按完整能力写**，不写「本期先只做…」>
- **边界**：<本 PRD 能力范围不含什么,其他 PRD 的已明确分工可写去向;容易被误解的地方在这里说明。「这期先不做」写 §7>
- **依赖**：<依赖别的 App/底座的写明；「未就绪则降级为 X」>
- **验收标准**（→ SPMS `acceptanceCriteria`,一行一条、无 markdown 语法;断言用户/外部系统可观察的业务结果,不断言内部实现;**跨期需求逐行加 `[P#]` 前缀,单期需求不加**）：

```
<角色>在<条件>下<业务动作>后，<预期状态 + 清晰判据;数值指标附必要口径>
<边界条件：为空/超限/无权限时的行为>
<可观测的落点：列表出现该行 / 通知送达 / 审计留痕>
```

> **仅跨期需求**：这条抄进 SPMS `description` 的开头（SPMS 里的读者看不到 PRD，PRD 条目里也留一份）——
> `> **分期与终验**：本需求跨 P1 / P2 交付，**终验期 = P2**。P1 完成后请停在交付段（已提交 / 可测试），**不要转「已上线」**——「已上线」是整条需求的验收，不是某一期的完工。`

- **UAT 场景**：UAT-<#>；对应 S<#> / 验收第 <#> 行；预期状态与通过条件见 §6.3

- **分期**：<P#｜跨期写「P1 / P2，**终验期 P2**」>（§7 定稿后回填）
- **重要度**：`critical|high|medium|low|none`
- **约束**：<作用域与质量门槛。性能/容量带数值与条件,其他属性也可用明确状态或不变量;不写测试工具/步骤。示例阈值不能当成项目已确认承诺>
- **验收标准**（同上格式，一行一条）：

```

```

- **UAT 场景**：UAT-<#> …；覆盖 S<#> / 验收第 <#> 行

## 7. 分期交付建议

> **全篇唯一谈交付节奏的地方**——§0–§6 一律按终局写。分期只改变顺序，**不改变需求集合**：这里不删需求、不砍验收标准、不把需求改小。
> 期次是产品侧建议,技术拆解由 dev-plan 判断。每期开发计划尽量控制在 **5–8 个 Milestone**,因交付连续性可为 **9–10 个**并说明理由,**最多 10 个**;小范围可更少,不凑数。这里只给规模预算,不列 M1…Mn 的实现任务或编造工期;实际超出时反馈拆期并同步完整终验关系。**「终验期」是整条需求何时算完成的口径**,不能只在下游计划里提前。

> 每条跨期需求要在**三处**都说得一样，缺一处就会有界面在说谎：① 本表；② 该需求 SPMS `description` 开头的「分期与终验」块；③ `acceptanceCriteria` 逐行的 `[P1]` / `[P2]` 前缀。
> 另：跨期需求的**版本（release）挂终验期那一版**（人工在 Web 补）——`releaseId` 是单值字段，挂首期会让版本报表把整条需求算成那一版已交付。

### 7.4 交给 dev-plan

- 交接单位是 **`FR-N` / `NFR-N` key 的集合**，不是整份文档。**PRD : 计划多对多**——可拆给多份计划，也可与别的 PRD 的需求合并进同一份。
- **终验期随 key 一起交出去**：逐条写明「本计划完成后 FR-38 仍停在交付段，终验在 P2」——只覆盖 P1 的计划里程碑全绿，也不代表跨期需求可以置「已上线」。
- SPMS 侧落点 `plan_create(projectId, title, requirementKeys=[…])` → `PLAN-N`；⚠️ 一个 `PLAN-N` 只能挂**同一项目**的需求。
- <若某条与另一份 PRD 的需求天然同批，点名：与 `docs/PRD-B.md` 的 FR-41 动同一块，建议合并一份计划>

## 常见毛病(自检时对照)

| 毛病 | 症状 | 改法 |
| --- | --- | --- |
| 验收标准是愿望 | 「体验流畅」「性能良好」「操作便捷」 | 写清预期状态和可判断条件;数值须有口径,明确状态也可验收 |
| 需求变方案 | 自行设计表/端点/库选型/技术里程碑 | 挪到 dev-plan;保留产品行为、体验与已给定约束 |
| 粒度失控 | 一条需求混入多个独立能力,或一条需求就是一个按钮 | 按用户可感知且可独立验收的能力拆分,不估算 Issue 数 |
| 产品只转录清单 | 没有六维推演或价值取舍,AI 只是多一个聊天入口 | 从主旅程寻找约束内的改进,采用的方向落实 FR/NFR 与验收 |
| UI 只有形容词 | 只写「美观、现代」或只剩可访问性指标 | 补信息主次、主操作、视觉一致性与相关状态要求 |
| UAT 变测试步骤 | 写测试账号/造数/点击脚本/探针/故障注入 | 保留场景、业务动作、预期状态与通过条件,方法交 test-plan |
| AI 没闭环 | 不知道何时触发、谁确认,不可用时只报错 | 补价值、用户控制、质量判据、依赖与降级状态 |
| SMAR 变口号 | 有功能名却无具体角色、结果或合理边界 | 对照 Specific / Measurable / Actionable / Reasonable,不凭空给日期 |
| 非目标空着 | 只有 1-2 条或直接省略 | 把评审会被问的相邻功能全列出来 |
| NFR 没门槛 | 「要安全」「要快」 | 补 `category` + 作用域 + 可判断门槛;数值指标带必要条件 |
| 编号错乱 | 需求标题/实体引用仍用 R1/R2,或与真实 key 混用 | 创建后回填 FR/NFR key;`R#` 只留在「承接」和 §6.1 作来源标识 |
| 角色含糊 | 通篇「用户」 | 落到租户内具体角色,并写清权限边界 |
| 领域词漂移 | 同一概念用多个词,或「账号/状态/任务」各自指多个东西 | 在 §2.1 选定规范词与定义,全篇统一 |
| 场景只写主路径 | 权限/租户/空数据/重复/状态边界没人拍板 | 用少量高信息量 `S#` 压测真正有关的边界 |
| 决策只留在对话 | 结论有了,但后来人不知道为什么 | 在 §5.1 只记录会影响范围/语义/验收的产品决策 |
| 阻塞问题伪装成默认 | 答案会改需求,但文档仍定稿/落库 | 保留在 frontier;未拍板只能交草稿,不写 SPMS |
| 追踪链断了 | 目标无需求、场景无预期状态或验收 | 补齐 §6.2–6.3;无 TC 不影响 PRD 成立 |
| 验收盯内部实现 | 断言表/函数/内部调用次数 | 改为用户或外部系统可观察的最高业务边界 |
| 分期混进正文 | 目标/行为/边界里出现「本期先只做…」「二期再说」 | §0–§6 按终局写;所有期次安排收进 §7 |
| 非目标当分期用 | 非目标去向写「二期 / 后期再做」 | 属于终局蓝图的挪回 §3 成为 FR/NFR,在 §7 排到靠后期次 |
| 分期只盘自己 | 分期矩阵里只有本 PRD 新建的几条 | 把查重命中的既有 key、以及同期必须一起上的别的 key 一并列进来并标来源 |
| 需求被期次切碎 | 一个可感知能力被拆成 FR-A(一期) / FR-B(二期) 两条 | 合回一条,在 §7.2 标成跨期并给终验期 |
| 按技术栈分期 | 「P1 后端、P2 前端」 | 每期必须说清哪个角色多了什么以前做不到的事;说不清就并掉 |
| 每期计划过大 | 建议超过 10 个 Milestone,或 9–10 个无理由 | 调整分期;尽量 5–8 个,连续性例外最多 10 个,具体拆解交 dev-plan |
| 跨期需求没终验期 | 一条需求横跨两期,却没说哪一期算整条完成 | §7.3 登记 + `description` 终验块 + 验收行 `[P#]` 前缀,三处齐 |
| 阶段完工当整条完成 | 首期 Issue 全绿就把需求转「已上线」 | 终验期未到不置终态;把终验声明写进需求正文,点按钮的人才看得见 |
| 版本挂错期 | 跨期需求的 release 挂了首期 | 挂**终验期**那一版,否则版本报表提前把它算成已交付 |
