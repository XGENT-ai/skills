# PRD 骨架 · `docs/PRD-<代号>.md`

`<尖括号>` 为占位;引用块是写作指引,**写完删掉指引**。示例里的 `docs/PRD-A.md` / `docs/PRD-B.md` 这类具体文件名也是占位——它们在本 repo 里没有对应文件,写作时替换成宿主 repo 的真实 PRD 名。全篇不出现技术方案(表/端点/库/里程碑)。
规模参考:**140–340 行**。范围(§1 目标/非目标)约占 1/4,需求条目(§3)约占 1/2;领域语言、场景与决策只留能改变理解的内容,不为凑篇幅扩写。

---

```markdown
# <代号> · <项目> · <功能中文名>（PRD）

> 所属项目：<项目名>（SPMS projectId `<uuid>`）· 版本/Release：<名称或「未挂版本」>
> 状态：草稿（全部需求 status=draft，待评审）· 撰写日期：<YYYY-MM-DD>
> 下游：本 PRD 的需求由开发计划承接（dev-plan skill 产出，位置循宿主 repo 的计划目录惯例）。**PRD 与计划多对多**——可拆给多份计划，也可能与别的 PRD 的需求合并进同一份；关联键是 FR/NFR key，见 §7

## 0. 一句话

<一句话说清：为谁、解决什么问题、做完之后什么变得可能。不要写「本文档描述了…」。>

## 1. 背景与目标

### 1.1 问题陈述与现状

> 先从用户视角说清「谁正被什么阻碍、造成什么影响」,再写现状与为什么是现在。不要把待做功能换个语序当成问题。有数据放数据（多少人/多少次/多少时间）。
> 调查中读到的现状带路径或出处，与用户假设冲突的地方在这里说清楚。

### 1.2 目标（可度量的结果，3–5 条封顶）

- G1 <结果句，带判据。例：租户管理员无需联系运维即可完成 X，全流程 ≤ 3 步>
- G2 …

### 1.3 非目标（逐条给去向）

| # | 不做什么 | 为什么 / 去向 |
| --- | --- | --- |
| N1 | <最容易被认为「顺手也该做」的相邻功能> | <二期 / 另立项 / 依赖 X 底座就绪 / 明确不做及理由> |

> 这张表是评审的挡箭牌。凡会被问「那 X 呢」的，都要提前出现在这里。

## 2. 领域语言、用户与场景

### 2.1 领域语言

| --- | --- | --- | --- |
| <本项目特有的概念> | <1–2 句说它是什么,不写实现> | <不再使用的别名/重载词> | <既有词汇/代码现状/本次已确认决策> |

> 只收录会改变需求理解的项目特有概念;通用软件词不收录。若没有需要新增/澄清的术语,写「沿用既有领域语言,本期无新增术语」,不为填表造词。

### 2.2 用户与权限边界

| 角色 | 是谁 | 本期关心什么 | 权限边界 |
| --- | --- | --- | --- |
| <租户管理员 / 普通成员 / 学生 / 平台运营> | … | … | <能看到/操作什么,不能看到/操作什么> |

### 2.3 关键业务场景

> 先用 3–6 步的编号叙事写一遍主场景（用户视角,不是系统内部视角）,再用少量高信息量场景压测关键边界。
>
> 1. <角色> 在 <入口> …
> 2. …

| # | 给定角色/数据/状态 | 执行动作 | 应出现的业务结果 | 压测边界 |
| --- | --- | --- | --- | --- |

## 3. 需求条目

> 每条一小节。SPMS key 在创建后回填;**需求标题和实体引用必须使用真实 FR/NFR key**。`R#` 不是需求编号,只在「承接」和 §6.1 作原始诉求来源标识。
> FR 与 NFR 分开成组（对应 SPMS 的「功能性 / 非功能性」分组）。

### FR-<N> <标题（动宾短语，一眼看出用户能做什么）>

- **优先级**：`urgent|high|medium|low|none`（紧急度）　**重要度**：`critical|high|medium|low|none`（需人工在 Web 补）
- **承接**：原始诉求 R<#> · 目标 G<#> · 场景 S<#…>
- **背景**：<为什么需要这条，一两句>
- **行为**：<谁在什么场景下能做什么。用户可感知的能力，不写实现>
- **边界**：<明确不含什么；容易被误解的地方在这里堵死>
- **依赖**：<依赖别的 App/底座的写明；「未就绪则降级为 X」>
- **验收标准**（→ SPMS `acceptanceCriteria`,一行一条、无 markdown 语法;断言用户/外部系统可观察的业务结果,不断言内部实现）：

```
<角色>在<条件>下<动作>后，<系统必须怎样，带数字>
<边界条件：为空/超限/无权限时的行为>
<可观测的落点：列表出现该行 / 通知送达 / 审计留痕>
```

- **测试用例种子**：TC-<N> <一句话标题>；覆盖 S<#> / 验收第 <#> 行；<还需要几条覆盖什么>

### NFR-<N> <标题（质量属性 + 约束对象）>

- **质量属性**（`category`）：`performance|security|usability|reliability|compatibility|maintainability`
- **优先级**：`…`
- **承接**：原始诉求 R<#> · 目标 G<#> · 场景 S<#…>
- **约束**：<必须带数值与作用域。例：列表首屏 p95 < 300ms @ 单租户 1 万行；超限行为是分页而非截断>
- **验收标准**（同上格式，一行一条）：

```
<可度量的断言，含数字与测量条件>
```

- **测试用例种子**：TC-<N> …；覆盖 S<#> / 验收第 <#> 行

## 4. 约束与前提

- **用户给定的约束**：<原话来源标注「用户原话」；这是 PRD 里唯一允许出现技术选型的地方>
```

## 常见毛病(自检时对照)

| 毛病 | 症状 | 改法 |
| --- | --- | --- |
| 验收标准是愿望 | 「体验流畅」「性能良好」「操作便捷」 | 换成带数字的断言;种不出 TC 就是没想清楚 |
| 需求变方案 | 出现表名/端点/库名/里程碑 | 挪到 dev-plan;PRD 只留「用户能做什么」 |
| 粒度失控 | 一条需求要 30 个 Issue,或一条需求就是一个按钮 | 拆到「一个可感知能力、3–10 个 Issue」 |
| 非目标空着 | 只有 1-2 条或直接省略 | 把评审会被问的相邻功能全列出来 |
| NFR 没数字 | 「要安全」「要快」 | 补 `category` + 数值 + 测量条件 |
| 编号错乱 | 需求标题/实体引用仍用 R1/R2,或与真实 key 混用 | 创建后回填 FR/NFR key;`R#` 只留在「承接」和 §6.1 作来源标识 |
| 角色含糊 | 通篇「用户」 | 落到租户内具体角色,并写清权限边界 |
| 领域词漂移 | 同一概念用多个词,或「账号/状态/任务」各自指多个东西 | 在 §2.1 选定规范词与定义,全篇统一 |
| 场景只写主路径 | 权限/租户/空数据/重复/状态边界没人拍板 | 用少量高信息量 `S#` 压测真正有关的边界 |
| 决策只留在对话 | 结论有了,但后来人不知道为什么 | 在 §5.1 只记录会影响范围/语义/验收的产品决策 |
| 阻塞问题伪装成默认 | 答案会改需求,但文档仍定稿/落库 | 保留在 frontier;未拍板只能交草稿,不写 SPMS |
| 追踪链断了 | 目标无需求、场景无验收、或 FR 无 TC | 补齐 §6.2,任一单元格为空都不定稿 |
| 验收盯内部实现 | 断言表/函数/内部调用次数 | 改为用户或外部系统可观察的最高业务边界 |
