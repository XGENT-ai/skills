# 实践案例：用文档交付链检验 agi-mode 的进化能力

这是仓库级实践案例，不是 agi-mode 的专用工作流或安装依赖。**最终评估对象是 agi-mode 的自进化方法；本案例中被它改进的对象是 PRD、开发计划及评审 skill，实际交付效果用于检验这些改进是否有效。**

用已授权项目已有的文档、评审、修订、阶段记录、验收和截图积累真实样本；沿用 [通用进化证据约定](../../../skills/agi-mode/references/evolution-evidence.md)。文档交付链只提供一种实践环境，不能据此声称 agi-mode 在其他任务上也具备进化效果。

仅要求沉淀时，完成版本保全、关联和证据完整性核对，不启动候选对比、重跑产品或自动修改其他 skill。普通工作也不因采集要求擅自发布、上传或运行外部操作。

## 实践的三层角色

| 层次 | 本案例中的对象 | 留下什么证据 |
| --- | --- | --- |
| 进化方法 | agi-mode 如何选样本、找原因、提出／筛选修改、确认结果 | 每轮可见样本、机制假设、候选 patch、验证、成本和去留依据 |
| 被优化对象 | prd、dev-plan、review-* 等生成与评审方法 | 方法的初始版本、候选版本及实际产生的文档／评审 |
| 效果环境 | 执行者依据这些产物完成开发与验收 | 阶段实现记录、截图、测试／运行证据、返工与最终效果 |

历史交付记录足以提供实践题目和问题线索；还需要保留 agi-mode 自己的演化过程，才能评价它是否作出了有效的学习与选择。一次任务最后通过，不等于已证明 agi-mode 的改进有贡献。

## 1. 以交付链为案例

沿实际关系建立链路，不靠文件名相同或一份报告来定义案例：

```text
用户目标与约束
  → PRD 版本 → 需求评审与修订
  → 计划版本 → 计划评审与修订
  → 各阶段实际使用的计划版本 → 实现与验收记录
  → 代码评审／修复 → 最终验收与交付差异
```

PRD 与计划可多对多；一份计划的不同阶段可能使用不同修订版本。复用现有需求、里程碑、检查、finding 和决策 ID，结合项目／文档身份定位，不能跨报告裸用 F-01。记录父阶段或输入产物版本，缺失关联标未知，不按时间接近猜因果。

从计划的记录索引进入，只沿与目标场景相关的证据链接读取必要材料。保留原目录与唯一进度汇总；采集索引不再维护一套里程碑状态。正常任务不默认加载整条历史，研究阶段才按问题展开。

## 2. 评分与归因分开

先从既定用户目标和验收合同定义评分项，再查看效果；历史缺少口径时标为回溯评定，并绑定协议版本，不冒充事前标准。默认先逐项结果与硬底线，再看交付成本；需要总分时预先约定权重，不用平均值掩盖关键失败。

| 效果维度 | 可用证据与边界 |
| --- | --- |
| 目标与行为是否兑现 | FR/NFR/UAT 对应的实际入口、测试／运行结果、交付差异；文档自称完成不算效果 |
| 体验与可用性 | 实际界面、操作路径、状态与用户任务结果；截图支持可见状态，静态图不证明交互、后端或性能 |
| 回归与可靠性 | 正常及边界行为、故障恢复、数据／权限约束、后续缺陷；未观测不自动记为无缺陷 |
| 完成代价 | 有记录的返工、修复、必要人工纠正、运行成本；区分主动耗时与等待依赖，未知不填零 |
| 交付过程 | 初次执行结果、被哪个检查发现、如何修正、最终结果及观察窗口；不能仅留最后一张绿灯图 |

正文长度、章节完整度、评审意见数量、采纳率和 judge 对文档的好感只作诊断信号，不替代上述结果。取消、暂停、外部阻塞和环境无效分别记录，不只收成功项目，也不将所有未完成一律判失败。

实际效果先属于整条交付链。再逐项提出有依据的原因：

- **上游遗漏／错误**：执行按当时计划进行，但必要约束、依赖或验收缺失，能关联到实际问题。
- **评审漏检／误报**：当时可见材料足以识别，评审未识别或引导了不必要返工；历史 findings 不是完整答案，未提及不等于不存在。
- **执行偏离**：当时文档已清楚规定，执行仍违反；不能直接以同义提醒扩充文档。
- **条件变化**：用户后来改目标、依赖变化、工具／环境故障；保留发生时间与原约束，不倒推上游应知道未来。
- **混合／未知**：无法区分时保留候选解释和补证要求，不强给每个 skill 分配因果分数。

采纳不证明正确，拒绝不证明误报，最终修好也不能抹掉前面的失败与补救成本。复核以真实产物、原始证据和适用契约为准。

## 3. 从现在保全哪些数据

复用项目现有版本归档；没有可恢复机制时，在主产物旁建立 `<文件名去扩展名>.history/<run-id>/`，保存阶段记录与必要快照。当前 PRD、计划、报告及 `.records/M<n>.md` 仍在原处，正文只链接归档。阶段 ID 唯一且稳定；同次执行补录可以更新未封存记录，后续执行建新 ID，不覆盖已封存内容。

三个记录时点：

1. **开始／修改前**：冻结当前任务与已知约束、输入文档及必要代码／规则，注明本阶段实际消费的版本。不要等最终交付才用已修订的文件补写“输入”。
2. **阶段交付／中断**：封存输出、实际检查与阶段状态；失败和未完成也保留。记录实际加载的 skill 与必要参考版本、执行配置，可获取才填，未知如实标明。它们放旁路记录，不进入产品或设计正文。
3. **后续效果到达**：追加带独立身份和时间的反馈，链接被评价的阶段／产物版本、需求与检查、执行证据和处置。反馈替代旧判断时记录替代关系，不改写旧事实。

每个阶段记录至少表达下表内容。已有 Markdown 可承载，需机器处理时保存 `run.json`；格式不是另建平台的理由。

| 内容 | 最小记录 |
| --- | --- |
| 身份与关系 | `run_id`、阶段、项目／仓库身份、上游 run 或带版本的输入引用、关联需求／任务 |
| 时间与任务 | 开始／交付时间、任务请求及当时已确认约束、信息截止点；历史补录注明补录时间和缺口 |
| 输入／输出 | 原路径、内容 hash、可恢复快照或可取回版本位置；输入和输出分别列出 |
| 方法与条件 | 实际 skill／参考版本、可获知的模型／工具配置、环境、代码起点；缺失项为未知 |
| 效果引用 | 需求／检查／场景 → 阶段记录 → 原始证据；注明观测对应的实现及实际消费的计划版本 |
| 处置与限制 | 通过／失败／未运行／环境无效／取消等真实状态，重试／修复关联，覆盖与恢复缺口 |

### 恢复性与原始材料

- hash 只用于核对，不能代替文件。已提交内容可引用能持久取回的仓库与完整 SHA；无法保证取回时保存必要快照。dirty 时保留相关 patch、必要 untracked 内容及其基线；index 与工作树分别作为目标时分别保留。
- 现有截图、录屏、测试输出和运行材料可直接引用稳定路径及 hash，不要求再复制一套。可能覆盖、临时目录或会过期的链接，要保存与本次范围相关的原件。新证据使用新路径／版本，不覆盖旧失败图与日志。
- 图像证据记录场景、页面／操作、关键前置状态、采集时间、实现版本、预期与实际观察；原记录已有则引用。旧截图不能因为报告更新就绑定新实现。
- 当前计划可只显示最新基线，但实际交给执行者的版本必须能恢复；验收记录后来更新也不能丢失评分所需的原结果。无需保存每次编辑或全量聊天、全部成功日志，只保留阶段边界与影响判定的材料。
- 仅保存授权工作材料与必要上下文，不归档凭据、无关会话或生产敏感数据。需脱敏时保留转换说明与对重放的影响。不得为了补采集自动提交、上传、安装依赖或扩展文件访问范围。
- 采集失败与业务结果分开报告：产物已交付可以成立，但不能声称案例已经可重放。发现历史缺失材料不得根据最终文档反向编造。

## 4. 历史重放能证明什么

| 操作 | 支持的结论 | 不能推出 |
| --- | --- | --- |
| 重读阶段记录、截图和验收，按固定口径重新评分 | 原交付的观测效果、证据缺口、值得改进的机制假设 | 新版 skill 会产生更好交付 |
| 给新版生成／评审方法当时的输入，检查是否覆盖已知缺陷 | 上游决策或缺陷识别变化；属于代理验证 | 已减少真实返工、已提高实际可用性 |
| 用候选产生的文档／评审处置驱动后续执行，并检查新产物 | 在该条件下实际观测到的交付效果 | 未测场景也会改善，或收益全来自单一上游因素 |

按预算与授权选层级。当前只积累数据时做到第一层的可核对准备即可，不要求立即运行以上评测。

以后要验证因果收益，固定起始仓库、公开目标、执行者模型／工具、环境与预算，改变一个上游表面；多个表面一起改只能评价组合流程。候选计划可能改变步骤，不能机械回放旧工具响应或直接沿用旧截图作为新结果。无法重建外部环境时，声明替代实验覆盖范围；必要时在后续真实任务中验证。

重放 PRD 编写时，不能让生成者读取后来计划与故障；重放某次评审时不能提供后续修复。分析者可读取开发案例全链以找根因，候选执行者只得到阶段截止时的材料，评判者持有效果证据。整条同源需求链及其修订／近重复按组划分，不能分散到搜索与最终确认两侧。

评分依据保持原定用户目标，不允许候选通过删除验收、缩小范围、隐藏失败或修改判定器赢分。用户正式改变目标时另记契约版本及适用阶段，不混比分数。

## 5. 积累阶段的验收

抽查一个案例，确认能够找到阶段实际输入、产物和适用版本，沿需求／检查定位执行证据，并区分初次、修复后与未验证结果。记录是否支持历史效果复核、上游重放、下游执行重放，各项分别写可用／缺口，不用单一“完整”掩盖能力差异。

积累后再按真实任务分布选案例，进入 [Eval](../../../skills/agi-mode/playbooks/eval.md) 建立判定和 [Hillclimb](../../../skills/agi-mode/playbooks/hillclimb.md) 改进方法。保持这份数据约定与 [评测记录](../../../skills/agi-mode/references/eval-protocol.md) 的关联；采集本身不宣称评测或能力提升已经完成。

## 6. 后续如何评价 agi-mode

在将来明确授权实践运行时，给 agi-mode 固定的初始 skill、可见样本、允许改动范围与预算。记录它提出的全部候选、对失败的解释、实测和撤回，不只保存最后版本。评价者依据独立确认的交付效果判断有效收益，并核对是否偷换目标、泄露答案、过度拟合或将未知当通过；诚实地没有找到改进可以是合格处置，不能为了演化分数强迫采用修改。

若要比较进化方法，保持被优化对象起点、样本、底层模型／工具、执行条件和总预算可比。区分被优化 skill 的效果变化与 agi-mode 的贡献；底层模型或执行环境变化不能直接归功于进化规则。本案例积累的所有样本按整条同源需求链分组，确认数据不由搜索者挑选。

当前阶段只积累和核对数据。为本案例增加的采集约定属于参与技能或目标项目；不要将 PRD 字段、里程碑结构和截图采集流程加入 agi-mode 的通用入口或通用评测协议。
