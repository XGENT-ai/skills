## 确认问题

1. [P1] F-01 · 多数信源没有原图尺寸来源，检索与联系表会把验收要求降成 `?`
   - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P3.md:378-400`（§5.2）、`:444-447`（§5.7）、`:571-576`（§5.12）；M1/M2；WORK-F7/AC-1、AC-2。
   - 问题：§5.2 只有 Commons 明确映射原图宽高；Poly Haven、Met、AIC、Cleveland、Rijks、Japan Search 与 LoC 没有尺寸字段映射，V&A/Wellcome 把 `info.json` 留到取用，NASA 也只约定取用时读资源清单。§5.7 又允许尺寸写成 `?×?`。按此实施，多数成功条目在检索结果和联系表中没有原图尺寸，直接违背“每条带原图尺寸”。
   - 证据：[PRD WORK-F7](../PRD-PHOENIX-UI-EVIDENCE-CRAFT.md) 第 316–317、324–325 行；计划 §5.2 的逐信源映射及 §5.7 的尺寸降级文字。
   - 修订：在 §5.2 为每个适配器写明原图宽高的确切字段或元数据请求及失败语义，在返回条目和生成联系表前完成；正常成功条目不得以 `?` 代替。若某信源确实无法提供，须明确其不可用/失败路径，或另行取得用户对需求变更的确认，不能静默降级。
   - 复核：逐信源核对尺寸来源与调用时点；V-1/V-9 的既有条目和联系表断言应确认每个成功条目都是真实原图宽高，而非预览尺寸或 `?`。置信度：高（计划映射与上游验收原文直接冲突）；阻塞：否，M1 适配器契约修订后即可继续。

2. [P1] F-02 · 已确认的浏览器残余请求放行没有同步到 WORK-N1/AC-4，终验可在仍违背 AC 时通过
   - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P3.md:254-256`（D15）、`:647-649`（§5.16）、`:652-655`（§6.5）、`:687-689`（§6.8）；V-3、V-9、M2/M5；WORK-N1/AC-4。
   - 问题：计划接受浏览器自身固定残余请求，并只允许把它记入测试与文档；§6.8 明确 PRD 其他内容不动。原 AC-4 仍要求页面检测/取证只请求目标页面及其资源。V-3 允许残余项后，即使原 AC 文字仍被违反，M5 也可被记为通过。
   - 证据：[PRD WORK-N1/AC-4](../PRD-PHOENIX-UI-EVIDENCE-CRAFT.md) 第 554、556 行；计划 §5.16 的两种排查结果与 §6.8 只改约束段的约定。D15 已记录用户 2026-11-11 对该口径的确认。
   - 修订：把 §6.8 扩展到 WORK-N1/AC-4 的对应表述，使其与 D15、V-3、docs 一致：引擎自身请求仍受原边界约束，仅如实列出的浏览器自身请求例外，不自动更新或下载；V-3 分开报告引擎请求与已登记浏览器残余，不能把例外扩成任意外发。
   - 复核：对照 D15、PRD 约束与 AC、V-3/V-9 及 docs，确认同一请求集合与通过条件；沿用 V-3 的拆分记录即可，不新增验收门。置信度：高；阻塞：否，用户取舍已有记录，只需完成契约同步。

3. [P2] F-03 · `image` 直接依赖未关闭默认特性，会突破“无新增包”约束
   - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P3.md:313-314`、`:767`（M1）；C-5。
   - 问题：M1 虽列出 `jpeg/gif/webp/png`，但没有 `default-features = false`。`image 0.25` 默认启用 `rayon` 与 `default-formats`，会额外引入 AVIF、EXR、TIFF 等格式及其依赖，扩大许可与审计面，违背 C-5。
   - 证据：`tools/phoenix-ui/Cargo.lock:480-499` 固定 `image 0.25.10`；本机锁文件对应依赖 `image-0.25.10/Cargo.toml:60-82` 的 `default = ["rayon", "default-formats"]`；现有最小特性写法见 `tools/phoenix-ui/crates/comp/Cargo.toml:24`。
   - 修订：M1 明确 `image = { version = "0.25", default-features = false, features = ["jpeg", "png", "gif", "webp"] }`。`ureq` 的 SOCKS 特性已由现有 `impeccable-context` 依赖启用，不作为本问题；不要为它另造依赖改造。
   - 复核：检查 M1 的依赖声明同时包含关闭默认特性与四种实际所需格式；V-8 的锁文件净新增包门保持不变。置信度：高；阻塞：否。

4. [P2] F-04 · 复用的静态服务器对 sibling `media` 模块不可见，按计划调用会在编译期失败
   - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P3.md:473`（§5.9）、`:528`、`:676-677`（§1.2/M2）；M2。
   - 问题：计划从新的 `media/poster.rs` 复用 `capture/serve.rs`，但 `serve` 当前是 `capture` 的私有子模块。若不先调整可见性，sibling 模块无法按设计调用 `serve::serve`。
   - 证据：`tools/phoenix-ui/crates/cli/src/capture/mod.rs:11` 为 `mod serve;`；`tools/phoenix-ui/crates/cli/src/capture/serve.rs:20,34` 的 `url_for` 与 `serve` 本身可用。
   - 修订：在 M2 明确将 `crates/cli/src/capture/mod.rs` 的声明收窄公开为 `pub(crate) mod serve;`，并把该文件加入 §1.2/M2 改动清单；不重写服务器。
   - 复核：核对调用路径、可见性和 M2 文件清单一致；由 M2 既有编译检查覆盖。置信度：高；阻塞：否。

5. [P2] F-05 · `header-only` 与文件签名被当作完整性通过，损坏/超限文件仍可进入成功清单
   - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P3.md:517-523`（§5.8）；M2；WORK-F8/AC-1、AC-4。
   - 问题：超过解码上限的图片只读头部即可登记为 `header-only`，视频仅凭 `ftyp` 签名即登记为 `signature`。这些状态都没有完成 PRD 所要求的解码完整性核对，却可与“取用成功”一同落清单；§5.8 末尾“不校验时坏文件会被登记”的风险因此仍在。
   - 证据：[PRD WORK-F8/AC-1、AC-4](../PRD-PHOENIX-UI-EVIDENCE-CRAFT.md) 第 338、346–347 行；计划 §5.8 第 2、3、6 步。
   - 修订：默认按 PRD 收紧成功语义：图片解码失败或超过既定解码上限即为该文件失败；视频须定义并执行足以满足 AC-1/AC-4 的完整性检查，未完成前不得以 `signature` 作为通过。若要放宽为头部/签名检查，必须先修改相应 AC 并取得用户确认。
   - 复核：§5.8 的失败、落位与来源登记顺序应保证未完整校验者不算成功；V-1/V-2 的既有损坏文件与登记断言按新语义核对，不另建检查组。置信度：高；阻塞：否，受影响的是 M2 成功契约。

6. [P2] F-06 · 视频没有首帧时仍登记视频成功，且平台检查允许把关键场景标成跳过
   - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P3.md:524-542`（§5.8–5.9）、`:550`（D9）、`:769`（V-11）；A-2；WORK-F8/AC-4、WORK-N2/AC-3。
   - 问题：首帧失败时计划仍保存视频及带来源记录，只加 `posterError` 并退出 2。这不符合“取用视频时同时得到首帧静态图”。V-11 又只记录首帧用例是执行还是跳过，可能把未证明的四平台视频能力当作候选通过。A-2 已明确指出部分 Linux Chromium 不支持 H.264，这不是纯假设。
   - 证据：[PRD WORK-F8/AC-4](../PRD-PHOENIX-UI-EVIDENCE-CRAFT.md) 第 339、347 行；计划 §5.9 的失败语义、§11 A-2 与 V-11 的跳过口径。
   - 修订：把 `posterError` 限定为失败诊断；未取得首帧时视频任务不得作为成功项登记。§4/docs 写清浏览器与编解码依赖及可见错误，V-2 增加既有取用场景中的“首帧失败不记成功”断言；V-11 对本期声明支持的真实 MP4/H.264 场景须实际执行，skip 只能记未验证，不能记通过。
   - 复核：核对 §5.8/§5.9、§4、V-2/V-11 与 A-2 使用同一成功条件；不新增 ffmpeg、转码器或本期排除的格式支持。置信度：高；阻塞：否，但 M2 契约与 M5 验收须先修订。

7. [P2] F-07 · `audit` 漏查许可/许可链接与短署名，可能漏报素材信息进入产品
   - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P3.md:566-571`（§5.11）；M2；WORK-F8/AC-3。
   - 问题：产品文件只含 `license`、HTTP(S) `licenseUrl`，或含不足 16 字符的精确署名时，当前三类发现都不会命中。这些都是来源清单已保存、但 PRD 明确要求不得进入产品的信息。
   - 证据：[PRD WORK-F8/AC-3](../PRD-PHOENIX-UI-EVIDENCE-CRAFT.md) 第 342 行；计划 §5.8 保存 `license`、`licenseUrl`、`attribution`，§5.11 却只查 URL 与长署名。
   - 修订：`credit` 同时匹配清单的 `license`、`licenseUrl` 与任意非空 `attribution` 原文，不设长度下限；保留误报由主代理判断并记录依据的既有约定。
   - 复核：在 V-2 的既有审计场景中补入短署名及仅许可链接两个断言即可，不新增验收组。置信度：高；阻塞：否。

8. [P2] F-08 · 无来源图片仍成功生成 `provenance: none` 输出，与本期来源验收直接冲突
   - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P3.md:608-609`（§5.14）、`:746`（V-4③）、`:750`（V-5）；M3；WORK-F9/AC-3。
   - 问题：没有内嵌来源的输入只记说明，仍成功写出无来源图片。对该输出目录运行 `embed-prompt --scan` 会失败，因而计划允许的成功路径与 AC-3 不能同时成立。V-4 只使用带来源夹具，覆盖不了这个分支。
   - 证据：[PRD WORK-F9/AC-3](../PRD-PHOENIX-UI-EVIDENCE-CRAFT.md) 第 358、360 行；`tools/phoenix-ui/crates/context/src/embed_prompt.rs:116-133,203-213` 的无来源读取与 scan 缺失退出语义。
   - 修订：采用严格路线：`read_provenance` 为空时该输入失败并在写出前停止，说明先嵌入来源；`provenance: none` 不再作为成功输出。不要新增来源参数、JSON 输出或新的旁注体系。
   - 复核：§5.14 的失败顺序、报告枚举、docs 与 V-4/V-5 一致；在 V-5 的既有输入校验中加入“无来源拒绝且无新输出”即可。置信度：高；阻塞：否。

9. [P2] F-09 · 多输入共享输出目录时同名输出会相互覆盖，报告却可能把两者都列为成功
   - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P3.md:603-609`（§5.14）、`:750`（V-5）；M3；WORK-F9/AC-1、AC-2。
   - 问题：两个不同目录中的同名输入配合共同 `--out` 时，会生成相同的 `<原名>-<宽>.<格式>`。当前只防输出覆盖输入，且允许同名输出直接覆盖；后处理的输入会覆盖先处理结果，使用户拿不到每个输入对应的交付文件。
   - 证据：计划 §5.13 的固定命名与 §5.14 第 8 步；[PRD WORK-F9/AC-1、AC-2](../PRD-PHOENIX-UI-EVIDENCE-CRAFT.md) 第 351、355 行要求每个输入得到相应输出。
   - 修订：处理前计算本批全部输出路径，对冲突给出可定位到输入的失败并避免两个成功项指向同一文件；或选择明确、稳定的唯一命名规则。不要把“最后写入者覆盖”保留为成功语义。
   - 复核：§5.13/§5.14 的命名、预检、错误与报告一致；V-5 的现有命名覆盖中加入两个同名输入加共享 `--out` 的断言。置信度：高；阻塞：否。

10. [P2] F-10 · 极端但合法的裁切比例会算出 0 像素几何，预检范围没有覆盖到计算结果
    - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P3.md:599-604`（§5.14）、`:750`（V-5）；M3；WORK-F9/AC-4、AC-5。
    - 问题：`--crop` 接受 `0.01–100`，但 `round(h × r)` 或 `round(w / r)` 可为 0；缩放后的高度同样可能为 0。输入校验虽检查比例范围，却没有保证实际裁切和输出至少为 1×1，合法调用会进入无意义几何或编码失败。
    - 证据：计划 §5.13 的范围与 §5.14 第 3、6 步公式；[PRD WORK-F9/AC-4、AC-5](../PRD-PHOENIX-UI-EVIDENCE-CRAFT.md) 第 361–362 行。
    - 修订：定义舍入后的最小几何（`cw/ch` 与输出宽高均至少 1）及比例取整口径，失败时仍是该文件错误并继续其他输入。
    - 复核：公式、预检和报告使用同一口径；V-5 的既有裁切边界断言覆盖会产生零几何的比例。置信度：高；阻塞：否。

13. [P2] F-13 · V-7 的单次非交互 Claude 调用没有选择回合，真实宿主无法证明按编号取用
    - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P3.md:697-701`（§6.7）、`:749`（V-7）；M4；WORK-F7、WORK-F8 主路径。
    - 问题：一次 `claude -p --output-format stream-json` 在没有交互注入接口的情况下完成首轮后，无法继续接收用户的编号选择。当前检查只能证明检索和展示联系表，不能证明后续 `fetch <编号>` 取用闭环。
