## 确认问题

1. [P2] F-01 · 字体事实跨元素聚合，改变“同一段汉字”的判定对象
   - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P2.md`，§5.2 D8、§5.5「字体事实取数」、§5.3 `xgent/cjk-font-fallback`；关联 WORK-F5/AC-3、AC-7。
   - 问题：计划按字体栈等属性拼接多个候选元素的全部汉字，只测一个临时 span，再把同一份实际字体事实回填给组内每个元素。若同栈的两个段落分别完整使用字体 A、字体 B，单段都没有混用，聚合探针却会返回两种字体并报意外回退；反向归属也无法指出真正发生混用的段落。规则层随后又只按 `fontFamily` 聚合，进一步丢失元素边界。
   - 证据：PRD `docs/PRD-PHOENIX-UI-EVIDENCE-CRAFT.md` WORK-F5/AC-3、AC-7 明确要求“同一段汉字”发生混用才报；§5.5 当前设计把不同元素的字符与结果先合并，无法满足这个判定粒度。
   - 修订：按元素保留独立文字 run 与 `R/S/failedFonts` 事实；可以批量执行探针，但不得把组内其他元素的实际字体结果写回该元素。只有各元素独立完成判定后，才可按既有输出策略去重发现。
   - 复核：§5.5 明确事实归属为元素而非字体栈组；在既有 V-2 字体组用例中加入“同栈、两个段落分别完整使用不同字体”和“只有其中一个段落混用”的断言，不新增检查组。
   - 置信度：高，计划的数据流与 PRD 验收对象直接冲突；阻塞：否。

2. [P2] F-02 · 探针候选只取直接文本，与元素候选及后代行文字不一致
   - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P2.md`，§5.2 D8、§5.5「候选与行文字」「字体事实取数」；关联 WORK-F5/AC-3、AC-7。
   - 问题：§5.2 的元素候选可凭“足够长的直接文本 + 子树中文占比”成立，§5.5 却只给直接文本含汉字的候选建立行文字与字体事实。直接文本无汉字的父元素会漏掉后代标题/正文行；直接文本含汉字但汉字位于 `<strong>`、`<a>` 等后代的字体 run 也未进入字体探针，导致孤字、拆单元或意外回退漏报。
   - 证据：`tools/phoenix-ui/crates/foundation/src/browser/dom.rs:190-204` 明确 `text_line_rects` 包含后代文本；`tools/phoenix-ui/browser-bundle/15-snapshot.js:74-88` 区分直接文本与后代行矩形。PRD 没有排除含内联标签的中文段落或标题。
   - 修订：探针元素集合与 §5.2 候选保持一致，按子树是否存在需测汉字决定测量；行文字继续覆盖后代。字体取数按元素纳入其直接及后代文本 run，并保留各 run 的实际字体选择属性，不能只测直接文本。
   - 复核：§5.5 的候选与文本范围同 §5.2 对齐；扩充既有 V-2 多行 `<strong>/<a>` 用例，覆盖“父元素直接文本无汉字”和“汉字只在内联后代”两种外部可观察结果。
   - 置信度：高，现有接口语义与计划限定条件可直接对照；阻塞：否。

3. [P2] F-03 · 隐藏字符会进入行文字，造成孤字与拆单元误报
   - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P2.md`，§5.5「候选与行文字」逐字 Range 算法；关联 WORK-F5/AC-3、AC-6。
   - 问题：算法只跳过“无 rect 的空白字符”，却规定非空白字符无 rect 时追加到当前行而不记坐标。`display:none` 后代中的非空白文字没有渲染 rect，仍会被拼入上一行或下一行，改变行尾内容、字长和数字/单位边界。
   - 证据：`tools/phoenix-ui/crates/foundation/src/browser/snapshot.rs:806-818` 显示当前可见文本接口只覆盖特定宿主，不构成对任意隐藏后代的保证；计划的逐字分支直接规定了隐藏字符进入文本，而非“可能”发生。
   - 修订：非空白字符没有任何正尺寸 rect 时同样跳过；仅在取得可归属的渲染行及几何信息时，把字符加入该行。保留空白与换行的既有去空格规则。
   - 复核：在既有 V-2 行文字用例加入隐藏前缀、隐藏后缀和隐藏数字/单位片段，断言隐藏字符不进入任何行文字，也不触发孤字或拆单元发现。
   - 置信度：高，算法分支与 DOM 渲染行为均明确；阻塞：否。

4. [P2] F-04 · 含 `<br>` 的元素被一律排除，漏掉手工断行造成的本期缺陷
   - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P2.md`，§5.2 D7、§5.5 候选限制；关联 WORK-F5/AC-3、WORK-F6/AC-1、AC-2。
   - 问题：只要候选含 `<br>`，孤字与拆单元规则就不评估。用户按语义手工断行仍可能把末行留成一个字，或把数字与单位拆开；PRD 把这类结果定义为缺陷，没有给手工断行豁免。
   - 证据：PRD WORK-F6 的“断行”要求同时涵盖首屏说明、图注的手工断句与“末行只剩 1–2 个字或词被拆到两行算缺陷”；§5.2 的全局 `<br>` 排除与这两个要求不能同时成立。
   - 修订：删除含 `<br>` 即不评估的整段排除；按真实渲染行及可见字符判断孤字和拆单元，`<br>` 只作为断行来源，不作为豁免理由。
   - 复核：在既有 V-1②③ 或 V-2 的行规则样本加入一个手工 `<br>` 造成的孤字和一个数字/单位断行，断言仍产生对应 advisory。
   - 置信度：高，需求没有该排除项；阻塞：否。

5. [P2] F-05 · Web 字体失败归属丢失字体面与回退顺序，会在正常渲染时报发现
   - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P2.md`，§5.2 D8、§5.5「失败 Web 字体」、§5.3 字体发现条件 1；关联 WORK-F5/AC-7。
   - 问题：失败集合只保留字体族名字符串，并按 family + Unicode 范围过滤 `document.fonts`，没有保留 D8 已承认会影响选择的 weight/style。700 加载失败、400 正常时，失败面会污染同族 400 分组；即使用的是同族正常字体，也可能满足发现条件。另一个分支把 `D` 中位于失败字体前的名字与实际字体名比较；若前面是已实际渲染的通用族，名称不相等会误判为没有更早可用字体。
   - 证据：D8 的探针分组键包含 `fontFamily/fontWeight/fontStyle`，而 §5.5 的失败记录只剩 `String`，两处接口直接丢失必要信息。PRD §2.1 与 WORK-F5/AC-7 要求只有失败实际导致汉字改由靠后字体或兜底字体渲染时才报，正常加载并渲染不报。
   - 修订：失败记录保留匹配当前文字 run 所需的字体面描述符，并区分同族不同 weight/style；发现条件依据当前声明顺序与实际回退结果判断该失败面是否是所选来源，不能用“实际字体名是否等于声明名”替代通用族已生效的事实。
   - 复核：§5.5 的失败身份与 §5.3 条件使用同一字体面；在既有 V-2 Web 字体分支加入“700 失败而 400 正常”及“更早通用族已渲染”的断言，均不报意外回退。
   - 置信度：高，计划自身对字体选择属性与失败记录的宽度不一致；阻塞：否。

6. [P2] F-06 · 无实际字体证据但存在失败声明时，计划反而要求报意外回退
   - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P2.md`，§5.5「字体事实取数」空 `R` 分支、§5.3 字体发现条件 1、V-2「读字体返回空列表」；关联 WORK-F5/AC-3、AC-7。
   - 问题：§5.5 只有 `R` 为空且失败集合为空才返回无事实；若 `R` 为空但失败集合非空，会构造 `fonts=[]` 的事实。此时发现条件 1 必然满足，恰好违背“无法确认实际渲染来源时不报”。V-2 又写“返回空列表不产生字体事实”，与 §5.5 的例外直接矛盾。
   - 证据：PRD WORK-F5/AC-3、AC-7 与 §5.2 D8 均规定无实际字体证据只备注、不报；本项可由计划两条规则静态推导，无须额外运行假设。
   - 修订：无论失败集合是否为空，只要实际字体集合 `R` 为空，就返回 `None` 并输出未核实备注，不构造可供规则触发发现的空字体事实；同步统一 V-2 与 §5.5。
   - 复核：§5.5 与 §5.3 不再存在“`R=[] + failed≠∅` 可报”的路径；把既有 V-2 空列表用例明确为同时存在失败 Web 字体声明，断言只有备注、没有字体发现。
   - 置信度：高，计划内部及 PRD 均有相反明确条款；阻塞：否。

7. [P2] F-07 · 字体未核实备注缺少 URL 与文本段定位，使用者无法执行人工核对
   - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P2.md`，§5.5 三类备注、§5.7 备注通道、V-1⑦；关联 WORK-F5/AC-7。
   - 问题：分组备注只有元素数量和字体栈，全局备注连分组也没有；`detect` 在整个运行结束后统一去重输出，未携带目标 URL。一次检测多个 URL，或一页有多个同栈文本段时，使用者无法知道哪一段需要核对。`capture` 虽可从所属图条目定位状态，仍不能定位具体文本段。
   - 证据：`tools/phoenix-ui/crates/detect/src/cli.rs:650-665` 的基础 `ScanOptions` 随多目标扫描复用，发现统一汇总；计划的备注模板没有 URL、选择器或文本样本。PRD WORK-F5/AC-7 要求注明“该段”字体来源未核实。V-1⑦ 虽同时检测两个 URL，却只检查是否出现 `note:`，不能发现错误归属。
   - 修订：备注携带目标 URL 与受影响文本段的稳定定位；复用探针已有数据附截断文本样本或既有选择器即可，全局能力缺失则明确到 URL/整个页面。`capture` 的 `findingsNotes` 使用同一可定位文本。
   - 复核：在既有 V-1⑦ 断言两条备注分别归属正确 URL 和文本段，并在 capture 记录中核对相同定位；不新增验收组。
   - 置信度：高，输出合同及现有多目标调用链均可直接核实；阻塞：否。

8. [P2] F-08 · `findingsNotes` 只有输出，没有完工链路的解释与披露合同
   - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P2.md`，§5.7、§6.1、§6.3–§6.4、V-7；关联 WORK-F5/AC-7、WORK-F6/AC-1、WORK-N4/AC-2。
   - 问题：capture 在字体仍加载或读取失败时写 `findingsNotes` 且不产生字体发现，但计划只补字段名；typeset 仅解释 detect 的 stderr，new-work 与完工评审没有要求消费这些备注。主代理可能把“没有回退发现”当成“字体已核实”，最终交付也不披露未验证状态。
   - 证据：§6.4 对 capture-report 只有字段增量；当前 `skills/phoenix-ui/src/reference/new-work.md` 把 capture 的 findings 作为页面检测并交给完工评审，`skills/phoenix-ui/src/subagents/phoenix-ui-finish-reviewer.md` 的输入合同没有备注处置语义。V-7 目前只检查未处理的 `xgent/cjk-*` 发现，不检查未核实备注。

   - 复核：V-3 核对上述复述一致；在既有 V-7 完工场景复用一个 slow-font 状态，核对仍未解除的备注进入最终交付未验证项，且没有额外 detector 轮次。
   - 置信度：高，输出、消费文本和验收判据之间存在可定位断链；阻塞：否。

9. [P2] F-09 · Linux 收口无法区分“正常无发现”与“字体读取为空”
   - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P2.md`，§11 A-1、V-9、§12 系统字体断言限制；关联 WORK-F5/AC-3、AC-7。
   - 问题：A-1 的后续路线取决于 Linux 探针是否返回真实字体；V-9 却只断言目标夹具通过和未发现。字体读取为空在修正 F-06 后同样不产生字体发现，因此当前命令即使遇到恒为空的故障也可通过，无法决定应按正常路径还是“不可核实”路径收口。
   - 证据：`tools/phoenix-ui/crates/cli/tests/xgent_rules.rs:260-267` 的测试 helper 丢弃 stderr；`:290-312` 的 URL 期望表只比较发现。A-1 已明确 Linux 行为未知，现有 V-9 没有观察能够区分两种状态的信号。
   - 修订：在 V-9 既有 clean/通用族控件上同时断言没有字体未核实备注，或保存等价的非空实际字体证据；这样空 `R` 会由备注/证据缺口显现。无需新增平台、运行组或故障注入门。
   - 复核：V-9 的命令与记录明确包含该断言，并说明失败时进入 A-1 已登记的不可核实路线；Linux 两个平台均留下对应结果。

10. [P2] F-10 · V-9 的 CI 取证未绑定候选 SHA
    - 定位：`docs/plan/PHOENIX-UI-EVIDENCE-CRAFT-P2.md`，V-9 命令与 §10 M4③；关联四平台候选收口。
    - 问题：`gh run list --workflow phoenix.yml --branch main -L 1` 只取 main 最新 run。授权推送后若 main 因其他推送前进，最新 run 可以属于另一提交，计划会把别人的 CI 结果记为本候选的四平台证据。
    - 证据：V-9 自身要求“同一候选提交”，M4③ 已产生候选 SHA，但命令没有使用它；并发推送即可触发，不需要额外环境假设。
    - 修订：用候选 SHA 查询 run，例如带 `--json databaseId,headSha` 后用 `jq` 精确匹配 `headSha`，未找到时报告缺失并继续等待/查明原因；再对匹配 run 执行 `gh run watch`。不要对未绑定 SHA 的记录执行最终结果回填。
    - 复核：V-9 与 M4③ 的记录模板同时包含候选 SHA、run ID 和精确匹配步骤；错误 SHA 或缺失 run 不能记为通过。
    - 置信度：高，命令选择条件与证据目标不符；阻塞：否。
