## 交付与结论

- A-1 解除：PostToolBatch 提醒送达；Stop 首次 `decision:block`、再次 `continue:false` 后出现「Goal paused · a hook ended the turn」；共 8 次结束回合，goal 评估器每次判「not yet met」，从未判 met/impossible；`continue:false` 同时压过评估器与另一个总是 block 的 Stop hook。
- A-2 解除（限本账号与以下三个模型）：statusLine 报告 `claude-opus-5-5` 与 `claude-sonnet-5-5` 无论是否 `[1m]` 均为 1,000,000，`claude-haiku-4-5-20251001` 为 200,000；transcript 只记录不带 `[1m]` 的模型 id，对这三个模型不影响窗口。
- 输出格式固定：空操作为 exit 0、无 stdout，未产生错误提示。
- 超时：整份读取并解析 38.5 MB 的真实 transcript 耗时 0.17 s（3 次），5 s 上限保留。

## 偏差与新发现（已就地修订计划）

1. goal 续轮的 Stop 输入 `stop_hook_active` 恒为 true（首轮及用户消息开启的回合为 false）。越线回合内已收到提醒时直接结束即可；越线后无工具批次的残余风险成立，保留兜底提示。
2. 暂停后仍在运行的后台命令会唤醒会话：goal 的 idle check-in（「background work still running」）与后台完成通知各开启一个回合；guard 每次 block 一次再结束，进度不前进，但每次唤醒多花两次简短模型调用。agent 在提醒「停止或记录」下选择了只记录 → 计划改为要求停止，并在 Stop 请求中列出 `background_tasks`。
3. 提醒不具强制力：同为在已暂停旧会话发「继续」，一次 agent 只确认收尾；另一次 agent 忽略 6 次提醒继续做完并让 goal 判 met。唯一强制点是 Stop → 计划提示措辞补充「即使收到继续指令也先收尾」，并把是否增加工具批次上的硬停止列为待用户决定的开放项。
4. Stop 的 block reason 在 UI 显示为「Stop hook error: …」，送给模型时为「Stop hook feedback: …」；功能正常，启用说明需解释。
5. `/clear` 后新会话的第一个工具批次时 transcript 尚无 usage，判定为无数据（空操作），符合设计。
6. 子 agent 内的 PostToolBatch 带 `agent_id`/`agent_type`，`transcript_path` 仍是主会话文件；主线程事件无 `agent_id`。
7. Claude Code 对连续 Stop block 有上限（9 次，`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` 可调）；本设计每条 Stop 链最多 block 一次，不触及上限。
8. `claude --resume <id>` 恢复已暂停 goal 为 active（计时重置），75 s 内无自动回合；发消息才继续，guard 随即再次收口。
