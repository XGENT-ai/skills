## 实施者定位

- **表达与源码**：报告用路径、需求/检查/里程碑 ID 定位，不复述计划。源码不放需求编号、agent 标记或规划元数据，注释解释必要原因；追溯放记录或提交说明。

本节是跨对话恢复的**唯一汇总入口**，协议文字不随实施改写，实施期只更新「恢复快照」和「完成记录」。续做时先读仓库规则、本节、当前任务相关正文与依赖，再核对 `git status` 和相关 diff；记录与工作树不符时先查明原因，不凭记录覆盖用户改动，也不凭代码存在推断验收已通过。只有继续未完任务、核验前置验收、排错或审查时，才按链接读取对应记录的相关部分；不要默认加载全部记录或原始日志。

**一次回写**：主 agent 更新对应记录，再同步快照变化字段和完成记录一行，不重写无变化内容或追加流水。快照写当前任务、进展与下一步，命令及证据只进记录。首次回写删占位行，每个已记进展的里程碑恰好一行，状态仅「进行中 / 阻塞 / 已完成」；完成时移至已完成行末，最近完成取该行。更新时间带时区，摘要 1–2 句，记录填相对计划的链接（如 `[M1 记录](FEATURE.records/M1.md)`）。范围、决策、接口、数据、风险或退出条件有偏差时，就地修订对应正文，不追加勘误历史。

**独立记录**：按需建 `<计划名>.records/M<n>.md`，头部写计划链接、更新时区、状态及验证基线（commit SHA；未提交写 dirty@起始SHA 与关键改动路径）。正文只写交付行为/路径、必要偏差、未完项与继续动作；验收按 `检查 ID/覆盖范围 | 命令或步骤 | 结果/必要证据` 记录，共同环境和基线在头部写一次，有差异再单列。同一测试组可覆盖多条退出条件，须逐条可追溯；引用原证据与复用依据，不复制断言全文、成功日志或调试流水。未运行、失败、环境缺失明确区分；只有复杂交接、排错或证据需独立保存时才另建任务记录/日志/截图并链接。

**回写后自查**：每次回写后直接核对以下条目：「当前进度 n/N」的 N 等于里程碑总数，n 只计状态为「已完成」的行；「最近完成」对应最后一条已完成记录，不按编号推算；链接指向已落盘文件。上述结构、计数与链接检查不证明验收真实通过。

### 0.3 关键取舍

本地 hook 与常驻 App Server 监听器都可以承载检测。前者随工具调用启动、部署较少，代价是记录延迟和格式兼容；后者可消费用量事件并调用 goal 接口，但需要长期连接、重连和连接身份管理。本期选择本地 hook，符合用户对本地读取与提前阈值的要求。若后续要求实时触发、纯 hosted-tool 回合也及时停止，或需绕过 agent 强制暂停，再重新评估监听器。

暂停也有两种路径：agent 操作原生 goal 工具，或 hook 通过 App Server 设置状态。采用前者，避免在 hook 内再建立控制连接。若 M1 证明目标 Codex 环境无法让 agent 完成暂停，则本方案不能按原需求启用；需重新设计控制路径，不能降级为“提醒过了就算暂停”。

## 2. 模块、接口与依赖

只有一个生产脚本，不新增通用 adapter、后台进程或插件框架。内部函数分别处理输入校验、线程定位、读取用量、读取状态和生成提示。

| 入口/数据 | 契约与不变量 | 依赖与验证 |
| --- | --- | --- |
| stdin | 读取一份 hook JSON；仅处理 `PreToolUse`、`Stop`；stdout 只能是合法 hook JSON 或允许的空输出 | 进程入口测试 |
| 当前线程 | 以本次 `transcript_path` 中 session 元信息定位实际 thread；与已验证的当前线程 env / hook 输入关系交叉核验 | M1 固定规则；异常时跳过，不跨线程搜索 |

| goal 状态 | `mode=ro` 连接当前 `CODEX_HOME` 下 SQLite，参数化查询 `thread_id`；无记录视为无 goal | 临时 SQLite；不能创建不存在的数据库 |

## 3. 数据与写入边界

**hook 运行期间不写任何进度、交接、缓存、完成标记或审计文件。** SQLite 使用只读连接，会话使用只读文件句柄；测试需核验文件内容与数据库逻辑值均未被 hook 改写。SQLite 自身 WAL / SHM 的运行管理不被当作业务状态写入授权。

不做数据库迁移、旧数据回填或会话改写。agent 依照原任务约定写文件，不能从 hook 提示自动推导一份新的记录目录。当前开发计划自己的实施记录遵循顶部协议，与 hook 服务的目标任务记录相互独立。

## 5. 核心机制

### 5.1 判定顺序

1. 校验事件与输入，确认是支持的根线程；子 agent 事件跳过，不能用父 session id 代替当前 thread id。fork 根线程仅在 M1 验证定位规则后支持。
2. 从当前 Codex home 读取对应线程的 goal；只有 `status == active` 才进行用量判定。其他状态及无记录不触发。
3. 从指定 transcript 取最新有效上下文统计；校验字段为非负整数，窗口为正整数。
4. 满足 §5.2 的比较后返回 §5.3 的收尾提示。提醒不是 tool deny，不阻断更新记录、轮询已启动进程或 goal 工具。

### 5.2 用量口径与边界

```text
used = info.last_token_usage.total_tokens
window = info.model_context_window
trigger = used * 100 > window * 65
display_percent = used / window * 100
```

使用整数比较，显示四舍五入的百分比不参与判定。该口径包含最近请求报告的输入和输出，作为保守估算；不得使用历史累计 tokens、goal 的 tokens_used、速率限制百分比，也不得再叠加 cached 或 reasoning 字段。

读取最新完整的 token 记录；忽略尚未写完的末行，但遇到更新的 compaction / 模型上下文切换后，在获得新的有效统计前不能回用切换前的数据。存在 token 事件但其有效载荷无法解析时按未知处理，不从较旧记录“凑”一个比例。

65% 是提前提醒阈值，保留余量用于收尾；不保证一次大输出或自动 compaction 前一定能捕获。`PreToolUse` 追加提示时，已被模型选定的本次工具调用可能仍完成；agent 在下一次模型续推进入收尾。纯 hosted-tool 工作和长时间运行的工具只能在后续支持的边界检测。

### 5.3 agent 收尾指令

提示明确用户设置的是“超过 65% 时暂停当前 active goal”，避免 agent 将收尾理解为 goal 已完成。每次提醒只包含比例、暂停条件与以下动作，不带对话摘录或任务内容：

1. 停止开始新的实质任务；处理已经启动的工作到可交接状态，不为收尾发起全量测试或额外研究。
2. 按当前任务已有约定更新进度和相关记录，写清已完成、未完成、已验证、未验证、下一步及仍在运行的进程。没有既有记录时，在最终回复中交接即可，不要求新建文件。
3. 使用原生 goal 工具将状态设为 `paused`，核对结果；不能标为 `complete`，也不能写库实现暂停。
4. 最终回复说明暂停原因、进度记录位置或交接摘要，并提醒用户在同一工作目录自己新开对话继续。

收尾先保存事实，再暂停，再结束回复。进度写入失败时 agent 必须如实说明，并在回复保存最小交接摘要后尝试暂停；不能为了反复修复记录而继续推进原目标。若目标已在触发后真实完成，agent 可以按原生契约标为 complete 并报告完成，无需制造未完交接。

hook 无自有去重状态；暂停前的多个工具调用可重复收到同一条短提示，agent 应将其视为同一收尾动作，不重复追加记录或重新开任务。提示控制在必要的几句话内。

### 5.4 Stop 补查与状态核验

- goal 已 paused / complete，或无 active goal：输出空操作结果。只依据状态结束判断，不解析自然语言判断“完成”或“已暂停”。
- goal 仍 active 且超过阈值，`stop_hook_active` 为 false：返回 `decision: "block"`，reason 为同一收尾指令，让 agent 补做收尾。这是一次收尾继续请求，不是暂停。
- 同一 Stop 已请求过继续，goal 仍 active 且超阈值：不再次请求继续，输出显式失败告警，提醒用户执行 `/goal pause`；不能显示“已暂停”。不得声称该输出可以阻止独立的 goal 续跑调度。

上述失败分支只是透明告警，不能作为 R-3 的成功降级。M1 必须证明正常链路可真正暂停并停止续跑；若收尾请求反复被 goal 自动续跑覆盖，A-1 未解除，该构建不属于支持范围。agent 已暂停但交接回复未完成时，Stop 不替 agent生成说明，真实链路验收检查两项行为。

## 6. 用户交互

正常触发后的回复由 agent 根据真实执行结果生成，例如：

> 上下文估算使用率已超过 65%，当前 goal 已暂停。进度已更新到当前任务计划，未完成项和下一步已记录。请在同一项目目录新开对话，提供计划路径并说明继续执行。

没有既有文档时，将“进度已更新到当前任务计划”换成实际交接摘要。暂停失败时明确失败，不照搬成功示例。hook 不替用户新开对话、不调用 thread 创建或发送消息工具，不要求继承原 goal。

## 7. 运行保障

- 兼容目标先限定为 M1 / M3 实测构建与环境，在说明中记录实际 CLI / 运行服务版本，不假定两者总是一致。
- 不引入后台 watcher、网络服务、锁文件或新增任务日志。告警使用 Codex 的 `systemMessage`；状态提示不包含 goal 全文、会话内容或秘密。
- 新 hook 按原生信任机制显式启用。不得伪造 trusted hash 或绕过信任；在启用说明中注明“启用即选择超过 65% 时由 agent 收尾并暂停”的行为。
- 不提供未经测试的“支持所有平台”声明。Python 3 与当前主机先验收，其他环境按实际验证补充。

## 8. 失败模式、启用与停用

| 失败/触发 | 影响与数据后果 | 用户表现/检测 | 恢复与验证 |
| --- | --- | --- | --- |
| 无 transcript、新格式、窗口缺失 | 当前线程无法判定；无任务数据修改 | 检测不可用告警，不能显示 0% | 修复兼容并重跑 V-2 / V-4 |
| 数据库缺失、锁冲突或 schema 改变 | 当前线程无法确认 active；不建库、不写库 | 检测不可用告警 | 下一次调用重读；持续异常按说明停用，V-4 |
| 子 agent / fork 定位错误 | 可能影响其他线程，属于启用阻塞 | V-1、V-2 的身份检查失败 | 禁用该映射；不带病启用 |
| agent 未收尾或暂停失败 | 原 goal 可能继续；hook 不伪装为成功 | Stop 告警与真实 goal 状态不符检查 | 用户 `/goal pause`；修正提示/契约并重跑 V-1 / V-5 |
| agent 写进度失败或仍有后台进程 | 交接不完整或进程继续运行 | agent 最终回复明确缺口与进程状态 | 原任务所有者处理；V-5 故障走查 |
| 同步 hook 超时 | 本次检测失效；不终止既有工具 | Codex hook 失败提示 | 缩减读范围、实测后调整运行上限；V-4 |
| 其他 Stop hook 要求继续或停止 | 收尾请求可能受合并语义影响 | 合并配置下实测，不能只验单个脚本 | V-4 / V-5；冲突未解决前不启用 |

启用顺序：先满足 M1 → 完成实现与本地测试 → 在隔离项目合并配置并按原生机制信任 → M3 验收 → 在说明中的已验证环境启用。配置保留其他 handler，不复制开发机绝对路径，不改用户全局 hooks。

停用只移除本 guard 的 handler；保留所有其他 hooks。已由 agent 保存的任务记录保留，已经暂停的 goal 保持 paused，恢复须由用户主动决定。脚本、配置没有数据库写入和迁移，停用无需回填。

## 12. 已知坑

- `AGENTS.md` §5 要求事实可追溯：目标 Codex 构建的文档、schema 与真实行为分别记录，不能用接口存在推断暂停成功。
- 官方 Hooks 文档中 `Stop` 的 `decision: block` 是继续请求；不能把它当成 goal 暂停。
- `PreToolUse` 不支持用 `continue: false` 停止工具；追加提醒也不会撤回已调度的工具调用。
- `session_id` 在子 agent 和 fork 场景不能直接等同当前线程；只查询当前已确认的 root thread。
- 用户指定 agent 写进度与交接：hook 不另建 checkpoint 文件、不追加任务摘要、不实现另一套记录规范。
