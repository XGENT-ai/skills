### 结果身份例外的对象、关系与交付阶段

在既有“记录→可得性例外→终局齐备”程序中，先确定例外是否约束**同一 Result 的实际处理身份及其交付**。原上下文§22的Evidence模型版本与§65的Result产生身份是不同关系；同名字段不能替代对对象、产生关系和适用阶段的核对。

- 独立、强制的每Result身份绑定，不因候选证据、能力发现或运行查询只提供“可得版本”而自动降为可得才记。那些信息可以不完整，同时Result仍另行保留必需处理身份。仅凭它们使用相同模型名或版本词，不足以推定完整Result可以缺失该身份。
- 若其他段落明确限制该Result实际处理身份的最终记录/交付，例外仍适用，不靠章节标题或字段拼写排除跨段语义等价。每Result版本清单本身被“可得/未知”限定，或文中明确允许处理版本未知的Result完整成功交付，均属于同一对象的例外；没有特定齐备/待验条件时仍只得记录半项1.25。
- 对同一Result明确保留“身份未齐仅供预览/对应完整交付或终验待验，齐备后才能完成”等条件，仍可得2.50；一般“全稿完成/全部AC通过”不能取消该Result身份的明确例外。当前依赖未就绪、非最终查询中的未知、真正未使用模型等，不自行变成最终身份豁免。
- 证据应分别指出Result绑定、所引用例外的对象和交付作用，以及适用或不适用的理由。判断的是能否在遵守全部条款时交付缺失该身份的完整Result；不能仅检索“可得”一词。确实无法分类仍保留unknown，不加第三票或折中补分。

该细化不改变六项2.50/半项1.25预算及其他85分。V16首真实稿作为开发反例：N07独立要求结果具有模型版本，F09候选证据/F23能力查询的可得信息没有明确允许Result处理版本未知时完整交付；新口径的模型版本参考为2.50。N07直接允许Result模型hash未知，且没有hash特定齐备条件，仍只得1.25；配置版本不等于实际设置，仍得0。该新参考须与“Result版本可未知成功交付”和“同一身份齐备前终验待验”的最小变体一起冻结重测；V16的95.00/96.25、Q未知和原证书保持，不回填新分。

### 配置记录与自动组批的可验承诺

按原上下文§65，版本清单中并列的config/config version是配置版本信息，不能单凭“每结果有版本清单”就给实际配置2.50分。仍需保存该结果的实际参数值，或明确绑定可解析、不可变的实际配置快照。实现只保存同一schema/config版本标签而丢失不同实际参数，仍满足版本清单文字却违背原要求，这是已知验收缺口；只在此身份预算扣分，不能连带否定其他已明确的版本身份。

按§43–44，GPU推理能处理batch与Scheduler自动组织工作是两项承诺：系统具备兼容批推理能力5分；在策略/能力/预算前提满足时主动组织适用任务/页/区域并以吞吐或利用率为目标5分。仅执行调用方预先拼好的batch即可满足“GPU可兼容批处理”，但没有系统自动组批；这类稿保留前5分，后5分不计。明确自动组批或跨段等价的系统行为可得后5分，不要求AutoBatcher名称、特定队列实现或每个任务必组批，性能目标可由全稿共同承接。仅报告提供方支持而未承诺系统批推理，前5分也不能自动获得。

先核对**本服务的执行能力**，再核对谁组成批次。能力发现、供应方说明、条件成立时的收益报告，与本服务能够接受/执行兼容批次是不同义务；报告可以正确说明“不支持/未执行”，同时系统仍不具备批执行能力。只有报告条款、技术候选或一般阶段名称时，执行能力得0，不能凭出现“GPU支持动态批量执行的能力可报告收益”就补5分。反之，“调用方可提交兼容的一批推理工作，由本服务执行并保持单项结果”的可用功能承诺可得5分，不要求“本服务”字样或内部实现；系统还承诺自动形成兼容批次并有吞吐/利用率目标时，两项各得5分。跨段的明确执行承诺同样计入。

### 版本绑定先于可得性判定

原§65要求保存产生每个结果的具体版本身份。对pipeline、model、prompt和parser，必须有操作性条款承诺对应版本、不可变版本标识/指纹，或结果明确引用可解析的不可变处理清单；名称和格式可语义等价，不要求固定字段拼写。共同的“版本”修饰语明确覆盖多个组件时可合并承接；仅有“版本复现”标题、一般可复现目标、源/结果版本，或清单中独立并列的`version`一项，不自动给其他组件补出版本关系。判断的反例是：只保留组件名称而丢弃产生结果的具体版本，是否仍满足该操作性条款。

“明确”按完整合同及正常局部分组判断。**同类组件组＋共有尾部属性**可以紧凑表达多个版本；尾部属性是一项version或version/hash链均可，不能仅因多个属性使用斜线就当成裸组件混列。例如在“修订可追溯pipeline/model version/hash、prompt/parser version、配置及证据”中，两个局部组的version分别共同修饰pipeline/model及prompt/parser，所要求的四个版本均建立绑定；模型hash及实际配置再按其独立规则判断，不新设pipeline_hash义务，也不要求重复写每个字段。共有组可由语义、标点或句法界定，不限定特定标点/英文拼写。名称实现反例必须遵守这个共有修饰的正常含义，不能人为只给组内末项版本来制造缺口。

当一个连续清单真正交错组件名称、带属性短语及之后恢复的裸组件，且没有明确的局部分组时，某个短语内部的version才不自动扩散到其它裸名称；若名称解释仍符合全文，该项版本承诺不充分，记录得0。文档本身的承诺不足与输入缺失/无法核实导致的评测unknown分开。跨段更强的结果版本绑定可以排除名称解释，照常得分。

例如，`parser/pipeline/model version/hash/prompt/config`混列名称与属性，单靠这一句不能证明parser及pipeline版本绑定；`parser version、pipeline version、model version、model hash、prompt、config`明确了前三项版本。`parser/pipeline/model各自的版本`、`versions of parser, pipeline and model`，或完整版本清单的明确共同修饰，同样可承接；不要求重复字段、特定标点或固定英语拼写。仍须分别检查可得性与终局，明确版本不自动变成齐备交付；prompt名称与config版本也不自动升级为prompt版本与历史实际设置。

先确认该项记录绑定，再检查适用于它的可得例外和终局完整性。没有记录绑定时固定得0，后续“终局未保留”与“不适用”的描述差异不再成为额外打分事项。绑定成立时仍严格沿用2.50/1.25的既定完整与记录半项预算；一般声明不能取消具体例外。实际configuration仍须关联历史有效设置或其不可变可解析快照，缓存/幂等比较和评测身份清单不能替代。

这只明确本任务六项身份的判断顺序，保留五维权重、其他85分、主分0.00–100.00、1.00分最小收益及原噪声/授权门。新参考须逐份核对全文，再在新协议校准；不把诊断标签或推导的身份信用当作历史产物的新总分。

每份产物仍只用两个独立主评审上下文。身份、完整上下文、证据哈希与引文先校验；硬底线保持二值且须一致，确定性 verifier/replay 结果不由 judge 覆盖。未知不填零或满分。
