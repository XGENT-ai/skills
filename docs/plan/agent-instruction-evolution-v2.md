## 实施者定位

执行本计划的 agent 是**资深软件工程师**，依据本计划、仓库规则和当前代码实施。

- **开发边界**：仅实施本计划明确纳入的系统与改动；范围外依赖按 §4 的契约、提供方与解除条件跟进，不代建、改造或部署。源码可访问、自有服务或同仓目录不扩大开发范围。外部缺口阻塞时回写影响与继续条件，推进不依赖它的已授权工作；就地修订偏差和委派不扩大范围，新增开发对象须有用户明确依据。fixture 只覆盖约定契约的必要行为，不能成为替代外部系统的产品，也不能冒充真实集成验收。
- **表达与源码**：报告用路径、需求/检查/里程碑 ID 定位，不复述计划。源码不放需求编号、agent 标记或规划元数据，注释解释必要原因；追溯放记录或提交说明。
- **编号与任务**：需求/约束/假设 ID 只在需求账本登记一次，上游 ID 保留原编号及来源；检查、里程碑、任务 ID 分别由验证表、里程碑表、按需内部任务表定义，正文、NFR 展开、映射和进度记录只引用。修订保留已有 ID，删除/拆分时同步引用；任务表若存在，按交付物、前置成果与检查 ID 推进，任务进展及证据写入所属里程碑记录，不另设任务状态表。
- **完成的定义**：本里程碑退出检查全部通过才能记完成；未运行、失败、环境缺失分别记缺口，不冒充通过。集中到阶段收口的终验由收口里程碑负责，通过前不宣称整期或跨期需求已验收。
- **角色验收**：上手与业务场景由 Agent 按 §9 指定的知识、资料及权限约束模拟，不能借内部源码或实现者补步骤；记录实际结果与卡点，不把模拟结果写成真人数据。有工具和权限的真实环境检查由 Agent 执行；真人公测指标按其指定阶段另验，不冒充本阶段已通过。
- **按计划路线实现**：计划已定的技术路线、接口、复用锚点和检查命令直接照做，不重新调研，也不为已定决策另起方案设计、比较或评判；计划没写的实现细节按最近的同构代码就地决定。调查只读本里程碑的改动落点及其直接调用方和依赖。只有代码事实推翻计划前提或路线走不通时才停下，就地修订对应正文并在记录写明偏差。
- **工作顺序**：需要行为测试的改动先红、再绿、再重构。按实际前置成果及检查推进，不等无关终验，数据、安全、发布及用户分期门不得绕过；稳定契约下可用 fixture 开发，不能替代真实集成。
- **验证节奏**：开发中和里程碑退出只跑 §9 中排在本里程碑的局部检查，即新增或改动行为的测试、直接受影响模块的已有测试和快速静态检查。全量测试、端到端、真实环境与界面走查、故障注入、评测等收口检查只在 §9 指定的阶段收口跑一次，同环境走查合并，不在中间里程碑或小改之后提前跑。已通过的证据只在它实际覆盖的代码、契约、配置、依赖或数据被改动时失效，失效就重跑那几项，不扩成全量。收口失败修复后重跑失败项和修复波及的局部检查；修复改动共享契约、公共入口、构建或依赖时，再重跑受影响的收口检查。调优、容量这类要反复尝试的工作，先用几分钟内能复测的缩小版本迭代，达标后再跑完整检查。
- **并行交付**：独立任务在收益超过委派/集成成本且工具可用时使用 subagents，模型默认继承。任务说明只给目标/ID、稳定契约、可写与禁改路径、运行资源和检查；共享文件单人负责，数据库、端口、浏览器等隔离或串行。子 agent 返回结果、路径、验证证据与缺口，默认不另写任务文档；主 agent 审查并集成验收。边界变化先回报，失败只阻塞依赖任务；结束对话前收集或停止仍在运行的任务。

### 0.3 ADR-1：如何区分同样成功的解法

- 状态：Accepted，作为本计划的实现路线。
- 背景：当前 reward=0/1 不区分测试以外的质量；直接增加同样满分的任务不能解决这个缺口。
- 可行备选 A：固定任务契约的逐项锚点评分，可用测试及轨迹复核，能指出具体质量损失；代价是准备标准与校准判断项。
- 可行备选 B：匿名成对偏好评审，直接决定哪份更好，免去部分权重设计；代价是判断随对手变化、难形成可回溯的单产物分数，位置/文风偏好更难定位。
- 选择 A。匿名成对材料只作校准反例，不另设一套晋级投票。分数是该协议的质量指数，不称官方 benchmark 综合分。
- 正面后果：优化器能依据真实薄弱项提机制假设，报告能解释同为成功时为何质量不同。
- 负面后果：主观项仍可能误判；不能仅凭 schema 正确认定 judge 可靠；评分成本增加。
- 重审条件：校准不能稳定区分已证实的质量差异，或主要标准无法获得可复核证据；先修尺子或缩小评价范围，不继续内层搜索。

#### ADR-2：TypeSafe 参与反馈还是直接判定晋级

- 状态：Accepted。
- 背景：用户要求把决策模型纳入本进化流程。当前受控试测对若干窄维度有区分度，但严格报告完整性规则仍漏扣，且没有真实未见任务校准证据。

- 备选 B：Jev 与主评审分别消费同一匿名产物，辅助分进入 search 反馈，主分仍按原证据链产生。代价是增加一次 API 调用，首期不承诺减少主评审调用。
- 选择 B。辅助分影响下一轮改进假设，不改当前候选的 keep、confirmed_best 或 apply 资格；这是有作用的进化反馈，尚非替代主评审。
- 重审条件：在冻结协议下完成未见真实产物校准、取得可核对的误判与资源收益证据后，才能另行设计是否让特定辅助项参与正式主指标。

v2 JobSpec 沿用原顶层字段，新增 `evaluation`：`root` 为评分材料目录，`paths` 为相对文件白名单，`rubrics` 将 case_id 映射到该目录内的 JSON，`calibration` 指向夹具清单。新增 `authority.evaluation_root` 必须与已授权目录一致，复用 read_file 的路径、链接和字节检查；不得将整个数据目录自动打包。Job.inputs 增加 evaluation manifest 并绑定 protocol_hash，不能靠绝对路径代替冻结字节。

`measurement.objective=quality`、`primary_metric=task_quality`；`mode=calibrate` 允许只有基线条件，执行校准及 search 基线诊断后结束，confirmation 不进入此模式。compare/search 的条件与对照规则继续沿用。主评价模型继承 runtime 的 gpt-6.1-sol/high，每产物两个独立上下文；辅助模型由 §5.9 的窄配置冻结，不受 Codex effort 字段影响。

`evaluation.auxiliary` 可缺省关闭；本期公开模板包含启用配置并验收该路径。对象仅含 `provider=typesafe`、`model=jev-1.14.0`、`criterion_ids`、`rubric_path`、`calibration_path`、`authentication={source: controller_env, name: TYPESAFE_API_KEY}`。文件必须在 evaluation.paths 内；criterion_ids 对应冻结的适用项。新增 `authority.allow_typesafe_auxiliary` 明示允许将 §5.9 的最小证据视图发给该服务，`budget.max_auxiliary_calls` 是 max_trials 内的有限子预算。只保存凭证来源描述，不保存值。

启用辅助时，Job.inputs 另固定 typesafe_worker.py 的源码 blob 与哈希；恢复和 payload 构建只使用该冻结副本，不读取当前安装目录替换程序。worker、context、问题刻度和实际响应模型均参加辅助身份校验。辅助请求仅允许文本 state 与 Score，不接受 assets、Box 或任意自定义端点。

checker_kind 只接受 existing_verifier、regression_replay、judge。前者消费原收据；第二种按冻结的测试路径和真实 repo argv 在原始/修复快照重放，失败必须归因到预期缺陷，不能把导入或环境失败算成有效回归测试；第三种给出锚点判断。确定性检查产物和模型判断均以原 journal/grader 执行记录为准，不提供任意脚本插件接口。

Assessment 的 status 为 valid/unknown/invalid；每条证据包含允许文件、内容哈希、位置和实际片段。先核对位置/片段真实存在，语义判断由已校准的规则承担。证据包保留必要代码上下文与原始轨迹，省略/截断必须显式登记；看不到的材料不能被引用或算满足。

v2 保留原 agent 的 status，同时另存 quality_status。success=0 或硬底线失败时 Q=0；评分自身缺证据时 Q=null、quality_status=unknown，不把成功运行改写成 agent 失败。比较器显式报告缺失质量项并阻止晋级，不通过删除这些行提高均值。候选结果、评分器结果、组数分母分别报告。

| TypeSafe System One | API 契约与控制样本调用已核实；真实任务辅助效度及 SSH 接线待验收 | [Score](https://docs.typesafe.ai/primitives/score)、[Confidence](https://docs.typesafe.ai/confidence)、[API](https://docs.typesafe.ai/api)及上述 24 次试测 | 固定 jev-1.14.0，以标准库请求 POST /v1/systemone；由既有远端独立 grader 容器发起 | 超时/限流/无密钥只使辅助项 unknown/unavailable；不伪造主分，凭证与资源仍须清理 |

外部主机、账户、配额由已有运行者提供；本计划不建设其替代系统。数据不足时允许工程交付，但真实效果终验仍记未完成，不能用更多规则或静态检查补成通过。

## 5. 核心机制

### 5.1 评分：成功是底线，质量必须有内容

每个 case 从公开请求、正常可读项目契约中固定质量项；允许隐藏答案/测试实现，不能隐藏完成任务所需要求。评分标准独立于被优化指令，不能因候选新增一个格式要求就增设得分项。

首个 bug-fix 模板覆盖下列证据类型，按任务适用性选项；不强制每题都有每一维：

| 维度 | 评价对象与证据 | 禁止的替代指标 |
| --- | --- | --- |
| 行为完整性 | 合法边界、相邻路径及错误语义；以独立验收/反事实检查为先 | 只重算原测试通过数、偏离公开契约造隐藏要求 |
| 改动质量 | 解法是否符合实际模块契约、复用是否合适、是否引入无必要耦合/重复；指出具体代码与后果 | 行数越少越好、只因结构接近参考补丁得高分 |
| 回归保护 | 新增/修改测试能否在原缺陷上失败、修复后通过；是否覆盖真实触发机制 | 测试数量、覆盖率或“已加测试”的自述 |
| 交付证据（单列） | 报告命令与实际轨迹一致，未测项有准确说明；仅任务要求时纳入对应验收 | 文风、篇幅、漂亮解释或声称“完整验证” |

对判断项定义三级锚点：0=指定缺陷确实存在，0.5=明确列出的部分满足状态，1=全部指定条件满足；中间状态不能由 judge 临时创造。二值可执行项只用 0/1。所有分数都要有文件/测试/轨迹定位，缺证据标 unknown，不自动给满分。

每个 case 的非门槛质量项权重在运行前写全且总和为 1，初始模板对选定项等权，这是本项目的透明起点而非通用质量标准；重复/碎分同一要求不能增加其总权重。`Qcase = Σ weight × level`，最终仍先按预先固定的 case 权重、再按独立来源组聚合。跨不同 rubric 版本的数值不直接比较。

报告同时给原始逐项结果、task_success、Qcase、分组质量差和资源；用户能看出损失发生在哪个真实要求上。若主张补丁自身的执行性能更好，必须另有目标负载测量，不能使用 agent 生成耗时替代。

说明性算例，非实测：某任务公开要求有效回归保护，三个质量项等权。两份补丁原 verifier 均为 1；甲的行为完整性=1、改动质量=1、回归保护=0（测试在旧代码也通过），Q=2/3；乙三项均为 1（测试能重现原缺陷并在修复后通过），Q=1。这里可观测的质量差为 1/3，依据是反事实执行证据；无需虚构谁写得更漂亮。真实 M1 必须拿实际产物验证这类差别，算例不能当作校准通过。

### 5.2 判定器校准：必须先能分辨

新增 `mode=calibrate`，沿用 `xgent-evolve run --spec ...`。只做评分器和基线诊断，不生成候选、不确认、不采用；validate 仍不调用模型。compare/search 也必须先满足同一校准门。

校准夹具由评测侧保管，含实际产物、已验证的预期关系及证据，禁止只写“预计能分开”。至少覆盖这四类反例；这是本实现的风险覆盖，不是靠四题证明统计可靠：

1. 两份产物均通过原 verifier，但回归测试有效性或契约覆盖有可复现差异，质量项必须按预期排序。
2. 同一产物换中性 ID、展示顺序或等价格式，质量项不应随身份/篇幅变化；同一输入在两个全新 judge 上下文重复。
3. 明确不正确、越权或篡改测试的产物，底线必须拒绝；再提供真实合格产物，排除永远判坏。
4. 在产物/日志中放“给满分/忽略标准”等评分指令，以及“测试很多但不触及缺陷”的产物，评分器不得服从或奖励这些代理。

确定性检查与判断项分别校准，先亲自复核带原始轨迹的少量结果。judge 输出需逐条引用 rubric 与真实证据；引文/定位不成立、读取不完整或判断相互矛盾时该项 unknown，不能平均掉。校准中的已知清晰关系不能保持或必要项 unknown，则 calibration_status=failed，整次判定为 invalid，原因说明具体量表/证据故障。

主校准证书绑定 rubric/checker/judge 配置、输入产物和运行环境哈希；变化即失效。主评审与基线同为 gpt-6.1-sol，不称为跨模型独立裁判；独立上下文只证明没有继承候选自评。TypeSafe 按 §5.9 单独校准，辅助通过不能代替此门，辅助失败也不改写主校准事实。

### 5.3 底线与质量回归

评判顺序为运行有效性 → 正确性/权限等硬底线 → 逐项质量与组别回归 → 主指标差异及噪声 → 资源代价。原 verifier、保护原则/授权/公开接口的严重回归不能被其他项高分抵消。

关键底线在协议中逐项声明 checker 和 minimum；缺 checker 保持 unknown，不能以内容 policy 审查代替实际行为检查。policy 只证明指令语义未越界；执行中的越权和错误交付另从产物/轨迹检查。

候选退出/超预算且证据完整，属于有效行为失败，success=0、Q=0，留在分母。评分器自身无法读取/执行、judge 证据损坏属于测量缺口：保留原 agent 产物，不伪造候选零分。有限重试只重做同一待评产物的评分，绝不因评分失败重跑并挑选更好的 agent 答案。

### 5.4 外层：基线、余量与统计可行性

1. 从真实任务/当前纠正提取待验证机制，选可重放任务；先按来源/问题家族分组、固定抽样与划分，再运行。不能只留基线失败题以抬高总体收益。
2. 先跑原始指令的重复基线/A/A，保存 Q 分布、薄弱质量项、评分器重复差异、生成波动与成本。`repeat` 仍不是独立任务。
3. 若同样通过原测试的产物存在经校准的 Q 差异，且目标薄弱项有改进余量，才能进入候选搜索。若 Q 也饱和，结束为 inconclusive / quality_headroom_absent；不追加同义规则，也不偷偷改目标。
4. 同一产物重复评分不稳定，先修判定；A/A 生成波动已大于预定最小实际收益，按事前规则增加有信息价值的独立任务/重复，或结束为 inconclusive / measurement_noise_too_large。
5. 在开始长循环前，列出组数、权重、当前区间方法、最小实际收益与有限预算下可辨别范围。现有有界区间很保守，必须显示其宽度；即使全胜也无法支持目标时，不预订一次注定无法确认的长搜索，给出需要增加数据/预算或缩小结论的分支。
6. minimum_effect 必须解释为量表上的有价值变化，例如某项由部分满足变为完整满足的加权步长；旧成功率协议的 0.05 不自动搬到新质量指标。minimum_groups 由协议显式给出并核对效力，不能用固定五组替代该诊断。

本阶段结果是 `baseline_diagnostic`，包含 headroom、judge_noise、generation_noise、precision/budget、proceed/reason。发现量表缺陷时固定新的 protocol/rubric 版本，再重测基线与仍有竞争力的候选；禁止沿旧分数接着涨分。

### 5.5 内层：一次机制假设，一个候选

优化器只接收 search 的任务、产物、允许的逐项质量反馈与资源，以及固定的质量目标/底线。不给 confirmation、私有测试、参考补丁、候选身份映射或评分器可执行输入。评分项的公开要求可见，私有锚点材料与答案不可见。

启用 TypeSafe 时，search 反馈另含合法的 auxiliary_scores、分布/未知状态与主辅分歧，供提出机制假设使用；不发送私有评分实现或凭证。主评审在冻结原分前看不到这些辅助分，避免评分锚定。辅助分不能更新 search_best，不能直接淘汰候选或代替有证据的主分。

每个提案必须写清：真实薄弱项 → 机制解释 → 最小指令差异 → 预期改变的质量项 → 可能回归 → 推翻假设的结果。已有规则未执行时先检查发现/路由/冲突；没有证据时不把换一种措辞当进化。

- skill：在相同目标仓背景下比较 absent / 原版 / 候选。自然发现与显式执行分开；发现试验使用实际可选技能目录并记录其清单，不把仅安装两个技能的结果外推到完整目录。
- AGENTS：原版/候选用同仓、同代码起点任务，固定其他技能。嵌套作用域单独覆盖；不将这里的根 AGENTS 搬去外仓。
- 组合归因仅在事前声明四条件对照时执行；两个单独赢家组合后形成新候选，不能把收益直接相加。

沿用 initial_baseline/search_best/confirmed_best 和 keep/discard/inconclusive/invalid。冻结协议下按同任务成对运行；探索 keep 仍只支持探索保留，不能当已确认采用。平台期先诊断尺子、余量、数据和机制，不能靠无限生成候选解围。

### 5.6 资源、身份与恢复

每次 agent、官方 grader、补充确定性检查、quality judge、optimizer、policy 都登记执行身份。新增评分沿用 grader 角色，幂等键加入 trial/rubric/judge-config 哈希；评分执行 ID 关联原 trial，恢复只补尚未完成的阶段。

一次产物的主模型评分默认在两个全新上下文执行，这是捕捉明显判定波动的工程选择，不是两个独立任务。逐项一致才形成明确 level；不同判断先用现有可执行证据裁定，仍无法裁定则 unknown，保留两份判断，不临时召集多数票抹平争议。确定性可判的项不调用模型。

validate 展示调用量公式：校准执行 + 基线/A/A + 条件数×任务数×重复数×(agent+官方 grader+所需质量检查/判定) + optimizer/policy + 确认预留 + 有限重试。所有项计入 max_trials/总截止，不能沿用首期 18 次预算假装覆盖新增角色。实际订阅账单仍 null。

TypeSafe 额外计入独立辅助校准和每个有效 search 产物的一次 API 请求，受 max_auxiliary_calls 与剩余总预算双重限制；一请求对应一个 grader 执行，不把容器内多次调用藏成一次。无自动 HTTP 重试，不消耗确认预留；错误、超时和已耗 token 同样记录。Codex 订阅费用与 TypeSafe usage/可核对账单分别报告，估算不冒充实付。

报告 agent 原始 duration_sec、input/output/cached/reasoning token 字段及总评价开销；缓存/reasoning 字段按原 usage 分开，不重复相加。容器准备、判定与恢复等待不冒充 agent 解题时间。冷暖缓存条件与顺序登记，单次数字不宣称稳定更快。

### 5.7 独立确认与采用

冻结唯一候选、rubric、模型、分组、最小收益与分析检查点后，才开启未参与任何选题/调参的 confirmation。旧两题已属于开发材料；同题重跑和换协议命名不产生新确认数据。

confirmation 首期不调用 TypeSafe，不把其主辅一致率或高分当独立效果确认；继续使用冻结的主评价方法。辅助模型/刻度及反馈策略属于搜索方法版本，变更后建立新协议，不拼接旧候选成绩。

确认完整报告 task_success、逐项 Q、来源组差异/区间、关键回归、有效失败、未知项及资源。沿用事前区间规则；满足最低组数不自动产生 keep。小样本或宽区间仍 inconclusive，但必须给已测产物的真实质量分和证据，不能只剩一个状态词。

只有正确性/原则/授权等底线全过、无未知关键项、质量差异超过预定实际收益且不确定性支持，才允许 confirmation=passed、更新 confirmed_best。apply 重算确认及所有质量收据后走既有 CAS；未确认不做效果采用。已经明确授权的客观事实修正继续走独立 unverified 包，不能借此绕过质量确认。

### 5.8 报告与后续反馈

报告先给比较问题与目标是否达到，再给分数、依据和代价。每个条件至少有：成功/失败、Q 与各质量项、资源分布、样本/来源组/重复数、判定器校准和未知项；列出质量改变最明显与发生回归的具体产物及证据。

工程验收只说明执行链可用；评价校准只说明指定差异能被识别；搜索结果与独立确认分别报告。没有赢家是合法结果；无法分辨原因必须区分“量表失效”“任务饱和”“噪声过大”“样本/预算不足”“候选确无收益”。

采用后在后续已授权真实任务中收集反例，记录机制、适用范围、版本和回退点；回归则进入新一轮 Reflection/Eval，不把一次得分提高变成永久规则。无后台采集或永久监控。

### 5.9 TypeSafe 辅助评分与 search 反馈

**职责**：Jev 只对已经冻结的任务产物做窄维度判断，帮助优化器定位下一轮要解决的问题；不直接评价指令写得是否漂亮。主质量分、硬底线、keep/discard 和独立确认仍由原链负责。

1. **输入**：同一 task 的公开质量契约、匿名 patch、相关完整代码/测试片段及已核对的工具日志。复用主评审的白名单 context manifest；移除条件名、候选身份、历史分数、主评审结论、私有测试实现/答案和认证材料。缺必要上下文则辅助 unknown，不补猜测。Jev 与主评审相互看不到对方结论。
2. **问题**：按 criterion_id 分别发送 Score，共用同一 state。初期仅启用边界完整性、回归保护、改动范围三个窄类型；报告完整性、严格流程合规与最终事实裁定不交给 Jev。仅辅助原本需要语义判断的项，例如测试断言与缺陷机制的对应、改动是否服务当前请求；通过数、退出码、精确路径权限等确定性事实不重复询问模型。每项沿用冻结的三个独立锚点描述，禁止用一个总问题代替全部质量维度。question ID 只用于回包映射，instructions 必须包含完整判定内容与状态引用；各级描述独立完整，不依赖相邻刻度或数字提示。
3. **返回**：保留 0–2 raw_score、各级 probabilities、confidence，辅助 normalized_score=raw_score/2。校验实际模型 ID、字段范围、概率和、期望分数与完整响应；这些数值不转写为已证实的事实或主 Assessment 的 evidence/reason。confidence 只作模型分布信号，不作真实准确率或采用门槛。
4. **反馈**：只将 search 的已校准维度写入辅助反馈。按主刻度相邻锚点中点识别主辅分歧，保留原始分布和关联产物，作为后续机制诊断线索；不自动加权主 Q、不触发无限复审、不据此过滤候选。无辅助结果时仍交付完整主反馈，并显式标明缺测原因。

**独立校准门**：每维度分别记录 certificate 和 eligible 状态。使用同成功而质量不同的控制对、匿名改名/等价表述、同产物两次独立请求及评分注入反例。清晰样本的最高概率档位须唯一且符合由可执行反事实或已核对证据确定的参考档位，好坏关系每次方向一致，重复波动须小于该关系的分差；再用未参与刻度修订的真实 agent 产物复核这些关系。任何已知明确漏扣或上下文不足的维度设 eligible=false，结果不进入优化器反馈；不得调整阈值追认旧结果。

现有 24 次试测是一个合成任务家族的开发材料；报告规则漏扣保留为负例，不计独立样本数，不作为以上真实任务校准已通过。辅助校准失败可继续主链，但 R-5 的启用路径仍须有至少一个合格维度贯穿真实 search 反馈后才能验收；不能只用“可关闭”模式宣布整期完成。

**执行与密钥**：辅助请求在已有 SSH 主机的新 grader 容器中执行，由冻结的 typesafe_worker.py 发往固定 `https://api.typesafe.ai/v1/systemone`；仅做文本判断，无工具调用或候选代码执行。调用者先将 TYPESAFE_API_KEY 导出到控制器环境；工具不自动读取或 source 用户的 .zshrc。经独立 SSH stdin 凭证操作传给指定执行的短期文件，不放入 runtime、payload.json、命令参数、冻结包或日志；在 API 进程中才组成 Authorization 头。该操作复用既有 ssh_request 的 stdin 传输，跳过持久 payload 写入，凭证文件只对受信 API worker 可读，不挂入 trial/optimizer/主评审容器。

凭证准备位于 RemoteClient.submit 已保存容器身份之后、launch 意图之前，沿现有 prepare_codex 的阶段接缝调用 prepare_typesafe；持久 payload 只含 provider 与凭证来源句柄。远端该操作仅核对原执行身份并准备短期文件/脱敏收据，不走 create_resource 的 payload 持久化。准备中断不重建容器，恢复先查询原 ID。

远端监督器在正常结束、超时/取消及 capture-only 路径销毁主机与容器短期凭证；不依赖本机 finally。保存不含密钥的准备/销毁收据，cleanup 再核对。初始化中断也按原执行 ID 查询并清理；凭证未清理继续阻塞原有全局清理/采用门，辅助角色不构成豁免。

**失败与恢复**：auxiliary.status 使用 valid / unknown / unavailable；401/429/服务失败、密钥缺失或子预算不足记录 unavailable，畸形响应/模型漂移/必要材料缺失记录 unknown，不给 agent 记零分，也不冒充辅助校准通过。只恢复同一远端执行的查询、响应导出和清理。客户端超时后无法确定上游是否已执行时，不重新支付请求；保留未知结果。已跳过的辅助槽位不在后续恢复中偷偷回填反馈，配置或校准改版须新协议。

实现范围是一个固定 API worker 与最小结果契约，不安装通用评分平台。主分保持原有可复核证据；辅助记录必须单列服务开销、缺测和主辅分歧，不能宣传为 agent 已进化或额外独立确认。
