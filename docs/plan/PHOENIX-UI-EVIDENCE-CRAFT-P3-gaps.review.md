## 1. 确认问题

### [P2] F-01 · 让残余保留路线能够取得完整证据并满足退出条件

- **定位**：[计划 §5.2:327、330、335](PHOENIX-UI-EVIDENCE-CRAFT-P3-gaps.md#52-linux-浏览器残余的关闭尝试)、[§9 V-4:373](PHOENIX-UI-EVIDENCE-CRAFT-P3-gaps.md#9-验证)；关联 WORK-N1/AC-4、A-1、D3、M2。
- **问题**：第一候选先清空 Linux 残余清单，而现有测试在第一个越界主机出现时立即停止。若开关无效，该平台拿不齐计划要求的四场景 netlog；未运行的场景不能证明另一个主机已清零。此外，§5.2 允许撤掉无效开关、登记剩余主机后收口，V-4 却无条件要求两个主机都没有请求。用户已认可的“没清零则保留登记”路线因此无法按原文完成判定及退出，实施者仍须自行改写关键验收口径。
- **证据**：
  - [network_boundary.rs:336](../../tools/phoenix-ui/crates/cli/tests/network_boundary.rs#L336) 在同一测试内按 detect/capture、内含/外部资源页面循环四场景；[390–400 行](../../tools/phoenix-ui/crates/cli/tests/network_boundary.rs#L390) 只保存当前场景日志；[436–440 行](../../tools/phoenix-ui/crates/cli/tests/network_boundary.rs#L436) 的循环内断言失败会中止后续场景。
  - [原 P3 收口记录:112](PHOENIX-UI-EVIDENCE-CRAFT-P3.records/M5.md#v-11-联网边界排查) 记载 Linux x64 的首个自包含 detect 场景即出现更新主机，arm64 在两个 detect 场景后、capture 自包含场景才出现 checkin 主机；同处第 139 行记载恢复残余清单后取得四场景日志。故原残余重现时分别只能留下 1/4、3/4 场景，属于已知路径。
  - [差异报告 D-01](PHOENIX-UI-EVIDENCE-CRAFT-P3.prd-dev-gaps.md#已决决策) 明确允许清零与未清零两种结果，未清零时按 PRD v1.3 的清单口径验收；没有要求候选必须先让 CI 失败。
- **最小修订**：首候选加入两个开关时暂保留既有残余清单，让现有测试跑完四场景，再用完整 netlog 逐主机决定开关、清单与 docs 的去留；清单不是判定开关有效的证据。V-4 改为条件式：清零的主机不再出现；未清零的主机只限最终登记清单；不得新增外发主机；最终四平台与 Node 18 全绿。同步 D3、§5.2、M2 的候选顺序和文字，不必改测试控制流或增加检查。若坚持候选先清空清单，则必须明确失败后如何补齐未运行场景的证据，不能直接把缺失日志当作清零。
- **改稿复核**：核对 D3、§5.2、V-4、M2 对同一候选/最终轮的取证和退出口径一致，完整日志先于逐主机结论，残余保留路线可满足退出条件；实施期继续由既有 V-4 承担验证。
- **置信度**：高，直接控制流与已有失败记录相互印证。**阻塞**：否，修订无需用户或外部新增决定；在 M2 对应步骤前修正即可。

多个视角重复发现的日志中断、逐主机判定及退出口径冲突合并为上述一个问题，不按症状重复计数。未发现其他可确认的 P0–P2 问题。
