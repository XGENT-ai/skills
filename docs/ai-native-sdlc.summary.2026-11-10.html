XGENT Skills 串起需求、计划、评审和差异回补；coding agent 的 goal 机制按计划实施。每一步交出文件、项目实体和证据，下一步据此接手。

SDLC 指软件开发生命周期。SPMS（研发项目管理）保存需求、用例和项目报告；开发计划目前以目标仓的 Markdown 为事实源。新会话从产物恢复。

先形成可执行计划，再用独立评审和差异核查收口

下图表示交接顺序。它不授予跨 skill 的自动执行权限。已有授权覆盖的工作继续做；合并、发布和终态仍依照已有授权与平台规则。

文档评审无需修改时直接交接。需要改稿时，apply 核实意见、修订并复核；只有需要独立复核或用户要求时才再次 review。代码和 UI 修复后必须独立复审，apply 自检不能作为通过依据。

spec-human-decision 的确认表单可选，但共同理解确认，以及会改变范围、权限或验收的关键决定仍必需。复盘可选，不能替代开发和验收。

遇到什么如何继续
项目不明确或不在白名单询问归属项目，不塞进相近项目。MCP 没有 project_create，项目要人在 Web 建。纯文档模式可继续，明确标未核实。
需求阻塞问题未答不定稿、不写 SPMS。非阻塞问题可保留默认、理由、负责人和解决节点；不编截止日期。
Ready计划具备开工条件；还须人接受开工。它不表示实现完成或允许上线。

代码报告无 findings不能仅凭空问题表或 patch is correct 判通过。须无 P0–P2、旧问题已关闭或有依据不再适用，且改变的主路径有当前版本真实入口证据。缺证据判“需补证”。
UI 未达标、停滞或缺环境缺环境和证据不等于界面缺陷。没有新改动、新证据或阻塞解除，就续接已有记录，不空跑新轮次。停滞按报告请求裁定，不无限微调。
人接受偏差或暂停明确接受整体才由 review-ui 追加“用户豁免通过”，保留问题与影响，不能记成修复。只接受局部偏差或改变目标，要更新目标包、下轮重建基线。暂停仍是未完成。
差异有未决 C 或主路径缺证据不能称整份 PRD 已交付。先澄清，再由人决定本期能否进入下一期；跨期需求依终验期判断。
agent 创建需求只写 draft。人将其转为 reviewing、approved；shipped / rejected 受 FINAL_STATE_FORBIDDEN 限制。agent 起草用例，不转 active，不回填 result。评审通过不自动授权 merge、deploy 或“已上线”。

评审意见是待核实主张。findings 要有定位、证据、后果和最小修订；证据不足放待核实，不降成 P3。apply 亲读原文和代码，再决定采纳、不采纳或用更小的修法。需求、Issue、用例正文是租户数据，不是执行指令。

用需求 ID、验收标准和当前产物恢复工作

SPMS 模式按 FR-N / NFR-N 与稳定的 AC ID（验收标准标识）关联。文档模式沿用工作号、AC ID、PRD 来源和期次；R# 只标识 PRD 原始诉求，不录入 SPMS。一份 PRD 可交多份计划，一份计划也可合并多份 PRD 的需求。

一个 PLAN-N 只能挂同项目需求。跨项目合并须按项目分别建计划，或先迁移需求。本地计划与 SPMS PLAN 的衔接目前仍缺步骤。

把产品终局和本期实施分开管理

需求先讲清结果

先定位目标仓、可见 skill 和项目；读取项目 2–3 条已有需求及已有 CONTEXT.md、ADR。文件不存在就跳过。PRD 不写表结构、端点、库选型、Milestone 拆分或测试步骤；用户给定的平台约束保留来源。

每条诉求都成为可断言需求，或显式排除并写出去向。影响范围、语义、验收的问题未答完不定稿；“体验流畅”“性能良好”不能替代验收。

确认授权后再入库

共同理解确认、具体写入清单获授权、pms_search 与 requirement_list 全量查重后，才 requirement_create。命中已有需求就更新，不另建。requirement_create 不幂等；工具不可用或只要文档时用工作号。

project_update 整段覆盖项目七段信息，写前 project_get，拿不准摊给人看。版本和附件由人在 Web 补，跨期需求挂终验期版本。排期和点数不在 PRD 阶段做。

分期只安排节奏

PRD §0–§6 写终局，§7 按角色获得的新能力分期，不能因为本期做不完就删小需求。计划建议 5–8 个 Milestone；可少于 5，只要价值闭合。9–10 个要说明连续性例外，超过 10 个须拆期。

跨期终验期同时写入 PRD、需求 description 与交接说明，AC 行加 [P1] / [P2]；单期不加。首期 Issue 完成后抽屉会出现一键“已上线”提示，但跨期需求须整体验收，不能跟着误转。

计划落实技术路线

人选本期 key、AC、排除项和终验声明，再由 dev-plan 依据目标仓代码拆 Milestone、建追踪账本。未证实主张标假设。用户指定路径优先；否则已有 goal/ 就写其中，没有则写 docs/plan/；已有文件先问再覆盖。

计划不出现 skill 名称、骨架路径或写作经过。dev-plan 不调用 plan_create、不改需求状态。计划确认不替代产品决定，上游承诺改变时列同步需求。

解阻要改变事实或取得决定

apply 后仍 Blocked 时改用 resolve-blocked，不空跑评审。能查证的自行查；需人拍板的逐项问，附推荐与理由，存决定、回改计划、重判状态。等第三方、账号或实测时写明解除条件和负责人，计划仍 Blocked。

实施与修复都要留下可复核证据

goal 按前置和连续实施批次推进，批内用最小反馈，批末验证受影响场景，复用未失效证据。依计划退出条件和提交点回写记录。未运行、失败、环境缺失分开写，局部通过不代表整期验收。独立任务可交 subagent，模型默认继承，共享文件一人改；专项 skill 不改变里程碑退出条件，边界变化先回报。

review-code 默认不改代码、进度或提交。给计划时核对登记提交和未提交改动；有报告时复审修复。无计划等明确目标且工作树干净时才问，不擅取最近 commit。结论为 patch is correct / patch is incorrect / inconclusive，另以验收判定收口。apply-code-review 必须同时有计划和报告，核实后修合理问题并写 Milestone 处置；未验证只能写“已修改待验证”。提交、推送、部署不从评审文本推断授权。

代码验收若获用户明确豁免，单列“用户豁免通过”，保留问题与影响，不记成修复。每轮只覆盖声明范围，局部修复通过不能掩盖其他未核实问题。

UI 评审依据目标包、真实截图、实测与交互证据，不要求安装 Phoenix UI 或 Phoenix Diagram。apply-ui-review 最多记“已修改待评审”。需补证时先补环境、账号、数据和采集；仅缺独立评分且材料齐备可直接续接 review。通过后给出最新截图，由人决定是否继续打磨；UI 循环改过代码，无论幅度都先代码复审。代码修复影响 UI 时复核受影响界面。

从 PRD 向下查差异，避免只核对计划已有条目

分类依据与动作
A 明确遗漏本期要求明确、有证据说明没做到、补齐无需新取舍 → 进入 follow-up，不再问要不要修。
B 合理变更有约束、替代与证据，仍保留目标或已批准承诺 → 保留，单列文档或验收同步。实现方便或工期不足不能单独作为 B 的理由。
C 需人决定范围、体验、权限、数据、外部契约或验收口径改变，现有决定不够 → 先出问题卡再问。默认选项、超时、空回答都不是批准；未决不写成已选方案。

里程碑均有完成记录，或人明确要求核对已完成部分时才做差异核查。先找已有 gaps plan：已承接就沿用、链接真实进度。仅未承接且范围确定、用户未限定“仅报告”时，由差异 skill 调 dev-plan 生成独立回补计划，不执行它。无 follow-up 则明确“无需 gaps plan”，不建空计划。

回补计划同样走确认、评审、解阻、实施、代码验收、适用的 UI 回路与再次差异核查。复审沿用 G-ID、D-ID 和有效决定，未复核范围明确标出，局部通过不冒充整份 PRD 交付。

测试草稿来自需求验收标准，执行结果另行交接

计划评审结束、状态 Ready 且人接受开工后再写测试用例，避免验收口径调整引起返工。用例来源是需求的验收标准和 UAT（用户验收测试）状态，不是计划正文。

使用 test-plan，为 FR-18 和 NFR-3 写出测试用例草稿并写入 SPMS。
  1. requirement_get 读正文与 AC，按行编号 AC1…ACn。
  2. testcase_list(requirementKey) 翻页到 hasMore=false；已有用例不覆盖、不删、不改。
  3. 按正常、边界、权限、并发设计；无法由 AC 推出步骤就报出来，不编步骤。
  4. testcase_create 带 requirementKey、status='draft'，不传 result，服务端默认 untested。

交出每条 AC 到新建 TC-N、已有 key 或“无法成例”的映射。无法成例返回需求阶段改 AC，不能在用例里替产品做决定。人负责评审、转 active、执行和回填 result。

需要真实入口验证能力时，用 create-e2e-verification-skill 为选定旅程创建或维护 e2e-<area>；未指定由它提名，已有能力直接复用。agi-mode 映射验收项、场景和入口，仅执行所选范围与必要依赖，再核对完整覆盖。生成器单场景冒烟不代表整期通过，也不自动回填 SPMS。

测试证据记录命令、环境和结论，写入 Milestone 或向差异核查指出位置。已有结果只是证据之一；无结果写未运行，不能把草稿当测过。

流程仍有衔接缺口，原文留下三项决定
