agi-mode 自进化方法论

agi-mode 要从真实任务里积累经验，提出可检验的改进，再用实际结果决定保留、撤回还是继续调查。最终要回答的问题只有一个：在既定目标与资源约束下，它能否持续找到并验证有效改进。

3个层次
进化方法、被优化对象、效果环境，混在一起就无法归因
2类记录
工作样本提供经验，进化尝试提供学习与选择的证据
3级重放
历史效果复核、代理验证、实际效果验证，能支持的结论各不相同
5个维度
收益、回归、成本、证据、迁移，门槛由实践目标预先定

三句话概括

  • 评价的是方法，不是被改好的那个东西。对象最终表现好，可能来自原有能力、人工补救或环境变化；要评价进化方法，还得核对改动、执行条件与效果之间的关系。
  • 现在只到「约定成文」。样本、尝试与效果的记录约定已经写好，参与技能没有自动生成统一归档，已有项目材料也没完成采集与审计，自进化能力更没有实证。
  • 业务只是实践环境。一条任务链的改善只支持该条件下的结论；对通用能力的判断需要来自不同任务族的证据。规则数量、修改次数、自我评价都不能当能力证明。

01要评价什么：先分清三个层次

每轮先限定允许修改的对象，再研究它对真实效果的影响。三个层次混着看，就无法判断改善从哪来。

层次 回答的问题 需要的证据
进化方法agi-mode 怎样从经验中找到、筛选和确认改进？可见样本、机制假设、实验选择、验证、成本及去留依据
被优化对象本次允许改变什么？初始版本、候选差异、父版本、采用版本与恢复点
效果环境使用这个对象完成任务，实际发生了什么？当时的输入、执行条件、产物、验收结果、失败与补救成本

能改的不止技能：技能指令、prompt、工具、执行流程都可以动，任务里的代码与配置也可以动。

两条不能省的前提

  • agi-mode 内维护任务无关的规则——怎样建立结果契约、取得信息、比较候选、验证、恢复、收敛，以及怎样保存进化证据。业务字段、阶段结构、采集入口和效果解释放在实践案例或目标项目里，不由通用方法规定。
  • 一次失败不能直接归因于某个 skill。归因不足时保留未知，不要补一个听上去合理的解释。

02现在到哪一步

已经成型的是说明和约定，不是能力。这三类状态必须分开看。

状态具体内容
已成文agi-mode 内的 Eval、Hillclimb、Arena、Reflection 与 skill 修订流程；区分工作样本、进化尝试和实际效果的通用证据约定；独立于通用 skill 的文档交付链实践案例。
未接入参与技能还没有自动生成统一归档；已有项目材料还没有完成采集与审计。当前阶段要先选实际项目、核对已有材料、接入必要的版本保全。
未实证自进化能力没有得到实证。文档约定已经形成，不代表自动采集已经接入，也不代表能力已被证明。

五个流程各管一段：Eval 建立并持有判定协议、校准评测、管理可见性与不确定性；Hillclimb 持有搜索状态、提出假设、执行实验、管理最佳版本和退出；Arena 在有价值的设计分叉上产生并比较候选；Reflection 从授权材料里提炼有出处的教训与机制假设；skill 编写把有依据的变化落到合适的指令位置。它们共享目标、协议和记录，按当前缺口调用，不必每次都跑全套流程。通用流程的权威位置在 agi-mode 内部，autoresearch、arena、reflect 只是对应流程的兼容入口。

03一轮进化怎么跑

实践开始前就要固定目标、主指标、质量底线、最小值得采用的收益、可修改范围、比较条件和预算；并分别保存初始基线、探索最佳和已确认版本——三者不能混成「最后一次尝试」。

每轮只推进一个机制假设

  1. 从允许读取的样本里找出问题，解释预期影响和可能回归，注明什么观察会推翻这个假设。
  2. 从明确的父版本产生候选。实现一个机制可以改多处内容，但不堆叠无法归因的猜想。
  3. 在固定协议下执行比较：先判断运行是否有效，再检查质量底线、收益、不确定性与维护成本。
  4. 记录保留、撤回、未定或无效及理由，再进入依赖它的下一轮。组合候选和移植片段都要作为新版本重新验证。

连续尝试停滞时先诊断

依次看任务、指导、执行、环境、评测和随机波动，不强求每轮都改代码或增加规则。评测有缺陷就修评测；已有指导没被执行，就调查它的位置、冲突和可见性；需要结构分叉时才动用 Arena。

达到预设条件后冻结，再确认

在未参与选择的代表性任务上确认候选。最终反馈一旦用于下一轮改动，这批材料就不再是未见数据。确认失败时恢复仍然有效的已确认版本，不能反复试同一个确认集直到出现赢家。

保住用户工作，并且有明确的收尾

恢复方案只撤回本轮拥有的改动。结束条件是目标达到、用户停止、既有资源边界到达，或后续探索缺乏合理的信息价值；结束时要区分「目标达成」和「此次搜索结束」。

保质降成本要事前定义

先定下可接受的质量损失边界。事后说「没有显著下降」，不能自动证明质量保住了。

04什么样的证据才算数

历史材料不能直接给新候选打分。材料的格式不决定它的价值——能否恢复当时情境并核对结果，才决定它支持什么判断。重放分三级，每一级能支持的结论不同。

层级 做什么 可以支持的结论
历史效果复核按明确口径重读原始产物与记录原任务发生了什么、材料缺什么、哪些机制值得调查
代理验证给候选当时的输入，检查决策、输出或错误识别是否变化局部机制假设获得支持；仍需核对实际效果
实际效果验证让候选参与新的可比执行，检查新产物和结果候选在这些条件下产生的真实效果变化
  • 先明确需要改变的实际结果，再选样本和判定方式。
  • 候选得到完成任务所需的公开要求和当时可见材料；后来的答案、修复与结果留给评判侧。
  • 候选改变了工作步骤时，不能拿旧工具响应或旧截图冒充新执行。
  • 环境无法恢复时，可以改用范围明确的替代实验，或在后续真实任务中收集证据，但结论必须对应实际执行层级。
  • 分析者可以读取开发案例的完整历史来提出假设；候选执行者仍受阶段信息截止点约束。后来出现的要求或纠正，不能倒推成当时已知的输入。

两类记录缺一不可

工作样本：真实任务的经验

记录真实任务的输入、处理条件、产物和效果，每条至少保留：身份与来源（稳定身份、项目／任务来源、同源关系、关联阶段）、当时的任务（请求、已知约束、确认的决定、信息截止点）、输入与输出（实际版本、可恢复位置、内容指纹，两者分别记录）、执行条件（实际使用的方法与可获取的模型／工具／环境，未知项如实标明）、效果证据（原始产物与观测、适用版本、覆盖范围、首次及补救后结果）、后续反馈（发生时间、针对的原版本、依据及替代关系）。

进化尝试：方法怎么用掉经验

每轮关联：进化方法的版本与运行条件 → 目标、范围、预算及可见样本 → 假设和来源证据 → 父版本与候选差异 → 实际验证及成本 → 去留理由 → 最终确认状态。沿用评测记录模板，不另建一套冲突台账。它从开始实践时产生，不能根据最后版本反向编造。

反馈与事实分开保存。采纳意见不自动证明意见正确，拒绝意见也不自动证明它是误报。没有发现缺陷，只支持已检查范围内的结论，不能把未观察到的行为记为通过。

保存与恢复：三个时点，三项能力

在任务或阶段开始时保全输入，在交付或中断时保全输出，在后续效果到达时追加关联反馈。当前工作文档可以更新，归档版本与原始结果应当保持可核对；优先复用已有的版本和证据位置，避免重复复制。

  • 内容 hash 只能检查是否变化，不能恢复文件。Git SHA 只有在对应内容仍可取回时才足够；未提交的修改、必要的新文件和临时材料，需要额外保留可恢复的内容。
  • 不能等原稿已经修订，再把现状补记为原始输入。
  • 截图、日志和报告必须关联它们实际观察的版本。截图能支持界面可见状态，交互、数据语义或性能仍需对应证据。后续报告更新不会使旧截图自动成为新版本的验证；成功重跑也不能抹去前面的失败和补救成本。
  • 只保存任务需要且已授权的材料，不要求完整聊天、每条命令或内部推理。缺失材料如实记录，采集失败与业务交付结果分别报告。
恢复能力逐项判断
历史效果能否核对历史效果及其证据范围
阶段输入能否还原某个阶段开始时的输入
重新执行能否重新执行并产生可比较的新结果

这三项可能不同时成立。只有效果记录的案例仍有复盘价值，但不能据此宣称它已经具备完整的执行重放条件。

05最容易自欺的地方

下面每一条都会把一个无效结果伪装成有效改善。它们不是提醒，是判定门槛。

01
用过程量冒充能力。规则数量、修改次数、自我评价，都不能作为能力证明。
02
同时改对象和评分口径。评测规则的修订与候选改进分别进行：候选在固定规则下接受检查；发现评测错误时，先保留旧结果，修订协议并重测可比基线。
03
判定器没校准就开跑。先用已知好坏及边界产物检查判定器能否区分目标行为，核对真实评分依据。能运行客观检查时优先使用，需要判断时使用有证据锚点的标准。
04
把三类失败混成一类。基础设施无效、候选行为失败、判定器波动要分别记录。不能通过筛掉不利的运行来制造改善。
05
样本只挑顺手的。样本要覆盖有价值的常见任务、重要失败、边界与不应触发的场景；不能只收成功项目，也不能只收某个模型恰好做错的题。
06
把同源任务当独立样本。同一来源的任务链、修订和近重复保持同组。一条任务链产生十份报告，不等于十个独立任务。
07
看了结果再抽样本。可见的搜索样本与未见的最终确认样本必须分开；分组与可见性在搜索前确定。验证反馈一旦用于选择候选，它就属于开发证据。
08
以为分开目录就是隔离。目录、分支或 worktree 分开不保证信息隔离；实际权限、可读历史、缓存和上下文都要核对。做不到时就明确写出评测限制。
09
越级使用证据。历史材料不能直接给新候选赋予效果分；代理验证只支持局部机制假设。
10
拿旧产物冒充新执行。候选改变了工作步骤时，旧工具响应或旧截图不能当新结果。
11
确认集反复试到出赢家。最终反馈一旦用于下一轮改动，这批材料就不再未见。确认失败时恢复仍有效的已确认版本。
12
把模型升级或人工加码算成功劳。比较不同进化方法时，对象起点、任务分布、模型／工具、执行条件与总预算都要可比，方法版本和对象版本分别记录。评价材料与确认反馈的可见范围也必须一致。
13
改 agi-mode 本身时放松标准。新规则同样作为候选接受固定协议检查，候选不能通过改写评价标准或自评结论获得晋级。
14
无限复用旧结论。已有结果只在相关输入、模型、工具与任务分布仍适用时才支持复用；条件改变后要重新检查受影响的部分。

06怎么评价 agi-mode 的进化能力

先看独立确认的实际改善，再看获得改善付出的代价，以及方法如何处理失败与未知。具体指标和门槛由实践目标预先确定。

维度核对的问题
有效收益相对初始对象，是否改善了真实效果？是否超过测量噪声且具有实际价值？
回归控制是否保住质量底线和重要相邻场景？是否拒绝或撤回有害候选？
资源效率在可比预算内，用多少实验、验证、运行和维护成本取得收益？
证据与判断假设和结论是否有来源？能否区分未知、执行失败、环境无效与评测失真？
学习与迁移能否避免重复已被反驳的方向？改进是否适用于未参与调优的任务？

两条关于结论边界的硬规定

  • 过程记录用来核对方法是否可靠，不能抵消缺少实际效果证据。
  • 诚实地没有找到有效改进，可以证明某些判断与停止行为正确，但尚不足以证明具备改进能力。

07当前选中的实践环境：文档交付链

PRD、开发计划、评审和实施记录被选作可以持续积累样本的环境。已有文件能把前期决策和后续效果连起来：需求和计划描述承诺，评审指出问题，修订说明处置，阶段记录及验收材料呈现实际执行。

  • 被改进的对象是 prd、dev-plan、review-* 等生成与评审方法。
  • 评分依据来自它们引导的实际交付：用户目标是否兑现、体验与行为、回归、返工和必要的人工补救。文档长度、章节齐全程度或评审意见数量只能提供诊断信号，不能当成绩。
  • 实践以完整任务关系组织材料，保留多对多关系和各阶段实际消费的版本。历史报告中的意见并非完整正确答案，后续的采纳与拒绝同样需要理由和证据。

一条用来说明归因边界的例子

假设某次交付因遗漏一个边界条件而返工。先核对该条件在当时是否可知、计划是否覆盖、评审是否有足够材料发现、执行是否遵循计划。若证据支持上游方法存在缺口，可以据此提出修订；新版评审能识别这个已知问题，只达到代理验证。是否真的减少返工，还要观察候选引导的新执行。

该案例保存在仓库级评测目录，不是 agi-mode 的运行依赖。业务字段、阶段记录格式与截图采集流程留在参与技能或目标项目里，不能由这个案例反向限定通用进化方法。

08推进条件：下一步靠什么事实解锁

不预设积累多少天或多少份文件就算够。决定下一步的是材料能否回答评测问题。

阶段进入下一阶段前需要成立的事实
样本积累能定位真实输入、输出和效果；可恢复程度、同源关系及缺口明确
评测准备样本具有目标代表性，判定器经过校准，基线可测，隔离和资源条件成立
进化实践按固定目标运行有边界的尝试，所有候选及去留均有记录
能力评价候选效果经过独立确认，方法贡献与限制可解释，结论不超出任务覆盖

现阶段可以先抽查真实案例的恢复与关联能力，发现缺口后补采集；无需为了填写结果提前启动版本对比。
