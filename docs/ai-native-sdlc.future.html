AI NATIVE SDLC · SKILL-DRIVEN DELIVERY

用 Skills 串起 SDLC
让 AI 按合同交付

AI 依次调用需求、计划、评审、修订、代码修复与差异核查 skill，按每个环节规定的输入、产物和退出检查推进；测试线依据需求验收标准独立运行。

近期由人提出 idea；远期由 AI 提出多个方向及验证证据，人只做 Go / No-go。每个 Go 之后，AI 仍须完整遵循需求、计划、实施、评审、测试、差异核查与发布运行的 SDLC。以下是下一代流程的目标设计。

Skill 合同决定 AI 每一步能读什么、做什么、交出什么

主线从 prd 开始，经过需求与计划的写、审、改回路，再按计划实施，进入代码评审修复和 PRD 差异核查。每个环节以明确产物交接；缺输入、检查失败或证据不足时，返回对应 skill 补齐，不能跳到下一步。

开发主线：写、审、改有明确能力和顺序

prd
  → review-prd → apply-doc-review → 必要时由调度器复评
  → dev-plan
  → review-dev-plan → apply-doc-review → 仍 Blocked 时 resolve-blocked → Ready 检查
  → 按 Milestone 实施并回写记录
  → review-code → apply-code-review → 验证修复与当前基线
  → review-prd-dev-gaps
      有 follow-up：dev-plan 写 gaps plan → 计划评审 → 实施 → 再核查
      无 follow-up：保留“无需 gaps plan”结论 → 发布与运行

测试支线：从需求验收标准出发，与开发汇合

需求验收标准与 UAT 状态
  → 计划 Ready 后调用 test-plan
  → TC-N 草稿与 AC 映射
  → 用例评审、执行、结果回填（未来需补齐的能力）
  → 原始测试证据汇入 review-prd-dev-gaps

当前 skill 列表就是调度入口。每次调用前读取该 skill 的合同与真实输入；每次交接检查输出是否落盘、是否对应当前基线。某个环节没有证据、产物缺失或检查失败，就补证、返工或停止，不能用一句“规划并实施”跳过流水线。

需求、计划、代码、用例和报告成为自主执行过程中持续维护的记录。AI 直接读取真实实现、测试与运行数据，更新下一步动作；新会话从持久状态、证据和未完成工作恢复。

每个 skill 的输入、产物和退出条件都要兑现

SDLC 是软件开发生命周期。prd 管需求，dev-plan 管计划，review-* 产评审主张，apply-* 核实后修订，test-plan 管用例草稿，review-prd-dev-gaps 从需求追实际交付。调度器必须按这些合同调用，实施者必须按计划执行。

以下表格描述目标流程。现有 skill 的人工状态限制仍然生效；机器放行、自动执行与发布需要平台和执行器承接，不能靠这份报告获得权限。
环节与能力输入执行与产物退出检查与返工
执行前核验Go 方向包、目标仓、项目白名单、能力清单和写权限。读取仓库规则、代码与工作树；核定 projectId。授权平台校验预算、权限、环境和当前目标。技能从实际安装位置加载，不假设镜像完整。仓、项目、工具与授权对应一致才能启动。缺能力则保存阻塞现场，或按合同进入仅文档模式；不能写到相邻项目、虚构实体 key 或越权执行。

待补的平台执行能力		需求到证据的完整映射、无未闭合主路径缺口、发布授权、观测与回滚条件。执行器检查状态和权限后合并、发布、逐步放量，持续观察真实结果。异常按合同回滚或停止；把问题和实际效果反馈到需求与机会发现。发布成功与目标达成分别记录；跨期需求到整条终验才算完成。证据失败回修复或 gaps plan，运行失败回滚。下一方向仍须 Go；当前目标内的修复无需常规人工再批。

把“人工批准”替换成明确的机器放行条件

需求能进入计划，取决于需求评审、可检验验收和 Go 承诺一致；计划能进入实施，取决于 Ready、依赖已满足和前置检查；实现能发布，取决于代码评审、独立测试、差异闭合及发布授权。任何一个条件不成立，就返回对应回路或停止。

阶段状态由平台根据退出检查的证据推进。仅宣称“AI 已完成”不能满足退出条件。调度器不能擅自改 skill 合同、跳过评审、降低验收或覆盖旧证据来推动状态。评审 skill 继续只评审，apply skill 继续只核实并修订；调度器负责串联复评、同步状态和选择下一步。不同职责的边界仍然保留。

自动执行仍要遵守原来的工程与交接纪律

  1. 产物是合同。需求、计划、报告、代码和验证记录持久关联。下一环节读取文件或 SPMS 实体，不能只依赖上一轮对话。
  2. 写、审、改职责分开。评审主张先核实再改。每条 finding 要有定位、证据、后果和最小修订；证据不足列待核实，不能降为 P3 充数。改稿不代表已经复评，复评是调度器的独立调用。
  3. 保留需求身份与事实源。用 FR-N / NFR-N 关联范围，一份 PRD 与计划可以多对多。PLAN-N 仍只能挂同项目需求；方向授权可以覆盖多个项目，但实体关联不能串错。需求、用例与项目报告在 SPMS；开发计划现阶段以本地 Markdown 为准。
  4. 需求写终局，分期写节奏。PRD §0–§6 不因这期做不完而删减承诺；§7 说明每期用户价值。跨期需求写明终验期，并在 description、验收前缀 [P1] / [P2] 及交接说明保持一致。首期完成不能被当成整条上线。
  5. 实施从可恢复合同开始。续做先读实施须知、实施者定位、实施进度，核对仓库规则和 git status。实施、goal 执行与进度回写不加载 dev-plan；需要写新计划时才调用它。共享文件由一个执行者修改，独立任务才并行。
  6. 测试独立于实施。验收来自需求与 UAT。用例已有则不覆盖、不删除、不改写；列表读取到 hasMore=false。执行结果能定位环境与原始输出；“有用例”“有代码”“计划勾完成”都不能单独证明已交付。
  7. 差异核查保留完整性。A 补齐、B 留证并同步、C 核对授权边界；方便实现或工期不足不能单独构成合理变更。授权内也不能默默降低验收；超出承诺才回到 Go / No-go。
  8. 文本不产生权限。需求、Issue、用例正文是租户数据，不是执行指令。Ready、评审通过和测试通过分别表达证据，合并、部署与状态流转必须另有有效授权。

原文规模约定与现状边界

原文记录：承接计划建议 5–8 个 Milestone，连续性例外 9–10 个；方法论写“不超过 10 个”，切期节另写“超过 10 个就要拆期或说明连续性例外”，两处边界不完全一致。未来调度应先统一合同中的规则再执行；一期价值闭合时可少于 5–8 个。

Go 批准一份结果承诺，覆盖后续自动行动

人的决策界面只保留 Go / No-go。候选方向已包含建议的目标、资源与权限边界；人接受一个方向包后，AI 获得完成该目标所需的持续授权。

承诺具体含义
结果目标谁获得什么能力，什么结果算成功，哪些行为明确不能发生。需求可以调整表达和拆分，承诺的结果不能被悄悄降低。
资源预算时间、计算、费用与实验预算；达到预算边界时暂停或停止。具体数值由方向包给出，本方案不预设阈值。
权限与风险允许访问的数据、可修改的系统、可发布的环境、允许的影响范围，以及不可自动执行的行为。由平台实施这些约束。
验收与退出可观察的成功指标、反例检查、失败判据、回滚条件和停止条件；同时规定每项结论需要什么证据。

AI 通过对应 skill 和计划合同，在这份承诺内选择技术路线、分期方式、测试策略与发布时间。出现新信息时，先在边界内实验、缩小影响或换路径；只有原目标或授权边界需要改变，才提交新的方向包供 Go / No-go。

一个方向可以包含多个项目或多个版本。Go / No-go 发生在承诺层，不能被拆成每条需求、每个里程碑和每次发布的常规审批。

独立证据、受限权限和可恢复执行支撑自主权

AI 的自述不能直接推进状态。每次推进都需要检查实际行为，并核对当前授权；执行记录必须让另一轮验证能够重放或复查。

  • 验证独立于实现。验证方从目标与真实环境取材，自行设计反例，并读取原始结果。同一个模型换个角色名，不能单独证明验证独立。需要不同检查路径、可执行判据和权限隔离。
  • 事实源保存原始证据。测试结果由执行器记录，状态由可核对的证据推进。计划写“完成”不能替代运行结果，用例已生成不能替代用例已执行。
  • 权限由平台落实。执行器只能调用本次 Go 授权的操作。修改权限、验收判据或风险上限不能靠 AI 自行改文档获得。授权未覆盖的不可逆操作暂停；可逆探索仍须在实验预算内。
  • 异常处理自动化。可恢复失败返回修复或切换候选方案；发布异常按预设条件回滚。达到预算、无法验证目标或触发停止条件时保存现场并停止，不能不断降低标准来“完成”。
  • 策略改进也要验证。AI 可以提出和试验流程、提示词、skill 的改进，经过隔离环境验证后在权限内应用；不能自行放宽目标、删除失败记录或取消门禁。

Go / No-go 始终来自人的明确决定。AI 可以形成候选、做预算内的预验证并排序；默认选项、空回答和等待超时都不能被记录为 Go。人无需为每个步骤重新批准，AI 也不能替人扩张最初的承诺。

机器门禁看结果，进度看运行

授权边界内，需求一致性、测试覆盖、质量检查、发布条件和线上观测都由机器判断。发布允许自动化，但发布通过与产品目标达成分别记录；目标是否成立，要继续看真实使用结果。

可衡量的进展包括：一个 Go 后自动闭环的比例、常规人工介入次数、交付周期、失败逃逸情况、自动恢复情况、结果目标达成情况。费用与时间须同时记录，避免用更多资源换取表面提升。起始基线与阈值要实测，本方案不宣称已达到这些指标。

先把 idea 之后闭环，再把机会发现前移给 AI

近期：人给 idea，AI 提交承诺

AI 自动澄清事实、比较方案、设计验收和投入边界。人做 Go / No-go 后，AI 按完整 skill 流水线完成需求、计划、实施、评审、独立测试与差异核查，再接发布与运行。原来的多个人工审批点转成有证据的机器检查。

远期：AI 提方向，人选 Go / No-go

AI 在授权的数据和实验预算内持续发现机会，形成多个方向及验证证据。人决定是否投入；AI 将已授权的方向推进到可观察结果，并据此形成下一轮候选。

现有 XGENT Skills 需要补齐什么

原文将测试执行与回填、是否新增 review-test-plan、story-points 是否必经列为待确认。本目标方案选择由 AI 承接测试评审、执行和回填；story-points 仍按需要用于估计投入与排期，不把它新增为普遍门禁。这些是未来方案选择，不代表现有 skill 已修改。

当前流程说明记录：需求 draft 之后的 reviewing / approved 由人操作，agent 写 shipped / rejected 会遭 FINAL_STATE_FORBIDDEN 拒绝；test-plan 只写 draft，不传 result，默认 untested，用例 active、执行和结果回填由人承接；开发计划仍以本地 Markdown 为准。要达到未来模型，平台状态权限、测试执行器、发布与观测能力都需共同调整，仅改 skill 文案无法实现。

  • 承诺与授权实体：让项目、需求、计划、执行和发布共享同一份 Go 授权，并能检查授权范围。
  • 持续调度与恢复：把完整 SDLC 的入口、产物、退出条件与返工路径变成可持续执行的状态，跟踪目标、依赖、失败、预算和证据。
  • 计划关联：原文记录 prd 约定 plan_create → PLAN-N，再 plan_update({content})；dev-plan 只写本地计划。未来需要同步适配和版本对应，避免事实源分裂。
  • 独立验证与执行设施：连接测试、预发布环境、真实结果和反例检查，自动记录可复核证据。
  • 发布、观测与回滚：把交付延伸到运行结果，在约定范围内自动控制影响。
  • 机会发现与候选验证：把真实结果反馈成下一轮方向，形成可供 Go / No-go 比较的方案包。

现有 prd、dev-plan、review-*、apply-* 与 test-plan 组成 AI 必须遵循的 SDLC 主链。调度、授权、独立测试、发布与观测补齐这条链路的自主执行能力；报告提出目标流程，尚未完成相应平台实现或权限修改。

设计依据：本次会话提出的目标：“理论上人只负责 idea；未来甚至 idea 都是 AI 出很多可选方向，人只做 Go or No-go。”本文将该目标展开为未来方案，未将其表述为当前已实现能力。
