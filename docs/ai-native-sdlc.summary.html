都有可接手的产物

XGENT Skills 用文件和项目实体串起需求、开发、评审与测试；人负责批准需求、确认测试结果和决定上线。

SDLC 是软件开发生命周期。这里的 AI Native，指 agent 依照明确的输入、产物和退出条件参与整条交付流程。

11 个原文统计：10 个直接调用的 skill，加上 elintp
2 条线开发与测试在计划可开工后并行，汇入差异核查
5 处原文列出的衔接缺口，仍需人工或后续承接
一期怎么走凭什么交接何时停下怎么操作尚未闭合

一期经过需求批准，以人的收口决定结束

需求和计划各走一遍“写作 → 评审 → 核实改稿 → 人放行”。改稿后不会自动重评；仍涉及范围、安全、数据、外部契约或关键非功能需求时，人决定是否再评。

这套回路表示操作次序，不是 SPMS 的状态机。SPMS 是研发项目管理系统。评审“通过”和计划 Ready 都不代表允许合并或部署。

下一环节接收文件、需求 key 和验证证据

SPMS 保存需求、用例和项目报告；开发计划目前以目标仓的 Markdown 为准。新会话从产物恢复，聊天记录不能替代交接合同。

关联单位是需求 key 集合：一份 PRD 可拆给多份计划，一份计划也可合并多份 PRD 的需求。PLAN-N 只能关联同一项目；跨项目须分开建计划，或先迁移需求。

先核实环境，再逐步推进到有证据的收口

准备四项前提

目标仓、可见的 skill、正确的 SPMS 项目、写权限，缺一项就停。运行时读目标仓规则与代码；不能套用 skills 仓的技术栈或借相邻项目凑齐。

安装命令：npx skills add XGENT-ai/skills。本仓也可直接读 skills/<name>/SKILL.md。MCP 无 project_create，项目须人在 Web 建；白名单找不到就问。

只要文档或工具不可用时，需求使用 WORK-F1 / WORK-N1，不虚构 FR-N。需要录入需求或用例时，工具须可用且人已确认可以写。

把想法写成可验收需求

prd 核定项目，读取 2–3 条已有需求及目标仓已有的 CONTEXT.md、ADR（架构决策记录）；文件不存在就跳过，不为写 PRD 新建。

PRD §0–§6 写最终能力，§7 安排分期。每条需求写清谁、条件、动作与目标状态；不能断言的列开放问题。原始诉求须成为需求或显式排除并写出去向。

不写表结构、端点、库选型、Milestone 拆分或测试步骤。用户给定的平台约束标来源。非阻塞问题保留默认、理由、负责人和解决节点，不编截止日期。

确认、查重、评审，再批准

确认共同理解后，先 pms_search，再 requirement_create draft；该创建不幂等。真实 key 回填 PRD，未录入条目保留工作号。

跨期需求在 description 写终验期，验收标准加 [P1] / [P2]；单期不加。人补版本和附件，跨期需求挂终验期版本。此时不排期、不估点。

project_update 整段覆盖项目基本信息七段：确认后才能写，写前先 project_get，拿不准先给人核对。建错 key 会影响排期与权限。

review-prd 查现状、产品、体验、验收；结论为通过／需修订／需补证。apply-doc-review 核实后改稿。改变已确认目标、权限、验收前问人；SPMS 同步、评论和代码修改另记处理。仍有 P1 或人要求时再评，旧结论不能当新证据。

按本期价值写计划

人按 PRD §7 选需求 key，交接验收标准、排除项及终验声明。分期须说明哪个角色增加了什么能力。终验声明示例：“本计划完成后 FR-38 仍停在交付段，终验在 P2”。

原文建议 5–8 个 Milestone；连续性例外可到 9–10 个，且写有“不超过 10 个”。其切期节另写：超过 10 个须拆期或说明连续性例外；两处边界表述并不完全一致。一期价值闭合时可少于 5–8 个。

dev-plan 把 key 作为 R1..Rn，读目标仓代码，未证实项标假设。优先用户路径；否则已有 goal 目录就写 goal，再否则 docs/plan。已有文件先问再覆盖。计划保留当前结论，不写 skill 名、骨架路径或写作经过。

review-dev-plan 查代码事实、路线、需求与里程碑映射、实际可用性；再用 apply-doc-review 改稿。Ready 且人接受开工后实施。

并行实施与编写用例

实施前读计划顶部三节和仓库规则，核对 git status、diff。原文实施节只点名顶部两节；恢复节要求三节，执行时一并读齐。记录与代码不符先查原因，不覆盖用户改动，也不推断验收通过。

实施、goal 执行、续做与进度回写不加载 dev-plan。需要行为测试时先红、再绿、再重构。退出检查通过即回写进度及 M<n>.md，之后再报完成；未运行、失败、环境缺失分开记，局部通过不等于整期通过。

独立任务可交 subagent，默认继承模型；共享文件一人改。边界变化先回报。architect、tdd、debugging 等专项 skill 按需用，不改退出条件。

test-plan 用 requirement_get 读正文及验收，编号 AC1…ACn；testcase_list(requirementKey) 翻至 hasMore=false，不覆盖、删除或改写已有用例。覆盖正常、边界、权限、并发；推不出步骤的验收标准列为“无法成例”，返回需求阶段修订。用 testcase_create 带 requirementKey 建 draft，并给出 AC 到新／旧 TC-N 的映射。

核实修复，再对照需求收口

里程碑交给下游或做差异核查前，用 review-code 评审，再用 apply-code-review 同时读取计划与报告。评审不改代码、进度或提交；对象不明且工作树干净就问，不擅取最近 commit。

代码结论为 patch is correct / patch is incorrect / inconclusive。修复逐条核实，只改合理问题；无验证写“已修改待验证”，不能写“已修复并验证”。

本期里程碑都有完成记录，或人要求检查已完成部分时，review-prd-dev-gaps 从 PRD 向下追实际交付。测试结果须能找到命令、环境和结论；草稿不是测过的证据，未运行如实记录。

没有未决 C 和未核实的主路径缺口后，人决定是否进入下一期。跨期需求的“已上线”表示整条验收；首期 Issue 完成会出现一键上线提示，因此终验期须同时写入 PRD、description 和交接说明。缺证据时不能宣称整份 PRD 已交付。

差异核查把遗漏、替代方案和未决取舍分开

差异成立条件接下来做什么
A · 明确遗漏本期要求明确，证据表明未做，补齐无需新产品取舍。进入 follow-up，不再问是否修。
B · 合理变更有约束、替代与证据，目标或已批准承诺仍成立。保留；另列文档和验收同步。方便实现或工期不足不能单独成立。
C · 需人决定范围、体验、权限、数据、外部契约或验收口径变化，已有决定不足。先出问题卡，再问人；未答保持待决，不能写成已选方案。

follow-up 非空时，差异 skill 调用 dev-plan 写 gaps plan；不改原 PRD、原计划或完成记录，也不开始执行。新计划重新评审再实施。没有 follow-up 就注明“无需 gaps plan”，不建空计划。

流程仍有五处未闭合，三个选择尚待确认

以下是原文记录的现状，本报告没有重新审计全部 skill，也没有把这些缺口认定为已补齐。

  1. SPMS 计划关联缺口：prd 的下游约定是 plan_create → PLAN-N、再 plan_update({content})；dev-plan 只写本地 Markdown，不调用 plan_create，也不改需求状态。本地计划与 SPMS 计划目前对不上号。
  2. 测试人工段：原文记录 skills/ 无 review-test-plan，无执行或回填 result 的 skill。评审、转 active、执行与结果回填由人承接。
  3. 上线由人完成：本流程没有 skill 修改需求“已上线”，agent 写终态被拒。
  4. 估点未设为门禁：story-points 可把点数写回 SPMS，但不是本文必经步骤，PRD 阶段不估点、不排期。
  5. 本地镜像不全：原文快照为 skills/ 47 个目录、.agents/skills/ 24 个；后者不含 prd、test-plan。npm 发布 skills/，不能把 .agents/skills/ 当全量副本。旧稿的“发布时同步到 .agents/skills/”与 README、package.json 不符，原文已弃用。
原文待确认，仍未作决定：

  • 是否补 review-test-plan，在 draft → active 前评审？
  • 是否把 story-points 设为进入迭代排期前的必经步骤？原文记录当前没有 skill 作此要求。
